# 06. 소프트웨어 아키텍처 기초

> **한 줄 요약.** 아키텍처는 소프트웨어의 **건축 설계도**이다. 어디에 무엇을 두고, 누가 누구와 대화할지를 정해 놓은 것이다. AIDOO Portal은 **클라이언트-서버 + 모노레포 + 다중 서비스** 조합이다.

---

## 1. 아키텍처란 무엇인가

아키텍처는 건축의 용어에서 빌려온 말입니다. 건물에서 아키텍처는
- 몇 층인가
- 어디에 기둥이 있는가
- 전기·수도·가스는 어디로 흐르는가
- 사람은 어떤 동선으로 움직이는가
를 결정합니다.

소프트웨어에서도 똑같습니다. 아키텍처는
- 프로그램을 몇 개의 덩어리로 나눌 것인가
- 각 덩어리는 무엇을 책임지는가
- 덩어리끼리는 어떻게 대화하는가
- 데이터는 어디에 저장되는가
를 정합니다.

아키텍처는 **나중에 바꾸기 어려운 결정** 입니다. 그래서 초반에 신중히 정하고, **ADR(Architecture Decision Record)** 이라는 문서로 남깁니다. 우리 프로젝트에도 `adr/0001-ai-platform-extensibility.md`, `adr/0002-mcp-capability-platform.md` 두 개의 ADR이 있습니다(7장에서 자세히).

## 2. 가장 기본 구조 — 클라이언트-서버

현대 웹 애플리케이션의 뼈대입니다.

- **클라이언트(Client)** — 요청하는 쪽. 여기서는 **사용자의 웹 브라우저.**
- **서버(Server)** — 응답하는 쪽. 여기서는 **우리 백엔드(FastAPI).**

예:
```
[브라우저(클라이언트)]   --HTTP 요청-->   [API 서버]
                        <--HTTP 응답--
```

**왜 클라이언트-서버로 나누는가?**

- 수백~수천 명의 브라우저가 동시에 접속해도 **공통 데이터는 서버에만** 있으면 되기 때문.
- 클라이언트는 사용자 디바이스에서 돌아가므로, 사용자마다 다른 환경에 대응.
- 보안: 민감한 데이터를 브라우저에 주지 않고 서버 안쪽에 둘 수 있음.

## 3. 3-Tier Architecture (3계층 아키텍처)

1990년대부터의 고전적 패턴이며, 지금도 웹 앱의 표준입니다.

| 계층 | 이름 | 역할 | 우리 프로젝트 |
|---|---|---|---|
| 1 | Presentation | UI 담당 | `apps/web` (React) |
| 2 | Application/Logic | 비즈니스 규칙 | `apps/api` (FastAPI) |
| 3 | Data | 영속성 | PostgreSQL + MinIO |

이 3개를 **분리** 하는 것이 핵심입니다. 분리되어 있으면
- UI만 바꾸고 싶을 때 서버를 안 건드려도 된다.
- 서버만 최적화하고 싶을 때 UI를 안 건드려도 된다.
- DB를 바꿀 때도 서버 로직만 수정하면 된다.

우리 프로젝트는 정확히 이 구조를 따르며, 여기에 추가로 **비동기 워커(Celery)** 와 **실시간 협업 서버(Yjs/y-websocket)** 가 덧붙은 형태입니다.

## 4. 모놀리식 vs 마이크로서비스

소프트웨어 아키텍처의 **가장 큰 분기점** 중 하나입니다.

### 4.1 모놀리식(Monolithic)

모든 기능이 **하나의 큰 서버 프로세스** 안에 있는 방식. 전통적이고 단순합니다.

```
[ 거대한 서버 하나 ]
  ├── 로그인
  ├── 결제
  ├── 채팅
  ├── 검색
  ...
```

- **장점**: 배포 단순, 개발 단순, 디버깅 쉬움.
- **단점**: 커질수록 복잡해지고, 한 부분 문제로 전체가 죽을 수 있음.

### 4.2 마이크로서비스(Microservice Architecture, MSA)

각 기능을 **독립된 작은 서비스** 로 쪼개 여러 서버로 나누는 방식. 2010년대 후반 크게 유행.

```
[로그인 서비스]  [결제 서비스]  [채팅 서비스]  [검색 서비스]
       ↕              ↕              ↕              ↕
              [API Gateway]
                    ↕
                [브라우저]
```

- **장점**: 서비스별 독립 배포, 서비스별 기술 선택 자유, 장애 격리.
- **단점**: 운영 복잡성이 매우 커짐(모니터링, 네트워크, 배포 파이프라인 × 서비스 수).

### 4.3 어느 쪽이 맞는가?

**90%의 프로젝트는 모놀리식으로 시작해야 합니다.** 이유는 마이크로서비스의 운영 비용이 초기에는 이득보다 크기 때문입니다. 업계에서는 이를 **"Monolith First"** 원칙이라 부릅니다(Martin Fowler).

우리 프로젝트도 **모놀리식** 입니다(`apps/api`가 단일 서버). 단, 비동기 작업은 **Celery 워커(apps/worker)** 로 분리했습니다. 이는 마이크로서비스라기보다 **"같은 모놀리스의 백그라운드 버전"** 입니다.

### 4.4 모듈러 모놀리스(Modular Monolith)

요즘 뜨는 중간 지점입니다. "내부는 잘 나눠진 모듈로 두고, 외부로는 하나의 서버로 배포" 방식. 필요할 때 특정 모듈만 마이크로서비스로 떼어낼 수 있음. 우리 프로젝트의 `aidoo_api/domains/` 구조가 바로 이 방향입니다.

## 5. 모노레포(Monorepo) vs 다중 저장소

소스 코드 **저장소 배치** 에 대한 이야기입니다. 아키텍처와는 다른 층위지만 자주 함께 논의됩니다.

| 구분 | 모노레포 | 폴리레포(각 프로젝트별 저장소) |
|---|---|---|
| 정의 | 여러 앱·패키지를 **한 저장소** 에 | 프로젝트마다 저장소 분리 |
| 장점 | 공통 코드 공유 쉬움, 일괄 변경 가능, 전체 버전 관리 | 서비스 독립성, 권한 분리 쉬움 |
| 단점 | 저장소가 커짐, 도구 필요(Nx, Turborepo) | 공통 변경 시 여러 저장소 건드려야 함 |

**우리 프로젝트는 모노레포**입니다. 이유:
- 프런트(TS)와 백(Python)이 **한 저장소**에 있으면 타입·API 명세를 동기화하기 쉽다.
- 5명짜리 팀이라 여러 저장소는 오버헤드.
- Nx가 있어 효율적으로 관리 가능(21장).

Google, Meta, Uber 같은 대형 회사들도 내부적으로 거대 모노레포를 씁니다. "코드가 많아질수록 모노레포가 맞다"는 업계 흐름입니다.

## 6. 이벤트 드리븐 아키텍처(Event-Driven)

최근 10년간 중요해진 패턴입니다. "직접 호출" 대신 "이벤트를 발생시키고 누군가 듣는" 방식입니다.

```
사용자가 회의 녹음 업로드
   ↓
[API] --이벤트 "recording_uploaded"--> [메시지 큐(Redis)]
                                           ↓
                                      [워커가 수신]
                                           ↓
                                      트랜스크립션·요약 수행
```

장점:
- API는 응답을 바로 반환(사용자 대기 없음).
- 워커가 느리거나 죽어도 메시지는 큐에 남아 있어 안전.

우리 프로젝트의 **Celery + Redis** 조합이 이 패턴의 가장 단순한 형태입니다(30장).

## 7. AIDOO Portal의 전체 그림

세 층 + 부가 서비스를 모두 그리면 이렇습니다.

```
                          사용자 브라우저
                               │ (HTTPS)
           ┌───────────────────┼───────────────────┐
           │                   │                   │
       정적 웹 호스팅       API 서버         WebSocket 서버
       (Nginx + dist/web)   (FastAPI)       (Yjs relay)
           │                   │                   │
           └────────────────── ┼───────────────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
          PostgreSQL        Redis           MinIO
          (메인 데이터)    (큐/캐시)       (파일/객체)
                              │
                              ↓
                         Celery 워커 프로세스
                         (느린 작업 전담)
                              │
                              └→ OpenAI API (외부)
```

이 한 장을 머리에 그리면, 앞으로 나오는 모든 기술 이야기가 "이 그림의 어느 부분인가"로 자리 잡을 수 있습니다.

## 8. 아키텍처를 판단하는 기준 (NFR: 비기능 요구)

어떤 아키텍처가 좋은가는 맥락에 따라 다릅니다. 그 맥락을 결정하는 것이 **비기능 요구사항(Non-Functional Requirements, NFR)** 입니다.

- **Scalability(확장성)** — 사용자가 10배 늘어도 버티는가
- **Availability(가용성)** — 장애 시 얼마나 빨리 복구되는가
- **Performance(성능)** — 응답 속도
- **Security(보안)** — 인증·권한·암호화
- **Maintainability(유지보수성)** — 6개월 뒤에도 이해 가능한가
- **Observability(관측성)** — 문제가 생겼을 때 원인을 빨리 찾을 수 있는가

우리 포털은 사내용이라 확장성 요구가 높지 않고, **보안·유지보수성·관측성** 이 가장 중요한 NFR입니다. 이 가치관이 현재 아키텍처를 결정했습니다.

---

## 9. 핵심 요약

- 아키텍처는 **소프트웨어의 건축 설계도**이며, **ADR**로 남긴다.
- 기본 골격은 **클라이언트-서버 + 3-Tier**.
- 모놀리식 vs 마이크로서비스는 **모놀리식으로 시작** 이 업계 정석. 중간이 **모듈러 모놀리스**.
- 우리 프로젝트는 **모듈러 모놀리스 + 모노레포 + 이벤트 드리븐 보조** 조합.
- 아키텍처 판단 기준은 **NFR**. 우리는 보안·유지보수성·관측성이 중심.
