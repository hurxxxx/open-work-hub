# 02. 소프트웨어란 무엇인가

> **한 줄 요약.** 소프트웨어는 "사람이 쓴 지시문"이며, 그 지시문을 컴퓨터가 한 줄씩 해석해 실행하는 것이다. 소프트웨어가 복잡한 이유는 **세상 자체가 복잡해서** 그 복잡함을 모두 담아야 하기 때문이다.

---

## 1. 비유로 시작하기 — 요리 레시피와 주방

소프트웨어를 요리로 비유해 봅시다.

- **레시피(코드)** — 무엇을 어떤 순서로 어떻게 만들지 적어 놓은 글.
- **요리사(CPU)** — 레시피를 한 줄씩 읽고 실행하는 사람.
- **주방 도구(운영체제·라이브러리)** — 칼, 프라이팬, 오븐 같이 요리사가 쓰는 도구들.
- **재료(데이터)** — 양파, 달걀, 고기. 요리마다 다른 입력.
- **완성 요리(결과)** — 사용자에게 내어 놓는 최종 산출물.

좋은 소프트웨어는 좋은 레시피와 같습니다.
- 초보가 읽어도 이해할 수 있도록 **명료하게** 쓰여야 하고,
- 순서가 뒤바뀌어도 혼란이 없도록 **단계가 나뉘어** 있어야 하고,
- 다른 요리사가 오늘 이어서 해도 되도록 **기록** 이 남아야 합니다.

개발자가 하는 일의 절반은 "새 레시피를 쓰는 것"이고, 나머지 절반은 "기존 레시피를 읽고 이해하고 고치는 것"입니다. 이 프로젝트에서 여러분이 하게 될 일도 대부분 "기존 레시피를 읽고 고치는 것"입니다.

---

## 2. 정식 정의

**소프트웨어(Software)** 는 컴퓨터가 특정한 일을 수행하도록 지시하는 **명령어의 모음** 입니다. 이 명령어들은 텍스트 파일 형태로 존재하며, 이를 **소스 코드(source code)** 라고 부릅니다.

소프트웨어는 크게 두 종류로 나뉩니다.

1. **시스템 소프트웨어(System software)** — 하드웨어와 가장 가까운 층. 예: Windows, macOS, Linux 같은 운영체제(OS).
2. **응용 소프트웨어(Application software)** — 우리가 일상에서 쓰는 것들. 예: 크롬, 카카오톡, Excel, 그리고 AIDOO Portal.

이 교육에서 우리가 만질 것은 **응용 소프트웨어**, 그중에서도 **웹(Web) 기반 응용 소프트웨어** 입니다.

---

## 3. 소프트웨어는 왜 복잡한가

개발 경험이 없는 분들이 코드를 처음 볼 때 "왜 이렇게 복잡하지?"라고 느낍니다. 그 이유는 단순합니다.

### 3.1 **세상 자체가 복잡하기 때문**

- "회의실을 예약한다"는 한 줄짜리 업무에도 실제로는 수많은 경우의 수가 있습니다. 예약자가 중복되면? 시간이 겹치면? 삭제된 회의실을 예약하려 하면? 사용자 권한이 없으면?
- 소프트웨어는 **모든 경우의 수를 미리 써 둬야** 합니다. 이 "엣지 케이스(edge case, 경계 상황)" 처리가 코드의 절반 이상을 차지합니다.

### 3.2 **혼자 쓰는 게 아니기 때문**

- 수백~수천 명이 동시에 접속합니다.
- 같은 문서를 여러 명이 동시에 편집할 수 있어야 합니다.
- 한 사람이 오래 쓰는 동안 다른 사람도 끊기면 안 됩니다.
- 이 "동시성(concurrency)" 문제가 복잡성을 크게 끌어올립니다.

### 3.3 **변한다는 것이 본성이기 때문**

- 오늘 만든 기능을 내일 바꿔야 합니다.
- 그래서 **나중에 쉽게 바꿀 수 있도록** 미리 준비하는 코드(설계)가 필요합니다.
- 이 "변경에 대한 준비"가 또 복잡성을 만듭니다.

복잡성을 없애는 것이 아니라 **잘 배치하는 것** 이 소프트웨어 공학의 본질입니다. 즉, 복잡성을 "여러 상자에 나눠 담고, 상자끼리의 연결을 줄이는 것"이 우리의 일입니다.

> 📖 *프레드릭 브룩스의 유명한 에세이 「No Silver Bullet(은탄은 없다)」(1986)의 요지도 이것입니다. "소프트웨어의 복잡성에는 본질적 복잡성(essential)과 우발적 복잡성(accidental)이 있고, 도구는 우발적 부분만 줄일 수 있다."*

---

## 4. 소프트웨어의 생애 — 만들고 끝이 아니다

많은 비개발자들이 오해하는 부분입니다. "소프트웨어는 한 번 만들면 끝"이 아닙니다. 실제 업계 통계는 이렇습니다.

- **소프트웨어 총 비용의 60~80%가 "유지 보수(maintenance)"에 쓰인다.**
- 처음 만드는 데 쓰는 시간보다 **고치고 늘리는 데 쓰는 시간이 훨씬 많다.**

그래서 개발자들은 항상 "나중에 읽는 사람"을 의식하며 코드를 씁니다. 함수 이름을 고민하고, 주석을 남기고, 폴더 구조를 정돈하는 이유가 여기 있습니다. "6개월 뒤의 내가 읽어도 이해될 만한가?" 가 코드의 품질 기준입니다.

## 5. 현대 웹 소프트웨어의 뼈대

AIDOO Portal 같은 웹 기반 소프트웨어는 대부분 이렇게 구성됩니다.

```
[ 사용자의 웹 브라우저 ]
         ↑↓ 인터넷(HTTP)
[ 웹 서버 / 프런트엔드 코드 ]   ← 화면과 상호작용
         ↑↓ API(HTTP/WebSocket)
[ 애플리케이션 서버(백엔드) ]  ← 비즈니스 로직
         ↑↓
[ 데이터베이스 ]  [ 파일 저장소 ]  [ 외부 API(예: OpenAI) ]
```

이 구조를 **3-Tier 아키텍처(3계층 구조)** 라고 부릅니다. 1990년대 중반부터 표준이 되었고, AIDOO Portal도 근본적으로는 이 구조를 따릅니다. 자세한 이야기는 6장에서 다룹니다.

## 6. "코드"의 실제 모습

용어가 추상적이라 낯설 수 있으니 실제로 우리 프로젝트의 코드가 어떻게 생겼는지 아주 짧은 예만 보겠습니다.

```python
# apps/api/src/aidoo_api/domains/auth/router.py (개념 예시)
@router.post("/login")
def login(body: LoginRequest):
    user = verify_password(body.email, body.password)
    if not user:
        raise HTTPException(status_code=401, detail="invalid credentials")
    return issue_session(user)
```

무슨 언어인지 지금은 몰라도 됩니다. 읽어 보면 **한국어 회의록처럼** 보입니다.
"`/login`이라는 주소로 요청이 들어오면, 이메일/비밀번호를 검증하고, 맞으면 세션을 발급하고, 틀리면 '401 유효하지 않은 자격'이라고 에러를 낸다."

놀랍게도 실제 개발자들이 하는 일의 80%는 이렇게 **자연어에 가까운 의사 코드(pseudocode)** 를 문법에 맞춰 쓰는 것입니다. AI는 바로 이 문법 부분을 우리 대신 써 줍니다.

## 7. 왜 "하나의 기술"이 아니라 "여러 기술의 조합"인가

여러분이 이 프로젝트를 보면 기술 이름이 수십 개 나옵니다. "왜 이렇게 많지?"라는 의문이 당연합니다.

이유는 **각 층마다 전문 도구가 있기 때문** 입니다.

- 화면(프런트)은 사람이 보는 거니까 **아름답고 빠르게** 반응해야 합니다 → React, Tailwind
- 서버(백)는 **안정적이고 빠르게** 많은 요청을 처리해야 합니다 → FastAPI, Python
- 데이터는 **영구적이고 안전하게** 저장해야 합니다 → PostgreSQL
- 대용량 파일은 별도 저장소가 효율적입니다 → MinIO
- 시간이 오래 걸리는 작업은 뒷줄로 빼야 합니다 → Celery + Redis
- AI는 전문 업체가 만든 걸 씁니다 → OpenAI API

이렇게 **"각 문제에 맞는 도구"** 를 조합한 것이 현대 소프트웨어 아키텍처입니다. 한 사람이 전부 다 깊게 알 필요는 없습니다. **각 도구가 왜 거기에 있는지** 만 알면 됩니다.

---

## 8. 핵심 요약

- 소프트웨어는 "컴퓨터에게 주는 지시문"이다.
- 복잡한 이유는 세상 자체가 복잡하기 때문이고, 그래서 복잡성을 **잘 나눠 담는 것** 이 설계의 본질이다.
- 소프트웨어의 생애는 만들기보다 **고치기가 훨씬 길다**. 그래서 "읽기 쉬운 코드"가 곧 좋은 코드다.
- 현대 웹 소프트웨어는 프런트(화면) ↔ 백(서버) ↔ 데이터/저장소/외부서비스의 **3계층 구조** 다.
- 한 시스템에 여러 기술이 공존하는 것은 **각 층마다 전문 도구가 다르기 때문** 이다.

## 9. 이해도 체크

1. "소프트웨어는 한 번 만들면 끝"이라는 말이 왜 틀렸는지, 회사 문서 양식 업데이트에 비유해 설명해 보세요.
2. 엣지 케이스(edge case)를 "회의실 예약" 업무에서 세 가지 들어 보세요.
3. 3-Tier 아키텍처의 세 층을 각각 이름과 역할로 적어 보세요.
4. 우리 프로젝트에 많은 기술이 쓰이는 이유를 한 문장으로 설명하세요.
5. "본질적 복잡성"과 "우발적 복잡성"의 차이를 짐작해 보세요. (정답은 본문에 있습니다.)
