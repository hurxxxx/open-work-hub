# 02. 소프트웨어란 무엇인가

> **한 줄 요약.** 소프트웨어는 "사람이 쓴 지시문"이며, 그 지시문을 컴퓨터가 한 줄씩 해석해 실행하는 것이다. 소프트웨어가 복잡한 이유는 **세상 자체가 복잡해서** 그 복잡함을 모두 담아야 하기 때문이다.

---

## 1. 소프트웨어를 구성 요소로 이해하기

소프트웨어 실행은 입력, 처리, 출력의 흐름으로 이해할 수 있습니다.

- **코드(Code)** — 컴퓨터가 수행할 절차를 순서대로 적은 지시문.
- **CPU** — 코드를 한 줄씩 읽고 실제 연산을 수행하는 처리 장치.
- **운영체제·라이브러리** — 코드가 하드웨어를 안전하게 사용하도록 돕는 실행 기반.
- **데이터(Data)** — 처리 대상 입력값.
- **결과(Output)** — 사용자에게 전달되는 최종 산출물.

좋은 소프트웨어는 다음 조건을 만족합니다.
- 초보가 읽어도 이해할 수 있도록 **명료하게** 쓰여야 하고,
- 순서가 뒤바뀌어도 혼란이 없도록 **단계가 나뉘어** 있어야 하고,
- 다른 사람이 이어서 수정해도 되도록 **기록** 이 남아야 합니다.

개발자의 핵심 업무는 "새 코드를 작성하는 것"과 "기존 코드를 읽고 수정하는 것"입니다. 이 프로젝트에서도 대부분의 작업은 기존 코드를 이해하고 개선하는 형태로 진행됩니다.

### 1.1 같은 개념을 다른 관점에서 정리하기

- **코드와 실행 환경 분리.** 같은 코드라도 CPU 성능, 운영체제, 런타임 버전이 다르면 실행 결과나 성능이 달라질 수 있습니다.
- **변경 이력 관리.** 소프트웨어는 버그 발견 → 수정 → 커밋 기록을 반복하며, 변경 이력이 품질과 협업의 기준이 됩니다.
- **병목 관리.** 입력 처리 파이프라인에서 한 단계가 느리면 전체 응답 시간이 길어집니다. 예를 들어 파일 업로드 지연은 이후 요약 처리 지연으로 이어질 수 있습니다.

### 1.2 바로잡고 싶은 오해들

- **"소프트웨어는 만들고 나면 완제품이다."**
  출시 이후에도 개정과 보수가 끊임없이 이어집니다. 완제품이 아니라 **지속적으로 변경되는 운영 자산** 입니다(4장 참고).
- **"코드는 지나치게 난해해서 읽을 수 없다."**
  실제로 대부분의 코드는 **영어 문장에 기호를 조금 섞어 놓은** 모양입니다. 6장에 나오는 `/login` 라우터 예시만 봐도 일반 문장 형태로 읽힙니다.
- **"AI가 일을 대신하니 이제 사람은 코드를 안 봐도 된다."**
  AI가 내놓은 결과물이 제대로 된 것인지 판별하려면 **코드가 대략 무슨 말을 하는지 읽어낼 감각** 은 있어야 합니다. 세부 문법까지 외울 필요는 없습니다.

## 2. 정식 정의

**소프트웨어(Software)** 는 컴퓨터가 특정한 일을 수행하도록 지시하는 **명령어의 모음** 입니다. 이 명령어들은 텍스트 파일 형태로 존재하며, 이를 **소스 코드(source code)** 라고 부릅니다.

소프트웨어는 크게 두 종류로 나뉩니다.

1. **시스템 소프트웨어(System software)** — 하드웨어와 가장 가까운 층. 예: Windows, macOS, Linux 같은 운영체제(OS).
2. **응용 소프트웨어(Application software)** — 우리가 일상에서 쓰는 것들. 예: 크롬, 카카오톡, Excel, 그리고 Open Work Hub.

이 교육에서 우리가 만질 것은 **응용 소프트웨어**, 그중에서도 **웹(Web) 기반 응용 소프트웨어** 입니다.

## 3. 소프트웨어는 왜 복잡한가

개발 경험이 없는 분들이 코드를 처음 볼 때 "왜 이렇게 복잡하지?"라고 느낍니다. 그 이유는 단순합니다.

### 3.1 세상 자체가 복잡하다

- "회의실을 예약한다"는 한 줄짜리 업무에도 실제로는 수많은 경우의 수가 있습니다. 예약자가 중복되면? 시간이 겹치면? 삭제된 회의실을 예약하려 하면? 사용자 권한이 없으면?
- 소프트웨어는 **모든 경우의 수를 미리 써 둬야** 합니다. 이 "엣지 케이스(edge case, 경계 상황)" 처리가 코드의 절반 이상을 차지합니다.

### 3.2 혼자 쓰는 것이 아니다

- 수백~수천 명이 동시에 접속합니다.
- 같은 문서를 여러 명이 동시에 편집할 수 있어야 합니다.
- 한 사람이 오래 쓰는 동안 다른 사람도 끊기면 안 됩니다.
- 이 "동시성(concurrency)" 문제가 복잡성을 크게 끌어올립니다.

### 3.3 어제 만든 것도 내일이면 바뀐다

- 오늘 만든 기능을 내일 바꿔야 합니다.
- 그래서 **나중에 쉽게 바꿀 수 있도록** 미리 준비하는 코드(설계)가 필요합니다.
- 이 "변경에 대한 준비"가 또 복잡성을 만듭니다.

복잡성을 없애는 것이 아니라 **관리 가능한 단위로 배치하는 것**이 소프트웨어 공학의 본질입니다. 즉, 기능을 모듈로 분리하고 모듈 간 결합을 줄이는 것이 핵심입니다.

> 📖 *프레드릭 브룩스의 유명한 에세이 「No Silver Bullet(은탄은 없다)」(1986)의 요지도 이것입니다. "소프트웨어의 복잡성에는 본질적 복잡성(essential)과 우발적 복잡성(accidental)이 있고, 도구는 우발적 부분만 줄일 수 있다."*

## 4. 소프트웨어의 생애 — 만들고 끝이 아니다

많은 비개발자들이 오해하는 부분입니다. "소프트웨어는 한 번 만들면 끝"이 아닙니다. 실제 업계 통계는 이렇습니다.

- **소프트웨어 총 비용의 60~80%가 "유지 보수(maintenance)"에 쓰인다.**
- 처음 만드는 데 쓰는 시간보다 **고치고 늘리는 데 쓰는 시간이 훨씬 많다.**

그래서 개발자들은 항상 "나중에 읽는 사람"을 의식하며 코드를 씁니다. 함수 이름을 고민하고, 주석을 남기고, 폴더 구조를 정돈하는 이유가 여기 있습니다. "6개월 뒤의 내가 읽어도 이해될 만한가?" 가 코드의 품질 기준입니다.

## 5. 현대 웹 소프트웨어의 뼈대

Open Work Hub 같은 웹 기반 소프트웨어는 대부분 이렇게 구성됩니다.

| 층 | 구성 | 주고받는 방식 |
| --- | --- | --- |
| 사용자 | 웹 브라우저(크롬·사파리·엣지) | 인터넷(HTTP/HTTPS) |
| 프런트엔드 | 웹 서버가 내려준 화면 코드(JS·CSS·HTML) | API(HTTP/REST, WebSocket) |
| 백엔드 | 애플리케이션 서버(비즈니스 로직) | DB 드라이버, 파일 SDK, 외부 API |
| 저장·외부 | 데이터베이스 · 파일 저장소 · 외부 API(OpenAI 등) | — |

이 구조를 **3-Tier 아키텍처(3계층 구조, 3-Tier Architecture)** 라고 부릅니다. 1990년대 중반부터 표준이 되었고, Open Work Hub도 근본적으로는 이 구조를 따릅니다. 자세한 이야기는 6장에서 다룹니다.

### 5.1 신입사원 김 대리의 첫 로그인

김 대리가 Open Work Hub에 처음 로그인하는 그 한 번의 클릭 뒤에는 이런 일들이 벌어집니다.

1. **브라우저** 가 `https://open-work-hub.example.com/login` 을 연다 → 웹 서버가 로그인 화면(HTML/JS)을 내려 준다.
2. 김 대리가 이메일·비밀번호를 입력하고 버튼을 누른다 → **프런트엔드 JS 코드** 가 그 값을 모아 백엔드로 HTTP 요청을 보낸다.
3. **백엔드(FastAPI)** 가 요청을 받고, **데이터베이스** 에서 김 대리의 계정 정보를 조회해 비밀번호 해시를 비교한다.
4. 맞으면 세션 토큰을 발급해 응답한다 → 프런트는 그 세션을 저장하고 메인 화면으로 전환.

이 네 계층이 **짧은 시간 안에 연쇄적으로 동작합니다.** 이 흐름이 머릿속에 그려지면 Part 2의 내용이 훨씬 편하게 읽힙니다.

## 6. "코드"의 실제 모습

용어가 추상적이라 낯설 수 있으니 실제로 우리 프로젝트의 코드가 어떻게 생겼는지 아주 짧은 예만 보겠습니다.

```python
# apps/api/src/open_work_hub_api/domains/auth/router.py (개념 예시)
@router.post("/login")
def login(body: LoginRequest):
    user = verify_password(body.email, body.password)
    if not user:
        raise HTTPException(status_code=401, detail="invalid credentials")
    return issue_session(user)
```

무슨 언어인지 지금은 몰라도 괜찮습니다. 찬찬히 읽어 보면 실행 흐름이 단계별로 읽힙니다.
"`/login`이라는 주소로 요청이 들어오면 이메일/비밀번호를 검증하고, 맞으면 세션을 발급하고, 틀리면 '401 유효하지 않은 자격'이라고 에러를 낸다."

사실 개발자가 하는 일의 대부분은 이렇게 **말에 가까운 의사 코드(pseudocode)** 를 문법에 맞춰 옮겨 적는 작업입니다. AI는 바로 이 문법을 맞추는 부분을 대신 해 줍니다.

## 7. 왜 "하나의 기술"이 아니라 "여러 기술의 조합"인가

여러분이 이 프로젝트를 보면 기술 이름이 수십 개 나옵니다. "왜 이렇게 많지?"라는 의문이 당연합니다.

이유는 **각 층마다 전문 도구가 있기 때문** 입니다.

- 화면(프런트)은 사람이 보는 거니까 **아름답고 빠르게** 반응해야 합니다 → React, Tailwind
- 서버(백)는 **안정적이고 빠르게** 많은 요청을 처리해야 합니다 → FastAPI, Python
- 데이터는 **영구적이고 안전하게** 저장해야 합니다 → PostgreSQL
- 대용량 파일은 별도 저장소가 효율적입니다 → MinIO
- 시간이 오래 걸리는 작업은 별도 비동기 처리 계층으로 분리해야 합니다 → Celery + Redis
- AI는 전문 업체가 만든 걸 씁니다 → OpenAI API

이렇게 **"각 문제에 맞는 도구"** 를 조합한 것이 현대 소프트웨어 아키텍처입니다. 한 사람이 전부 다 깊게 알 필요는 없습니다. **각 도구가 왜 거기에 있는지** 만 알면 됩니다.

### 7.1 여기서 짚고 갈 오해들

- **"기술이 많을수록 과잉 설계이거나 허세다."**
  각 계층에서 다루는 문제가 워낙 달라서, 하나의 도구로 전부 감당하려 들면 오히려 비효율이 커집니다. 문제는 **도구의 숫자가 아니라 "왜 이걸 골랐는지 설명이 안 되는 것"** 입니다.
- **"한 번 고른 기술은 끝까지 그대로 써야 한다."**
  필요하면 얼마든지 교체합니다. 예컨대 MinIO를 AWS S3로 갈아 끼우는 일은 드물지 않습니다. 그래서 코드를 짤 때 **"저장소가 바뀌어도 흔들리지 않도록"** 구조를 미리 잡아 둡니다(6장 아키텍처).
- **"개발자는 모든 층을 다 잘 알아야 한다."**
  풀스택(full-stack)이라 불리는 개발자도 실제로는 **깊이가 층마다 다릅니다.** 정말 중요한 것은 "내가 모르는 층이 어디인지 아는 지도 감각"입니다.

## 8. 핵심 요약

- 소프트웨어는 "컴퓨터에게 주는 지시문"이다.
- 복잡한 이유는 세상 자체가 복잡하기 때문이고, 그래서 복잡성을 **잘 나눠 담는 것** 이 설계의 본질이다.
- 소프트웨어의 생애는 만들기보다 **고치기가 훨씬 길다**. 그래서 "읽기 쉬운 코드"가 곧 좋은 코드다.
- 현대 웹 소프트웨어는 프런트(화면) ↔ 백(서버) ↔ 데이터/저장소/외부서비스의 **3계층 구조** 다.
- 한 시스템에 여러 기술이 공존하는 것은 **각 층마다 전문 도구가 다르기 때문** 이다.
