# 18. 설계와 구현 관리 — AI Agent의 작업을 작게 나누고 통제하기

> **한 줄 요약.** 설계는 개발자만 하는 도면 작업이 아니라, **무엇을 어디까지 바꾸고 어떤 위험을 감수할지 결정하는 관리 행위**다.

---

## 학습 목표

이 장을 읽고 나면 다음을 할 수 있어야 합니다.

1. 요구사항을 구현 가능한 작은 작업 단위로 나누는 이유를 설명할 수 있다.
2. AI Agent가 제안한 변경 계획에서 위험 신호를 찾을 수 있다.
3. 설계 판단, 구현 범위, PR 단위를 구분해 작업을 관리할 수 있다.

---

## 1. 설계는 "코드 구조"만 뜻하지 않는다

설계라고 하면 클래스, 함수, DB 구조 같은 기술적 그림을 떠올리기 쉽습니다. 하지만 비개발자에게 더 중요한 설계는 다음 질문에 답하는 일입니다.

- 어떤 화면이나 API가 바뀌는가?
- 기존 사용자 흐름에 영향을 주는가?
- 데이터 구조가 바뀌는가?
- 권한이나 보안 조건이 추가되는가?
- 한 번에 배포해도 되는가, 나눠야 하는가?
- 문제가 생기면 되돌릴 수 있는가?

AI Agent는 구현안을 빠르게 만들 수 있지만, 어떤 변경이 작고 안전한지는 항상 잘 판단하지 못합니다. 그래서 사람은 **설계 검토자** 역할을 해야 합니다.

---

## 2. 요구사항을 작업 단위로 나누기

예시 요구사항:

```text
문서 검색 결과가 없을 때 빈 상태 UI를 보여 준다.
```

이 요구사항은 작아 보이지만, 구현 작업은 여러 조각으로 나눌 수 있습니다.

| 작업 단위 | 설명 | 검증 |
|---|---|---|
| 상태 분기 확인 | 검색 결과가 0개인 경우를 구분 | 빈 배열 입력 테스트 |
| UI 문구 추가 | 안내 제목과 설명 표시 | 화면 렌더링 확인 |
| 다시 검색 행동 | 사용자가 검색어를 수정할 수 있게 함 | 수동 테스트 |
| 기존 결과 유지 | 결과가 있을 때 기존 목록 유지 | 기존 테스트 통과 |
| 테스트 추가 | 빈 상태 렌더링 테스트 | Vitest 통과 |

이렇게 나누면 AI Agent에게 한 번에 모든 것을 맡기지 않고, 각 단계별로 확인할 수 있습니다.

---

## 3. AI Agent에게 먼저 계획을 요구하기

구현 전 프롬프트:

```text
아래 요구사항을 구현하기 전에 계획만 작성해 줘.

요구사항:
문서 검색 결과가 없을 때 빈 상태 UI를 보여 준다.

계획에 포함할 것:
- 수정할 파일
- 변경 순서
- 추가할 테스트
- 위험하거나 확인이 필요한 부분
- 이번 작업에서 건드리지 않을 파일

아직 파일은 수정하지 마.
```

사람은 이 계획을 보고 승인하거나 수정 요청을 합니다.

### 3.1 계획에서 봐야 할 위험 신호

- 요구사항에 없는 파일을 많이 바꾸려 한다.
- 새 라이브러리를 추가하려 한다.
- 검색 API나 DB 쿼리까지 바꾸려 한다.
- 테스트 추가가 빠져 있다.
- "관련 파일 전체 리팩토링" 같은 큰 작업을 끼워 넣는다.
- 운영 데이터나 권한 정책을 건드리려 한다.

이런 신호가 있으면 바로 구현을 멈추고 계획을 줄여야 합니다.

---

## 4. 설계 판단의 5가지 축

비개발자가 모든 기술 세부를 알 필요는 없습니다. 대신 설계 판단을 아래 다섯 축으로 질문할 수 있어야 합니다.

### 4.1 변경 범위

이 변경은 한 화면만 바꾸는가, API와 DB까지 바꾸는가?

범위가 넓을수록 테스트와 리뷰가 더 필요합니다.

### 4.2 데이터 영향

기존 데이터의 모양이나 의미가 바뀌는가?

DB 마이그레이션, 데이터 삭제, 필드 의미 변경은 특별히 조심해야 합니다.

### 4.3 사용자 영향

사용자가 보던 화면이나 행동이 바뀌는가?

작은 문구 변경도 업무 흐름에서는 중요할 수 있습니다.

### 4.4 운영 영향

배포 후 문제가 생기면 되돌릴 수 있는가?

롤백이 어렵거나 운영 데이터가 바뀌면 출시 전 승인이 필요합니다.

### 4.5 유지보수 영향

이번 수정이 나중에 이해하기 쉬운가?

AI가 만든 코드는 당장은 동작해도, 이름이 이상하거나 중복이 많으면 나중에 비용이 됩니다.

---

## 5. PR 단위로 생각하기

AI Agent는 큰 변경을 한 번에 만들 수 있지만, 사람은 큰 diff를 제대로 리뷰하기 어렵습니다. 그래서 구현 관리는 **PR 단위**로 생각해야 합니다.

좋은 PR:

- 하나의 문제만 해결한다.
- 변경 파일이 적다.
- 테스트가 포함되어 있다.
- PR 본문에 검증 방법이 있다.
- 롤백이 어렵지 않다.

나쁜 PR:

- 버그 수정, 리팩토링, 디자인 변경이 섞여 있다.
- 새 의존성이 설명 없이 추가된다.
- 테스트 없이 "확인 완료"라고만 적혀 있다.
- 관련 없는 파일 포맷 변경이 섞여 있다.

비개발자는 PR을 직접 승인하지 않더라도, "이 변경은 너무 큰 것 아닌가요?"라고 질문할 수 있어야 합니다.

---

## 6. 기술 부채를 이해하기

기술 부채는 "나중에 갚아야 할 개발상의 빚"입니다.

예를 들어 급해서 중복 코드를 넣거나, 테스트 없이 임시 분기를 추가하면 지금은 빨리 끝납니다. 하지만 다음 수정 때 더 어렵고 위험해집니다.

AI Agent와 일할 때 기술 부채는 더 쉽게 생깁니다.

- AI가 기존 패턴을 충분히 읽지 않고 새 패턴을 만든다.
- 비슷한 코드를 복사해 여러 곳에 둔다.
- 테스트 없이 "작동할 것 같은" 코드를 만든다.
- 이름이 모호한 함수나 변수를 만든다.

기술 부채를 완전히 피할 수는 없습니다. 중요한 것은 **의식적으로 기록하고 관리하는 것**입니다.

PR 본문에 이렇게 적을 수 있습니다.

```text
남은 부채:
- 빈 상태 UI 문구는 임시 문안입니다. 디자인/UX 검토 후 조정 필요.
- 검색 실패 상태와 빈 결과 상태는 다음 작업에서 더 명확히 분리할 예정입니다.
```

---

## 7. 작업 브리프 템플릿

AI Agent에게 구현을 맡기기 전, 아래 정도의 작업 브리프를 만들면 안정적입니다.

```text
# 작업 브리프

## 목표
문서 검색 결과가 없을 때 빈 상태 UI를 보여 준다.

## 변경 범위
- 대상 화면: 문서 검색 화면
- 대상 파일 후보: RagSearchView 관련 파일
- API/DB 변경: 없음

## 하지 않을 일
- 검색 알고리즘 변경
- 새 라이브러리 추가
- 전체 레이아웃 개편

## 구현 순서
1. 빈 결과 상태 분기 확인
2. 안내 UI 추가
3. 빈 상태 테스트 추가
4. 기존 결과 상태 회귀 확인

## 검증
- 빈 결과 테스트 통과
- 기존 결과 렌더링 테스트 통과
- 로컬 화면 수동 확인

## 승인 필요
- 새 의존성 제안 시 중단
- API 변경 필요 시 중단
```

이 브리프는 개발자에게도 좋고 AI Agent에게도 좋습니다. 누가 구현하든 같은 기준을 보게 만들기 때문입니다.

---

## 8. 구현 중 멈춰야 하는 순간

다음 상황에서는 AI Agent가 계속 진행하려 해도 멈춥니다.

- DB 스키마 변경이 필요하다고 말한다.
- 새 패키지 설치를 제안한다.
- 인증·권한 로직을 수정하려 한다.
- 운영 환경 변수나 시크릿을 요구한다.
- 많은 파일을 한꺼번에 리팩토링하려 한다.
- 테스트가 실패했는데 원인을 모른 채 테스트를 삭제하려 한다.
- 요구사항에 없던 기능을 추가하려 한다.

멈춘 뒤에는 이렇게 요청합니다.

```text
지금부터는 구현하지 말고, 왜 이 변경이 필요한지와 대안 2가지를 설명해 줘.
각 대안의 위험과 검증 방법도 함께 정리해 줘.
```

---

## 9. AI Agent 작업 관리 프롬프트

```text
너는 지금 구현자가 아니라 작업 계획자다.

요구사항:
문서 검색 결과가 없을 때 빈 상태 UI를 보여 준다.

다음 기준으로 작업을 쪼개 줘:
- 각 단계는 1개 PR로 만들 수 있어야 한다.
- 각 단계마다 검증 방법이 있어야 한다.
- DB, API, 새 의존성 변경은 기본적으로 제외한다.
- 필요하다고 판단되면 "사람 승인 필요"로 표시한다.

출력:
1. 권장 작업 순서
2. 각 단계의 변경 파일 후보
3. 테스트 계획
4. 위험 신호
5. 내가 승인해야 할 결정
```

이 프롬프트는 AI Agent가 코드를 쓰기 전에 작업을 통제 가능한 크기로 나누게 합니다.

---

## 10. 구현 완료 후 설계가 바뀌었는지 확인하기

구현이 끝난 뒤에도 설계 검토는 필요합니다. AI Agent가 구현 과정에서 처음 계획과 다른 길을 택했을 수 있기 때문입니다.

확인할 항목:

- 처음 계획에 없던 파일이 바뀌었는가?
- 처음 제외한 범위가 몰래 포함되었는가?
- 새 의존성이나 설정 변경이 들어갔는가?
- 테스트가 요구사항을 검증하는가, 구현 세부만 검증하는가?
- 코드를 읽는 사람이 이름만 보고 의도를 알 수 있는가?

이 검토는 "잘못을 찾기"보다 "처음 합의한 설계와 실제 변경이 일치하는지 확인"하는 과정입니다.

## 11. 5분 실습

아래 요구사항을 3개 이하의 PR 단위로 쪼개 보세요.

```text
문서 검색 화면을 개선해서 결과 없음, 로딩 중, 오류 상태를 더 명확하게 보여 주고 싶다.
```

각 PR에 대해 작성할 것:

- 목표
- 바꿀 가능성이 있는 파일
- 하지 않을 일
- 테스트 방법
- 사람 승인 필요 여부

---

## 12. 핵심 요약

- 설계는 코드 도면만이 아니라 변경 범위, 데이터 영향, 운영 위험을 결정하는 일이다.
- AI Agent에게는 구현보다 먼저 계획을 요구해야 한다.
- 좋은 작업은 작은 PR로 나뉘고, 각 PR은 하나의 문제만 해결한다.
- 비개발자는 변경 범위, 위험 신호, 승인 지점을 관리하는 역할을 할 수 있다.

---

## 완료 기준

이 장을 끝냈다면 다음을 할 수 있어야 합니다.

- AI Agent가 제안한 구현 계획에서 과잉 변경을 찾을 수 있다.
- 요구사항 하나를 1~3개의 PR 단위로 나눌 수 있다.
- DB, 권한, 새 의존성, 대량 리팩토링 앞에서 멈춰야 한다고 말할 수 있다.
