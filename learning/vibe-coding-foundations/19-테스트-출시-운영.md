# 19. 테스트, 출시, 운영 — 만든 기능을 안전하게 사용자에게 전달하기

> **한 줄 요약.** 기능은 코드가 완성됐을 때 끝나는 것이 아니라, **테스트를 통과하고 안전하게 출시된 뒤 운영에서 문제없이 쓰일 때** 비로소 완성된다.

---

## 학습 목표

이 장을 읽고 나면 다음을 할 수 있어야 합니다.

1. 테스트, QA, 출시 승인, 운영 관찰의 차이를 설명할 수 있다.
2. AI Agent가 만든 기능을 출시하기 전 확인할 체크리스트를 만들 수 있다.
3. 장애나 사용자 피드백을 다음 개선 작업으로 연결할 수 있다.

---

## 1. 테스트와 출시는 다른 일이다

테스트가 통과했다는 말은 중요하지만, 그것만으로 출시 준비가 끝난 것은 아닙니다.

| 구분 | 확인하는 것 |
|---|---|
| 자동 테스트 | 코드가 정해진 조건에서 동작하는가 |
| 수동 QA | 실제 화면과 업무 흐름에서 자연스러운가 |
| 출시 승인 | 지금 사용자에게 내보내도 되는가 |
| 운영 관찰 | 출시 후 실제로 문제없이 쓰이는가 |

AI Agent가 코드를 만들고 테스트까지 추가해도, 실제 사용자 흐름과 운영 리스크를 판단하는 일은 사람이 해야 합니다.

---

## 2. 테스트 전략의 큰 그림

테스트는 여러 층으로 나뉩니다.

### 2.1 단위 테스트

작은 함수나 컴포넌트가 의도대로 동작하는지 확인합니다.

예:

- 검색 결과가 빈 배열이면 빈 상태 문구를 렌더링한다.
- 날짜 포맷 함수가 올바른 문자열을 반환한다.

### 2.2 통합 테스트

여러 부분이 함께 연결될 때도 동작하는지 봅니다.

예:

- 검색 API 응답을 받아 화면에 결과를 표시한다.
- 권한이 없는 사용자는 관리자 API에 접근하지 못한다.

### 2.3 E2E 테스트

사용자처럼 브라우저에서 실제 흐름을 따라가며 확인합니다.

예:

- 사용자가 로그인한다.
- 문서 검색 화면으로 이동한다.
- 검색어를 입력한다.
- 결과 없음 안내를 확인한다.

비개발자가 특히 잘 볼 수 있는 것은 통합 테스트와 E2E 관점입니다. 코드 내부보다 실제 업무 흐름을 확인하기 때문입니다.

---

## 3. AI Agent가 만든 테스트를 검토하는 법

AI Agent가 테스트를 만들었다고 해서 충분하다고 믿으면 안 됩니다. 테스트도 리뷰 대상입니다.

확인할 질문:

- 정상 케이스만 있고 실패 케이스가 빠지지 않았는가?
- 빈 데이터, 권한 없음, 네트워크 오류 같은 상황이 있는가?
- 테스트 이름만 그럴듯하고 실제 검증은 약하지 않은가?
- 기존 테스트를 삭제하거나 약하게 만들지 않았는가?
- 구현에 맞춘 테스트가 아니라 요구사항에 맞춘 테스트인가?

나쁜 테스트:

```text
화면이 렌더링되는지만 확인한다.
```

좋은 테스트:

```text
검색 결과가 0개일 때 빈 상태 안내 문구와 다시 검색 행동이 보이는지 확인한다.
```

## 4. 출시 전 체크리스트

작은 기능이라도 출시 전에는 아래를 확인합니다.

### 4.1 기능 확인

- 요구사항의 성공 기준을 모두 만족하는가?
- 정상 상태, 빈 상태, 오류 상태를 확인했는가?
- 기존 기능이 깨지지 않았는가?

### 4.2 기술 확인

- 자동 테스트가 통과했는가?
- 린트와 타입 체크가 통과했는가?
- 새 의존성이 없다면 정말 없는가?
- DB 마이그레이션이 있다면 적용·롤백 방법이 있는가?

### 4.3 운영 확인

- 문제가 생기면 되돌릴 수 있는가?
- 로그나 에러 메시지로 원인을 파악할 수 있는가?
- 사용자에게 안내가 필요한 변경인가?
- 배포 후 누가 확인할지 정해져 있는가?

### 4.4 보안 확인

- 시크릿이나 개인정보가 로그, PR, 프롬프트에 노출되지 않았는가?
- 권한 없는 사용자의 접근을 막는가?
- AI 도구나 MCP가 쓰기 권한을 과하게 갖지 않았는가?

## 5. 릴리스 노트 작성

릴리스 노트는 "무엇이 바뀌었는지"를 팀이 이해할 수 있게 남기는 짧은 기록입니다.

좋은 릴리스 노트:

```text
변경:
- 문서 검색 결과가 없을 때 빈 상태 안내를 표시합니다.
- 사용자가 검색어를 수정해 다시 검색할 수 있습니다.

검증:
- 빈 결과 상태 렌더링 테스트 추가
- 기존 검색 결과 렌더링 테스트 통과
- 로컬 화면에서 결과 있음/없음 상태 확인

운영 확인:
- 배포 후 문서 검색 화면에서 빈 결과 상태를 1회 수동 확인
- 사용자 문의 증가 여부 관찰
```

AI Agent에게 릴리스 노트 초안을 맡길 수 있지만, 사람은 실제 검증 내용이 맞는지 확인해야 합니다.

## 6. 출시 승인 미니 회의

작은 기능도 출시 전 5분 정도는 아래 질문을 확인하는 것이 좋습니다.

| 질문 | 확인 내용 |
|---|---|
| 무엇이 바뀌었나 | 사용자에게 보이는 변화와 내부 변화 |
| 왜 지금 내보내나 | 문제 해결 효과와 우선순위 |
| 무엇으로 검증했나 | 자동 테스트, 수동 QA, 실제 화면 확인 |
| 실패하면 어떻게 하나 | 롤백, 기능 끄기, 담당자 |
| 배포 후 무엇을 볼 것인가 | 로그, 문의, 지표, 화면 동작 |

이 회의는 길 필요가 없습니다. 중요한 것은 출시를 "개발 완료의 자동 결과"가 아니라 **사람이 승인하는 운영 행위**로 보는 것입니다.

---

## 7. 롤백과 피처 플래그

출시는 항상 되돌릴 수 있어야 합니다.

**롤백**은 문제가 생겼을 때 이전 버전으로 되돌리는 것입니다.

**피처 플래그**는 기능을 코드에 넣어 두되 설정으로 켜고 끌 수 있게 하는 방식입니다.

작은 UI 개선은 롤백만으로 충분할 수 있습니다. 하지만 운영 데이터, 권한, 결제, 외부 전송과 관련된 기능은 피처 플래그나 단계적 출시를 고려해야 합니다.

비개발자가 물어볼 질문:

- 문제가 생기면 끌 수 있나요?
- 이전 버전으로 돌아갈 수 있나요?
- DB 데이터가 바뀌면 되돌릴 수 있나요?
- 일부 사용자에게만 먼저 켤 수 있나요?

---

## 8. 운영 관찰

배포 후에는 기능이 실제로 어떻게 쓰이는지 봐야 합니다.

관찰할 수 있는 것:

- 에러 로그
- 사용자 문의
- 검색 실패율
- 기능 사용 횟수
- 응답 속도
- 특정 화면에서의 이탈

예를 들어 검색 빈 상태 UI를 출시했다면 다음을 봅니다.

- 사용자가 결과 없음 상태에서 다시 검색하는가?
- 같은 문의가 줄었는가?
- 검색 오류 로그가 늘지 않았는가?
- 빈 상태 문구가 오해를 만들지 않는가?

운영 관찰은 다음 기획의 재료입니다.

---

## 9. 장애 대응의 기본 흐름

장애가 나면 먼저 원인을 완벽히 찾으려 하지 말고, 사용자의 피해를 줄이는 것이 우선입니다.

1. **인지**: 알림, 사용자 제보, 모니터링으로 문제를 안다.
2. **영향 파악**: 누구에게, 어느 기능에서, 얼마나 발생하는지 본다.
3. **즉시 완화**: 롤백, 기능 끄기, 임시 안내를 한다.
4. **원인 분석**: 로그, 배포 이력, 최근 변경을 본다.
5. **재발 방지**: 테스트, 알림, 절차를 보강한다.
6. **회고**: 사람 탓이 아니라 시스템의 빈틈을 기록한다.

AI Agent는 로그 요약과 원인 후보 정리에 도움을 줄 수 있습니다. 하지만 운영 조치의 우선순위와 사용자 커뮤니케이션은 사람이 결정해야 합니다.

---

## 10. 운영 피드백을 다음 요구사항으로 바꾸기

운영에서 나온 피드백은 바로 구현 요청이 아닙니다. 다시 요구사항으로 바꿔야 합니다.

예:

```text
운영 피드백:
빈 상태 문구를 보고도 사용자가 무엇을 해야 할지 모르겠다는 문의가 있었다.

다음 요구사항 후보:
검색 결과가 없을 때 추천 행동을 더 명확히 보여 준다.

성공 기준:
- 사용자가 검색어를 수정하라는 안내를 볼 수 있다.
- 다시 검색 버튼 또는 입력 위치가 명확하다.
- 기존 검색 결과 화면은 바뀌지 않는다.
```

운영 피드백을 바로 "버튼 하나 추가"로 바꾸면 원인을 놓칠 수 있습니다. 먼저 문제가 무엇인지 다시 정의해야 합니다.

## 11. AI Agent에게 출시 전 검토를 맡기는 프롬프트

```text
아래 변경을 출시 전 관점에서 검토해 줘.

변경:
문서 검색 결과가 없을 때 빈 상태 안내를 표시한다.

검토 기준:
- 요구사항 충족 여부
- 빠진 테스트
- 기존 기능 회귀 가능성
- 운영 리스크
- 롤백 가능성
- 사용자 안내 필요 여부

출력:
1. 출시 가능 여부
2. 출시 전 반드시 확인할 항목
3. 출시 후 관찰할 항목
4. 사람 승인이 필요한 결정

주의:
모르는 것은 추측하지 말고 "확인 필요"로 표시해 줘.
```

이 프롬프트는 AI Agent에게 개발자 관점뿐 아니라 운영 관점의 검토를 시키는 데 유용합니다.

## 13. 핵심 요약

- 테스트 통과와 출시 가능은 같은 말이 아니다.
- 출시 전에는 기능, 기술, 운영, 보안을 함께 확인해야 한다.
- 롤백과 운영 관찰은 작은 기능에도 필요하다.
- 장애 대응은 원인 찾기보다 사용자 피해 완화가 먼저다.
- AI Agent는 검토를 도울 수 있지만 출시 승인과 운영 판단은 사람이 해야 한다.
