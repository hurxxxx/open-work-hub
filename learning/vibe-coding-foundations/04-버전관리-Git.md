# 04. 버전 관리와 Git

> **한 줄 요약.** Git은 코드의 **무한 실행취소(Undo)이자 협업용 타임머신**이다. 모든 변경은 "커밋"이라는 단위로 기록되고, 서로 다른 사람의 변경이 **브랜치**로 안전하게 공존하다가 **머지**로 합쳐진다.

---

## 1. 왜 버전 관리가 필요한가

Microsoft Word 문서를 만들 때 이런 경험이 있을 겁니다.

- `기획서.docx`
- `기획서_v2.docx`
- `기획서_v2_최종.docx`
- `기획서_v2_최종_진짜최종.docx`
- `기획서_v2_최종_진짜최종_김과장수정.docx`

웃기지만 매우 현실적인 풍경입니다. 소프트웨어 프로젝트는 수천 개의 파일로 이루어져 있습니다. 이런 식으로 백업하면 아무도 지금이 어떤 버전인지 모릅니다.

그래서 개발자들은 **버전 관리 시스템(Version Control System, VCS)** 을 씁니다. 지금의 사실상 세계 표준은 **Git** 입니다(2005년 리누스 토르발스가 만듦). 우리 프로젝트도 당연히 Git으로 관리합니다.

Git이 하는 일을 한 문장으로 요약하면 이렇습니다.

> **"모든 변경을 작은 스냅샷으로 차곡차곡 쌓아 두고, 언제든 과거의 임의 지점으로 돌아갈 수 있게 해 준다."**

---

## 2. 핵심 용어 — 이 장만으로도 충분

다음 5~6개의 용어가 Git의 99%입니다.

### 2.1 저장소(Repository, Repo)

Git이 관리하는 한 덩어리의 프로젝트. AIDOO Portal 저장소 = `doowon/` 폴더 전체.

### 2.2 커밋(Commit)

한 번의 "기록 시점"입니다. 회사 문서로 치면 **"승인 날인"** 같은 것. 어떤 변경 묶음을 "자, 이 상태를 영구 기록하자" 하고 도장을 찍는 행위입니다.

각 커밋에는
- **해시(hash)** — 고유 번호 (예: `a3f1b2c`)
- **메시지** — 이 커밋이 왜 생겼는지 (예: "로그인 오류 메시지 한글화")
- **작성자** — 누가 만들었는지
- **부모(parent)** — 바로 이전 커밋

이 붙습니다. 커밋들은 **부모에서 자식으로 이어진 체인** 을 형성합니다.

### 2.3 브랜치(Branch)

커밋 체인에서 갈라져 나온 **평행 세계**. 회사 문서로 치면 **"원본에서 복사해서 내 수정안을 만드는 것"** 과 같습니다.

- `main` 브랜치 = 공식 버전
- `feature/login-fix` 브랜치 = 나 혼자 실험하는 가지

브랜치를 쓰면 여러 명이 동시에 서로 다른 작업을 **충돌 없이** 할 수 있습니다.

### 2.4 머지(Merge) / 풀 리퀘스트(PR)

브랜치의 작업이 끝나면 원래 줄기로 합치는 것을 **머지** 라고 합니다. 그리고 대부분의 팀은 GitHub/GitLab 등에서 **풀 리퀘스트(Pull Request, PR)** 라는 절차를 거칩니다. PR은 이런 것입니다.

> "제가 `feature/login-fix` 브랜치에서 이런 변경을 했습니다. `main`에 합쳐도 될까요? 동료분들 검토해 주세요."

팀원들이 코드를 읽고 의견을 남기고, 문제가 없으면 **승인 → 머지** 합니다. 이 절차가 품질을 지키는 **사실상 유일한 안전장치** 입니다.

### 2.5 푸시(Push) / 풀(Pull)

- **푸시(push)** — 내 PC의 Git 기록을 원격(GitHub)으로 업로드.
- **풀(pull)** — 원격의 최신 기록을 내 PC로 내려받기.

회사 문서로 치면 푸시는 "메일에 첨부해서 보내기", 풀은 "메일함에서 받기"입니다. 실제로는 훨씬 정교하지만 이 비유로 감을 잡으면 충분합니다.

### 2.6 충돌(Conflict)

같은 줄을 두 사람이 서로 다르게 고치면 Git은 **"두 변경 중 어떤 게 맞는지 자동으로 못 고른다"** 고 중단합니다. 이를 충돌이라고 하며, 사람이 직접 "어느 쪽을 택할지" 결정해야 합니다. AI가 충돌 해결을 굉장히 잘 도와줍니다.

## 3. 일반적인 작업 흐름 (매일 반복할 리듬)

실제 개발자가 하루에 수십 번 반복하는 사이클입니다.

```
1. git pull                 (원격의 최신 main 받기)
2. git checkout -b feature/X (새 브랜치 생성)
3. ...코드 변경하기...
4. git add .                (변경을 담을 상자에 넣기)
5. git commit -m "메시지"   (상자에 라벨 붙여 기록)
6. git push                 (내 브랜치를 원격으로 업로드)
7. GitHub에서 PR 생성
8. 동료 리뷰 → 머지 → 브랜치 삭제
```

이 8단계를 몸에 익히면 Git의 90%는 끝납니다. 나머지 10%는 "꼬였을 때 푸는 기술"인데, 요즘은 AI가 거의 대부분 해결해 줍니다.

## 4. 좋은 커밋 메시지 쓰기

커밋 메시지는 "6개월 뒤의 내가 읽을 쪽지"라고 생각해야 합니다. 업계에서 많이 쓰는 컨벤션 중 하나가 **Conventional Commits** 입니다.

```
<타입>: <요약>

타입 예시:
  feat:     새 기능
  fix:      버그 수정
  docs:     문서 변경
  refactor: 코드 재정리(동작 변화 없음)
  test:     테스트 추가/수정
  chore:    빌드/설정 등 잡일
```

예시:
```
feat: 로그인 실패 시 3회 이상 시 5분간 잠금
fix: 한글 회의실 이름이 공백 한 번 들어갈 때 500 에러
docs: 03장 런타임 비유에 표 추가
```

**나쁜 예시:**
```
수정함
작업
ㅁㄴㅇㄹ
```

지금 당장 완벽할 필요는 없습니다. AI에게 변경 내용을 보여주며 "Conventional Commit 형식으로 메시지를 써 줘"라고 하면 됩니다.

## 5. 흔히 하는 실수와 구조되는 법

| 상황 | 해결 방향 | AI에게 이렇게 물어보기 |
|---|---|---|
| 실수로 다른 브랜치에 작업했다 | 체리픽 또는 새 브랜치로 이동 | "현재 커밋들을 새 브랜치 X로 옮기고 싶어. 지금 브랜치는 main이야" |
| 방금 한 커밋 메시지를 잘못 썼다 | `git commit --amend` | "방금 커밋 메시지만 수정하고 싶어" |
| 파일을 실수로 커밋에 포함시켰다 | 파일 제거 후 amend | "특정 파일만 이전 커밋에서 빼고 싶어" |
| 머지 충돌이 났다 | 해당 파일 열어서 `<<<<<<<` 표시 정리 | 충돌한 파일 내용을 그대로 AI에게 붙여넣고 "충돌 해결해 줘" |
| 실수로 중요한 커밋을 날렸다 | `git reflog`로 복구 | "reflog 써서 10분 전 상태로 돌아가고 싶어" |

규칙 하나: **"당황하면 아무 명령어도 추가로 치지 말고 일단 AI에게 현재 상태를 그대로 보여주자."**

## 6. GitHub — Git의 "공용 저장소 호스팅"

Git이 **도구** 라면 GitHub은 **그 도구를 팀이 함께 쓰기 위한 웹 서비스** 입니다. GitLab, Bitbucket도 비슷하지만 업계에서 압도적 1위는 GitHub입니다.

GitHub이 제공하는 핵심 기능:

- **원격 저장소 호스팅** — 우리 팀의 코드를 클라우드에 두기.
- **풀 리퀘스트** — 코드 리뷰의 공식 도구.
- **이슈(Issues)** — 버그·기능 요청 트래커.
- **Actions(CI/CD)** — 자동 테스트·자동 배포(11장에서 다룸).

우리 팀은 당분간 **PR 기반 리뷰** 만 제대로 지켜도 품질이 크게 오릅니다.

## 7. 이 프로젝트와 Git

저장소 루트에 `.git` 이라는 숨김 폴더가 있습니다. 이것이 실제 **Git의 모든 기록이 사는 곳** 입니다. 이 폴더를 지우면 모든 역사가 날아갑니다(원격에 푸시한 것은 안전하지만).

또, `.gitignore` 라는 파일이 있습니다. 여기에 적힌 파일·폴더는 Git이 추적하지 않습니다. 예를 들어 `.env` 같은 비밀번호 파일, `node_modules/` 같은 자동 생성 폴더들이 들어 있습니다. **개발자가 자주 확인해야 할 파일 중 하나** 입니다.

`.gitignore`에 비밀번호 파일이 없어서 실수로 커밋되면 → **회사 보안 사고**. Git은 한 번 올라간 비밀을 완벽히 지우기가 어렵습니다. 그래서 "커밋 전 뭐가 추가됐는지 확인"이 절대적으로 중요합니다.

---

## 8. 바이브 코딩과 Git

AI와 작업할 때 Git은 **생명선** 입니다. 이유는 이렇습니다.

- AI가 만든 변경이 예상과 다르게 동작할 수 있음 → 즉시 `git checkout .` 으로 되돌림.
- AI에게 큰 작업을 시킬 때는 "작업 전 브랜치 따고, 중간 결과를 자주 커밋하라"고 시킴.
- 잘못됐을 때 "이전 커밋으로 돌아가"만 기억하면 세상이 안 무너짐.

AI 코드 에디터(Cursor, Claude Code 등)는 대부분 Git 상태를 볼 수 있고, **"커밋된 변경만 안전하게 수정"** 하는 방향으로 동작합니다. 여러분이 기억할 한 가지 습관은 **"작업 전 커밋, 작업 후 커밋"** 입니다.

---

## 9. 핵심 요약

- Git은 프로젝트의 **모든 변경을 커밋 단위로 기록** 하는 도구다.
- 주요 개념 6가지: 저장소, 커밋, 브랜치, 머지/PR, 푸시/풀, 충돌.
- 하루 흐름: **pull → branch → 작업 → add → commit → push → PR → merge**.
- 커밋 메시지는 "6개월 뒤의 나에게 쓰는 쪽지"다. Conventional Commits 형식이 널리 쓰인다.
- 바이브 코딩에서 Git은 **AI의 실수를 되돌릴 안전망** 이므로 작업 전후 커밋 습관이 필수다.
