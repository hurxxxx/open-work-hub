# 16. 소프트웨어 생애주기 — 아이디어가 운영 서비스가 되기까지

> **한 줄 요약.** 소프트웨어는 "만들고 끝"이 아니라 **문제 발견 → 기획 → 설계 → 구현 → 테스트 → 출시 → 운영 → 개선**을 반복하는 살아 있는 시스템이다.

---

## 학습 목표

이 장을 읽고 나면 다음을 설명할 수 있어야 합니다.

1. 하나의 기능이 실제 사용자에게 도달하기까지 어떤 단계를 거치는지 말할 수 있다.
2. 각 단계에서 사람과 AI Agent가 각각 맡아야 할 일을 구분할 수 있다.
3. "아직 구현하면 안 되는 상태"와 "출시해도 되는 상태"를 판단할 수 있다.

---

## 1. 소프트웨어 생애주기란 무엇인가

소프트웨어 생애주기(SDLC, Software Development Life Cycle)는 하나의 기능이나 제품이 만들어지고 운영되는 전체 흐름입니다.

```
문제 발견
→ 기획
→ 요구사항 정의
→ 설계
→ 구현
→ 테스트
→ 출시
→ 운영
→ 피드백과 개선
```

중요한 점은 이 흐름이 한 번만 도는 것이 아니라는 점입니다. 출시 후 사용자가 쓰기 시작하면 새로운 문제가 발견되고, 그 문제는 다시 기획과 요구사항으로 돌아갑니다.

비개발자가 AI Agent와 함께 개발에 참여할 때 가장 먼저 알아야 할 것은 **지금 우리가 어느 단계에 있는지**입니다. 단계가 헷갈리면 AI에게 너무 이른 구현을 맡기거나, 아직 검증되지 않은 기능을 출시하려고 하게 됩니다.

---

## 2. 단계별로 사람이 해야 할 일과 AI Agent가 도울 일

| 단계 | 사람이 책임질 일 | AI Agent가 도울 일 |
|---|---|---|
| 문제 발견 | 실제 불편, 업무 손실, 사용자 맥락을 설명 | 인터뷰 메모 요약, 문제 후보 정리 |
| 기획 | 해결할 문제와 하지 않을 범위 결정 | 대안 목록, 우선순위 질문 생성 |
| 요구사항 정의 | 성공 기준, 예외 상황, 권한 조건 확정 | 요구사항 초안, 빠진 케이스 질문 |
| 설계 | 영향 범위와 리스크 승인 | 관련 파일 탐색, 변경 계획 제안 |
| 구현 | 변경 범위 감시, 중간 승인 | 코드·테스트·문서 초안 작성 |
| 테스트 | 실제 업무 기준으로 확인 | 테스트 케이스 작성, 실패 로그 해석 |
| 출시 | 배포 가능 여부 승인 | 릴리스 노트, 체크리스트 초안 |
| 운영 | 장애·불편·사용량 관찰 | 로그 요약, 반복 이슈 분류 |
| 개선 | 다음 반복의 우선순위 결정 | 회고 정리, 개선안 후보 제안 |

AI Agent는 많은 일을 빠르게 도울 수 있지만, **무엇이 중요한지 결정하는 책임**은 사람에게 남습니다.

---

## 3. 단계별 산출물

각 단계는 말로만 지나가면 안 됩니다. 다음 단계 사람이 이어받을 수 있는 **산출물**이 남아야 합니다.

| 단계 | 최소 산출물 | 좋은 산출물의 조건 |
|---|---|---|
| 문제 발견 | 문제 메모 | 누가, 언제, 무엇 때문에 불편한지 들어 있음 |
| 기획 | 해결 방향 메모 | 이번에 할 일과 하지 않을 일이 구분됨 |
| 요구사항 | 스펙 초안 | 성공 기준과 예외 상황이 있음 |
| 설계 | 변경 계획 | 수정 파일 후보, 위험, 테스트 계획이 있음 |
| 구현 | PR 또는 diff | 하나의 목적만 담고 리뷰 가능한 크기 |
| 테스트 | 검증 기록 | 자동 테스트와 수동 확인이 분리됨 |
| 출시 | 릴리스 노트 | 변경 내용, 검증, 롤백 방법이 있음 |
| 운영 | 관찰 메모 | 로그, 문의, 지표, 후속 개선이 정리됨 |

비개발자가 특히 신경 쓸 것은 문제 메모, 스펙 초안, 검증 기록, 운영 관찰 메모입니다. 이 네 가지가 좋으면 AI Agent와 개발자는 훨씬 안정적으로 움직일 수 있습니다.

---

## 4. 같은 기능을 생애주기로 따라가기

예시로 "문서 검색 화면에서 결과가 없을 때 빈 상태 UI를 보여 주는 기능"을 생각해 봅니다.

### 4.1 문제 발견

사용자가 검색어를 입력했는데 결과가 없으면, 현재 화면이 비어 보입니다. 사용자는 "검색이 실패한 건지, 결과가 없는 건지" 알기 어렵습니다.

이 단계에서 좋은 질문은 다음입니다.

- 누가 불편을 겪는가?
- 얼마나 자주 발생하는가?
- 지금 사용자는 어떤 행동을 하는가?
- 화면 문구만 바꾸면 되는가, 검색 로직도 바꿔야 하는가?

### 4.2 기획

해결 방향을 정합니다.

- 검색 결과가 없을 때 안내 문구를 보여 준다.
- 다시 검색할 수 있는 버튼을 제공한다.
- 검색 로직 자체는 이번 범위에서 바꾸지 않는다.

이때 중요한 것은 **하지 않을 일**을 정하는 것입니다. 예를 들어 "검색 품질 개선", "추천 검색어", "검색어 자동완성"은 모두 좋은 아이디어지만, 이번 변경에 함께 넣으면 범위가 커집니다.

### 4.3 요구사항 정의

이제 완료 기준을 적습니다.

```text
성공 기준:
- 검색 결과가 0개이면 "검색 결과가 없습니다" 안내가 보인다.
- 사용자는 검색어를 수정해 다시 검색할 수 있다.
- 기존 검색 결과가 있을 때의 화면은 바뀌지 않는다.
- 빈 상태 렌더링 테스트가 추가된다.
```

이 문장이 있어야 AI Agent가 코드 초안을 만들 때 방향을 잃지 않습니다.

### 4.4 설계

AI Agent에게 바로 "구현해 줘"라고 하지 않고 먼저 묻습니다.

```text
위 요구사항을 구현하기 전에 수정할 파일, 변경 순서, 필요한 테스트를 먼저 제안해 줘.
실제 파일 수정은 하지 말고 계획만 보여 줘.
```

사람은 계획을 보고 다음을 판단합니다.

- 관련 없는 파일을 건드리려 하지 않는가?
- 새 라이브러리를 추가하지 않는가?
- 테스트 파일이 포함되어 있는가?
- 변경 범위가 작게 유지되는가?

### 4.5 구현과 테스트

계획이 적절하면 작은 단위로 구현합니다.

1. 빈 상태 컴포넌트 또는 분기 추가
2. 테스트 추가
3. 기존 검색 결과 렌더링이 유지되는지 확인
4. 화면에서 직접 검색해 보기

AI Agent가 코드를 작성하더라도, 사람은 diff를 보고 "요구사항에 없는 변경"이 들어갔는지 확인해야 합니다.

### 4.6 출시와 운영

출시 전에는 다음을 확인합니다.

- 테스트가 통과했는가?
- 실제 화면에서 문구가 자연스러운가?
- 기존 사용자 흐름을 깨지 않았는가?
- 롤백이 필요한 수준의 위험이 있는가?

출시 후에는 사용자 문의가 줄었는지, 검색 사용 중 이탈이 줄었는지, 추가 불편이 생기지 않았는지 봅니다. 운영 관찰 결과는 다음 개선의 시작점이 됩니다.

## 5. 단계가 섞일 때 생기는 문제

### 구현을 너무 빨리 시작하는 경우

문제가 충분히 정의되지 않았는데 AI Agent에게 코드를 만들게 하면, 빠른 초안은 나오지만 나중에 대부분 다시 고치게 됩니다.

신호:

- "일단 만들어 보고 생각하자"가 반복된다.
- 성공 기준이 없다.
- 테스트할 사람이 무엇을 확인해야 할지 모른다.

### 테스트를 출시 직전으로 미루는 경우

테스트는 마지막 관문이 아니라 요구사항을 확인하는 방법입니다. 테스트를 늦게 생각하면 요구사항의 빈틈도 늦게 발견됩니다.

신호:

- PR 본문에 "검증: 눈으로 확인"만 있다.
- 실패 케이스가 없다.
- 권한 없는 사용자나 빈 데이터 상태를 확인하지 않았다.

### 운영을 고려하지 않고 출시하는 경우

기능은 배포 후부터 진짜 사용됩니다. 로그, 알림, 롤백, 사용자 안내가 없으면 작은 오류도 큰 장애처럼 보일 수 있습니다.

신호:

- 문제가 생겼을 때 끌 방법이 없다.
- 누가 확인할지 정해져 있지 않다.
- 배포 후 관찰할 지표가 없다.

## 6. 비개발자가 특히 잘해야 하는 일

비개발자가 모든 코드를 이해할 필요는 없습니다. 대신 아래 네 가지는 강하게 가져가야 합니다.

1. **문제의 현실성 확인**
   실제 사용자가 겪는 문제인지, 추측인지 구분합니다.

2. **성공 기준 작성**
   "좋아져야 한다"가 아니라 "무엇이 보이면 완료인지"를 적습니다.

3. **범위 통제**
   좋은 아이디어라도 이번 변경에 넣을지 다음으로 미룰지 결정합니다.

4. **출시 승인**
   테스트 통과만이 아니라 실제 업무 흐름에서 받아들일 수 있는지 판단합니다.

AI Agent가 강해질수록 이 네 가지는 더 중요해집니다. 구현 속도가 빨라지면 잘못된 방향으로도 빨리 갈 수 있기 때문입니다.

---

## 7. 생애주기 회의에서 비개발자가 물어볼 질문

회의에서 아래 질문을 순서대로 던지면 단계가 섞이는 것을 막을 수 있습니다.

1. 지금 우리는 문제를 정의하는 중인가, 해결책을 고르는 중인가?
2. 이 기능의 성공 기준은 문장으로 적혀 있는가?
3. 이번 변경에서 하지 않을 일은 무엇인가?
4. AI Agent가 구현하기 전에 계획만 먼저 받아 봤는가?
5. 테스트는 어떤 사용자 상황을 증명하는가?
6. 출시 후 누가 무엇을 확인할 것인가?
7. 문제가 생기면 어떻게 되돌릴 것인가?

이 질문들은 개발자를 압박하기 위한 것이 아닙니다. 팀이 같은 단계에 있는지 맞추기 위한 안전장치입니다.

---

## 8. AI Agent에게 생애주기를 설명하는 프롬프트

```text
아래 기능을 소프트웨어 생애주기 관점으로 나눠 줘.

기능: 문서 검색 결과가 없을 때 빈 상태 UI 표시

다음 표로 정리해 줘:
- 단계
- 사람이 결정해야 할 것
- AI Agent가 도울 수 있는 것
- 산출물
- 다음 단계로 넘어가기 전 완료 기준

주의:
- 아직 구현하지 말 것
- 요구사항이 불명확하면 질문으로 표시할 것
```

이 프롬프트는 기능을 바로 코드로 바꾸기 전에, 팀이 같은 지도를 보게 만드는 데 유용합니다.

## 10. 핵심 요약

- 소프트웨어는 문제 발견부터 운영 개선까지 반복되는 생애주기를 가진다.
- AI Agent는 구현을 빠르게 돕지만, 단계별 승인과 판단은 사람이 해야 한다.
- 좋은 개발은 "빠른 구현"이 아니라 "올바른 문제를 작은 단위로 안전하게 운영에 반영하는 것"이다.
- 비개발자는 문제 정의, 성공 기준, 범위 통제, 출시 승인에서 큰 역할을 한다.

## 완료 기준

이 장을 끝냈다면 다음을 할 수 있어야 합니다.

- 기능 하나를 생애주기 단계로 나눠 설명할 수 있다.
- AI Agent에게 바로 구현을 맡기기 전 필요한 산출물을 말할 수 있다.
- 출시 전과 출시 후에 확인해야 할 일을 구분할 수 있다.
