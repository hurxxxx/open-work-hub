# 11. 배포와 DevOps

> **한 줄 요약.** 배포(deploy)는 "내 PC에서만 돌던 코드를 실제 사용자 서버에 올리는 작업"이다. 오늘날의 배포는 **컨테이너(Docker)**로 감싸서 **자동 파이프라인(CI/CD)**으로 굴리는 것이 상식이다.

---

## 1. "내 PC에서는 되는데요?"가 반복되는 이유

개발자들이 가장 많이 듣는 불평입니다.

- 내 PC의 Python 버전은 3.12
- 동료의 PC는 3.10
- 운영 서버는 3.11
- 누구의 것이 맞나요? 셋 다 다르게 동작합니다.

이 "환경 차이" 문제를 근본적으로 없애기 위해 등장한 것이 **컨테이너(Container)** 입니다.

### 1.1 컨테이너 핵심 직관

- 컨테이너는 앱과 실행 의존성을 함께 묶어 환경 차이로 인한 재현 실패를 줄입니다.
- 동일 이미지를 사용하면 서버가 바뀌어도 동일 구성으로 배포할 수 있습니다.

### 1.2 ⚠️ 바로잡고 싶은 오해

- **"동료 PC에서도 되니까 운영도 될 것이다"** — 운영 서버의 OS 버전·메모리·네트워크·시간대 설정이 달라 **조용히 실패**한다. 컨테이너는 이 변수들을 제거한다.
- **"배포는 파일을 서버에 올리는 일 아닌가"** — 현대 배포는 **이미지 생성 → 테스트 → 점진 교체 → 헬스체크**를 포함한 파이프라인이다.

---

## 2. 컨테이너 — 2010년대의 대혁명

컨테이너는 **"앱 + 런타임 + 라이브러리 + 설정"**을 하나의 실행 단위로 묶는 기술입니다. 같은 이미지를 쓰면 어느 서버에서도 동일하게 동작합니다.

### 2.1 가상머신(VM) vs 컨테이너

둘 다 "격리된 환경"을 주지만 차이가 있습니다.

| 구분 | VM | 컨테이너 |
|---|---|---|
| 격리 단위 | OS 전체 | OS의 커널을 공유, 프로세스만 격리 |
| 크기 | 수 GB | 수십~수백 MB |
| 시작 속도 | 분 단위 | 초 단위 |
| 밀도 | 서버당 몇 개 | 서버당 수백 개 |

컨테이너가 압도적으로 가벼워 **"앱 배포의 기본 단위"** 가 됐습니다.

### 2.2 Docker

Docker는 컨테이너를 **쉽게 만들고 돌리는 도구** 입니다. 업계 표준입니다.

용어 3개만 알면 됩니다.

- **Image** — 컨테이너의 **정적 실행 템플릿**. "Ubuntu + Python 3.12 + 우리 앱" 같은 구성.
- **Container** — 이미지가 실제로 돌고 있는 상태(동적).
- **Dockerfile** — 이미지를 만드는 **레시피** 파일.

### 2.3 Docker Compose

여러 컨테이너를 한 번에 올리는 도구. 우리 프로젝트는 이걸 씁니다.

- `ops/compose/open-alm-dev.infra.yml` — Redis, MinIO, OpenSearch, Qdrant, Nginx 등을 한 묶음으로 띄움.
- PostgreSQL은 Docker Compose가 아니라 서버 native PostgreSQL(`127.0.0.1:5432`)을 씀.

**"dev"** 는 "운영과 비슷한" 이라는 뜻이며, 개발자 PC에서 **운영과 최대한 같은 상태를 재현하기 위한 환경** 입니다. 운영에서만 터지는 버그를 개발에서 미리 잡기 위한 장치입니다.

### 2.4 컨테이너 오케스트레이션 — Kubernetes

여러 대의 서버에 컨테이너를 **자동으로 배치·복구·확장** 해주는 시스템. 대표가 **Kubernetes(K8s)**. 엄청난 기능이 있지만 **운영 복잡도** 도 엄청납니다. 사내용 포털 규모에서는 과잉이기 쉽습니다.

대안:
- **Docker Compose + 수동 배포** (지금 단계 적합)
- **Nomad** (HashiCorp, 더 간단)
- **Fly.io, Railway, Render** (관리형 PaaS)
- **Kubernetes** (대규모)

**이 프로젝트의 현 단계: Docker Compose로 충분**.

### 2.5 ⚠️ 자주 듣는 오해

- **"Kubernetes 안 쓰면 뒤처진 팀 아닌가"** — 팀 규모·트래픽·24/7 요구가 갖춰져야 비로소 K8s가 이득이다. 사내 포털이 2~3대 서버라면 Compose가 **더 빠르고 싸고 안정적**이다.
- **"Docker 이미지는 한 번 빌드하면 재사용만 하면 된다"** — **보안 패치**를 위해 주기적으로 **베이스 이미지**를 갱신해야 한다.
- **"컨테이너는 VM보다 가벼우니 완전히 격리된다"** — 컨테이너는 **커널을 공유**한다. 완전 격리가 필요하면 VM을 병행한다.

### 2.6 🛠️ 5분 실습

- 프로젝트 루트에서 `docker ps` 실행 → 현재 돌고 있는 컨테이너 목록 확인.
- `ops/compose/open-alm-dev.infra.yml` 파일을 열어 정의된 서비스 이름(예: `redis`, `minio`, `nginx`)을 눈으로 훑어 본다.
- "이 파일 한 줄 한 줄이 컨테이너 하나"라는 감각을 얻는다.

## 3. 배포 환경의 흐름 — "환경들"

소프트웨어는 보통 여러 "환경"을 거쳐 배포됩니다.

```
[ 개발(local/dev) ]  →  [ 스테이징(staging) ]  →  [ 운영(production) ]
  내 PC             예비 환경, QA           실제 사용자
```

환경마다
- DB 주소가 다르고
- API 키가 다르고
- 디버그 로그 수준이 다르고
- 실제 외부 API 대신 **모의(mock)** 를 쓸 수도 있습니다.

환경 차이는 **환경 변수(`.env`)** 와 **설정 파일**로 관리합니다. 이 프로젝트의 `.env.example`이 그 템플릿입니다.

### 3.1 🏢 업무 시나리오

**케이스 — 스테이징 건너뛰었다가 생긴 사고.**
"급한 버그 수정"이라는 이유로 개발 → 바로 운영으로 배포. 운영 DB만 가지고 있던 특수 데이터 조합에서 500 에러가 터져 **30분 전사 다운**. 스테이징에서 한 번만 돌렸다면 미리 잡았을 문제. "환경 단계"는 번거로워 보이지만 **실제로 지켜야** 한다.

### 3.2 ⚠️ 짚고 갈 오해

- **".env 파일을 Git에 올려야 공유된다"** — `.env`에는 **비밀값**이 들어가므로 `.gitignore`에 반드시 추가해야 한다. 공유는 **비밀 매니저**(1Password, Vault, Doppler 등) 또는 팀 암호 관리자로 한다.

## 4. CI/CD — 자동화된 배포 파이프라인

5장에서 개념만 봤습니다. 이제 구체를 봅니다.

### 4.1 CI (Continuous Integration)

코드가 푸시되면 자동으로:

1. **체크아웃**: 최신 코드 받기
2. **의존성 설치**: `pnpm install`, `uv sync`
3. **린트**: `pnpm lint`, `ruff check`
4. **타입 체크**: `tsc --noEmit`
5. **테스트**: `pnpm test`, `pytest`
6. **빌드**: `pnpm build`

이 중 **하나라도 실패하면 PR 머지가 막힘**.

### 4.2 CD (Continuous Delivery / Deployment)

CI 통과 후:

1. **이미지 빌드**: `docker build -t open-alm-api:v1.2.3 .`
2. **이미지 레지스트리에 푸시**: 운영 서버가 가져갈 수 있도록.
3. **배포**: 운영 서버에서 새 이미지로 컨테이너 교체.
4. **헬스체크**: 새 컨테이너가 정상인지 확인.
5. **롤백 준비**: 문제 시 이전 이미지로 복귀.

### 4.3 대표 CI/CD 도구

- **GitHub Actions** — 가장 널리 쓰임. 저장소와 통합.
- GitLab CI / Jenkins / CircleCI — 전통적 선택.
- ArgoCD, Flux — Kubernetes 기반 GitOps.

이 프로젝트는 현재 **수동 배포 스크립트(`prod.sh`, `scripts/dev-*.sh`)** 로 돌아갑니다. 다음 단계는 GitHub Actions로 CI를 자동화하는 것입니다.

### 4.4 배포 전략

- **재배포(Recreate)**: 구 버전 종료 → 새 버전 시작. 순간 다운타임 있음.
- **Rolling update**: 여러 인스턴스를 **하나씩** 교체. 다운타임 없음.
- **Blue/Green**: 새 환경(녹) 구축 → 트래픽 전환 → 구 환경(청) 제거. 가장 안전하지만 비용 2배.
- **Canary**: 5% 사용자에게만 먼저 새 버전 → 이상 없으면 확대.

사내 포털 규모에서는 **롤링 업데이트** 가 현실적 최상.

### 4.5 배포 전략 핵심 정리

- **CI/CD 파이프라인**은 코드 변경을 자동 검증·빌드·배포하는 절차이며, 실패 단계에서 즉시 중단해 결함 확산을 막습니다.
- **Blue/Green 배포**는 기존 환경과 신규 환경을 동시에 유지하다가 트래픽만 전환하는 방식으로 다운타임을 최소화합니다.

### 4.6 ⚠️ 헷갈리기 쉬운 것들

- **"CI가 성공하면 배포도 성공한다"** — CI는 **빌드·테스트**만 확인한다. 운영 환경 차이(네트워크·권한·DB 마이그레이션)로 배포가 실패할 수 있다.
- **"한 번에 전체를 교체해야 안전하다"** — **점진 교체(롤링·카나리)** 가 오히려 장애 영향을 최소화한다.

## 5. Nginx — 이 프로젝트의 관문

Nginx는 **리버스 프록시(reverse proxy)** 및 **정적 파일 서버** 로 널리 쓰이는 고성능 웹 서버입니다. 우리 `compose.dev.yml`에 등장합니다.

역할:

1. **정적 파일 서빙**: 빌드된 React 앱(`dist/apps/web`)을 사용자에게 보냄.
2. **API 프록시**: `/api/*` 요청을 FastAPI 서버(8000포트)로 전달.
3. **HTTPS 종결**: TLS 인증서 처리(보통 여기서 끝맺음).
4. **부하 분산**: API 서버가 여러 개면 라운드 로빈으로 분배.

사용자 입장에서는 **Nginx 하나에만 말을 걸고** 뒷단의 복잡성(앱 서버, API, WebSocket)은 숨겨집니다.

대안: Caddy(더 간단), Traefik(동적 라우팅), Apache(전통).

## 6. 관측성과 장애 대응

배포했다고 끝이 아닙니다. **돌고 있는지 감시** 해야 합니다.

### 6.1 기본 지표

- **가용성(Uptime)**: 99.9%면 한 달에 43분까지 다운 허용.
- **응답 속도(Latency)**: p50, p95, p99. "99% 사용자는 n초 이내에 응답을 받음".
- **에러율(Error Rate)**: 5xx 에러 비율.

### 6.2 알림(Alerting)

임계값(예: 에러율 5% 초과)에 도달하면 **자동으로 담당자에게 알림**. 사내 Slack, PagerDuty 등을 연동.

### 6.3 장애 대응(Incident Response)

장애가 터지면:

1. **인지**: 알림 or 사용자 제보
2. **즉시 완화**: 롤백, 기능 끄기(피처 플래그)
3. **원인 파악**: 로그 · 모니터링 · 트레이스
4. **재발 방지**: 포스트모템(postmortem) 문서화

장애를 **"누가 잘못했냐"** 보다 **"시스템의 어떤 취약점이 드러났냐"** 관점으로 다루는 **비난 없는(blameless) 문화** 가 DevOps의 핵심 가치입니다.

### 6.4 🏢 업무 시나리오

**케이스 — 포스트모템(postmortem, 사후 검토) 문서가 자산이 된다.**
지난 분기 "파일 업로드 실패" 장애의 포스트모템 문서가 위키에 남아 있어, 이번 분기 비슷한 증상이 재발했을 때 **5분 만에 원인을 특정**했다. 비난 대신 학습 기록으로 보는 문화가 장기적으로 팀을 강하게 만든다.

### 6.5 ⚠️ 오해하기 쉬운 것들

- **"장애가 없으면 시스템이 건강한 것 아닌가"** — **관측이 없어서** 장애를 못 보고 있을 수도 있다. 로그·메트릭·알림이 갖춰져야 "건강하다"라고 말할 수 있다.
- **"99.9% 가용성은 쉽다"** — 한 달 43분 초과 다운이 안 되려면 **자동 복구·다중화·알림**이 필수다. 규모가 커질수록 9 하나 추가에 10배의 비용이 든다.

## 7. 이 프로젝트의 현재 상태와 진화 방향

### 7.1 현재

- Docker Compose로 로컬 + dev 인프라 구동.
- `prod.sh`, `dev.sh`로 수동 구동 스크립트.
- CI/CD 파이프라인 미구성(수동 배포).

### 7.2 권장 진화 단계

1. **단계 1** (지금): Docker Compose + 수동 배포. PR 머지 전 수동 테스트.
2. **단계 2**: GitHub Actions CI로 린트·테스트 자동화. PR 체크에 포함.
3. **단계 3**: 이미지 빌드·레지스트리 푸시까지 자동. 배포는 여전히 수동(한 줄 명령).
4. **단계 4**: 스테이징 자동 배포. 운영은 승인 기반 자동 배포.
5. **단계 5**: 관측성 스택(로그/메트릭/트레이스) 도입.
6. **단계 6**: 필요 시 Kubernetes로 이전.

서두를 것 없습니다. **팀 성숙도에 맞춰 올라가면 됩니다.**

## 8. 핵심 요약

- 컨테이너(Docker)는 **"내 PC에서는 됐는데"** 문제를 끝낸 기술.
- Compose로 여러 컨테이너를 한 번에 관리. Kubernetes는 대규모일 때.
- 환경(dev → staging → prod)은 **환경 변수**로 분리.
- CI/CD = **"푸시하면 자동으로 린트/테스트/빌드/배포"**.
- Nginx는 **관문 역할**: 정적 서빙 + API 프록시 + HTTPS.
- 관측성·장애 대응은 DevOps의 필수 축. **비난 없는 문화** 가 중요.
