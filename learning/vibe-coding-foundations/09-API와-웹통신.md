# 09. API와 웹 통신 — HTTP, REST, WebSocket, SSE

> **한 줄 요약.** API는 "프로그램끼리 대화할 때 쓰는 약속된 언어"다. 가장 흔한 HTTP 기반 REST API, 양방향 실시간용 WebSocket, 서버가 일방적으로 밀어넣는 SSE를 알면 이 프로젝트의 통신 대부분이 설명된다.

---

## 1. "API"라는 말을 정리하자

API = **Application Programming Interface**. 직역하면 "응용 프로그램 인터페이스"이며, 프로그램이 외부에 제공하는 **호출 규격**을 뜻합니다.

API는 클라이언트와 서버가 합의한 호출 규격입니다. 서버 내부 구현이 바뀌어도 API 계약(경로, 파라미터, 응답 형식)이 유지되면 클라이언트 코드는 계속 동작합니다.

우리 프로젝트에서 "API"라고 하면 대부분 **"웹 브라우저가 우리 백엔드 서버에게 보내는 HTTP 요청/응답"** 을 뜻합니다.

### 1.1 API 계약의 핵심

- 엔드포인트와 파라미터 규격이 명확하면, 서버 내부 로직을 수정해도 클라이언트 영향 범위를 줄일 수 있습니다.
- 엔드포인트별 입력 스키마를 검증하면 잘못된 요청을 초기에 차단할 수 있습니다.

### 1.2 ⚠️ 짚고 갈 오해

- **"API는 개발자끼리 쓰는 거창한 기술 용어다."**
  API는 **"호출 계약"** 입니다. 함수 호출 규약도 API의 한 형태입니다.
- **"API는 외부에 공개된 서비스만 가리킨다."**
  같은 회사 안에 있는 두 앱 사이의 대화도 API입니다. **공개·비공개는 별개의 축** 입니다.

## 2. HTTP — 웹의 기본 규약

HTTP(HyperText Transfer Protocol)는 1989년 팀 버너스 리가 설계한 웹의 기본 프로토콜입니다. 오늘날 모든 웹 서비스가 HTTP(또는 그 암호화 버전 HTTPS)를 씁니다.

### 2.1 요청-응답 모델

```
[클라이언트] --- HTTP 요청 --->  [서버]
             <--- HTTP 응답 ---
```

한 번의 대화는 요청 1개, 응답 1개로 끝납니다. 이를 **stateless(상태 없음)** 이라 합니다.

### 2.2 요청의 구성

```
POST /ai/chat HTTP/1.1
Host: portal.doowon.co
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{"message": "요약해 줘", "conversationId": "abc"}
```

- **메서드(Method)**: GET, POST, PUT, PATCH, DELETE
- **경로(Path)**: `/ai/chat`
- **헤더(Headers)**: 메타 정보 (인증 토큰, 콘텐츠 타입 등)
- **본문(Body)**: 보내는 데이터

### 2.3 응답의 구성

```
HTTP/1.1 200 OK
Content-Type: application/json

{"reply": "요약입니다: ..."}
```

- **상태 코드(Status Code)**: 200(성공), 400(잘못된 요청), 401(인증 실패), 403(권한 없음), 404(없음), 500(서버 오류)
- 자주 보는 상태 코드만 외워두면 디버깅이 쉽습니다.

### 2.4 ⚠️ 헷갈리기 쉬운 것들

- **"HTTP와 HTTPS는 거의 같다."**
  HTTPS는 암호화(TLS) 계층이 끼어 있어 **중간에서의 도청과 변조를 막아 줍니다.** 사내용 서비스라 해도 HTTPS가 기본이어야 합니다.
- **"404가 뜨면 무조건 서버 고장이다."**
  404는 "그 주소에 해당하는 리소스가 없다"는 **정상 응답** 이기도 합니다. 오타나 권한 설정 문제로 뜨는 경우가 많습니다.
- **"stateless라서 서버는 사용자 정보를 기억 못 한다."**
  요청마다 **토큰이나 쿠키** 로 신원을 함께 보내면 됩니다. stateless는 "매 요청이 독립적"이라는 뜻이지 "영영 모른다"는 뜻이 아닙니다.

### 2.5 🏢 401과 403, 한 코드 차이가 만드는 경험

사용자가 회의록 페이지를 열었을 때 서버가 **401** 을 돌려주면 "먼저 로그인해 주세요" 화면을 띄워야 합니다. **403** 이 오면 "이 워크스페이스의 멤버가 아닙니다"라는 안내를 보여야 하고요. 코드 하나 차이가 사용자 경험을 꽤 크게 가릅니다.

## 3. REST — 가장 널리 쓰이는 API 스타일

REST(REpresentational State Transfer)는 2000년 Roy Fielding의 박사 논문에서 등장한 HTTP 기반 API 설계 **스타일** 입니다.

### 3.1 핵심 규칙

- 모든 것은 **리소스(resource)** 다. `users`, `meetings`, `documents`
- 리소스에 대한 행위는 **HTTP 메서드** 로 표현한다.

| 행위 | 메서드 | 경로 예 |
|---|---|---|
| 목록 조회 | GET | `/users` |
| 단건 조회 | GET | `/users/123` |
| 생성 | POST | `/users` |
| 전체 수정 | PUT | `/users/123` |
| 부분 수정 | PATCH | `/users/123` |
| 삭제 | DELETE | `/users/123` |

### 3.2 왜 REST가 표준이 됐나

- HTTP의 기본 어휘(메서드, 상태코드)를 그대로 씀 → **학습 비용 낮음**.
- URL만 봐도 용도 짐작 가능 → **협업 편함**.
- 인프라(캐시, 게이트웨이, 로드밸런서)가 이미 HTTP에 맞춰져 있음.

### 3.3 REST의 한계

- **여러 리소스를 한 번에 조회** 하는 게 비효율적 (여러 번 요청해야 함).
- **실시간 푸시** 에 적합하지 않다.
- 명세가 말랑말랑해서 팀마다 스타일이 갈린다.

### 3.4 REST의 대안

- **GraphQL** (2015, Facebook): 클라이언트가 필요한 필드만 쿼리. 복잡한 UI에 좋음. 단점: 서버 구현이 복잡.
- **gRPC** (2015, Google): 고성능 바이너리 프로토콜. 서비스 간 통신에 좋음. 브라우저 직접 사용은 제약.
- **tRPC** (TypeScript 전용): 프런트와 백이 같은 타입을 공유하는 RPC. 모노레포 + 풀 TS에 최적.

우리 프로젝트는 **REST(JSON over HTTP)** 를 선택. 이유:

- 프런트(TS)와 백(Python) 언어가 달라 gRPC·tRPC보다 REST가 자연스럽다.
- FastAPI가 REST + 자동 OpenAPI 문서를 기본 제공.
- 읽기 쿼리가 대체로 단순해 GraphQL의 장점이 과잉.

### 3.5 ⚠️ 자주 듣는 오해

- **"REST만이 '올바른' API 설계다."**
  REST는 어디까지나 **스타일** 중 하나입니다. 실시간 협업이나 AI 스트리밍 같은 상황에서는 WebSocket, SSE가 더 어울립니다.
- **"URL에 동사를 쓰면 안 된다 (`/getUsers` 금지)."**
  REST 관점에서는 맞지만, 현실에서는 **행위 기반 엔드포인트**(예: `/meetings/123/cancel`)가 더 자연스러운 경우도 많습니다. 규칙은 도구일 뿐입니다.

## 4. OpenAPI (Swagger) — API 명세의 표준

OpenAPI는 REST API의 엔드포인트·파라미터·응답 형식을 표준 포맷으로 정의한 명세입니다(구명칭 Swagger).

**FastAPI는 타입 정의만 해 두면 OpenAPI를 자동 생성** 합니다. `/docs` 경로로 들어가면 브라우저에서 바로 테스트 가능한 UI가 나옵니다.

```
http://localhost:8000/docs
```

이게 정말 강력합니다. 비개발자도 이 페이지만 열면 "어떤 API가 있고 뭘 받고 뭘 돌려주는지" 즉시 확인할 수 있습니다. 커뮤니케이션 비용이 크게 줍니다.

### 4.1 🛠️ 5분 실습

- 로컬에서 백엔드가 떠 있다면 브라우저로 `http://localhost:8000/docs` 에 접속.
- 엔드포인트 한 개를 펼쳐서 **"Try it out"** 버튼을 눌러 직접 호출해 본다.
- 응답 JSON이 화면에 뜨는 순간, 요청/응답 계약이 어떻게 동작하는지 바로 체감할 수 있습니다.

### 4.2 ⚠️ 짚고 갈 오해

- **"OpenAPI 문서는 별도로 써야 한다."**
  FastAPI는 **타입 힌트만 달아 두면 자동으로 생성해 줍니다.** "문서가 항상 최신 상태"가 보장된다는 뜻입니다.

## 5. WebSocket — 양방향 실시간 통신

HTTP는 "한 번 묻고 한 번 답"입니다. 여러 명이 동시에 문서를 편집하려면 어떻게 할까요? 서버가 변경을 **능동적으로** 클라이언트에 밀어넣어야 합니다. 이걸 HTTP만으로 처리하려면 짧은 주기로 반복 요청하는 **폴링(polling)** 이 필요해 비효율적입니다.

**WebSocket** 은 이 문제를 해결합니다. 한 번 연결을 맺으면 양쪽이 언제든 메시지를 교환할 수 있는 **지속 연결 채널**이 유지됩니다.

### 5.1 우리 프로젝트의 WebSocket

- **실시간 협업 에디터(BlockNote + Yjs)** — 문서 편집 변경을 실시간 전파.
- 서버 측 구현: `ypy-websocket` (Python Yjs 구현) + FastAPI의 WebSocket 지원.
- 클라이언트: `y-websocket` JS 라이브러리.

자세한 것은 26장에서 다룹니다.

## 6. SSE (Server-Sent Events) — 서버에서 클라이언트로의 일방향 스트림

WebSocket이 **양방향** 이라면, SSE는 **서버→클라이언트 일방향** 입니다. 그리고 HTTP 위에서 동작하므로 WebSocket보다 가볍고 구현이 간단합니다.

### 6.1 언제 쓰는가

- AI 응답을 **한 글자씩** 흘려보낼 때 ← **이 프로젝트의 메인 용도**
- 서버의 진행률 업데이트(예: 파일 업로드, 트랜스크립션 진행률)
- 대시보드의 실시간 수치 업데이트

### 6.2 우리 프로젝트의 SSE

AI 채팅이 핵심 예입니다.

```
클라이언트 → POST /ai/chat  (요청)
서버 ← 응답 시작, Content-Type: text/event-stream
서버 → event: token  data: "안"
서버 → event: token  data: "녕"
서버 → event: token  data: "하세요"
서버 → event: tool_call  data: {...}
서버 → event: done
```

한 번의 요청에 대해 서버가 **계속 이벤트를 전송하고**, 브라우저는 이를 받아 화면에 실시간으로 누적 표시합니다.

서버 측 라이브러리: **`sse-starlette`** (FastAPI용).
클라이언트 측: **`eventsource-parser`** (프런트 의존성에 등록돼 있음).

### 6.3 WebSocket vs SSE — 언제 뭐를?

| 상황 | 선택 |
|---|---|
| 둘 다 메시지 주고받음 (채팅, 게임, 협업 에디터) | **WebSocket** |
| 서버만 밀어넣음 (AI 스트리밍, 알림, 진행률) | **SSE** |
| 단순 요청/응답 | **HTTP(REST)** |

### 6.4 통신 방식 차이 빠르게 정리

- **WebSocket**은 양방향 실시간 통신, **SSE**는 서버→클라이언트 단방향 스트림, **REST**는 요청 1회-응답 1회 구조입니다.
- 협업 편집처럼 상호 반응이 필요하면 WebSocket, 토큰 스트리밍처럼 서버 발신 중심이면 SSE, 일반 CRUD는 REST가 적합합니다.

### 6.5 ⚠️ 자주 듣는 오해

- **"WebSocket이 '더 좋은' 기술이니 무조건 써야 한다."**
  WebSocket은 **상태를 유지** 해야 해서 서버 부담과 운영 복잡도가 큽니다. 일방향이면 SSE만으로도 충분합니다.
- **"SSE는 구식이다."**
  AI 응답처럼 긴 텍스트가 조금씩 생성되는 화면에서 자주 쓰입니다. 여러 LLM API도 토큰을 스트림 형태로 흘려보냅니다.

## 7. RPC와 그 바리에이션

RPC(Remote Procedure Call) = **"원격 함수 호출"**. 네트워크 너머 서버의 함수를 로컬 함수 호출과 유사한 방식으로 호출하는 패턴입니다.

### 7.1 JSON-RPC

단순하게 JSON으로 "이 함수를 이 인자로 불러줘"라고 보내는 방식.

```
→ {"method": "calendar.create", "params": {...}, "id": 1}
← {"result": {...}, "id": 1}
```

**MCP(Model Context Protocol)** 가 JSON-RPC 2.0을 베이스로 합니다. 32장에서 자세히.

### 7.2 gRPC / Protocol Buffers

Google이 만든 고성능 RPC. 텍스트가 아닌 **이진(binary)** 포맷을 씀. 마이크로서비스 간 내부 통신에 인기.

우리 프로젝트에는 **쓰지 않습니다**. 이유: 브라우저에서 gRPC 직접 사용이 제약 많고, 내부 서비스 수가 적다.

## 8. 인증(Authentication) 과 권한(Authorization)

API 보안에는 두 개념이 붙어 다닙니다.

- **Authentication(인증)** = **"당신이 누구인가"** 확인.
- **Authorization(권한)** = **"당신이 이 일을 할 수 있는가"** 확인.

### 8.1 흔한 토큰 방식

- **Session Cookie** (전통적): 서버가 상태를 보관, 브라우저에는 쿠키.
- **JWT** (Stateless): 서명된 토큰 안에 사용자 정보가 담겨 있음. 서버는 서명만 검증.
- **OAuth 2.0 + OpenID Connect**: 타사 로그인(Google, Microsoft 등).

### 8.2 이 프로젝트

- 현재 구현은 **ID/PW + 토큰** 기반이며, SSO/OIDC는 전사 인증 체계와 맞춰 별도 결정할 영역입니다.
- 관리자/워크스페이스 멤버십에 따른 **권한 가드**가 백엔드 `require_workspace_membership` 같은 의존성으로 걸려 있음.

### 8.3 인증과 권한의 차이

- **인증(Authentication)** 은 사용자가 누구인지 확인하는 단계이고, **권한(Authorization)** 은 해당 리소스를 수행할 자격이 있는지 확인하는 단계입니다.
- 로그인 성공 이후에도 리소스별 접근 권한 검사는 매 요청마다 별도로 수행되어야 합니다.

### 8.4 ⚠️ 헷갈리기 쉬운 것들

- **"로그인만 돼 있으면 모든 걸 볼 수 있다"** — 로그인은 **1단계**일 뿐이다. 매 요청마다 "이 리소스에 접근할 권한이 있는가"는 별도로 체크되어야 한다. 이것이 OWASP Top 1인 **Broken Access Control** 문제의 핵심이다.
- **"JWT는 로그아웃이 어렵다"** — 맞는 말이다. JWT는 서버에 상태를 두지 않는 방식이라 즉시 무효화가 원천적으로 까다롭다. 그래서 토큰 만료 시간을 짧게 두거나 블랙리스트를 함께 쓴다.

## 9. API 설계의 좋은 습관

### 9.1 버전 관리

`/api/v1/users` 처럼 버전을 경로에 넣으면, 나중에 `v2`를 만들어도 기존 클라이언트가 깨지지 않는다.

### 9.2 에러는 일관된 포맷으로

```json
{
  "error": "invalid_credentials",
  "message": "이메일 또는 비밀번호가 일치하지 않습니다.",
  "details": { ... }
}
```

### 9.3 idempotent(멱등)한 메서드

GET, PUT, DELETE는 **여러 번 호출해도 같은 결과** 여야 합니다. POST는 예외입니다.

### 9.4 페이지네이션

목록 조회는 반드시 페이지네이션. `?page=2&size=20` 또는 **커서 기반** (`?cursor=abc`).

### 9.5 Rate limiting

악성 요청·과도한 호출을 막기 위한 제한. 특히 AI 엔드포인트는 비용이 드니 필수.

## 10. 핵심 요약

- API는 프로그램 간의 **호출 계약**. 가장 보편적인 기반은 **HTTP**.
- **REST**는 HTTP 메서드로 리소스를 조작하는 스타일. 우리 프로젝트의 메인.
- **OpenAPI**는 REST API의 표준 명세. FastAPI가 자동 생성.
- **WebSocket**은 양방향 실시간. 우리는 BlockNote 협업에 사용.
- **SSE**는 서버→클라이언트 일방향. 우리는 AI 스트리밍에 사용.
- 인증/권한은 API의 보안 기둥. 현재는 ID/PW + 토큰.
