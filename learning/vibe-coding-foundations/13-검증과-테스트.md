# 13. 검증과 테스트 — AI가 만든 코드를 어떻게 믿을까

> **한 줄 요약.** 바이브 코딩에서 "**작성"은 AI가, "**검증**"은 사람이 한다**. AI 결과물을 어떻게 확인할지를 모르면 속도가 아니라 **버그 공장**이 된다. 이 장은 비개발자가 매일 쓸 수 있는 **7가지 검증 습관**을 정리한다.

---

## 1. 왜 검증이 핵심인가

10장에서 테스트·품질·보안을 다뤘고, 12장에서 LLM의 **환각(hallucination)** 을 배웠습니다. 이 둘을 잇는 질문이 이 장의 주제입니다.

> "AI가 써 준 코드가 **진짜로 맞는지** 나는 어떻게 알 수 있는가?"

비개발자 TF에게 이것은 단지 품질 문제가 아니라 **책임 문제**입니다. 여러분이 열어 머지한 PR은 **여러분의 PR**입니다. AI가 썼다고 해서 책임이 AI에게 가지 않습니다.

### 🔑 핵심 비유 — "비서가 쓴 보고서"

실력 좋은 비서가 회장님께 올릴 보고서를 대신 써 왔다고 합시다. 숫자·문장·결론 모두 그럴듯해 보입니다. 그렇다고 **읽지도 않고 서명해서 올리진 않죠**. 최소한 다음을 확인합니다.

1. 숫자가 소스 데이터와 맞는가?
2. 회사가 정한 용어·톤을 지켰는가?
3. 결론이 이번 회의의 의제에 부합하는가?

AI가 쓴 코드에 대한 검증도 정확히 이와 같은 일입니다. 여러분은 **"AI 결과물 최종 승인자"** 입니다.

---

## 2. 검증이 실패하는 전형적 장면

실제 TF에서 흔히 벌어지는 5가지 실패 패턴입니다. 한 번쯤 해볼 수 있는 실수이니 미리 눈에 익혀 둡시다.

### 2.1 "돌아간다 = 맞다"의 함정

AI가 만든 코드가 **오류 없이 실행된다고** 기능이 맞는 건 아닙니다. 예를 들어 "주간 매출 합계"를 계산하는 코드가, 사실은 월요일이 주 시작이어야 하는데 일요일 시작으로 계산해도 에러는 안 납니다. 실행은 되는데 숫자가 틀리는 겁니다.

### 2.2 "테스트가 통과했다 = 맞다"의 함정

AI가 **자기 코드에 유리한 테스트만 써 놓으면** 당연히 통과합니다. 예를 들어 "음수 입력 처리" 테스트를 아예 안 쓰면, 음수에서 깨지는 버그는 영원히 드러나지 않습니다.

### 2.3 "눈으로 봐서 괜찮아 보인다"의 함정

UI 변경을 AI에게 시켰는데 스크린샷상 멀쩡해 보여도, **모바일 화면**·**다크 모드**·**빈 데이터 상태** 에서는 깨질 수 있습니다. 보는 각도가 부족한 거죠.

### 2.4 "설명이 그럴듯하다 = 맞다"의 함정

AI의 **"이렇게 고쳤습니다. 이유는 ..."** 라는 자연어 설명이 논리정연해 보여도, 실제 diff는 설명과 다를 수 있습니다. 설명과 코드를 **따로** 확인해야 합니다.

### 2.5 "내가 모르니까 맞겠지"의 함정

가장 위험합니다. "어차피 난 코드를 잘 몰라서 AI 판단을 믿을 수밖에 없다"는 태도. 이 자료 전체가 이 태도를 반박하기 위해 존재합니다. **검증은 코드 실력이 아니라 습관**입니다.

## 3. 비개발자를 위한 7가지 검증 습관

이 7가지는 코드 한 줄 못 치는 사람도 할 수 있는 점검입니다. 순서대로 체크리스트처럼 돌리세요.

### 3.1 습관 1 — **"내가 시킨 게 맞나" 읽기**

AI 응답을 받으면 **코드보다 먼저** 설명을 읽습니다. 그 설명이 **여러분이 부탁한 것**과 일치하나요? 엉뚱한 일을 시작하고 있다면 여기서 잡아야 낭비가 없습니다.

| 내가 부탁한 것 | AI가 이해한 것 | OK? |
|---|---|---|
| "주간 매출을 월요일 시작으로 합산" | "주간 매출을 일요일 시작으로 합산" | ❌ |
| "로그인 실패 5회 시 계정 잠금" | "로그인 실패 3회 시 계정 잠금" | ❌ |
| "이 페이지에 다크 모드 지원 추가" | "다크 모드 추가. 색 변수는 `--bg-dark` 등 새로 정의" | ✅ |

다르면 **바로 멈춰 주세요**. 코드를 읽기 전에.

### 3.2 습관 2 — **diff를 한 줄씩 따라 읽기**

Git 또는 에디터의 "변경 내역(diff)" 뷰를 엽니다. 모르는 줄이 나와도 괜찮습니다. 다음 세 질문만 반복합니다.

1. "이 파일은 왜 바뀌었나?"
2. "이 줄은 뭘 하는 것처럼 보이나?" (짐작이면 충분)
3. "이 변경이 내가 부탁한 기능과 **연관** 있어 보이나?"

세 번째가 특히 중요합니다. AI가 **부탁하지 않은 파일**까지 건드렸다면 즉시 멈추고 이유를 물어야 합니다.

> 🏢 **업무 예시**: "캘린더에 필터 토글 추가" 요청을 했는데 diff에 `package.json` 변경과 새 의존성 `lodash-es` 추가가 있다면? → "왜 새 의존성을 설치했어? 토글 하나에 필요한가?"라고 되물어야 합니다.

### 3.3 습관 3 — **테스트를 먼저 쓰게 시킨다**

이미 12장·35장에서 나온 팁이지만 다시 강조합니다.

```
먼저 실패하는 테스트 3개를 써 줘. 내가 OK하면 구현 시작해 줘.
```

이러면 **요구사항이 명문화**됩니다. AI가 스스로 채점 기준을 먼저 정하는 셈이죠. 구현 후 테스트가 초록불이면 적어도 **자기가 쓴 기준은 통과한 것**입니다.

추가로 여러분이 직접 **"이런 입력도 테스트에 넣어 줘"** 라고 가장자리 조건(edge case)을 추가하면 방어선이 두꺼워집니다.

- 빈 값 (`""`, `null`, `0`, `[]`)
- 아주 큰 값·아주 오래된 날짜
- 한글·이모지 같은 비-ASCII
- 동시 요청 (두 명이 같은 자원을 수정)

### 3.4 습관 4 — **눈으로 직접 돌려본다**

AI가 "잘 동작합니다"라고 말해도, 여러분이 **실제로** 브라우저나 API 테스터에서 눌러봐야 합니다. 다음 시나리오를 최소한으로 돌리세요.

1. **골든 패스**: 사용자가 정상적으로 쓰는 길. 예: 로그인 → 문서 작성 → 저장.
2. **빈 상태**: 데이터가 아직 없는 경우. 예: 새로 가입해서 문서가 0건일 때.
3. **실패 경로**: 비번 틀리기, 네트워크 끊기.
4. **권한 경로**: 관리자 vs 일반 사용자에서 같은 화면이 다르게 보이는가.

비개발자도 **첫 번째·두 번째 시나리오 2분 확인** 만 해도 버그의 50% 이상이 드러납니다.

### 3.5 습관 5 — **작은 단위로 쪼개 머지**

한 번에 10개 파일·500줄 diff를 받는 건 검증을 사실상 포기하는 것과 같습니다. 34·35장의 원칙을 이 장에서 다시:

> 한 PR은 **한 가지 일**만. 테스트 + 리뷰 + 머지 가능한 크기로.

AI에게 **"이걸 3단계로 나눠서 1단계부터 보여 줘"** 라고 시키세요. 3개의 작은 PR이 1개의 거대 PR보다 **훨씬 리뷰하기 쉽습니다**.

### 3.6 습관 6 — **AI에게 "스스로 비판"을 시킨다**

모델의 **Reflection(자기반성)** 패턴을 활용합니다. 2026년 기준 널리 쓰이는 고급 패턴입니다.

```
방금 네가 쓴 코드와 스펙을 스스로 교차 검증해 줘.
- 스펙이 요구하는데 구현 안 된 부분
- 스펙에 없는데 추가된 부분
- 실패 경로 처리가 빠진 부분
- 가장자리 조건에서 깨질 가능성
한 가지라도 찾으면 목록으로 알려 주고, 필요하면 패치 제안해 줘.
```

놀랍게도 LLM은 **자기 실수를 다시 물어보면 꽤 잘 찾습니다**. 특히 긴 세션일수록 효과가 큽니다.

### 3.7 습관 7 — **두 번째 의견(second opinion)을 받는다**

한 모델의 답에만 의존하지 마세요.

- 중요한 변경은 **다른 모델** 이나 **다른 세션** 에서 리뷰 시키기
- Claude Code에서는 **subagent** 를 써서 격리된 컨텍스트로 "이 diff 리뷰해 줘"
- Cursor 에서는 **Agents Window** 로 별도 에이전트에게 리뷰 요청
- 팀 동료 한 명의 **인간 리뷰**는 여전히 가장 강력한 방어선

이게 번거롭게 느껴지면 **원칙**을 생각하세요. **운영 환경에 영향 있는 변경은 사람 최소 1명 승인** 은 아직도 2026년 기준 업계 표준입니다.

## 4. 테스트의 종류 — 비개발자용 한 페이지 정리

10장에서 상세히 다뤘지만, 이 장에서는 **"언제 무엇을 주문할지"** 관점에서 다시 정리합니다.

| 종류 | 무엇을 확인? | 비용 | 언제 주문? |
|---|---|---|---|
| **단위 테스트(Unit)** | 함수 하나, 로직 한 조각 | 거의 공짜 | 새 유틸리티·계산 로직 만들 때 |
| **통합 테스트(Integration)** | 두세 모듈의 협업 | 중간 | API 라우터 + DB 엮을 때 |
| **E2E 테스트(End-to-End)** | 사용자 시나리오 전체 (브라우저 자동화) | 비쌈 | 핵심 플로우(로그인, 결제 등) |
| **수동 확인(Manual)** | 눈으로 직접 | 공짜지만 비선형적 | 처음·UI 변경·디자인 |

비개발자가 AI에게 주문할 기본 조합:

> "이 변경에 대해 **단위 테스트 2~3개** 와 **E2E 1개** 를 써 줘."

이 한 줄로 웬만한 작업의 기본 방어선이 서립니다.

## 5. 코드 리뷰 체크리스트 (비개발자용)

PR을 열기 전·머지하기 전에 다음을 확인합니다. 순서대로 돌리면 2~5분 걸립니다.

### 5.1 내용 체크

- [ ] diff의 **파일 수**가 합리적인가? (너무 많으면 쪼갤 것)
- [ ] 변경된 파일들이 **이 작업과 관련** 있어 보이는가?
- [ ] AI가 **이유 없는 새 의존성**을 추가하지 않았는가? (`package.json`, `pyproject.toml` 확인)
- [ ] **시크릿(`.env`, API 키)이 코드에 박혀 있진** 않은가?
- [ ] 기존 **한국어 주석·문구 스타일**과 이질감이 없는가?

### 5.2 동작 체크

- [ ] `pnpm lint` / `pnpm test` 가 초록불인가?
- [ ] 브라우저에서 **골든 패스**를 실제로 눌러 봤는가?
- [ ] **빈 상태** (데이터 0건)에서도 화면이 정상인가?
- [ ] **실패 경로**를 적어도 하나 확인했는가? (잘못된 입력, 네트워크 오류)

### 5.3 협업 체크

- [ ] PR 제목이 **한 줄로 뭘 바꿨는지** 전달되는가? (`update stuff` 금지)
- [ ] PR 본문에 **무엇을 / 왜 / 어떻게 검증했는지** 적었는가?
- [ ] 영향받는 **팀원·기능**을 알렸는가?

이 체크리스트를 **노션·위키에 복붙** 해 두고 매번 돌리세요. 반복이 실력을 만듭니다.

## 6. ⚠️ 자주 하는 오해

**"AI가 쓴 코드는 사람이 쓴 것보다 정확하다"**
최신 모델도 SWE-Bench Verified(2026.04 기준)에서 **평균 63.4%** 정답률입니다. 40%는 틀립니다. 정확도가 높아진 건 맞지만 **검증 없이 믿을 수준은 아닙니다**.

**"테스트가 초록불이면 버그 0이다"**
테스트는 **커버한 시나리오에서만** 통과를 보장합니다. 테스트가 없는 영역의 버그는 그대로 살아 있습니다. 그래서 "테스트 + 수동 확인 + 코드 리뷰"의 세 겹이 필요합니다.

**"린트와 타입 검사가 통과하면 기능도 맞다"**
린트·타입은 **문법적 오류**만 걸러냅니다. **의도와 다르게 동작하는 버그**는 전혀 못 잡습니다. 예를 들어 "더하기"를 써야 할 자리에 "빼기"를 써도 타입상으로는 OK가 나옵니다.

**"AI가 자신 있게 답하면 맞는 거다"**
LLM은 **확신도를 정직하게 표현하지 못합니다**. 틀린 답도 확신에 차서 말합니다. 말의 톤으로 정답 확률을 추정하지 마세요.

**"내가 잘 모르는 분야는 어쩔 수 없이 AI를 믿어야 한다"**
모를수록 **검증 습관**이 더 중요합니다. 모른다면 AI에게 **"초보자용 설명"** 을 요청해서 맥락부터 올리세요. 그다음 검증하세요.

## 7. 🏢 좋은 바이브 코딩 vs 나쁜 바이브 코딩

### 7.1 나쁜 바이브 코딩: 검증 없는 속도

```
TF원 A — "결재 승인 화면에 '지연된 결재만 보기' 필터 추가해 줘."
AI — [diff 120줄 제시]
A — "오케이 바로 머지할게." [PR 생성 → 셀프 승인 → main 머지]
…3일 후
운영 — "결재 담당자 전체 목록이 이상해졌어요. 지연 안 된 결재도 안 보입니다."
A — "어?! AI가 왜 필터가 아니라 **목록 쿼리 자체**를 바꿨지?"
```

**무엇을 놓쳤나?** diff를 읽지 않음 (습관 2). 골든 패스·빈 상태 확인 안 함 (습관 4). 팀 리뷰 없음 (습관 7).

### 7.2 좋은 바이브 코딩: 검증 포함한 속도

```
TF원 B — "결재 승인 화면에 '지연된 결재만 보기' 필터 추가해 줘.
          먼저 계획만 보여줘. 변경 범위·테스트 항목 포함."
AI — [3단계 계획 + 테스트 3개 + UI 변경 1개]
B — "좋아. 단, '지연'의 기준은 '마감일 + 1일' 로 해 줘. 테스트에 반영."
AI — [테스트부터 작성 → 실패 확인 → 구현 → 통과]
B — [diff 각 줄 훑어보기 → 브라우저에서 필터 켜고 끄고 확인 → 빈 상태 확인]
B — "@동료1, 리뷰 부탁해."
[동료1 승인]
B — [머지]
```

**무엇이 달랐나?** 계획부터 물음 (습관 1). 테스트 먼저 (습관 3). diff 읽음 (습관 2). 실제 눌러봄 (습관 4). 인간 리뷰 (습관 7).

속도 차이는 **머지 후 3일간의 장애 처리 시간** 에서 나옵니다.

## 9. 핵심 요약

- 바이브 코딩에서 **작성**은 AI가 하고 **검증**은 사람이 한다. 책임은 사람에게 있다.
- 실패 패턴 5가지: "돌아가면 맞다 / 테스트 통과하면 맞다 / 눈으로 괜찮아 보인다 / 설명이 그럴듯하다 / 내가 모르니 믿자" — **전부 함정**.
- 7가지 검증 습관: ① 의도 확인 ② diff 읽기 ③ 테스트 선작성 ④ 직접 실행 ⑤ 작게 쪼개 머지 ⑥ Reflection 요청 ⑦ 두 번째 의견.
- 테스트 4종(Unit / Integration / E2E / 수동)을 상황별로 조합해 주문한다.
- 체크리스트를 **매번** 돌리는 반복이 실력을 만든다.
