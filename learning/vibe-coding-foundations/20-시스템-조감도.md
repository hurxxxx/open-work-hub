# 20. 시스템 조감도 — AIDOO Portal 전체 구조 한눈에 보기

> **한 줄 요약.** AIDOO Portal은 **Nx 모노레포** 위에 **React(프런트) + FastAPI(백) + Celery 워커 + PostgreSQL/Redis/MinIO 인프라 + OpenAI**를 엮은 **모듈러 모놀리스**이다. 이 장은 Part 2의 지도이다.

> 🔑 **한 마디로.** "한 건물(모노레포) 안에 **접수대(Nginx), 사무실(FastAPI), 서류 창고(PostgreSQL), 우편함(Redis), 자료실(MinIO), 뒷방 작업반(Celery), 외주 컨설턴트(OpenAI)**가 각자 일하면서 서로 공문으로 소통"한다고 보면 된다.

### 병원, 식당, 사내 행정으로 보기

- **병원**: 접수창구(Nginx) → 진료실(FastAPI) → 차트 보관소(PostgreSQL) → 대기번호 알림판(Redis) → X-ray 필름 보관실(MinIO) → 야간 검체 검사실(Celery Worker) → 외부 판독 전문의(OpenAI).
- **식당**: 홀 서버(프런트엔드) ↔ 주방장(백엔드) ↔ 식자재 창고(DB). 주문 한 건이 들어오면 서버가 주방에 전달, 주방은 창고에서 재료를 꺼내 요리. 오래 걸리는 스튜(녹취 트랜스크립션)는 **야간 조리팀(Celery)** 이 뒷방에서 맡는다.
- **사내 행정**: 프런트엔드 = 신청서 양식, 백엔드 = 담당 주임, DB = 원장, Redis = 결재 대기함, MinIO = 첨부파일 캐비닛, Celery = "처리해 두고 내일 말씀드리겠습니다"의 주무관.

## 1. 프로젝트의 목적

`docs/product/ai_portal.md` 와 `docs/product/idea.md`, 그리고 `docs/planning/*` 에 담긴 구상을 종합하면, AIDOO Portal은 두원그룹 내부 업무를 위한 **"AI 퍼스트 통합 워크스페이스"** 입니다. 주요 기능:

- **AI 채팅 + 도구 호출** — 회사 데이터·도구와 연결된 사내 AI 비서
- **위키/문서 협업** — 실시간 공동 편집(BlockNote + Yjs)
- **프로젝트 관리(PMS)** — 이슈, 마일스톤, 보드
- **회의·캘린더** — 일정 관리, 회의실, 녹음/트랜스크립션
- **관리자 콘솔** — 워크스페이스·사용자·권한

이 모든 기능이 하나의 포털 안에서 **공통 사용자·권한 체계** 로 돌아갑니다.

## 2. 저장소 배치 (모노레포)

```

│   ├── api/        ← 백엔드 API (FastAPI, Python 3.12)
│   ├── worker/     ← 비동기 워커 (Celery)
│   └── ops/        ← 운영 도구 (플레이스홀더 단계)
├── packages/
│   ├── ui/         ← 공통 UI 컴포넌트 라이브러리
│   └── contracts/  ← (예정) 프런트·백 공유 타입·스키마
├── adr/            ← 아키텍처 결정 기록
├── docs/           ← 기능 기획·계획 문서
├── ops/            ← 운영 스크립트
├── scripts/        ← 셸 스크립트
├── compose.*.yml   ← Docker Compose 파일
├── nx.json         ← Nx 모노레포 설정
├── pnpm-workspace.yaml
├── package.json    ← 프런트·도구 의존성
└── .env.example    ← 환경변수 템플릿
```

Nx와 pnpm의 결합으로, **한 저장소에 여러 앱과 패키지가 공존** 하면서도 빌드·테스트·의존성이 각자 격리됩니다. 자세히는 21장.

## 3. 실행 시 아키텍처

사용자 브라우저에서 출발한 HTTPS 요청은 **Nginx → FastAPI** 경로를 타고, FastAPI 는 아래 네 개의 데이터·외부 서비스와 맞물려 동작합니다.

| 컴포넌트 | 포트 | 역할 |
| --- | --- | --- |
| Nginx | 4200 | 정적 웹 서빙 · HTTPS 종결 · `/api` 프록시 |
| FastAPI | 8000 | REST API · SSE 스트리밍 · WebSocket |
| PostgreSQL | 5432 | 메인 DB |
| Redis | 6379 | Celery 큐 · 캐시 · Yjs 릴레이 |
| MinIO | 9000 | 객체 저장소 (파일·녹음·첨부) |
| Celery 워커 | 별도 프로세스 | Redis 큐에서 작업을 꺼내 장시간 작업 수행 |
| OpenAI API | 외부 | LLM 스트리밍 소스 |

> 연결 관계: **브라우저 → Nginx → FastAPI → {PostgreSQL, Redis, MinIO, OpenAI}**.  
> Redis 에 쌓인 작업은 **Celery 워커** 가 소비해 비동기 처리하고, 결과는 다시 PostgreSQL/MinIO 로 넘어갑니다.

### 3.1 요청의 두 가지 흐름

**즉시 응답형 (빠른 요청)**

```
사용자 → Nginx → FastAPI → DB → FastAPI → 사용자
```

예: 회의실 목록 조회, 로그인, 문서 저장

**비동기 워커형 (느린 작업)**

```
사용자 → FastAPI → Redis 큐에 작업 등록 → 즉시 응답 "처리 중"
Celery 워커 → Redis에서 작업 가져감 → 장시간 작업 수행
→ 결과를 DB에 저장 → 사용자가 나중에 조회
```

예: 회의 녹음 트랜스크립션(몇 분 걸림), OCR, 이미지 변환.

**스트리밍형 (AI)**

```
사용자 → FastAPI → OpenAI (스트리밍)
                    → 토큰마다 SSE로 사용자에게 흘림
```

### 3.2 요청 하나의 여정 (트레이스) — "문서를 열었다"

화면에서 문서 하나를 클릭하는 순간, 이런 여행이 일어납니다.

1. 브라우저: `/w/doowon-hq/docs/123` 주소로 **HTTPS 요청**을 쏜다.
2. **Nginx(4200 포트)**: SSL을 벗겨내고 "이건 `/api/...` 요청이네" → FastAPI로 전달.
3. **FastAPI(8000)**: 쿠키 세션을 꺼내 "이 사람 로그인돼 있네, 워크스페이스 멤버도 맞네" 확인.
4. **PostgreSQL(5432)**: "docs 테이블에서 id=123 가져와" → 제목, 메타, 작성자 정보 반환.
5. **MinIO(9000)**: (필요 시) 문서 안 첨부 이미지 URL 서명 → 브라우저가 직접 다운로드 가능하게.
6. FastAPI: JSON 응답 조립 → Nginx → 브라우저.
7. React: 화면에 문서 본문 렌더 + **별도로 WebSocket**을 열어 `ypy-websocket` 릴레이와 연결 → 실시간 협업 시작.

"AI 채팅 한 줄 물어봄" 같은 경우는 6번에서 분기합니다. FastAPI → OpenAI로 **토큰이 한 개씩 흘러올 때마다** SSE로 브라우저에 즉시 전달, 화면에서 글자가 타자기처럼 찍힌다.

"회의 녹음을 업로드"는 또 다르다. FastAPI가 파일을 **MinIO에 저장**하고, "이 파일 텍스트로 바꿔 줘"라는 **쪽지를 Redis 큐에 넣고** 즉시 응답한다. 뒤에서 Celery 워커가 그 쪽지를 꺼내 실제 작업을 수행 → 완료되면 DB에 결과를 쓰고, 사용자는 나중에 새로고침해서 결과를 본다.

## 4.5 ⚠️ 구조에서 자주 하는 오해

- **"모놀리스는 구식이다, 당장 마이크로서비스로 쪼개야 한다"** — 우리가 쓰는 건 **모듈러 모놀리스**(내부는 잘 나뉘어 있지만 하나의 앱으로 배포되는 구조)다. 소규모~중규모 팀에서는 이것이 오히려 가장 빠르고 안정적이다. 마이크로서비스는 조직이 수십 팀으로 커질 때의 해법이다.
- **"Nginx·Redis·MinIO 세 개는 취향 차이 아닌가"** — 각자 전혀 다른 역할이다. Nginx = **문지기**, Redis = **쪽지통**, MinIO = **창고**. 어느 하나라도 빠지면 다른 것으로 대체가 어렵다.
- **"Celery 워커는 AI 전용이다"** — AI 호출은 대부분 **SSE 스트리밍**(서버가 데이터를 조금씩 흘려보내는 방식)으로 즉시 응답한다. Celery는 오히려 **녹취 트랜스크립션·OCR·이미지 변환**처럼 몇 초~몇 분 걸리는 무거운 잡일에 쓰인다.
- **"프런트엔드 = 디자인, 백엔드 = 기능"** — 프런트엔드도 **상태 관리·라우팅·실시간 동기화**처럼 복잡한 로직을 담당한다. 디자인만이 아니다.
- **"운영 서버에는 Node.js가 돌아간다"** — 이 프로젝트의 프런트는 **빌드하고 나면 정적 HTML/JS/CSS 파일**만 남는다. Nginx가 그냥 파일을 내려줄 뿐, Node는 돌지 않는다. (23장에서 자세히)

## 4.6 🏢 회의록 한 건이 태어나는 흐름

**상황:** 김과장이 수요일 회의에서 녹음을 30분 진행했고, 종료 직후 "회의록 초안 생성" 버튼을 눌렀다.

1. 브라우저가 녹음 파일(예: `meeting.mp3`, 40MB)을 **FastAPI에 업로드**. FastAPI는 파일을 **MinIO에 넣고** DB에는 "meeting 123 녹음 파일 있음"만 기록, 즉시 "처리 중" 응답.
2. FastAPI가 **Redis 큐에 "트랜스크립션 잡"** 을 올려놓는다. 사용자는 이제 다른 작업을 해도 된다.
3. **Celery 워커**가 큐에서 잡을 꺼내 MinIO에서 파일을 받아 OpenAI(혹은 Whisper)에 보낸다. 2~3분 후 텍스트 결과 반환.
4. 워커가 텍스트를 DB에 저장하고, "AI 요약" 잡을 다시 큐에 올린다.
5. AI 요약이 끝나면, 사용자의 문서 에디터(BlockNote)가 **이미 Yjs WebSocket으로 연결돼 있어서** 초안이 자동으로 채워진다.

이 한 시나리오에 **Nginx, FastAPI, MinIO, Redis, Celery, OpenAI, PostgreSQL, Yjs WebSocket** 8개 컴포넌트가 모두 쓰였다. 각자가 왜 필요한지 감이 잡히면 이 장의 80%는 잡은 것이다.

## 6. 주요 환경과 구동

개발자 PC에서의 구동은 간단합니다.

```bash
# 의존성 설치
pnpm install              # 프런트·노드 의존성
cd apps/api && uv sync    # 백엔드 Python 의존성

# 인프라 띄우기(Docker)
docker compose -f compose.postgres.yml up -d

# 전 개발 서버(프런트+백)
./dev.sh
# 또는 나눠서:
pnpm dev:web        # 프런트만
pnpm dev:api        # 백만
pnpm dev:worker     # 워커만
```

Prod-like 환경은 실제 운영과 같은 컨테이너 구성으로 돌려볼 수 있습니다.

```bash
pnpm prodlike:infra:up    # 전체 인프라
pnpm prodlike:smoke       # 스모크 테스트
```

## 7.5 🛠️ 5분 실습 — 아키텍처 살피기

1. 개발 서버가 돌아가는 상태에서 F12 → **Network** 탭을 연다.
2. 좌측 메뉴를 여기저기 클릭. "**`/api/...`** 로 끝나는 요청 = 백엔드 호출, JS/CSS 호출 = 정적 자산 로드"로 구분해 본다.
3. AI 채팅을 한 번 시도 → **EventStream** 혹은 **Fetch/XHR** 탭에서 **토큰이 조각조각 들어오는 SSE** 응답을 볼 수 있다.
4. 문서 페이지 하나를 열고 **WS** 탭으로 바꾸면 **`/yjs/...`** WebSocket 연결이 보인다 — 실시간 협업 릴레이.

이 세 가지 종류(일반 REST, SSE, WebSocket)가 한 포털 안에 공존하는 것을 눈으로 확인하세요.

## 8. 핵심 요약

- AIDOO Portal은 **모듈러 모놀리스 + 모노레포** 구조의 사내 AI 허브.
- 두 언어(**TypeScript, Python**)를 **HTTP API**로 연결한 고전적 3-Tier.
- 인프라는 **PostgreSQL + Redis + MinIO** 세 축.
- 느린 작업은 **Celery 워커**로 밀고, AI 응답은 **SSE 스트리밍**, 협업은 **Yjs WebSocket**.
- 프런트/백 폴더가 **도메인 이름으로 거울상** 을 이룬다 — 기능 단위 이동이 쉽다.
