# 14. 프롬프트 워크북 — 손으로 쓰면서 익히는 AI 주문법

> **한 줄 요약.** 좋은 프롬프트는 **도덕적 소질**이 아니라 **반복 훈련**이다. 이 장은 비개발자가 즉시 베껴 쓸 수 있는 **프롬프트 템플릿 15개** 와 **5단계 변환 실습**을 제공한다.

---

## 1. 왜 "워크북"인가

12장과 35장에서 프롬프트 엔지니어링의 이론을 이미 다뤘습니다. 이 장은 **실제로 손을 움직이는** 장입니다.

비개발자 5명이 AI 앞에 앉았을 때 가장 큰 벽은 **"뭐라고 쳐야 할지 모르겠다"** 는 순간입니다. 이 벽을 넘기려면 머릿속에 **"최소 15개의 즉시 베낄 수 있는 틀"** 이 있어야 합니다. 그 틀 위에 매번 자기 상황을 갈아 끼우는 훈련이 이 장의 목표입니다.

### 🔑 비유 — "외국어 회화 책의 예문 100개"

새 언어를 배울 때 문법책보다 **예문 100개** 가 훨씬 실용적인 경우가 많습니다. "안녕하세요 / 이거 얼마예요? / 화장실 어디예요?" 같은 예문을 통째로 외워 두면, 문법 체계를 몰라도 여행은 됩니다. 프롬프트도 같습니다.

### 📎 2026.04 흐름 참고

- 12장에서 본 것처럼 "프롬프트 엔지니어링"이란 단어는 이제 **"Context Engineering"** 의 하위 개념으로 이동 중입니다. 본 장의 템플릿들은 단일 프롬프트뿐 아니라 **세션 전체의 맥락 설계** 에 도움 되도록 설계되었습니다.
- 기계적 JSON 프롬프트보다 **자연어** 가 더 좋은 결과를 내는 경향이 실험적으로 확인되었습니다 (2025-2026 업계 보고). 따라서 이 워크북의 템플릿도 **자연어 중심** 입니다.

## 2. 프롬프트의 5가지 구성 요소 — 다시 한 번

12장에서 다뤘지만 워크북 용으로 압축해서 리마인드합니다.

| 요소 | 무엇을 담나 | 빠졌을 때의 증상 |
|---|---|---|
| **목표(Goal)** | 뭘 이루고 싶은가 | AI가 엉뚱한 방향으로 감 |
| **배경(Context)** | 왜 이걸 하고 싶은가, 프로젝트·도메인 | 일반적·평범한 답 |
| **제약(Constraint)** | 하면 안 되는 것, 반드시 지켜야 할 것 | 원치 않는 라이브러리 도입, 스타일 변경 |
| **입출력(I/O)** | 무엇을 받고 무엇을 내놓는가 | 형식이 안 맞음, 인자 순서 틀림 |
| **검증(Verification)** | 어떻게 맞음을 확인할지 | 테스트 없음, 실행해 보면 깨짐 |

**외우는 법**: "목·배·제·입·검". 한 글자씩 입에 붙이세요.

## 3. 즉시 베낄 수 있는 템플릿 15개

아래 템플릿의 `<대괄호>` 자리에 여러분 상황을 넣으면 됩니다.

### 3.1 🌱 기본형

**템플릿 1 — 새 기능 추가**

```
목표: <기능을 한 문장으로>.
배경: <현재 불편한 점 1~2문장>.
경로: <수정할 파일·폴더>.
제약: 기존 스타일 유지. 새 의존성 추가는 사전 확인.
검증: <단위 테스트 또는 확인 방법> 포함.
```

**템플릿 2 — 버그 수정**

```
증상: <무엇이 어떻게 잘못 보이는가>.
재현: <단계 1, 2, 3>.
기대: <어떻게 되어야 하는가>.
대상 파일 추정: <가장 연관 있어 보이는 폴더 경로>.
제약: 최소 수정. 연관된 테스트 추가.
```

**템플릿 3 — 리팩토링**

```
목표: <지금의 무엇을 어떻게 바꾸고 싶은가>.
제약: 동작은 바뀌지 않아야 한다.
검증: 기존 테스트 전부 초록불 유지. 필요하면 특성 테스트(golden test) 먼저 추가.
```

### 3.2 🧭 계획형 (Plan-and-Execute)

**템플릿 4 — 계획부터 먼저**

```
아래 요구를 구현하기 **전에**, 수정할 파일·변경 순서·예상 diff 크기를 먼저 보여 줘.
내가 OK하면 단계 1부터 시작해 줘.

요구:
<여기에 자유 서술>
```

**템플릿 5 — 단계 쪼개기**

```
이 작업을 **3~5개의 작은 단계**로 쪼개 줘. 각 단계는 따로 PR이 될 수 있어야 하고,
단계 사이에 테스트가 초록불인 상태로 유지돼야 해.

작업: <자유 서술>
```

### 3.3 🪞 검증형 (Reflection)

**템플릿 6 — 스스로 교차 검증**

```
방금 쓴 코드와 내가 준 스펙을 교차 검증해 줘.
- 스펙이 요구하는데 구현 안 된 것
- 스펙에 없는데 추가된 것
- 실패 경로 처리가 빠진 것
- 가장자리 조건에서 깨질 가능성
한 가지라도 있으면 목록으로 알려줘.
```

**템플릿 7 — 테스트 커버리지 점검**

```
이 변경에 대해 다음 각각에 테스트가 있는지 알려 줘. 빠진 게 있으면 추가해 줘.
1) 정상 입력
2) 빈 값 (null, '', 0, [])
3) 비정상 입력 (타입 틀림, 음수, 너무 긴 값)
4) 권한 없는 사용자의 호출
5) 동시 호출
```

**템플릿 8 — "내가 AI라면 놓쳤을 것" 물어보기**

```
내가 비개발자라서 놓쳤을 수 있는 리스크 5가지를 솔직히 말해 줘.
보안·성능·유지보수·테스트 커버리지·의존성 관점 각 1개씩.
```

### 3.4 🔍 학습·탐색형

**템플릿 9 — 코드 설명 요청**

```
아래 파일/함수를 **비개발자에게 설명하듯** 단계별로 풀어 줘.
- 이 코드가 해결하는 문제는 무엇인가?
- 핵심 흐름을 3~5단계로
- 이 안에서 가장 중요한 1줄 하이라이트
- 이 코드 주변에서 조심해야 할 것 (수정하면 영향 범위)

파일: <경로>
```

**템플릿 10 — "어디에 있을지" 찾기**

```
이 프로젝트에서 <기능 설명>을 구현한 코드가 **어느 폴더/파일**에 있을 것 같은지
3가지 후보를 짐작해 줘. 각각의 근거와 함께.
```

**템플릿 11 — 개념 비유 요청**

```
<기술 용어>를 업무 경험이 있는 비개발자에게 설명할 때 쓸 만한
일상 비유 2가지를 제안해 줘. 각 비유의 한계도 한 줄씩.
```

### 3.5 🛡️ 안전형

**템플릿 12 — 운영 영향 확인**

```
이 변경이 운영에 미칠 수 있는 영향을 나열해 줘.
- DB 스키마 변경 유무
- 기존 데이터 마이그레이션 필요 여부
- 롤백 가능 여부·절차
- 다운타임 필요 여부
```

**템플릿 13 — 민감 정보 점검**

```
이 변경에서 로그·커밋·PR 본문에 **민감 정보(시크릿·개인정보)**
가 유출될 가능성이 있는지 점검해 줘.
```

### 3.6 🔄 반복형 (에러 해결)

**템플릿 14 — 에러 그대로 붙이기**

```
아래 에러가 <상황>에서 발생했어. 원인을 찾아 최소 수정으로 고쳐 줘.
같은 원인으로 재발하지 않도록 테스트도 추가해 줘.

에러 로그:
<전체 로그 붙이기>
```

**템플릿 15 — "왜?"를 3번 묻기 (근본 원인 분석)**

```
아래 증상의 **근본 원인(Root cause)** 을 "왜?"를 최소 3번 반복해 찾아 줘.
증상 → 왜? → 왜? → 왜? → 진짜 원인 → 대응책.

증상: <자유 서술>
```

## 4. 변환 실습 — 나쁜 프롬프트를 좋은 프롬프트로

**원본 (나쁨)**
```

```

**1단계: 목표 구체화**
```

```

**2단계: 배경 추가**

```

제약: Mantine 컴포넌트 사용, 기존 `useAuth` 훅에서 제공하는 `login(email, password)` 호출.
    에러 메시지는 `lib/toast.ts` 의 errorToast 사용.
```

**4단계: 입출력·검증 추가 (최종)**
```

대상: apps/web/src/domains/auth/pages/LoginPage.tsx (신규)
입력: 이메일·비밀번호 텍스트필드 + Mantine Button.
동작: submit 시 useAuth.login(email, password) 호출.
      성공하면 `/w/:slug/docs` 로 이동. 실패하면 errorToast.
검증: Vitest 단위 테스트 2개 (성공 · 실패 시나리오).
제약: 기존 컴포넌트 스타일 따름. 새 의존성 금지.
```

## 5. 🏢 AIDOO Portal에서 자주 쓰는 복합 프롬프트 예시

이 프로젝트 맥락에서 실제로 자주 등장하는 요청 패턴입니다. 통째로 즐겨찾기 해도 됩니다.

### 5.1 "새 도메인 추가" 표준 프롬프트

```
목표: `<도메인명>` 도메인을 새로 추가하고 싶어. (예: notes, bookmarks)

스펙:
- URL: /w/:slug/<도메인명>(목록), /w/:slug/<도메인명>/:id(상세)
- 백엔드: apps/api/src/aidoo/domains/<도메인명>/{router,service,models,schemas}.py

- 프런트: apps/web/src/domains/<도메인명>/
- 관리자 화면에 카운트 위젯 (기존 dashboard 패턴 따라감)

제약:
- 테스트: 백엔드 pytest 3개, 프런트 Vitest 2개
- 기존 docs 도메인과 같은 구조·스타일 유지
- 새 3rd-party 의존성 금지

먼저 수정·생성할 파일 목록과 순서만 보여 줘. 내가 OK하면 시작.
```

### 5.2 "MCP capability 하나 추가" 표준 프롬프트

```
목표: `<capability 이름>` MCP capability를 추가하고 싶어.

우리 프로젝트 규약 (adr/0002-mcp-capability-platform.md 참고):
- human-friendly REST DTO 와 AI-friendly Pydantic DTO 를 분리

먼저 capability 스펙(입력·출력·permission·approval 여부)을
표로 정리해 줘. 구현은 내 OK 이후 시작.
```

## 6. ⚠️ 프롬프트에서 자주 하는 오해

**"짧고 간결한 프롬프트가 좋은 프롬프트다"**
보편적으로 맞는 말은 아닙니다. **필요한 맥락이 있으면 길어야** 합니다. 짧을수록 AI가 **일반적·무난한** 답을 주는 경향이 있습니다. 단 **반복이나 불필요한 장식**은 빼세요.

**"JSON 같은 정형 포맷으로 주면 정확해진다"**
2025~2026년 실험에서 JSON 프롬프트가 **자연어 프롬프트보다 오히려 40% 더 오래 걸리고 이슈가 더 많았다**는 보고가 있습니다. 기계적 포맷보다 **잘 쓴 자연어**가 낫습니다.

**"같은 프롬프트면 같은 답이 나온다"**
LLM은 확률적입니다. 중요한 경우 같은 프롬프트를 **2~3번 돌려** 결과를 비교하면 품질 향상에 유효합니다.

**"프롬프트는 한 번에 완성해야 한다"**
대부분의 프롬프트는 **대화**로 완성됩니다. 첫 응답 후 "아, 이 부분도 추가해 줘"를 3~5번 반복하는 것이 오히려 정상입니다.

**"프롬프트 잘 쓰는 법 = 커닝페이퍼 하나면 끝"**
이 장을 읽고 **자기만의 즐겨찾기 템플릿**을 3개만 만들어도 큰 도약입니다. 거기서부터 **자기 도메인에 맞게** 변형하며 늘려가는 것입니다.

## 8. 핵심 요약

- 좋은 프롬프트는 **목·배·제·입·검** (목표 / 배경 / 제약 / 입출력 / 검증).
- 기계적 JSON보다 **자연어** 가 종종 더 잘 통한다.
- 템플릿 15개를 즐겨찾기 → 상황에 갈아 끼우는 훈련이 실력의 지름길.
- 계획형(Plan-and-Execute), 검증형(Reflection), 안전형(운영 영향) 등 **패턴별 전용 템플릿** 을 구비하면 언제든 꺼내 쓸 수 있다.
- 프롬프트는 **대화**로 완성된다. 한 번에 끝낸다는 환상 버리기.
