# 34. 테스트와 품질 도구 — Vitest · Playwright · pytest · ESLint · Ruff

> **한 줄 요약.** 코드는 "작동하는 것"만으로는 부족하다. 빨리·자동으로 **확인**하고, 통일된 **스타일**로 유지해야 바이브 코딩도 안전하다. 이 장은 이 프로젝트의 테스트·품질 도구 지도다.

> 🔑 **한 마디로.** 테스트는 **AI가 만든 코드를 믿을 이유**이자 **내일의 나를 살려 줄 안전망**이다. AI가 코드를 짜는 시대일수록 "돌려 보는 자동 장치"의 가치가 커진다.

### 테스트/품질 도구를 이해하는 3가지 관점

1. **검증 범위 분리**: 단위 테스트는 작은 로직 검증, E2E는 사용자 흐름 전체 검증으로 역할이 다릅니다.
2. **검증 시점 분리**: 구현 단계에서는 단위 테스트로 빠르게 확인하고, 배포 전에는 E2E로 통합 동작을 확인합니다.
3. **자동 품질 게이트**: 린터·포매터는 문법/스타일/일부 잠재 버그를 자동 검출해 리뷰 부담을 낮춥니다.

### ⚠️ 테스트·품질 도구에서 헷갈리기 쉬운 것들

1. **"테스트 = 커버리지 100%"** — 목표가 아닙니다. **중요한 로직이 커버되는지**가 핵심이고, 맹목적 100%는 오히려 변경에 걸림돌이 됩니다.
2. **"AI가 짠 코드는 따로 테스트 안 해도 돼"** — 정반대입니다. AI는 그럴듯하지만 틀린 코드(hallucinated API 호출, 잘못된 타입)를 종종 만듭니다. **테스트 통과는 머지의 전제 조건**입니다.
3. **"E2E가 최고, 단위 테스트는 보조"** — 반대입니다. E2E는 느리고 깨지기 쉽습니다. **단위가 많고 E2E가 적은 피라미드**가 현실적입니다.
4. **"린트 경고는 스타일 문제라 무시해도 된다"** — 많은 린트 규칙은 **버그 예방** 규칙입니다(예: `no-unused-vars`, `no-floating-promises`). AI가 `// eslint-disable`로 우회하려 할 때가 많습니다. 이를 허용하지 않아야 합니다.
5. **"테스트 쓰면 개발 속도가 느려진다"** — 단기적으론 느립니다. 하지만 **AI 코딩과 결합될 때는 더 빨라집니다**. 테스트가 있으면 AI에게 "이거 다시 짜 봐"를 겁 없이 시킬 수 있기 때문입니다.

## 1. 왜 이 장이 비개발자에게도 중요한가

바이브 코딩으로 AI가 고친 코드를 **신뢰할 수 있는가?** 는 결국 "자동 테스트가 돌아가느냐"에 달려 있습니다. 테스트가 있으면:

- AI가 엉뚱한 코드를 만들었을 때 자동으로 빨간불.
- 한 번 만든 기능이 다음 수정에서 망가지지 않음(회귀 방지).
- 여러분이 "이걸 고쳐도 되나?" 를 덜 두려워하게 됨.

10장의 이론을 이 프로젝트의 실물 도구에 매핑해 봅시다.

## 2. 프런트엔드 테스트 — Vitest + Testing Library

### 2.1 Vitest

- Vite 진영에서 만든 **매우 빠른 테스트 러너**.
- Jest API와 호환돼 학습 비용이 낮음.
- TypeScript 기본 지원.

```ts
// src/lib/format.test.ts
import { describe, it, expect } from 'vitest';
import { toKoreanDate } from './format';

describe('toKoreanDate', () => {
  it('포맷을 YYYY년 M월 D일로 바꾼다', () => {
    expect(toKoreanDate(new Date('2026-04-21'))).toBe('2026년 4월 21일');
  });
});
```

### 2.2 React Testing Library

컴포넌트를 **사용자 관점**으로 테스트.

```tsx
import { render, screen } from '@testing-library/react';
import { Button } from './Button';

test('버튼이 라벨을 보여준다', () => {
  render(<Button>저장</Button>);
  expect(screen.getByRole('button', { name: '저장' })).toBeInTheDocument();
});
```

### 2.3 대안

| 도구 | 비고 |
|---|---|
| **Vitest 4.1** | 우리 선택. Vite와 궁합 완벽. |
| **Jest** | 수년간 표준. React·Node 호환 좋음. |
| **Mocha/Chai** | 오래된 선택. 구성 자유도 높지만 초기 설정 많음. |
| **Node test runner** | Node 20+ 내장. 간단한 라이브러리용. |

### 2.4 Vitest의 주요 흐름

- **더 빠른 격리 모드**: 이전 버전 대비 워커 재사용이 개선되어 CI에서 체감 속도가 눈에 띄게 올랐습니다.
- **Browser mode**: 실제 브라우저에서 테스트를 실행할 수 있어 JSDOM 환경과 실제 브라우저 차이로 인한 버그를 잡는 데 유용합니다(그래도 E2E는 Playwright가 정답).
- **typecheck 모드**: `vitest --typecheck` 로 타입 에러까지 테스트 결과에 포함할 수 있습니다.
- Vite 생태계와의 **설정 공유**(`vite.config.ts` 하나)는 변함없이 Vitest의 가장 큰 장점입니다.

## 3. E2E 테스트 — Playwright

### 3.1 무엇인가

**Playwright**는 마이크로소프트가 만든 **브라우저 자동화·E2E 테스트** 프레임워크입니다. 실제 브라우저(Chromium, WebKit, Firefox)를 실행해 사용자 상호작용을 재현합니다.

```ts
import { test, expect } from '@playwright/test';

test('문서를 만들고 제목을 입력한다', async ({ page }) => {
  await page.goto('/w/doowon-hq/docs');
  await page.getByRole('button', { name: '새 문서' }).click();
  await page.getByPlaceholder('제목').fill('주간 보고');
  await expect(page.getByRole('heading')).toHaveText('주간 보고');
});
```

### 3.2 왜 E2E를 하는가

단위 테스트는 부품이 맞는지, E2E는 **완성품이 돌아가는지**를 확인. 둘 다 필요합니다.

### 3.3 테스트 피라미드(10장 복습)

위부터 아래로:

- **E2E** — 몇 개, 느리지만 사용자 시나리오 전체 커버.
- **Integration** — 여러 단위 연결, 중간 개수.
- **Unit** — 많음, 아주 빠름.

비율을 지키는 것이 포인트. E2E가 너무 많으면 파이프라인이 길어지고 불안정해집니다.

### 3.4 대안

- **Cypress**: 대중적. 개발자 경험 좋음. 다중 브라우저·iframe에 제약.
- **Selenium**: 역사적 표준. 느리고 설정 복잡.
- **Playwright**: 최근 업계 선호. 병렬 실행·자동 대기·다중 탭 등 현대적.

### 3.5 Playwright의 강점

- **Trace Viewer**: 테스트 실행을 **타임라인·스크린샷·네트워크·콘솔 로그와 함께 재생**합니다. 실패한 E2E 테스트 디버깅 시간이 수십 분에서 수 분으로 단축.
- **UI Mode (`playwright test --ui`)**: 로컬에서 테스트를 한 줄씩 실행하며 DOM 상태를 시각적으로 확인.
- **Codegen**: 브라우저에서 사용자 동작을 기록하면 Playwright 스크립트가 자동 생성. 초안 작성에 유용(그대로 쓰지 말고 정제 필요).
- **자동 대기**: `waitFor` 남발 없이도 요소가 준비될 때까지 내부적으로 기다립니다. 이것이 Cypress 대비 큰 장점 중 하나.

## 4. 백엔드 테스트 — pytest

### 4.1 pytest

파이썬의 사실상 표준 테스트 도구. 단순한 함수 `def test_*` 만 있어도 테스트로 인식.

```python
# tests/domains/auth/test_service.py
from ai_do_api.domains.auth.service import verify_password

def test_비밀번호_검증():
    hashed = "..."
    assert verify_password("secret", hashed)
```

### 4.2 Fixture — "테스트용 준비물"

```python
import pytest
from sqlalchemy.orm import Session

@pytest.fixture
def session() -> Session:
    # 테스트 DB 세션 생성
    ...

def test_사용자_저장(session):
    ...
```

Fixture로 공통 준비(DB 연결, 임시 파일)를 한 번만 쓰고, 테스트마다 주입.

### 4.3 FastAPI + httpx로 API 테스트

```python
from httpx import AsyncClient
from ai_do_api.main import app

async def test_로그인():
    async with AsyncClient(app=app, base_url="http://test") as ac:
        resp = await ac.post("/auth/login", json={...})
    assert resp.status_code == 200
```

### 4.4 대안

- **unittest**: 파이썬 표준 라이브러리. 장황함.
- **nose2**: 거의 은퇴.

현대 파이썬에서 pytest 외 다른 선택은 드뭅니다.

### 4.5 pytest 8.3 — 이 프로젝트의 실사용 포인트

- **XFail·Skip 개선**: 환경별로 특정 테스트만 스킵하기 쉬워졌습니다.
- **Warning 관리**: 라이브러리 `DeprecationWarning`을 테스트에서 명시적으로 잡거나 무시하는 API가 정돈됐습니다.
- 비동기 코드는 **`pytest-asyncio`** 플러그인 + `@pytest.mark.asyncio` 로. FastAPI·SQLAlchemy 2.x 비동기 세션을 테스트할 때 필수.
- **`pytest -x --lf`**: "첫 실패에서 멈추고 다음 실행 때 실패한 것만" — AI와 디버깅 루프를 돌릴 때 최고의 조합.

## 5. 린터 · 포매터 — "스타일 경찰"

### 5.1 왜 필요한가

팀이 여러 명이면 코드 스타일이 제각각이 됩니다. **린터**가 버그 가능성을 경고하고, **포매터**가 들여쓰기·따옴표 같은 것을 일괄 정돈.

- 리뷰 시간 감소 — "세미콜론 넣으세요" 같은 코멘트가 사라짐.
- 휴먼 에러 감소 — "사용하지 않는 변수", "변수 이름 중복" 자동 감지.
- AI 협업에 유리 — AI가 제안한 코드를 자동 포맷해 팀 스타일로 통일.

### 5.2 JS/TS: ESLint + Prettier

- **ESLint 9**: 문법·버그·스타일 검사. `typescript-eslint` 플러그인 + 우리 커스텀 `eslint-plugin-ai-do`.
- **Prettier**: 포매팅 전담. 들여쓰기·줄바꿈·따옴표 등.

```bash
pnpm lint
pnpm format
```

### 5.3 Python: Ruff

**Ruff 0.11** 은 Rust로 작성된 초고속 파이썬 린터·포매터. 2023년 이후 사실상 표준.

- `flake8` + `isort` + `black` + `pyflakes` + 수많은 플러그인을 **단일 도구**로 대체.
- 속도가 기존 도구 대비 **수십 배 빠름** (대형 코드베이스에서 초 단위 → 밀리초 단위).
- `pyproject.toml` 한 파일로 설정 통합.
- `ruff format` 은 black과 99% 호환. 팀이 black에서 옮겨올 때 **마찰 거의 0**.

```bash
ruff check .       # 린트
ruff format .      # 포맷
ruff check --fix . # 자동 수정 가능한 것 고치기
```

### 5.4 JS/TS 도구 풍경

우리 프로젝트는 **ESLint 9 + Prettier** 를 유지하지만, 커뮤니티에는 Ruff와 비슷한 철학의 차세대 도구가 있습니다.

| 도구 | 성격 | 비고 |
|---|---|---|
| **Biome** | Rust 기반 린터+포매터 통합 | ESLint+Prettier 대체 시도. 아직 플러그인 생태계 부족. |
| **Oxlint** | Rust 기반 린터 | 매우 빠르지만 ESLint 규칙 커버리지 미완. |
| **ESLint 9 (Flat Config)** | 전통 강자 | 우리 선택. 플러그인·규칙이 압도적이고 `eslint-plugin-ai-do` 같은 커스텀 규칙도 확장 가능. |

Python의 Ruff가 흐름을 바꿨듯, JS/TS도 통합 도구 방향으로 가는 중입니다. 다만 **전환 타이밍은 생태계 성숙도를 본 뒤**가 정답입니다.

### 5.5 에디터 연동

대부분의 코드 에디터에서 파일 저장 시 자동 포맷. 여러분이 신경 쓰지 않아도 저장하는 순간 정돈됨.

## 6. 타입 체크 — `tsc` & `mypy`/`pyright`

### 6.1 TypeScript

- `tsc --noEmit` 이 CI에서 돌며 타입 에러 검사.
- 대부분의 코드 에디터는 편집 중에도 실시간 체크.

### 6.2 Python

- 정적 타입 힌트는 선택이지만 이 프로젝트는 `typing` 기반 힌트를 폭넓게 씀(Pydantic과 합). mypy·pyright로 검사 가능.
- Ruff도 기본 체크 일부를 커버.

타입 검사는 **실행 전에 버그를 잡는** 가장 싼 방법이며, AI 코드 검토에도 큰 도움.

## 7. 커밋 훅 · CI

### 7.1 pre-commit

커밋 직전에 포매터·린터·타입 검사를 자동 실행. 나쁜 코드가 저장소에 들어가지 못하게.

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    hooks: [{id: ruff}, {id: ruff-format}]
  - repo: local
    hooks:
      - id: eslint
        name: eslint
        entry: pnpm lint
        language: system
```

### 7.2 CI 파이프라인 요약

GitHub Actions · GitLab CI 등으로 Push/PR마다:
1. `pnpm install --frozen-lockfile`
2. `pnpm lint && pnpm typecheck`
3. `pnpm test` (Vitest)
4. `uv sync && pytest` (API)
5. `playwright test` (E2E)
6. 실패 시 PR 머지 차단.

### 7.3 Coverage

테스트 커버리지(라인 중 몇 %가 테스트됐는지). 100%가 목적은 아니고, **중요한 로직이 커버되는지** 가 핵심.

## 9. 바이브 코딩 관점의 팁

- **테스트부터 주기**: AI에 "이 함수에 대한 테스트부터 써 줘"라고 먼저 시키면, 기대치가 명확해져 AI 구현 품질이 오릅니다.
- **실패 테스트를 복붙**: 테스트가 실패하면 그대로 AI에게 붙여넣고 "고쳐 줘". 가장 빠른 디버깅 루프.
- **린트 경고를 무시하지 말 것**: AI가 종종 경고를 무시하려 시도합니다. "무시하지 말고 수정"하도록 지시해야 합니다.
- **작은 PR**: 바이브 코딩의 결과는 매 단계 커밋·푸시·테스트. 큰 덩어리로 쌓이면 AI도 여러분도 통제를 잃습니다.
- **"AI가 짠 코드도 테스트 통과해야 머지"**: 이것이 유일한 룰입니다. 아무리 그럴듯해 보여도 테스트·린트·타입 체크가 통과하지 않으면 `main`에 들어갈 수 없습니다. 사람이 작성한 코드와 동일한 잣대를 AI 생성 코드에도 적용하는 것이 **일관된 품질의 유일한 보장**입니다.

### 🏢 고친 건 맞지만 옆 기능이 터졌을 때

상황: AI에게 "캘린더 필터 로직 좀 고쳐 줘"라고 시켜 머지했더니, 며칠 후 "공휴일 토글이 안 먹어요"라는 버그 제보가 들어옴. 원인 분석 시 AI가 옆 기능의 훅을 함께 수정했던 것이 드러납니다.

- 예방책 1: **PR마다 전체 테스트 실행** (Nx `affected` 로 영향 범위만 돌려도 됨).
- 예방책 2: 해당 훅에 **회귀 테스트**가 있었다면 CI에서 바로 빨간불.
- 예방책 3: AI에게 수정 요청 전 "변경 계획부터 제시해" 프롬프트로 영향 범위 확인.

즉 **테스트는 AI 리팩토링의 안전벨트**입니다.

### 🛠️ 5분 실습 — 실패하는 테스트 만들어 보기

```bash
# 1. 프런트 테스트 하나 새로 추가
# apps/web/src/lib/__tests__/example.test.ts
# 2. 일부러 실패하는 단언을 넣는다
# expect(1 + 1).toBe(3);

pnpm vitest run apps/web/src/lib/__tests__/example.test.ts
# 빨간불 확인 → AI에게 "이 테스트 지나가게 로직 바꿔 줘" 또는
# "이 테스트가 맞게 작성됐는지 검토해 줘"
```

"빨간불 → 초록불"의 **루프 감각**이 바이브 코딩의 핵심입니다.

## 10. 핵심 요약

- 프런트: **Vitest**(단위) + **React Testing Library** + **Playwright**(E2E).
- 백엔드: **pytest** + httpx.
- 스타일: **ESLint + Prettier (JS/TS)** · **Ruff (Python)**.
- 타입 검사: `tsc`, (선택) mypy/pyright.
- 자동화: **pre-commit** + **Nx** + **CI**.
- 테스트는 바이브 코딩의 안전망. 없으면 AI 결과를 믿을 수 없음.
