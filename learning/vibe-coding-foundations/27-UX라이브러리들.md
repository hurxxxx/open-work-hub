# 27. UX 라이브러리들 — FullCalendar, dnd-kit, TanStack Table, Recharts

> **한 줄 요약.** 달력·드래그앤드롭·테이블·차트는 직접 만들면 끝이 없어서 각 분야의 **최강 라이브러리**를 가져다 쓴다. 이 장은 이 프로젝트에 들어가 있는 네 가지 특수 UX 도구의 지도다.

> **🔑 한 마디로.** "달력·드래그·표·차트"는 업무 웹 어디에나 들어가는 뻔한 UI 네 가지인데, 이걸 잘 만든 전문 팀의 완성품을 그대로 수입해서 쓴다는 뜻입니다. 우리가 할 일은 고르고·조립하고·우리 디자인에 맞추는 것.

### 왜 전문 라이브러리를 조합하는가

- 달력·드래그·테이블·차트는 복잡도가 높아 검증된 전문 라이브러리를 사용하는 것이 개발/유지보수 비용 측면에서 유리합니다.
- 공통 UX 기능은 외부 라이브러리로 해결하고, 도메인 고유 로직과 통합 흐름에 개발 역량을 집중합니다.
- 기본 UI는 내부 컴포넌트로 유지하고, 고난도 상호작용은 전용 라이브러리 기능을 활용하는 하이브리드 전략이 효과적입니다.

### ⚠️ 라이브러리 도입에서 자주 하는 오해

- **"라이브러리 4개면 앱이 4배 무거워지겠다"** — Vite의 **Tree Shaking**(쓰지 않는 코드 자르기)이 실제 사용된 부분만 번들에 포함해, 기능 대비 놀라울 정도로 가볍습니다.
- **"유명 라이브러리니까 우리 디자인과 알아서 어울리겠지"** — TanStack Table은 디자인이 **아예 없습니다**(헤드리스). FullCalendar는 기본 디자인이 있지만 우리 Mantine 톤과 색·간격을 맞추는 CSS 작업이 필요합니다.
- **"오픈소스면 비용과 제약이 전혀 없다"** — FullCalendar는 MIT 버전과 상용(Premium) 버전이 나뉩니다. 우리는 오픈소스 플러그인으로 충분하지만 "리소스 뷰" 같은 고급 기능은 Premium입니다.
- **"드래그앤드롭은 마우스 코드 몇 줄이면 된다"** — 키보드로만 쓰는 사용자, 스크린 리더 사용자까지 고려하면 **접근성** 처리가 매우 복잡합니다. dnd-kit이 그 책임을 떠맡아 줍니다.
- **"차트는 예쁜 게 최고다"** — 데이터가 많아질 때 속도, 반응형, 색각 이상(color-blind) 사용자 배려가 디자인보다 중요합니다.

## 1. FullCalendar — 캘린더의 사실상 표준

### 1.1 무엇인가

**FullCalendar** 는 2007년부터 발전해 온 대표적인 JavaScript 캘린더 라이브러리입니다. Google Calendar, Outlook과 유사한 UI를 React·Vue·Angular에서 쉽게 구현할 수 있게 해 줍니다.

### 1.2 이 프로젝트의 FullCalendar 조각

```
@fullcalendar/core
@fullcalendar/react
@fullcalendar/daygrid    (월간 달력)
@fullcalendar/timegrid   (주간/일간 시간표)
@fullcalendar/list       (목록형 뷰)
@fullcalendar/interaction (드래그·클릭)
@fullcalendar/luxon3     (Luxon 시간 라이브러리 통합)
```

**플러그인 기반 아키텍처**입니다. 필요한 뷰만 골라 붙입니다.

### 1.3 주요 기능

- 월/주/일 뷰 전환
- 이벤트 드래그로 시간 이동
- 반복 이벤트(rrule)
- 타임존 처리 (→ Luxon 플러그인)
- 한국어 로케일

### 1.4 이 프로젝트에서의 용도

- `apps/web/src/domains/calendar/` — 개인·팀 캘린더
- `apps/web/src/domains/meeting/` — 회의실·회의 일정
- `apps/web/src/domains/planner/` — 플래너·일정 계획

### 1.5 한국 공휴일 처리

`package.json` 의존성에 `@hyunbinseo/holidays-kr` 가 있습니다. 한국 법정 공휴일(대체 공휴일 포함) 데이터를 제공하는 라이브러리. FullCalendar의 이벤트로 주입해 "빨간 날"을 표시합니다. `docs/product/korean-holidays.md` 도 이 주제를 다룹니다.

### 1.6 대안

| 라이브러리 | 비고 |
|---|---|
| **FullCalendar 6.1** | 우리 선택. 기능·안정성 최강. 오픈소스 버전으로 충분. |
| React Big Calendar | 가볍지만 기능 부족. |
| Scheduler Pro (Bryntum) | 유료. 고급 기능. |
| 직접 구현 | 시간 낭비. |

### 1.7 🏢 업무 시나리오

**케이스 — 팀 캘린더에 "휴가·회의·외근"을 색으로 구분**
- AI-DO Portal `/calendar` 도메인에 세 종류 이벤트 소스를 FullCalendar에 넣습니다. 휴가(빨강), 회의(파랑), 외근(회색). 공휴일 레이어는 `@hyunbinseo/holidays-kr`.
- 이벤트를 드래그해서 다른 날로 옮기면 `eventDrop` 콜백이 FastAPI의 `PATCH /calendar/events/{id}` 를 호출합니다. 사용자가 한 기능을 누릴 때 프런트의 FullCalendar·React Query·백엔드가 함께 움직이는 좋은 사례입니다.

## 2. dnd-kit — 현대적 드래그앤드롭

### 2.1 무엇인가

**dnd-kit** 은 2021년 등장해 빠르게 React의 드래그앤드롭 표준이 됐습니다. 이전의 `react-dnd`를 대체하는 흐름입니다.

장점:
- **접근성**: 키보드·스크린 리더 지원 내장.
- **작다**: 코어가 10KB 안쪽.
- **유연**: 복잡한 정렬, 중첩 드롭, 다중 컨테이너 모두 지원.
- **React 중심**: 훅 기반 API.

### 2.2 이 프로젝트의 dnd-kit

```
@dnd-kit/core
@dnd-kit/sortable     (정렬 가능 리스트)
@dnd-kit/utilities
```

### 2.3 용도

- **PMS 보드** — 이슈 카드를 컬럼 간 이동 (칸반 보드)
- **리스트 순서 변경** — 문서 페이지 순서, 메뉴 순서
- **에디터** — BlockNote 내부 블록 이동(BlockNote가 일부 내부적으로 사용)

### 2.4 개념적 예시

```tsx
import { DndContext, closestCenter } from '@dnd-kit/core';
import { SortableContext, arrayMove } from '@dnd-kit/sortable';

function KanbanBoard() {
  const [items, setItems] = useState(['카드1', '카드2', '카드3']);
  
  return (
    <DndContext
      collisionDetection={closestCenter}
      onDragEnd={(event) => {
        const { active, over } = event;
        if (active.id !== over.id) {
          setItems(arrayMove(items, 
            items.indexOf(active.id),
            items.indexOf(over.id)));
        }
      }}
    >
      <SortableContext items={items}>
        {items.map(id => <SortableItem key={id} id={id} />)}
      </SortableContext>
    </DndContext>
  );
}
```

### 2.5 대안

- **react-dnd**: 원조. 옛 코드 베이스에 남아 있음. 접근성 약함.
- **hello-pangea/dnd**: `react-beautiful-dnd`의 후계. 리스트 정렬에 강함.
- **dnd-kit**: 유연하고 접근성·성능·훅 기반 API가 좋아 우리 선택.

### 2.6 🏢 업무 시나리오

**케이스 — PMS 칸반 보드에서 "검토중 → 완료"로 이슈 카드 옮기기**
- 컬럼(To do / In progress / Review / Done) 4개를 `DndContext`로 감쌉니다.
- 카드를 Review에서 Done으로 드래그하면 `onDragEnd`에서 상태 전이 API를 호출.
- **키보드 접근성 보너스**: 마우스가 안 되는 사용자는 카드에 포커스를 두고 스페이스·화살표로 이동할 수 있습니다. 이것이 dnd-kit을 고른 핵심 이유.

## 3. TanStack Table — "헤드리스" 테이블의 최강자

### 3.1 무엇인가

**TanStack Table** (구 react-table, 버전 8.21 사용) 은 테이블의 **로직**만 제공하는 헤드리스(headless, 머리 없는 — UI 없이 훅만) 라이브러리입니다. 스타일은 우리가 Mantine·Tailwind로 붙입니다.

"헤드리스"는 정렬·필터·페이지네이션 같은 로직만 제공하고 UI는 제공하지 않는 방식입니다. 그래서 우리 디자인 시스템(Mantine/Tailwind)과 충돌 없이 결합할 수 있습니다.

제공하는 것:
- 정렬(sort), 필터(filter), 페이지네이션
- 컬럼 그룹, 리사이즈, 드래그
- 가상 스크롤(수만 행)
- 행 선택, 확장(expand)

### 3.2 왜 헤드리스인가

디자인 시스템마다 스타일이 다르기에, **로직과 스타일을 분리**하는 것이 재사용에 유리합니다. Mantine의 Table 컴포넌트와 TanStack Table의 `useReactTable` 훅을 조합하면, 우리 디자인을 유지하면서 강력한 테이블 기능을 얻습니다.

### 3.3 이 프로젝트의 TanStack Table

```
@tanstack/react-table v8
```

### 3.4 용도

- **관리자 콘솔**: 사용자 목록, 워크스페이스 목록, 감사 로그
- **PMS**: 이슈 목록 테이블
- **각종 데이터 뷰**

### 3.5 개념적 예시

```tsx
import {
  useReactTable,
  getCoreRowModel,
  getSortedRowModel,
  getPaginationRowModel
} from '@tanstack/react-table';

const columns = [
  { accessorKey: 'email', header: '이메일' },
  { accessorKey: 'displayName', header: '이름' },
  { accessorKey: 'createdAt', header: '가입일' }
];

function UserTable({ users }) {
  const table = useReactTable({
    data: users,
    columns,
    getCoreRowModel: getCoreRowModel(),
    getSortedRowModel: getSortedRowModel(),
    getPaginationRowModel: getPaginationRowModel()
  });
  return (
    <table>
      <thead>...</thead>
      <tbody>...</tbody>
    </table>
  );
}
```

### 3.6 대안

| 라이브러리 | 비고 |
|---|---|
| **TanStack Table 8.21** | 우리 선택. 헤드리스 강자. |
| AG Grid | 기능 최상, 상업적 쓰임 많음. 무겁고 라이선스 비용 있음. |
| Material Table | MUI 종속. |
| mantine-react-table | Mantine + TanStack 합본. |

### 3.7 🏢 업무 시나리오

**케이스 — 관리자 콘솔 "사용자 목록 1만 명" 화면**
- 이름·이메일·가입일·권한 컬럼. 사용자 1만 명이어도 가상 스크롤(virtual scroll, 보이는 행만 그리기)로 60fps 유지.
- 검색창에 "kim"을 치면 필터 훅이 즉시 반응. 헤더 클릭으로 정렬 방향 토글. 페이지네이션은 서버 사이드(백엔드가 offset/limit 반환)로 구성.
- UI는 전부 Mantine `Table` + Tailwind 간격 유틸리티로 입힌다는 점이 핵심.

## 4. Recharts — 친숙한 React 차트

### 4.1 무엇인가

**Recharts** 는 React와 D3(Data-Driven Documents, 시각화의 저수준 엔진)를 결합한 차트 라이브러리입니다. 2016년 출시, 가장 널리 쓰이는 React 차트 라이브러리 중 하나. 한 문장으로 "D3 위에 JSX로 쉽게 쓰도록 포장한 것".

특징:
- 선언형 API(`<BarChart>`, `<XAxis>` 처럼 JSX로)
- SVG 기반
- 반응형 크기(기본 제공)
- 애니메이션

### 4.2 이 프로젝트의 Recharts

```
recharts v3
```

### 4.3 용도

- **PMS 대시보드** — 마일스톤 진행률, 이슈 상태 분포
- **관리자** — 사용자 활동 추이, 스토리지 사용량
- **회의 분석** — 주별 회의 시간 통계

### 4.4 개념적 예시

```tsx
import { BarChart, Bar, XAxis, YAxis, Tooltip } from 'recharts';

const data = [
  { week: 'W1', meetings: 12 },
  { week: 'W2', meetings: 18 },
  { week: 'W3', meetings: 9 }
];

<BarChart width={600} height={300} data={data}>
  <XAxis dataKey="week" />
  <YAxis />
  <Tooltip />
  <Bar dataKey="meetings" />
</BarChart>
```

### 4.5 대안

- **Chart.js**: Canvas 기반, 대량 데이터에 유리. 비-React.
- **Apache ECharts**: 기능 매우 풍부. 학습 비용 있음.
- **Visx**: 저수준. 커스텀에 강함.
- **Tremor**: 대시보드 전용, shadcn 스타일.
- **Nivo**: D3 기반, 애니메이션 강함.

### 4.6 🏢 업무 시나리오

**케이스 — PMS 대시보드 "이번 분기 마일스톤 진행률"**
- 백엔드 `/pms/milestones/stats`가 주 단위로 완료·진행·지연 건수를 반환.
- Recharts `<BarChart>` + 세 개 `<Bar>` 계열로 누적 막대. 반응형 컨테이너(`<ResponsiveContainer>`)를 씌우면 좌우 패널 크기가 바뀔 때 자동 리사이즈.
- 색은 Mantine 테마 토큰(`var(--mantine-color-blue-6)`)을 CSS 변수로 주입해 다크/라이트 테마에도 대응.

## 5. 기타 주목할 의존성들

### 5.1 `lucide-react`

오픈소스 아이콘 세트. Feather Icons의 후속. 우리 프로젝트 전반에 아이콘으로 사용.

### 5.2 `motion` (Framer Motion)

선언형 애니메이션 라이브러리. "`<motion.div animate={{ opacity: 1 }} />`" 같은 식. 부드러운 UX의 핵심.

### 5.3 `react-markdown` + `remark-gfm` + `rehype-highlight` + `highlight.js`

마크다운 렌더링 파이프라인. AI 응답을 **마크다운으로 받아 HTML로 렌더**할 때 쓰입니다.

- `react-markdown` — 메인 렌더러
- `remark-gfm` — GitHub Flavored Markdown(테이블, 취소선 등)
- `rehype-highlight` + `highlight.js` — 코드 블록 하이라이팅

### 5.4 `dompurify` + `@types/dompurify`

HTML을 안전하게 **정화**하는 라이브러리. 사용자가 입력한 HTML에서 `<script>` 같은 것을 제거해 **XSS 공격**을 막습니다.

### 5.5 `eventsource-parser`

SSE(32장)의 이벤트 스트림을 파싱. AI 응답을 한 글자씩 받아올 때 사용.

### 5.6 `class-variance-authority`, `clsx`, `tailwind-merge`

24장에서 본 스타일 조합 유틸들.

## 6. 라이브러리가 이렇게 많은데 괜찮나?

"의존성이 너무 많은 거 아닌가?"는 자연스러운 우려입니다. 대응:

1. **각 라이브러리가 맡는 영역이 구분돼 있다.** 중복 없음.
2. **Vite + Tree Shaking**으로 실제 빌드에는 **쓰는 것만** 들어감.
3. **대부분 업계 표준**이라 유지보수·AI 지원이 풍부.
4. **버전 업그레이드**를 주기적으로 (분기 1회 정도) 해야 함 — 별도 관리.

### 6.1 🛠️ 5분 실습 — "데모 사이트 3곳만 눌러 보기"

1. FullCalendar 공식 데모(`fullcalendar.io/demos`)에서 "Drag & Drop" 달력을 열고, 이벤트를 마우스로 끌어 옮겨 봅니다.
2. dnd-kit 스토리북에서 "Sortable List" 예제를 열고, **Tab 키**로 항목에 포커스 → **스페이스 → 화살표**로 키보드만으로 정렬을 바꿔 봅니다.
3. Recharts 공식 예제에서 `BarChart` 샘플의 `data` 배열 값을 직접 바꿔(브라우저 개발자도구 → React DevTools) 막대가 즉시 반응하는 것을 확인.

5분 안에 "아, 이 세 라이브러리는 정말 완성품이구나"가 체감됩니다.
