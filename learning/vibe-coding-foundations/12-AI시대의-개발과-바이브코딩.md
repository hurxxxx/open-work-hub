# 12. AI 시대의 개발과 바이브 코딩

> **한 줄 요약.** 2023년 이후 개발의 풍경은 근본적으로 바뀌었다. **LLM**이 코드의 대부분을 직접 써 주고, 개발자는 **"무엇을 시킬지, 어떤 맥락을 줄지, 결과가 맞는지"**를 판단한다. 이 새로운 작업 방식이 **바이브 코딩**이다.

---

## 1. LLM은 무엇인가 (최소한의 이해)

**LLM(Large Language Model, 대규모 언어 모델)** 은 엄청난 양의 텍스트로 학습해 "다음 단어"를 예측하도록 훈련된 인공지능입니다. 대표: OpenAI의 **GPT** 계열, Anthropic의 **Claude** 계열, Google의 **Gemini**, Meta의 **Llama**.

LLM이 하는 일은 단순합니다. **"앞 문맥을 보고 그다음으로 올 확률 높은 토큰을 고르기"** 를 아주 잘합니다. 이 단순한 능력이 엄청난 다재다능함으로 나타나는 이유는 텍스트에 "요약, 번역, 코드 작성, 추론, 질의응답" 등 **세상의 거의 모든 지적 활동이 녹아 있기 때문** 입니다.

### 1.1 컨텍스트 윈도우

LLM은 한 번에 처리할 수 있는 텍스트 양이 정해져 있습니다. 이를 **컨텍스트 윈도우(context window)** 라 합니다. 2025년 기준 주요 모델은 20만 토큰 이상. 토큰은 대체로 한글 0.7글자/영어 4글자당 1개 정도입니다.

컨텍스트에 들어가지 않은 정보는 LLM이 모릅니다. 그래서 **"맥락을 잘 집어 넣어 주는 것"** 이 바이브 코딩의 핵심입니다.

### 1.2 한계 — 환각(Hallucination)과 최신성

- **Hallucination**: 그럴듯하지만 사실이 아닌 것을 만들어낼 수 있음. 특히 라이브러리 API, 파일 경로에서 자주 발생.
- **지식 컷오프**: 학습 시점 이후의 정보는 모름. 최신 라이브러리 변경 등.

→ 그래서 **검증** 이 인간의 역할입니다.

## 2. 바이브 코딩(Vibe Coding)의 본질

2025년 초 Andrej Karpathy가 트윗에서 쓴 말이 유행하면서 일반명사가 됐습니다. 그의 말을 요약하면:

> "코드를 보는 게 아니라 **결과물을 보면서** AI와 대화로 조정해 나가는 방식."

전통적 프로그래밍과의 대비는 1장에서 이미 봤습니다. 여기서는 한 단계 더 들어갑니다.

### 2.1 바이브 코딩의 3단계 루프

```
  ┌──────────────────────────┐
  │ 1. 의도를 말한다          │
  │ 2. AI가 변경을 제안한다   │
  │ 3. 사람이 검증한다        │
  └──────────────────────────┘
        ↑                ↓
        └── 피드백 ──────┘
```

이 루프가 몇 초~몇 분 안에 돌아가는 것이 이상적입니다. 사람은 루프를 **빨리 돌릴 수 있는 환경** 을 만들어야 합니다(작은 테스트, 빠른 빌드, 쉬운 롤백).

### 2.2 "왜 AI에게 맥락을 줘야 하는가"

LLM은 우리 프로젝트를 **모릅니다**. 학습 데이터에 없습니다. 그래서 질문할 때 반드시 **맥락(context)** 을 줘야 합니다. 맥락 종류:

1. **코드 맥락** — 관련 파일, 함수, 타입
2. **의도 맥락** — 무엇을 하려는지, 왜
3. **제약 맥락** — 하면 안 되는 것, 성능 기준, 보안 요구
4. **예시 맥락** — 비슷한 이미 되어 있는 예시

맥락이 부실하면 AI는 **"그럴듯하지만 틀린"** 답을 줍니다. 그래서 실력의 본질이 **"맥락을 잘 정리해 주는 능력"** 이 됐습니다.

## 4. 프롬프트 엔지니어링 — "AI에게 잘 시키는 기술"

프롬프트(prompt)는 LLM에게 주는 지시문입니다. 좋은 프롬프트의 공통 요소:

### 4.1 역할·목표 명시

❌ "로그인 만들어줘"
✅ "우리는 FastAPI + Pydantic 기반 백엔드이고, ID/PW 기반 로그인을 구현하려 해. JWT 대신 서버 세션을 쓴다. `/login` POST 엔드포인트를 만들어 줘."

### 4.2 입력·출력 명세

✅ "입력은 `{email, password}` JSON. 출력은 성공 시 `{user_id, session_id}`, 실패 시 401 + `{error, message}`."

### 4.3 제약 조건

✅ "비밀번호는 bcrypt로 검증. 연속 5회 실패 시 5분 잠금."

### 4.4 예시 제공

✅ "우리 프로젝트의 기존 엔드포인트 `/logout` 이 이런 식이야: [코드 붙여넣기]. 동일한 스타일을 따라줘."

### 4.5 단계 지시

✅ "1) 라우터에 엔드포인트 추가 2) 서비스 레이어에 로직 3) 실패 테스트부터 쓰고 4) 성공 테스트 추가 5) 마지막에 PR용 요약."

이런 프롬프트 한 번이 **여러 번의 수정 왕복** 을 절약합니다.

## 5. 에이전트(Agent) — 자율적으로 일하는 AI

LLM이 단순 "응답"만 하는 것이 아니라, **도구를 불러오고 결과를 보고 다음 수를 두는** 것을 에이전트라 부릅니다. Claude Code, Cursor의 "Agent 모드"가 모두 이에 해당합니다.

에이전트의 기본 루프:

```
관찰 → 사고 → 행동(도구 호출) → 관찰 → ...
```

"ReAct(Reason + Act) 패턴"이라고 부릅니다. 2022년 논문에서 체계화됐습니다.

에이전트에게 주는 도구 예: 파일 읽기, 파일 쓰기, 셸 실행, 웹 검색, DB 조회. AIDOO Portal이 자체적으로 만들고 있는 AI 기능도 **사내용 에이전트** 입니다. 도구들이 사내 데이터와 연결돼 있어 **훨씬 유용한 비서** 가 됩니다.

---

## 6. MCP — Model Context Protocol

Anthropic이 2024년 11월에 공개한 **개방형 표준** 입니다. AI에게 "도구를 붙이는 규약"을 표준화했습니다.

비유: 이전에는 AI마다, 앱마다 다른 방식으로 도구를 붙였습니다("USB 포트가 제조사마다 다른 시대"). MCP는 이것을 **USB 표준처럼 통일** 하려 합니다.

- **MCP Server**: 도구를 제공하는 쪽. 예: "회의실 예약 툴을 제공"
- **MCP Client**: AI 측. 서버에 물어 도구 목록을 받고, 필요할 때 호출.

### 6.1 우리 프로젝트의 MCP

`adr/0002-mcp-capability-platform.md` 가 이 프로젝트의 핵심 설계 결정입니다. 요약:

- **AI 능력(capability)을 MCP 방식으로 등록**.
- 각 능력은 **human-friendly REST DTO** 와 **AI-friendly Pydantic DTO** 를 따로 가짐.
- **발견(discoverability) 규칙, 미리보기(preview), 승인(approval)** 을 능력 선언에 포함.
- 이 덕분에 에이전트가 **사용자 권한 맥락 안에서만** 도구를 고를 수 있음.

즉, 우리 포털의 AI는 "도구를 붙이는 아주 많은 것이 추가될" 예정이며, 그 추가가 매번 앱 수정으로 이어지지 않도록 **플러그인 스타일의 확장성** 을 미리 설계해 둔 것입니다. 자세한 해설은 32장.

## 7. RAG (Retrieval-Augmented Generation) — 맥락 주입의 표준

LLM이 모르는 것(사내 데이터, 최신 문서)을 **검색해서 프롬프트에 넣어 주는 기법** 입니다.

```
질문: "3월 이사회 결의사항 요약해 줘"
  ↓
[벡터 DB에서 관련 문서 3개 검색]
  ↓
"참고 문서: ... 질문: 3월 이사회 ..."
  ↓
LLM → 답변
```

- **임베딩(embedding)**: 문서를 수치 벡터로 변환.
- **벡터 DB**: Chroma, Pinecone, pgvector(PostgreSQL 확장).

이 프로젝트는 아직 RAG를 본격 도입하지 않았지만, 위키/문서 검색이 성숙하면 자연스러운 다음 단계입니다.

## 8. AI 시대의 개발자 역량 재편

과거에 중요했던 역량 vs 지금도 중요한 역량:

| 덜 중요해진 것 | 더 중요해진 것 |
|---|---|
| 언어 문법 암기 | 문제를 잘 쪼개는 능력 |
| 라이브러리 이름 외우기 | 좋은 맥락을 구성하는 능력 |
| 빠른 타이핑 | 좋은 질문을 하는 능력 |
| 혼자서 다 아는 것 | AI 제안을 비판적으로 평가하는 능력 |

그리고 **여전히** 중요한 것:

- **도메인 지식** (이 업무가 뭘 의미하는지)
- **시스템 감각** (어디에 무엇이 있고, 왜 그런지)
- **책임감** (AI가 만든 결과도 내 것)

## 9. 실전 수칙 — 우리 TF가 지킬 5가지

1. **항상 브랜치에서 작업.** 바로 main에 푸시 금지.
2. **작게 묻고 자주 커밋.** 한 번에 거대한 작업을 AI에 시키지 않기.
3. **출력한 코드를 읽기.** 이해가 안 되는 코드는 머지하지 않기.
4. **테스트도 같이 만들게 시키기.** 새 기능엔 새 테스트.
5. **AI의 말이 이상하면 그만두고 사람이 생각.** 무한 반복 수정은 AI의 잘못이 아니라 맥락이 부실한 것.

---

## 10. 핵심 요약

- LLM은 **다음 토큰 예측기** 이다. 맥락을 잘 주면 거의 다 할 수 있지만, 환각 위험을 안는다.
- 바이브 코딩 = **의도 전달 → AI 제안 → 사람 검증** 의 빠른 루프.
- 좋은 프롬프트는 **역할, 입력·출력, 제약, 예시, 단계** 를 포함.
- 에이전트(ReAct) + 도구 호출이 AI의 새로운 표준. **MCP** 는 그 도구 연결의 개방 표준.
- 우리 프로젝트는 **MCP 퍼스트 능력 플랫폼** 을 목표로 설계됨.
- AI 시대에도 **도메인 지식 + 시스템 감각 + 책임감** 은 여전히 사람의 몫.
