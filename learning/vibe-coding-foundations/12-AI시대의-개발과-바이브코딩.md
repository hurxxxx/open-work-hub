# 12. AI 시대의 개발과 바이브 코딩

> **한 줄 요약.** 2023년 이후 개발의 풍경은 근본적으로 바뀌었다. **LLM**이 코드의 대부분을 직접 써 주고, 개발자는 **"무엇을 시킬지, 어떤 맥락을 줄지, 결과가 맞는지"** 를 판단한다. 이 새로운 작업 방식이 **바이브 코딩(vibe coding)** 이고, 2026년 초부터 업계는 이를 **에이전틱 엔지니어링(agentic engineering)** 으로 재정의하고 있다.

---

## 1. LLM은 무엇인가 (최소한의 이해)

**LLM(Large Language Model, 대규모 언어 모델)** 은 엄청난 양의 텍스트로 학습해 "다음 단어"를 예측하도록 훈련된 인공지능입니다. 대표: OpenAI의 **GPT** 계열, Anthropic의 **Claude** 계열, Google의 **Gemini**, Meta의 **Llama**, 중국 DeepSeek·Alibaba의 **Qwen**.

LLM이 하는 일은 단순합니다. **"앞 문맥을 보고 그다음으로 올 확률 높은 토큰(token, 글자의 부분 조각)을 고르기"** 를 아주 잘합니다. 이 단순한 능력이 엄청난 다재다능함으로 나타나는 이유는 텍스트에 "요약, 번역, 코드 작성, 추론, 질의응답" 등 **세상의 거의 모든 지적 활동이 녹아 있기 때문** 입니다.

### 1.1 컨텍스트 윈도우

LLM은 한 번에 처리할 수 있는 텍스트 양이 정해져 있습니다. 이를 **컨텍스트 윈도우(context window, 한 번에 보는 창)** 라 합니다. 2026년 4월 기준 주요 프런티어 모델은 **100만(1M) 토큰** 까지 지원합니다(Claude Opus 4.7, Sonnet 4.6, Gemini 3 Pro). 토큰은 대체로 한글 0.7글자/영어 4글자당 1개 정도입니다. 100만 토큰은 대략 A4 **2,000페이지** 분량입니다.

컨텍스트에 들어가지 않은 정보는 LLM이 모릅니다. 그래서 **"맥락을 잘 집어 넣어 주는 것"** 이 바이브 코딩의 핵심입니다.

### 1.2 한계 — 환각(Hallucination)과 최신성

- **Hallucination(환각)**: 그럴듯하지만 사실이 아닌 것을 만들어낼 수 있음. 특히 라이브러리 API, 파일 경로에서 자주 발생. GPT-5 이후 환각률이 약 **45% 감소**했다고 보고되지만 여전히 **사라지지는 않았다**.
- **지식 컷오프(knowledge cutoff)**: 학습 시점 이후의 정보는 모름. 최신 라이브러리 변경 등.

→ 그래서 **검증** 이 인간의 역할입니다.

### 1.3 신입 직원, 통역사, 타자수

- **엄청나게 책을 많이 읽은 신입 직원**: 지식의 폭은 넓지만, **우리 회사 사정은 모른다**. 업무 설명서(컨텍스트)를 안 주고 일을 시키면 **그럴듯하게 지어내는** 실수를 한다.
- **외국인 통역사**: 문법·어휘는 완벽하지만, 회의에서 오가는 **업계 관행·내부 약어**를 모르면 번역이 엇나간다.
- **검색+요약 엔진이 내장된 타자수**: 빠르고 정확히 쓰지만, 무엇을 쓸지 정하는 건 사람 몫.

### 1.4 ⚠️ 바로잡고 싶은 오해

- **"LLM이 생각한다"** — 기능적으로는 **다음 토큰의 확률을 예측하는 것**이다. 결과가 사고처럼 보일 뿐이다.
- **"컨텍스트가 크면 클수록 답이 좋다"** — 오히려 **관련성 낮은 정보가 많으면 성능이 떨어진다**. 맥락은 **넓이가 아니라 선별**이 핵심이다.
- **"최신 모델이 나오면 이전 모델은 다 열등하다"** — 가격·지연·품질의 trade-off가 있어 **업무별 최적 모델**이 다르다.

## 2. 바이브 코딩(Vibe Coding)에서 에이전틱 엔지니어링(Agentic Engineering)으로

### 2.1 용어의 탄생과 진화

- **2025년 2월**: Andrej Karpathy(OpenAI 공동창업자)가 트윗에서 **vibe coding** 을 "코드를 보는 게 아니라 **결과물을 보면서** AI와 대화로 조정해 나가는 방식"이라고 정의. 유행어가 됨.
- **2026년 초**: 업계에서 **"vibe coding is passé(지난 유행)"** 라는 선언이 나오며, **agentic engineering(에이전틱 엔지니어링)** 이 새 주류 용어로 자리 잡음.
- **새 정의**: AI 에이전트가 **구조화된 감독(structured supervision)** 아래 **계획·작성·테스트·배포**까지 수행하고, 인간은 **"자율 에이전트를 지휘하는 기술 감독관(technical supervisor)"** 역할을 맡는다.

두 용어를 같이 기억하면 됩니다. **바이브 코딩은 입문 개념, 에이전틱 엔지니어링은 성숙 단계의 방식**입니다. 이 자료는 비개발자 입문을 위해 "바이브 코딩"이라는 친숙한 용어를 계속 쓰되, **실제 현업 추세는 에이전틱 엔지니어링**임을 염두에 두세요.

### 2.2 바이브 코딩의 3단계 루프

1. **의도를 말한다** (사람 → AI)
2. **AI가 변경을 제안한다** (AI → 코드)
3. **사람이 검증한다** (사람 → 승인/거절)

→ 피드백이 돌면서 다시 1번으로. 이 루프가 몇 초~몇 분 안에 돌아가는 것이 이상적입니다. 사람은 루프를 **빨리 돌릴 수 있는 환경** 을 만들어야 합니다(작은 테스트, 빠른 빌드, 쉬운 롤백).

### 2.3 건축주·설계사무소, 셰프와 수셰프

- **설계·시공 분리**: 건축주(사람)가 요구사항을 말하면 설계사무소(AI)가 도면과 시공을 하고, 건축주는 **중간 검수와 승인**만 한다. 에이전틱 엔지니어링은 이 분업과 가깝다.
- **셰프와 수셰프**: 셰프(사람)는 메뉴와 플레이팅을 결정, 수셰프(AI)는 **손질·조리를 실행**한다. 셰프의 역할은 **메뉴 기획과 맛 검수**.

### 2.4 ⚠️ 자주 하는 오해

- **"바이브 코딩은 대충 감으로 코딩하는 것"** — 이름은 가볍지만 **맥락 준비와 검증**은 오히려 더 빡빡해진다.
- **"AI가 다 해주니 사람은 할 일이 없다"** — **무엇을 만들지, 어떻게 평가할지**를 정하는 건 여전히 사람이다. AI는 **실행자**이지 의사결정자가 아니다.
- **"바이브 코딩하면 코드 품질이 떨어진다"** — **좋은 맥락 + 테스트 + 리뷰**가 갖춰지면 혼자 작성한 코드보다 **일관성이 더 높다**는 사례도 많다.

## 4. 프롬프트 엔지니어링 → 컨텍스트 엔지니어링(Context Engineering)

### 4.1 용어 확장

2023~2024년엔 **프롬프트 엔지니어링(prompt engineering)**, 즉 "질문 문장을 잘 짜는 기술"이 유행이었습니다. 2025~2026년엔 개념이 확장돼 **컨텍스트 엔지니어링(context engineering)** 으로 부릅니다.

> **Context Engineering**: "에이전트가 작동하는 **전체 정보 환경**(파일, 도구, 메모리, 히스토리, 스키마, 규칙 문서)을 **큐레이션**하는 기술."

한 문장 프롬프트 → 한 환경 설계로 초점이 옮겨간 셈입니다. **CLAUDE.md** 같은 프로젝트 규칙 파일, 에이전트용 Skills·Subagents·MCP 서버 구성 등이 모두 컨텍스트 엔지니어링의 요소입니다.

### 4.2 좋은 프롬프트(요청)의 공통 요소

- **역할·목표 명시** ❌ "로그인 만들어줘" → ✅ "FastAPI + Pydantic 기반, 서버 세션 방식, ID/PW 로그인을 `/login` POST로 구현해 줘"
- **입력·출력 명세** ✅ "입력은 `{email, password}` JSON. 성공 시 `{user_id, session_id}`, 실패 시 401 + `{error, message}`"
- **제약 조건** ✅ "bcrypt 검증. 5회 실패 시 5분 잠금"
- **예시 제공** ✅ "기존 `/logout` 스타일을 따라라: [코드 붙여넣기]"
- **단계 지시** ✅ "1) 라우터 추가 2) 서비스 로직 3) 실패 테스트 4) 성공 테스트 5) PR 요약"

### 4.3 ⚠️ 오해하기 쉬운 것들

- **"프롬프트만 잘 쓰면 결과가 좋다"** — 에이전트 시대의 품질은 **프롬프트 < 컨텍스트 < 도구 구성** 순으로 크게 좌우된다. 프롬프트는 입구일 뿐이다.
- **"긴 프롬프트가 좋은 프롬프트"** — **관련 없는 정보가 섞이면 오히려 환각이 늘어난다**. 짧고 정확한 쪽이 낫다.
- **"프롬프트는 매번 즉흥적으로 쓰는 것"** — 반복되는 작업의 프롬프트는 **템플릿·Skill**로 자산화해야 한다.

### 4.4 🛠️ 5분 실습

- 본인 업무에서 자주 하는 반복 작업 하나를 골라 "역할·입출력·제약·예시·단계" 5요소를 채운 프롬프트를 **한 번** 써 본다.
- 그 프롬프트를 바로 지우지 말고 **메모 앱·사내 위키**에 저장한다 → 이것이 **컨텍스트 엔지니어링 자산화**의 시작이다.

## 5. Spec-Driven Development (SDD) — 스펙 기반 개발

2025~2026년 급속히 부상한 실무 패턴입니다.

> **SDD**: **스펙(specification, 명세서)** 을 **영구적 프롬프트(permanent prompt)** 로 활용해, 에이전트가 스펙을 읽고 구현·테스트·문서화까지 수행하게 하는 개발 방식.

### 5.1 왜 등장했는가

바이브 코딩은 "대화로 조정"하기 때문에 **의사결정이 대화창에 흩어집니다**. 다시 만들 때 같은 결과가 재현되지 않습니다. 스펙을 **파일로 고정**해 두면, 에이전트가 매번 같은 기준으로 작업합니다.

### 5.2 대표 도구

- **GitHub Spec Kit** — 스펙 파일 구조·워크플로를 제안하는 오픈소스 툴킷.
- **Microsoft SpecKit** — 엔터프라이즈 통합.

### 5.3 스펙에 적는 항목(예시 골격)

- 문제 정의·사용자 스토리
- 입출력 계약(DTO, 에러 코드)
- 비기능 요구(성능·보안·감사)
- 수용 기준(acceptance criteria)
- 예시 시나리오·엣지 케이스
- 참조 설계 문서·ADR 링크

### 5.4 🏢 업무 시나리오

**케이스 — 회의록 요약 기능.**
기획자가 "회의록 요약 v1 스펙" 마크다운을 작성(입력 포맷·요약 길이·민감 정보 마스킹 규칙·승인 흐름 포함). 개발자는 에이전트에 **"이 스펙대로 구현하고 테스트까지 써 줘"** 만 지시. 결과물이 스펙 조건을 만족하는지 **체크리스트로 검증**. 3주 뒤 요구사항이 바뀌면 **스펙만 고치면** 에이전트가 재구현한다.

### 5.5 ⚠️ 자주 듣는 오해

- **"SDD는 워터폴로의 회귀 아닌가"** — 스펙은 **살아 있는 문서**로 짧게 자주 업데이트한다. 전통적 워터폴의 수백 페이지 요구명세와는 다르다.
- **"스펙 작성이 번거로우니 생략해도 된다"** — 스펙을 생략하면 **결과가 매번 달라지고** 검증이 주관적이 된다.

## 6. 에이전트(Agent) — 자율적으로 일하는 AI

LLM이 단순 "응답"만 하는 것이 아니라, **도구를 불러오고 결과를 보고 다음 수를 두는** 것을 에이전트라 부릅니다. Claude Code, Cursor의 "Agent 모드"가 모두 이에 해당합니다.

기본 루프: **관찰(observe) → 사고(reason) → 행동(act/tool call) → 관찰 → …**

### 6.1 에이전트 패턴 7가지 (2026 정리)

| 패턴 | 요지 | 적합한 상황 |
|---|---|---|
| **ReAct** (Reason + Act) | 사고와 행동을 번갈아. 2022년 기본형. | 일반 도구 호출 전반 |
| **Reflection (Reflexion)** | 자기 결과를 되돌아보고 개선. | 코드 리뷰, 자기 수정 |
| **Tool Use** | 외부 도구(검색, DB, API)를 호출. | 사실 조회·쓰기 작업 |
| **Planning (Plan-and-Execute, ReWOO)** | 먼저 전체 계획을 세우고 순차 실행. | 다단계 복잡 작업 |
| **Multi-Agent Collaboration** | 역할 분담 에이전트끼리 협업(Planner/Coder/Reviewer). | 대형 작업, 품질 요구 |
| **Sequential Workflows** | 정해진 순서로 파이프라인. | 재현성 중시 업무 |
| **Human-in-the-Loop** | 핵심 단계에서 사람 승인. | 쓰기·결제·배포 |

### 6.2 익숙한 장면으로 패턴 감잡기

- **ReAct**: 장보면서 "이것도 필요하네" 하며 메모를 갱신하는 모습.
- **Reflection**: 보고서 초안을 쓰고 **스스로 다시 읽어 고치는** 과정.
- **Plan-and-Execute**: 출장 일정 **먼저 다 짜 놓고** 그대로 움직이는 유형.
- **Multi-Agent**: 기획·디자인·개발 **역할 분담**으로 한 제품을 만드는 팀.
- **Human-in-the-Loop**: 은행 이체가 **OTP 승인** 후에만 실행되는 흐름.

### 6.3 우리 프로젝트의 에이전트

AIDOO Portal의 AI 기능도 **사내용 에이전트**입니다. 도구들이 사내 데이터와 연결돼 **훨씬 유용한 비서**가 됩니다. 쓰기 권한 도구는 **Human-in-the-Loop 승인 플로우**로 감쌉니다(32장 참조).

### 6.4 ⚠️ 헷갈리기 쉬운 것들

- **"에이전트에게 모든 권한을 주면 더 똑똑해진다"** — **Excessive Agency(과도한 자율권)** 는 OWASP LLM Top 10의 주요 위협이다. 승인 플로우가 반드시 필요하다.
- **"에이전트는 항상 멀티 에이전트가 낫다"** — 단순 작업에는 **1 에이전트 + 적절한 도구**가 더 빠르고 싸다. 멀티는 조율 비용이 크다.

## 7. MCP — Model Context Protocol

Anthropic이 2024년 11월에 공개한 **개방형 표준** 입니다. AI에게 "도구를 붙이는 규약"을 표준화했습니다.

비유: 이전에는 AI마다, 앱마다 다른 방식으로 도구를 붙였습니다("USB 포트가 제조사마다 다른 시대"). MCP는 이것을 **USB 표준처럼 통일**하려 합니다.

- **MCP Server**: 도구를 제공하는 쪽. 예: "회의실 예약 툴을 제공".
- **MCP Client**: AI 측. 서버에 물어 도구 목록을 받고, 필요할 때 호출.

### 7.1 2026.04 성숙도

- Anthropic이 2024.11 공개 이후 **16개월 만에** 월 Python/TS SDK 다운로드 **약 9,700만 건**.
- 공개 MCP 서버 **17,000개+** (Anthropic 집계 10,000개+ 활성).
- 벤더 지원: **Anthropic, OpenAI, Microsoft, Google, Amazon** 모두 공식. 사실상 **업계 표준화 단계**.
- 공식 레퍼런스 서버: **Filesystem, Git, Memory(지식 그래프), Sequential Thinking, Fetch, Time**.
- 2026은 업계에서 **"엔터프라이즈-ready MCP 채택의 해"** 로 평가.

### 7.2 우리 프로젝트의 MCP

`adr/0002-mcp-capability-platform.md` 가 이 프로젝트의 핵심 설계 결정입니다. 요약:

- **AI 능력(capability)을 MCP 방식으로 등록**.
- 각 능력은 **human-friendly REST DTO** 와 **AI-friendly Pydantic DTO** 를 따로 가짐.
- **발견(discoverability), 미리보기(preview), 승인(approval)** 을 능력 선언에 포함.
- 이 덕분에 에이전트가 **사용자 권한 맥락 안에서만** 도구를 고를 수 있음.

즉, 우리 포털의 AI는 "도구를 붙이는 아주 많은 것이 추가될" 예정이며, 그 추가가 매번 앱 수정으로 이어지지 않도록 **플러그인 스타일의 확장성**을 미리 설계해 둔 것입니다. 자세한 해설은 32장.

### 7.3 ⚠️ 자주 하는 오해

- **"MCP는 Anthropic 전용 기술"** — OpenAI·Google·Microsoft·Amazon 모두 공식 지원하는 **개방 표준**이다.
- **"MCP 서버를 만들면 보안 문제가 해결된다"** — MCP는 **도구 연결의 문법**일 뿐이다. 승인·감사·권한 설계는 여전히 앱 몫이다.

## 8. RAG (Retrieval-Augmented Generation) — 맥락 주입의 표준

LLM이 모르는 것(사내 데이터, 최신 문서)을 **검색해서 프롬프트에 넣어 주는 기법**입니다.

흐름:

1. 사용자 질문 도착
2. **임베딩(embedding, 의미를 수치 벡터로 변환)** 으로 관련 문서 검색
3. 상위 N개 문서를 프롬프트에 첨부
4. LLM이 그것을 근거로 답변

- **벡터 DB**: Chroma, Pinecone, Weaviate, **pgvector**(PostgreSQL 확장).
- 1M 컨텍스트 시대에는 "모든 걸 그냥 넣기" 유혹도 있지만, **정확도·비용·속도** 면에서 **선별 주입(RAG)** 이 여전히 유리한 경우가 많습니다.

### 8.1 🏢 업무 시나리오

"3월 이사회 결의사항 요약"을 묻는다면:

1. 검색 엔진이 관련 회의록 3건을 벡터 유사도로 찾는다.
2. 그 본문을 프롬프트에 붙여 LLM에게 요약 요청.
3. 근거 문서 링크를 함께 응답에 붙여 **추적 가능성(traceability)** 보장.

## 9. 에이전트 평가 벤치마크 (2026.04)

"AI가 얼마나 잘 코딩하는가"를 정량 측정하는 업계 표준 벤치마크가 **SWE-Bench** 계열입니다.

| 벤치마크 | 의미 | 2026.04 수치 |
|---|---|---|
| **SWE-Bench Verified** | 실제 GitHub 이슈를 에이전트가 해결하는 테스트 | **Claude Mythos Preview 93.9%**, **GPT-5.3 Codex 85%**, **Claude Opus 4.5 80.9%**, 전체 83개 모델 **평균 63.4%** |
| **SWE-Bench Pro** | 더 어려운 변형 | **최상위 57%**, **평균 ~25%** |

해석 가이드:

- 2년 전(2024년 초) SOTA가 5% 수준이었음을 감안하면 **급격한 향상**.
- 그러나 **Pro 버전의 낮은 수치**가 보여주듯 여전히 **어려운 실제 문제는 사람의 감독이 필수**.

### 9.1 ⚠️ 바로잡고 싶은 오해

- **"벤치마크 점수가 높으면 실무에 바로 투입해도 된다"** — 벤치마크는 **제한된 환경**의 지표일 뿐이다. 실제 코드베이스는 관례·도메인·레거시가 더해져 훨씬 복잡하다.

## 10. AI 시대의 개발자 역량 재편

과거에 중요했던 역량 vs 지금도 중요한 역량:

| 덜 중요해진 것 | 더 중요해진 것 |
|---|---|
| 언어 문법 암기 | 문제를 잘 쪼개는 능력 |
| 라이브러리 이름 외우기 | 좋은 맥락을 구성하는 능력(**Context Engineering**) |
| 빠른 타이핑 | 좋은 질문을 하는 능력 |
| 혼자서 다 아는 것 | AI 제안을 **비판적으로 평가**하는 능력 |
| 특정 프레임워크 숙련 | **스펙을 글로 정리**하는 능력 (SDD) |

그리고 **여전히** 중요한 것:

- **도메인 지식** (이 업무가 뭘 의미하는지)
- **시스템 감각** (어디에 무엇이 있고, 왜 그런지)
- **책임감** (AI가 만든 결과도 내 것)

### 10.1 비개발자 AX TF에게 특히 유리한 점

- **도메인 지식**이 이미 풍부하다 → 컨텍스트 엔지니어링의 원자재가 풍부.
- **업무 스펙을 글로 정리하는 능력**은 기획·PM이 가진 강점 그대로 → SDD 적합.
- 개발자가 몰라서 생기는 **"기능은 됐는데 업무엔 안 맞는"** 문제를 원천 봉쇄할 수 있다.

## 11. 실전 수칙 — 우리 TF가 지킬 7가지

1. **항상 브랜치에서 작업.** 바로 main에 푸시 금지.
2. **작게 묻고 자주 커밋.** 한 번에 거대한 작업을 AI에 시키지 않기.
3. **출력한 코드를 읽기.** 이해가 안 되는 코드는 머지하지 않기.
4. **테스트도 같이 만들게 시키기.** 새 기능엔 새 테스트.
5. **AI의 말이 이상하면 그만두고 사람이 생각.** 무한 반복 수정은 AI의 잘못이 아니라 맥락이 부실한 것.
6. **반복 작업은 스펙·Skill·CLAUDE.md로 자산화**. 같은 프롬프트를 세 번 쓰고 있다면 파일로 고정.
7. **쓰기 도구·결제·배포 등 "파괴적 행위"는 반드시 Human-in-the-Loop**.

## 12. 🏢 TF 첫 주의 모습 한눈에 보기

**월요일**: 기획자가 "주간 업무 보고서 자동 요약" 스펙을 마크다운 1페이지로 작성.
**화요일**: Claude Code에 스펙을 주고 "이 기능을 `domains/reports/`에 추가하고 테스트도 써 줘"라고 지시.
**수요일**: PR이 올라오고 코드 리뷰. 에이전트가 **Reflection 패턴**으로 자기 리뷰를 먼저 한 뒤 사람이 최종 확인.
**목요일**: 스테이징에서 실제 사용자 2명과 시범 사용. 피드백을 **스펙 파일에 추가**(살아 있는 문서).
**금요일**: 운영 배포. Human-in-the-Loop 승인 플로우로 쓰기 작업은 사용자 승인 후 실행.

→ 전 과정에서 **타이핑량은 적지만 스펙 작성·검증 판단은 사람이** 한다. 이것이 **에이전틱 엔지니어링의 일상**입니다.

## 13. 핵심 요약

- LLM은 **다음 토큰 예측기**. 맥락을 잘 주면 거의 다 할 수 있지만 **환각** 위험을 안는다.
- **바이브 코딩**(Karpathy, 2025.02)은 2026년 초 **에이전틱 엔지니어링**으로 재정의됐다.
- 2026.04 프런티어 모델: **Claude Opus 4.7 / Sonnet 4.6 / Haiku 4.5, GPT-5, Gemini 3 Pro**. 1M 컨텍스트가 상용 수준.
- **프롬프트 엔지니어링 → 컨텍스트 엔지니어링**으로 개념 확장. **SDD(Spec-Driven Development)**가 실무 표준으로 부상.
- 에이전트 패턴 **7가지**: ReAct, Reflection, Tool Use, Planning, Multi-Agent, Sequential, **Human-in-the-Loop**.
- **MCP**는 도구 연결의 개방 표준. 2026.04 기준 벤더 전면 지원, 공개 서버 1만 7천 개+.
- SWE-Bench Verified **평균 63.4%**, 최상위 93.9%까지 도달했지만 **어려운 문제엔 여전히 사람의 감독**이 필수.
- 비개발자 AX TF의 도메인 지식·문서화 역량은 **에이전틱 엔지니어링의 핵심 자산**이다.
