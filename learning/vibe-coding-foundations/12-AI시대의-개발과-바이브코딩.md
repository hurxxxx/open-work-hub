# 12. AI 시대의 개발과 바이브 코딩

> **한 줄 요약.** AI는 코드를 빠르게 써 주지만, 무엇을 만들지 정하고 결과가 맞는지 판단하는 일은 여전히 사람의 몫이다. 바이브 코딩의 핵심은 **자연어로 지시하고, 작게 확인하고, 검증하며 반복하는 습관**이다.

---

## 1. LLM을 개발 동료로 이해하기

LLM(Large Language Model, 대규모 언어 모델)은 많은 텍스트와 코드 패턴을 학습해 다음에 올 말을 예측하는 AI입니다. 개발에서는 다음 일을 잘합니다.

- 코드 초안 작성
- 기존 코드 설명
- 에러 로그 해석
- 테스트 케이스 제안
- 문서 요약
- 반복적인 리팩토링 보조

하지만 LLM은 **의도를 자동으로 알지 못하고**, **현재 프로젝트의 숨은 맥락을 모를 수 있으며**, **그럴듯하지만 틀린 답**을 만들 수 있습니다. 그래서 AI를 쓰는 개발은 "AI에게 맡기기"가 아니라 **AI가 일할 조건을 사람이 설계하는 작업**에 가깝습니다.

### 1.1 AI가 잘하는 일과 사람이 해야 하는 일

| 구분 | AI가 잘하는 일 | 사람이 책임질 일 |
|---|---|---|
| 요구사항 | 문장을 정리하고 빠진 항목을 질문 | 무엇이 진짜 필요한지 결정 |
| 구현 | 기존 패턴을 따라 코드 초안 작성 | 변경 범위와 품질 기준 승인 |
| 테스트 | 정상·예외 케이스 제안 | 어떤 테스트가 충분한지 판단 |
| 보안 | 위험 후보를 체크리스트로 나열 | 민감 정보·권한·운영 영향 최종 판단 |
| 문서 | 초안과 요약 작성 | 사실 여부와 조직 맥락 검토 |

비개발자에게 중요한 메시지는 단순합니다. **코드를 직접 다 이해하지 못해도, 목표와 기준은 설명할 수 있어야 합니다.**

---

## 2. 바이브 코딩이란 무엇인가

바이브 코딩은 자연어로 AI에게 의도를 설명하고, AI가 만든 결과를 보며 다시 수정 요청을 하는 개발 방식입니다. 이름은 가볍지만 실무에서는 꽤 엄격한 습관이 필요합니다.

좋은 바이브 코딩은 다음 순서로 진행됩니다.

1. 목표를 한 문장으로 말한다.
2. 왜 필요한지 배경을 준다.
3. 관련 파일·화면·데이터를 알려 준다.
4. 하면 안 되는 일을 제약으로 건다.
5. AI가 만든 결과를 작게 확인한다.
6. 테스트·화면·로그로 검증한다.
7. 다음 수정으로 넘어간다.

나쁜 바이브 코딩은 반대입니다.

- "대충 예쁘게 해 줘"처럼 기준이 없음
- 한 번에 큰 기능 전체를 맡김
- AI 설명만 믿고 실행 결과를 확인하지 않음
- 테스트 없이 PR을 만듦
- `.env`나 고객 데이터를 프롬프트에 그대로 붙임

### 2.1 수업 활동

아래 요청을 좋은 요청으로 바꿔 보세요.

```text
검색 화면 좀 고쳐 줘.
```

좋은 요청은 이런 식입니다.

```text
목표: 문서 검색 화면에서 결과가 없을 때 안내 문구와 다시 검색 버튼을 보여 줘.
배경: 지금은 빈 화면처럼 보여서 사용자가 검색이 실패했는지 알기 어렵다.
대상: apps/web/src/app-modules/ai/views/RagSearchView.tsx
제약: 기존 UI 컴포넌트와 스타일을 유지하고 새 라이브러리는 추가하지 않는다.
검증: 결과가 없을 때 안내 문구가 보이는 테스트를 추가한다.
```

## 3. 개발용 AI 도구를 고르는 기준

도구 이름은 계속 바뀝니다. 그래서 교재에서는 특정 제품의 세부 기능보다 **도구를 평가하는 기준**을 익히는 것이 더 오래 갑니다.

| 도구 유형 | 쓰기 좋은 상황 | 주의할 점 |
|---|---|---|
| 브라우저형 AI 채팅 | 개념 설명, 문장 다듬기, 설계 상담 | 현재 코드 전체를 모르므로 추측할 수 있음 |
| IDE형 AI 도구 | 작은 UI 수정, 자동완성, 파일 단위 편집 | 변경 범위가 커지면 놓치는 파일이 생길 수 있음 |
| 터미널형 AI 도구 | 테스트 실행, 여러 파일 수정, 리팩토링 | 권한이 큰 만큼 승인 지점을 분명히 둬야 함 |
| 사내 연결형 AI | 내부 문서 검색, 업무 데이터 기반 질의 | 접근 권한과 감사 로그가 필요함 |

도구를 고를 때는 아래 질문을 먼저 합니다.

- 프로젝트 파일을 안전하게 읽을 수 있는가?
- 수정 전 계획을 보여 주고 멈출 수 있는가?
- 테스트와 린트를 실행할 수 있는가?
- 민감 정보 접근을 제한할 수 있는가?
- 변경 내용을 사람이 diff로 검토할 수 있는가?

## 4. 프롬프트보다 넓은 것: 작업 맥락

프롬프트는 AI에게 보내는 요청 문장입니다. 하지만 실무 결과를 좌우하는 것은 문장 하나보다 **작업 맥락 전체**입니다.

작업 맥락에는 다음이 포함됩니다.

- 이번 작업의 목표
- 왜 필요한지에 대한 업무 배경
- 관련 파일과 화면
- 기존 코드 스타일과 프로젝트 규칙
- 수정하면 안 되는 범위
- 성공 기준과 테스트 방법
- 민감 정보·권한·운영 영향

### 4.1 좋은 맥락의 예

```text
이 작업은 문서 검색 화면의 빈 상태 UI를 개선하는 일이다.
대상 파일은 RagSearchView.tsx이고, 현재 검색 결과 배열이 비어 있을 때 별도 안내가 없다.
새 의존성은 추가하지 말고 기존 컴포넌트 스타일을 따른다.
검증은 Vitest로 빈 결과 상태 렌더링 테스트를 추가한다.
```

### 4.2 나쁜 맥락의 예

```text
검색 UX 개선해 줘. 알아서 예쁘게.
```

두 요청의 차이는 문장 길이가 아니라 **판단 기준의 유무**입니다.

## 5. 스펙 먼저 쓰기

AI에게 바로 구현을 시키기 전에 스펙을 먼저 쓰면 실수가 줄어듭니다. 스펙은 거창한 문서가 아니라, AI와 사람이 같은 기준을 보게 만드는 짧은 약속입니다.

좋은 스펙은 다섯 가지를 담습니다.

1. **목표**: 무엇을 만들거나 고칠 것인가.
2. **배경**: 왜 지금 필요한가.
3. **제약**: 하지 말아야 할 것, 지켜야 할 규칙은 무엇인가.
4. **성공 기준**: 완료를 어떻게 판단할 것인가.
5. **관련 자료**: 파일, 화면, 로그, 이슈, ADR 등.

### 5.1 스펙 예시

```text
목표: 문서 검색 결과가 없을 때 빈 상태 UI를 보여 준다.
배경: 현재는 사용자가 검색이 실패한 것인지 결과가 없는 것인지 구분하기 어렵다.
제약: 새 라이브러리 추가 금지. 기존 레이아웃과 톤 유지.
성공 기준:
- 검색 결과가 0개이면 안내 문구가 보인다.
- 다시 검색할 수 있는 버튼이 보인다.
- 기존 검색 결과 렌더링은 깨지지 않는다.
관련 파일:
- apps/web/src/app-modules/ai/views/RagSearchView.tsx
```

이 스펙을 AI에게 주고 바로 구현을 맡기기보다, 먼저 이렇게 요청합니다.

```text
위 스펙을 구현하기 전에 수정할 파일, 변경 순서, 필요한 테스트를 먼저 제안해 줘.
내가 승인하면 1단계부터 진행해 줘.
```

## 6. 에이전트처럼 일한다는 뜻

AI가 단순히 답변만 하는 것이 아니라 파일을 읽고, 명령을 실행하고, 테스트 결과를 보고 다음 작업을 이어 가면 에이전트처럼 일한다고 볼 수 있습니다.

비개발자는 내부 구현을 모두 알 필요는 없습니다. 대신 아래 패턴을 알고 있으면 AI에게 일을 더 안전하게 맡길 수 있습니다.

| 패턴 | 쉬운 설명 | 언제 쓰나 |
|---|---|---|
| 계획 후 실행 | 먼저 작업 순서를 쓰고 승인 후 진행 | 새 기능, 큰 수정 |
| 실행 후 관찰 | 명령을 실행하고 결과를 보고 다음 판단 | 테스트 실패, 빌드 오류 |
| 자기 검토 | AI가 자기 결과를 다시 비판 | PR 전 품질 점검 |
| 역할 분리 | 조사, 구현, 리뷰를 다른 세션으로 나눔 | 큰 코드베이스 탐색 |
| 사람 승인 | 위험한 단계 전 멈춤 | DB 변경, 삭제, 운영 반영 |

### 6.1 사람 승인 지점

다음 상황에서는 AI가 제안해도 바로 진행하지 않습니다.

- DB 스키마 변경
- 운영 데이터 수정
- 새 의존성 추가
- 대량 파일 삭제나 이동
- 외부 API 키·시크릿 사용
- 권한·보안 정책 변경

이때는 "실행하지 말고 계획과 영향만 설명해 줘"라고 지시합니다.

## 7. RAG와 MCP를 비개발자 말로 이해하기

AI 기능을 만들 때 자주 나오는 두 단어가 RAG와 MCP입니다.

**RAG**는 AI가 모르는 사내 문서나 데이터를 검색해서 답변에 참고하게 하는 방식입니다. 예를 들어 AI-DO의 문서 검색 결과를 AI 답변에 붙여 주면, AI는 일반 지식이 아니라 우리 회사 문서를 근거로 답할 수 있습니다.

**MCP**는 AI가 외부 도구나 시스템을 호출할 수 있게 해 주는 연결 방식입니다. 예를 들어 일정 조회, 문서 검색, 이슈 생성 같은 기능을 AI가 도구처럼 사용할 수 있습니다.

비개발자 관점에서 기억할 것은 하나입니다.

- RAG는 **읽을 근거를 주는 장치**입니다.
- MCP는 **행동할 도구를 주는 장치**입니다.

읽기보다 쓰기가 더 위험합니다. 그래서 MCP처럼 AI가 실제 행동을 할 수 있는 기능에는 권한, 미리보기, 승인, 감사 로그가 필요합니다.

## 8. 벤치마크를 보는 법

AI 모델 벤치마크는 참고 자료일 뿐, 우리 프로젝트의 품질 보증서가 아닙니다. 공개 벤치마크에서 높은 점수를 받은 모델도 다음 상황에서는 실패할 수 있습니다.

- 우리 코드베이스 구조를 충분히 읽지 못한 경우
- 사내 업무 규칙을 모르는 경우
- 테스트가 부족해 틀린 구현이 통과되는 경우
- 프롬프트에 성공 기준이 빠진 경우
- 권한이나 운영 데이터 같은 위험을 사람이 확인하지 않은 경우

따라서 실제 기준은 모델 순위가 아니라 **우리 프로젝트에서 통과해야 할 검증 목록**입니다.

### 8.1 자체 평가 세트 만들기

팀에서 자주 맡기는 AI 작업을 5~10개만 모아도 좋은 평가 세트가 됩니다.

- 빈 상태 UI 추가
- API 에러 메시지 개선
- 권한 없는 사용자 접근 차단
- 검색 결과 정렬 변경
- 테스트 실패 로그를 보고 원인 수정

AI 도구나 모델을 바꿀 때 이 과제를 다시 시켜 보면, 우리 팀 기준에서 어떤 도구가 더 맞는지 판단할 수 있습니다.

## 9. 비개발자의 강점

비개발자는 코드 문법에서 개발자보다 느릴 수 있습니다. 하지만 AI 협업에서는 다음 강점이 큽니다.

- 업무 맥락을 잘 안다.
- 사용자가 무엇을 불편해하는지 안다.
- 좋은 설명과 나쁜 설명을 구분할 수 있다.
- 문서, 회의록, 요구사항을 정리할 수 있다.
- 결과가 실제 업무에 맞는지 판단할 수 있다.

AI가 코드를 빠르게 쓰는 시대에는 이 강점이 더 중요해집니다. 개발자는 구현 구조를 검토하고, 비개발자는 목표·맥락·검증 기준을 선명하게 만드는 방식으로 협업하면 됩니다.

---

## 10. 한 주짜리 실전 흐름

**월요일**: 사용자가 겪는 불편을 한 문장으로 적습니다.

**화요일**: 목표, 배경, 제약, 성공 기준을 포함한 스펙을 씁니다.

**수요일**: AI에게 구현 계획을 먼저 요청하고, 변경 범위를 확인합니다.

**목요일**: 작은 단계로 구현하고 테스트를 실행합니다.

**금요일**: AI에게 자기 검토를 시킨 뒤, 사람이 화면과 테스트 결과를 보고 PR을 준비합니다.

이 흐름에서 핵심은 타이핑량이 줄었다는 점이 아닙니다. **사람이 더 좋은 기준을 세우고, AI가 그 기준 안에서 빠르게 움직이게 한다**는 점입니다.

---

## 11. 핵심 요약

- AI는 빠른 초안 작성자이고, 사람은 목표·맥락·검증 기준의 책임자입니다.
- 바이브 코딩은 자연어로 시키는 기술이 아니라 **작게 맡기고 자주 확인하는 작업 습관**입니다.
- 좋은 요청은 목표, 배경, 제약, 관련 파일, 검증 기준을 포함합니다.
- 스펙을 먼저 쓰면 AI 결과가 흔들릴 때 돌아갈 기준이 생깁니다.
- RAG는 읽을 근거를 주는 장치, MCP는 행동할 도구를 주는 장치입니다.
- 벤치마크보다 중요한 것은 우리 프로젝트의 테스트와 검증 체크리스트입니다.
- 비개발자의 업무 맥락과 문서화 능력은 AI 협업에서 핵심 자산입니다.
