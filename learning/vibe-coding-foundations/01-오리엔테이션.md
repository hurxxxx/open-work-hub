# 01. 오리엔테이션 — 비개발자의 마음가짐

> **한 줄 요약.** 개발은 한 번에 완성하는 학습이 아니라 반복 학습이다. 완벽한 이해보다 **작게 실행하고 확인하는 습관**이 먼저다.

---

## 1. 바이브 코딩(Vibe Coding)이란

바이브 코딩(Vibe Coding)은 자연어로 AI에게 의도를 설명하고, AI가 만든 결과를 사람이 검토하면서 개발을 진행하는 방식입니다. 용어의 유행보다 중요한 의미는 이렇습니다.

> **"문법이나 세부 구현을 외우지 않고, 원하는 바를 자연어로 AI에게 설명하면서 코드를 만들어 나가는 방식."**

전통적 프로그래밍과 비교하면 이렇습니다.

| 구분 | 전통 프로그래밍 | 바이브 코딩 |
|---|---|---|
| 주체 | 사람이 코드를 친다 | 사람이 요구·검증, AI가 코드를 친다 |
| 요구 기술 | 언어·라이브러리 문법 숙지 | 요구사항을 잘 쪼개서 설명하는 능력 |
| 속도 | 느림 | 매우 빠름 |
| 위험 | 오타·버그 | 잘못된 방향·환각(hallucination, 그럴듯하게 지어낸 거짓말) |
| 필요한 인간 역량 | 타이핑 속도 | 판단력·맥락 제공·검증 |

바이브 코딩은 "누구나 다 할 수 있다"는 뜻이 아니라, "**잘 설명하고 잘 검증하는 사람이 개발자가 될 수 있다**"는 뜻입니다. 잘 설명하려면 **도메인 지식 + 시스템에 대한 대략적 지도** 가 필요합니다. 이 자료가 바로 그 지도를 그려 줍니다.

### 1.1 용어보다 중요한 것 — 감독관 모드

바이브 코딩이라는 말은 가볍게 들릴 수 있습니다. 하지만 실무에서 필요한 태도는 즉흥적으로 AI에게 맡기는 것이 아니라 **감독관 모드**입니다.

감독관 모드는 다음 네 가지를 사람이 책임지는 방식입니다.

| 사람이 책임질 것 | 예시 |
| --- | --- |
| 목표 정의 | 어떤 사용자의 어떤 문제를 해결할지 정한다 |
| 맥락 제공 | 관련 화면, 파일, 업무 규칙, 제약을 알려준다 |
| 중간 승인 | 계획, 테스트, diff를 보고 다음 단계 진행 여부를 판단한다 |
| 최종 검증 | 실제 화면, 테스트, 권한, 보안을 확인한다 |

AI는 구현 속도를 높여 줍니다. 하지만 **무엇이 맞는지 판단하는 기준**은 사람에게서 나옵니다. 이 교재는 그 기준을 만드는 훈련입니다.

#### 수업 활동

아래 두 요청을 비교해 보세요.

```text
나쁜 요청:
문서 기능 좀 개선해 줘.

좋은 요청:
문서 목록 화면에서 검색어를 입력했을 때 결과가 0건이면
"검색 결과가 없습니다"라는 빈 상태를 보여줘.
대상은 docs 도메인 프론트 코드로 제한하고, 새 의존성은 추가하지 마.
검증은 검색 결과 있음/없음 두 케이스를 테스트로 확인해 줘.
```

두 요청의 차이는 문장 길이가 아니라 **판단 기준이 들어 있는가**입니다.

### 1.2 역할 변화 한눈에 보기

- **구현자에서 감독자로.** 전통 개발에서 사람이 직접 코드를 구현했다면, 바이브 코딩에서는 사람이 방향·품질·정합성을 관리하고 AI가 구현을 담당합니다.
- **실행보다 검수 중심으로.** 사람이 직접 타이핑하던 시간을 줄이고, AI에 작업을 정확히 지시한 뒤 결과를 검수하고 수정 방향을 결정하는 비중이 커집니다.

### 1.3 바로잡고 싶은 오해들

- **"바이브 코딩은 아무나 몇 마디 던지면 앱이 나온다는 뜻이다."**
  요구를 모호하게 던지면 결과도 모호하게 돌아옵니다. 요구를 **쪼개고, 맥락을 얹고, 검증 기준을 함께** 넘겨주는 사람만 실제로 쓸 만한 결과물을 얻어 갑니다.
- **"AI가 내 업무 도메인을 자동으로 안다."**
  AI는 코드는 잘 쓰지만 **우리 회사의 규정, 업무 용어, 내부 정책** 은 문서로 주입해 주지 않으면 알 길이 없습니다. 오히려 그래서 "도메인 지식을 가진 여러분"의 가치가 더 올라갑니다.
- **"AI가 만든 코드는 일단 돌아가면 안전하다."**
  "돌아감"과 "맞음"은 다른 이야기입니다. 환각으로 없는 라이브러리 함수를 지어낸다거나, 보안상 위험한 방식으로 짠다거나, 이 프로젝트의 컨벤션과 동떨어진 스타일로 쓴다거나, **반드시 검토가 필요한 결과** 가 자주 섞여 나옵니다.
- **"프롬프트 한 줄만 잘 쓰면 된다."**
  좋은 결과는 한 줄짜리 주문에서 나오지 않습니다. 스펙, README, 기존 코드, 테스트 기준처럼 AI가 참고할 **작업 맥락**을 함께 줘야 합니다.

## 2. 개발자처럼 생각하는 3가지 습관

### 2.1 "뭐가 어디 있는지 안다"는 감각

좋은 개발자는 **모든 코드를 다 외우는 사람이 아닙니다**. 오히려 "어디에 있을지 짐작하는 감각"이 훨씬 중요합니다.

좋은 개발자는 모든 코드를 외우지 않아도 "어디를 먼저 찾아야 하는지"를 압니다. AI-DO Portal 기능을 수정할 때 **"이 기능은 `apps/web/src/domains/docs/` 근처겠구나"** 같은 위치 감각이 생기면 작업 속도가 크게 올라갑니다.

### 2.2 "작게 쪼갠다"는 본능

개발자는 큰 문제를 늘 **더 작은 문제들의 연속** 으로 바꿉니다. "로그인 기능을 만든다"는 말은 실제로는 다음의 연속입니다.

- 로그인 화면 그리기
- 이메일·비밀번호 입력 받기
- 서버에 로그인 요청 보내기
- 서버가 맞는지 확인
- 맞으면 세션 저장, 틀리면 오류 보여주기
- 세션을 가진 사람만 다른 페이지 접근 허용

이 **쪼개는 습관** 은 AI에게 일을 시킬 때 결정적으로 중요합니다. "로그인 만들어줘"처럼 넓은 요청은 결과가 일반화되기 쉽지만, 위처럼 6단계로 쪼개면 훨씬 정확한 결과가 나옵니다.

### 2.3 "일단 돌리고, 깨지면 고친다"는 태도

비개발자들이 코드를 만지다가 자주 빠지는 함정이 **"한 번에 완벽히 이해하고 고치겠다"** 는 욕심입니다. 실제 개발자들은 오히려 이렇게 합니다.

1. 변경을 아주 작게 한다.
2. 바로 실행해 본다.
3. 깨지면 에러 메시지를 그대로 AI에게 보여준다.
4. 되면 커밋(기록)하고 다음 작은 변경으로 넘어간다.

"**작은 성공을 자주 쌓는다**"는 리듬이 중요합니다. 이 리듬이 있으면 몇 시간 뒤에도 어디서부터 잘못됐는지 쉽게 되짚을 수 있습니다.

## 3. 최소한으로 익혀야 할 용어 감각

다음 단어들은 이 자료 전체에서 반복해서 등장합니다. 정확한 정의는 뒤에서 다시 다룹니다. 지금은 **냄새만 맡아 둡시다.**

- **코드(code)** — 컴퓨터가 실행할 명령을 글로 쓴 것. 단순한 텍스트 파일입니다.
- **프로젝트(project)** — 여러 코드 파일과 설정을 묶은 한 단위. 여기서는 AI-DO Portal 전체가 한 프로젝트입니다.
- **저장소(repository, 레포, repo)** — 프로젝트의 모든 파일과 역사(변경 이력)를 담는 폴더. Git으로 관리됩니다.
- **프런트엔드(frontend)** — 사람이 보는 화면(브라우저에서 보이는 부분).
- **백엔드(backend)** — 화면 뒤에서 돌아가는 서버. 데이터를 저장하고 계산합니다.
- **데이터베이스(DB)** — 데이터를 영구히 보관하는 저장소.
- **API** — 프런트와 백이 데이터를 주고받을 때 따르는 요청·응답 규격.
- **빌드(build)** — 우리가 쓴 코드를 컴퓨터가 빠르게 실행할 수 있는 형태로 바꾸는 작업.
- **배포(deploy)** — 빌드된 결과물을 실제 사용자가 쓸 수 있는 서버에 올리는 작업.
- **환경(environment)** — 개발용 / 테스트용 / 실제 운영용 등 코드가 도는 무대.

이 용어들에 **거부 반응만 없어져도** 교육의 1/3은 끝난 셈입니다.

## 4. AI-DO Portal은 어떤 물건인가

아주 크게 나눠 이렇게 생겼습니다. 흐름은 위에서 아래로 읽습니다.

| 층 | 구성 요소 | 설명 |
| --- | --- | --- |
| 1. 사용자 | 사용자 브라우저 | 화면을 보고 클릭·타이핑 |
| 2. 프런트엔드(Web) | React SPA(단일 페이지 앱) | 화면 렌더링, 입력 수집 |
| 3. 백엔드(API) | Python FastAPI | 비즈니스 로직, 권한, 데이터 가공 |
| 4. 저장·부가 | DB · Redis · MinIO(파일) · 워커(Celery) · OpenAI | 데이터 보관, 큐, 파일, AI 호출 |

프런트가 API로 요청을 보내면, API가 필요한 만큼 DB·Redis·MinIO·워커·OpenAI를 묶어 처리한 뒤 응답을 돌려주는 구조입니다.

이 포털이 현업에 제공하는 기능은 대략 이런 것들입니다.

- **AI 채팅** — 사내 데이터와 연결된 대화형 AI.
- **위키·문서 편집** — BlockNote 에디터로 여러 명이 **동시 편집**.
- **프로젝트 관리(PMS)** — 이슈, 마일스톤, 보드.
- **캘린더·회의** — FullCalendar 기반 일정·회의실 관리.
- **워크스페이스 관리자 콘솔** — 사용자·권한·감사 로그.

이 자료의 Part 2에서는 위 각 기능이 **어떤 기술로 구현되어 있는지** 를 하나씩 뜯어봅니다.

## 6. 핵심 요약

- 우리는 "코드를 직접 치는 개발자"가 아니라 "AI에게 정확히 시키고 검증하는 개발자"를 목표로 한다.
- 바이브 코딩의 핵심은 **도메인 지식 + 시스템 지도 + 검증 습관** 이다.
- 개발자의 3가지 습관: ① 어디 있는지 짐작, ② 작게 쪼개기, ③ 작은 성공 반복.
- AI-DO Portal은 프런트(React) ↔ 백(FastAPI) ↔ DB/Redis/MinIO/워커/OpenAI 의 여러 층으로 된 시스템이다.
