# 01. 오리엔테이션 — 비개발자의 마음가짐

> **한 줄 요약.** 개발은 외국어 배우기와 비슷하다. 완벽히 이해하려 하지 말고, **일단 통하는 수준** 부터 쌓아 올린다.

---

## 1. 왜 우리가 코드를 만져야 하나

회사가 AX(AI Transformation)를 한다는 말은, 이제 업무가 "문서와 회의"뿐 아니라 "소프트웨어"로도 돌아간다는 뜻입니다. 소프트웨어는 한 번 만들고 끝나는 물건이 아닙니다. 마치 회사의 **사규처럼** 끊임없이 고치고 보강하며 살아 움직이는 것입니다.

우리는 이 포털을 단순히 "쓸 사람"이 아니라 "고쳐서 쓸 사람"이 되어야 합니다. 그래야 현업의 문제에 맞춰 포털을 빠르게 진화시킬 수 있습니다.

좋은 소식이 있습니다. 과거에는 이 일을 하려면 3~5년의 프로그래밍 경력이 필요했지만, 이제는 **AI가 대부분의 코드를 직접 써 줍니다**. 우리는 "뭘 하고 싶은지"를 정확히 설명하고, "AI가 한 일이 맞는지"를 확인할 줄 알면 됩니다.

그래서 이 교육의 목표는 **"코드를 직접 치는 사람"** 이 아니라 **"AI와 함께 코드를 만드는 사람"** 을 기르는 것입니다.

---

## 2. 바이브 코딩(Vibe Coding)이란

바이브 코딩이라는 용어는 2025년 초에 유행하기 시작했습니다. 의미는 이렇습니다.

> **"문법이나 세부 구현을 외우지 않고, 원하는 바를 자연어로 AI에게 설명하면서 코드를 만들어 나가는 방식."**

전통적 프로그래밍과 비교하면 이렇습니다.

| 구분 | 전통 프로그래밍 | 바이브 코딩 |
|---|---|---|
| 주체 | 사람이 코드를 친다 | 사람이 요구·검증, AI가 코드를 친다 |
| 요구 기술 | 언어·라이브러리 문법 숙지 | 요구사항을 잘 쪼개서 설명하는 능력 |
| 속도 | 느림 | 매우 빠름 |
| 위험 | 오타·버그 | 잘못된 방향·환각(hallucination) |
| 필요한 인간 역량 | 타이핑 속도 | 판단력·맥락 제공·검증 |

바이브 코딩은 "누구나 다 할 수 있다"는 뜻이 아니라, "**잘 설명하고 잘 검증하는 사람이 개발자가 될 수 있다**"는 뜻입니다. 잘 설명하려면 **도메인 지식 + 시스템에 대한 대략적 지도** 가 필요합니다. 이 자료가 바로 그 지도를 그려 줍니다.

---

## 3. 개발자처럼 생각하는 3가지 습관

### 3.1 "뭐가 어디 있는지 안다"는 감각

좋은 개발자는 **모든 코드를 다 외우는 사람이 아닙니다**. 오히려 "어디에 있을지 짐작하는 감각"이 훨씬 중요합니다.

비유하자면, 큰 도서관의 사서는 수십만 권의 책을 다 읽지 않았어도 "이 책은 아마 3층 동양사 서가에 있을 것"이라고 짐작할 수 있습니다. 우리가 배워야 하는 것도 그런 감각입니다. AIDOO Portal의 어떤 기능을 고치려 할 때, **"아, 이건 `apps/web/src/domains/docs/` 어딘가에 있겠지"** 라고 짐작할 수 있으면 절반은 성공입니다.

### 3.2 "작게 쪼갠다"는 본능

개발자는 큰 문제를 늘 **더 작은 문제들의 연속** 으로 바꿉니다. "로그인 기능을 만든다"는 말은 실제로는 다음의 연속입니다.

- 로그인 화면 그리기
- 이메일·비밀번호 입력 받기
- 서버에 로그인 요청 보내기
- 서버가 맞는지 확인
- 맞으면 세션 저장, 틀리면 오류 보여주기
- 세션을 가진 사람만 다른 페이지 접근 허용

이 **쪼개는 습관** 은 AI에게 일을 시킬 때 결정적으로 중요합니다. "로그인 만들어줘"라고 말하면 AI는 대충 만들어 주지만, 위처럼 6단계로 쪼개서 주문하면 훨씬 정확한 결과가 나옵니다.

### 3.3 "일단 돌리고, 깨지면 고친다"는 태도

비개발자들이 코드를 만지다가 자주 빠지는 함정이 **"한 번에 완벽히 이해하고 고치겠다"** 는 욕심입니다. 실제 개발자들은 오히려 이렇게 합니다.

1. 변경을 아주 작게 한다.
2. 바로 실행해 본다.
3. 깨지면 에러 메시지를 그대로 AI에게 보여준다.
4. 되면 커밋(기록)하고 다음 작은 변경으로 넘어간다.

"**작은 성공을 자주 쌓는다**"는 리듬이 중요합니다. 이 리듬이 있으면 몇 시간 뒤에도 어디서부터 잘못됐는지 쉽게 되짚을 수 있습니다.

## 4. 최소한으로 익혀야 할 용어 감각

다음 단어들은 이 자료 전체에서 반복해서 등장합니다. 정확한 정의는 뒤에서 다시 다룹니다. 지금은 **냄새만 맡아 둡시다.**

- **코드(code)** — 컴퓨터가 실행할 명령을 글로 쓴 것. 단순한 텍스트 파일입니다.
- **프로젝트(project)** — 여러 코드 파일과 설정을 묶은 한 단위. 여기서는 AIDOO Portal 전체가 한 프로젝트입니다.
- **저장소(repository, 레포, repo)** — 프로젝트의 모든 파일과 역사(변경 이력)를 담는 폴더. Git으로 관리됩니다.
- **프런트엔드(frontend)** — 사람이 보는 화면(브라우저에서 보이는 부분).
- **백엔드(backend)** — 화면 뒤에서 돌아가는 서버. 데이터를 저장하고 계산합니다.
- **데이터베이스(DB)** — 데이터를 영구히 보관하는 창고.
- **API** — 프런트와 백이 대화할 때 쓰는 약속(전화번호부 같은 것).
- **빌드(build)** — 우리가 쓴 코드를 컴퓨터가 빠르게 실행할 수 있는 형태로 바꾸는 작업.
- **배포(deploy)** — 빌드된 결과물을 실제 사용자가 쓸 수 있는 서버에 올리는 작업.
- **환경(environment)** — 개발용 / 테스트용 / 실제 운영용 등 코드가 도는 무대.

이 용어들에 **거부 반응만 없어져도** 교육의 1/3은 끝난 셈입니다.

## 5. AIDOO Portal은 어떤 물건인가

아주 크게 나눠 이렇게 생겼습니다.

```
 [사용자 브라우저]
      ↓  (화면)
 [ 프런트엔드 Web ]  ←— React로 만든 단일 페이지 앱(SPA)
      ↓  (API 호출)
 [ 백엔드 API ]     ←— Python FastAPI
      ↓↑
 [ DB ] [ Redis ] [ MinIO(파일) ] [ 워커(Celery) ] [ OpenAI ]
```

이 포털이 현업에 제공하는 기능은 대략 이런 것들입니다.

- **AI 채팅** — 사내 데이터와 연결된 대화형 AI.
- **위키·문서 편집** — BlockNote 에디터로 여러 명이 **동시 편집**.
- **프로젝트 관리(PMS)** — 이슈, 마일스톤, 보드.
- **캘린더·회의** — FullCalendar 기반 일정·회의실 관리.
- **워크스페이스 관리자 콘솔** — 사용자·권한·감사 로그.

이 자료의 Part 2에서는 위 각 기능이 **어떤 기술로 구현되어 있는지** 를 하나씩 뜯어봅니다.

- [ ] 작은 변경 → 바로 실행 → 깨지면 고치기 리듬을 연습할 준비가 되었다.
- [ ] 이 포털에서 **내가 가장 먼저 고쳐 보고 싶은 화면/기능** 을 하나 머릿속에 정해 두었다.

## 7. 핵심 요약

- 우리는 "코드를 직접 치는 개발자"가 아니라 "AI에게 정확히 시키고 검증하는 개발자"를 목표로 한다.
- 바이브 코딩의 핵심은 **도메인 지식 + 시스템 지도 + 검증 습관** 이다.
- 개발자의 3가지 습관: ① 어디 있는지 짐작, ② 작게 쪼개기, ③ 작은 성공 반복.
- AIDOO Portal은 프런트(React) ↔ 백(FastAPI) ↔ DB/Redis/MinIO/워커/OpenAI 의 여러 층으로 된 시스템이다.
