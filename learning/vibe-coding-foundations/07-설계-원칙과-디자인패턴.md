# 07. 설계 원칙과 디자인 패턴 — SOLID, DDD, ADR

> **한 줄 요약.** 설계 원칙은 "코드를 어떻게 나눠야 나중에 후회가 적은가"에 대한 **경험의 압축**이다. 외울 필요는 없고, **왜 그런 원칙이 생겼는지**만 감각하면 충분하다.

---

## 1. 왜 원칙이 필요한가

코드를 "일단 돌아가게만" 쓰면 한 달은 편합니다. 그러나 3개월이 지나면 코드가 스파게티가 되어 있고, **한 줄 고치면 다른 열 군데가 깨지는** 상태가 됩니다. 이런 코드를 **"레거시"** 라고 부르고, 많은 개발자가 평생의 업무 시간 대부분을 레거시 처리에 씁니다.

설계 원칙은 **"스파게티를 만들지 않기 위한 예방 규칙"** 입니다.

---

## 2. DRY, KISS, YAGNI — 이름이 재미있는 3대 원칙

가장 자주 들리는 원칙들입니다.

### 2.1 DRY (Don't Repeat Yourself)

"같은 지식을 두 군데에 써 두지 말라." 같은 규칙이 두 군데에 있으면 한쪽만 바꿀 때 **두 코드가 거짓말을 하는 상태** 가 됩니다.

예: "회의실 예약 시간 단위는 30분"이라는 규칙이 프런트에도, 백에도 따로 하드코딩되어 있으면 정책이 바뀔 때 실수가 생깁니다. 한 군데에 **상수**나 **설정**으로 두어야 합니다.

### 2.2 KISS (Keep It Simple, Stupid)

"바보가 봐도 이해할 만큼 단순하게 유지하라." 똑똑한 코드보다 **읽기 쉬운 코드** 가 낫습니다. 성능 최적화는 **문제가 생겼을 때만** 합니다. 이를 "**premature optimization** 은 악의 근원" (도널드 크누스)이라고도 합니다.

### 2.3 YAGNI (You Aren't Gonna Need It)

"당장 필요하지 않은 기능은 미리 만들지 마라." 많은 개발자가 "언젠가 쓰겠지"라며 과하게 일반화된 코드를 짜는데, 대부분의 경우 그 "언젠가"는 오지 않습니다.

이 세 가지를 몸에 붙이면 코드 품질의 70%가 잡힙니다.

---

## 3. SOLID — 객체지향 설계의 5대 원칙

로버트 C. 마틴(Uncle Bob)이 정리한 원칙입니다. 이름은 외우기 어렵지만 **감만** 잡으면 됩니다.

| 글자 | 원칙 | 한 줄 요약 |
|---|---|---|
| **S** | Single Responsibility | 한 클래스·함수는 **한 가지 책임** 만 진다. |
| **O** | Open/Closed | 기능 추가에는 열려 있고, 수정에는 닫혀 있어야 한다(상속·확장으로 늘리기). |
| **L** | Liskov Substitution | 자식 클래스는 부모를 **대체 가능** 해야 한다. |
| **I** | Interface Segregation | 큰 인터페이스 하나보다 **작게 쪼갠 여러 개** 가 낫다. |
| **D** | Dependency Inversion | 구체적 구현이 아니라 **추상(약속)에 의존** 하라. |

### 3.1 비유로 한 번 더

- **SRP(S)**: 스위스 아미 나이프보다 **한 가지 일을 잘하는 도구** 가 낫다. "로그인과 이메일 발송을 동시에 하는 함수"는 분리하라.
- **OCP(O)**: 결제 수단을 추가할 때 기존 코드를 수정하지 말고, 새 파일을 추가해서 기능을 확장하는 구조가 이상적.
- **LSP(L)**: `Bird`의 자식 `Penguin`이 "날다"를 구현하지 못하면 잘못된 상속이다.
- **ISP(I)**: "로봇 청소기"가 구현해야 할 인터페이스에 "말하기"까지 들어 있다면, 로봇은 쓸모없는 메소드 때문에 부담을 안게 된다.
- **DIP(D)**: "OpenAI만 쓸 수 있게" 하드코딩하지 말고 "LLM이라는 추상"에 의존해서, 나중에 Anthropic으로 바꿔도 코드 수정이 적게끔.

SOLID는 객체지향에 뿌리를 두지만, 함수형·TypeScript·Python 어디에서도 **감각의 층위에서** 유효합니다.

## 4. DDD (Domain-Driven Design)

Eric Evans가 2003년 책에서 체계화한 방법론입니다. 핵심 한 줄:

> **"코드를 기술이 아니라 비즈니스 도메인 중심으로 나누라."**

### 4.1 전통적 구조 vs DDD 구조

**전통적 구조(기술 기반):**
```
src/
  controllers/
    LoginController.py
    PmsController.py
    DocsController.py
  services/
    LoginService.py
    PmsService.py
    ...
  models/
    ...
```
→ "같은 종류끼리 모아두기". 기능 하나 고칠 때 **여러 폴더를 왔다갔다** 해야 함.

**DDD 구조(도메인 기반):**
```
domains/
  auth/
    router.py
    service.py
    models.py
  pms/
    router.py
    service.py
    models.py
  docs/
    ...
```
→ "한 기능에 필요한 것은 한 폴더에". **인지 비용** 이 훨씬 낮음.

### 4.2 우리 프로젝트는?

당연히 **DDD형**입니다. 실제 폴더 구조:

```
apps/api/src/aidoo_api/domains/
  ai/         ← AI 에이전트, 채팅, 도구 호출
  auth/       ← 로그인, 세션
  admin/      ← 관리자 콘솔
  calendar/   ← 일정
  conversations/
  docs/       ← 위키 문서, 실시간 협업
  documents/
  drafts/
  media/
  meeting/
  ocr/
  planner/
  pms/        ← 프로젝트 관리
  plm/
  wiki_pms/
```

프런트(`apps/web/src/domains/`)도 같은 구조로 거울상을 이룹니다. 프런트와 백의 도메인 이름이 같으면 **두 세계를 넘나들 때 길 찾기가 쉬워집니다.**

### 4.3 DDD의 핵심 개념

- **Ubiquitous Language (보편 언어)** — 비즈니스 쪽과 개발 쪽이 **같은 용어** 를 써야 한다. "예약"을 한쪽에서 reservation, 다른쪽에서 booking이라고 쓰면 안 됨.
- **Bounded Context** — 도메인의 경계. 이 경계를 넘어서는 공유는 신중하게.
- **Entity / Value Object** — 정체성이 있는 것(사용자) vs 값 자체가 중요한 것(주소).
- **Aggregate** — 하나처럼 묶여 있는 여러 엔티티(주문과 주문아이템은 "주문" 단위로 묶임).
- **Repository** — 영속성(DB) 접근을 추상화한 인터페이스.

비개발자 단계에서는 **"도메인별 폴더 구조가 왜 편한가"** 만 감각하면 충분합니다.

## 5. 디자인 패턴 — 반복되는 문제의 정형 해법

디자인 패턴은 1994년 *Design Patterns* (Gang of Four, GoF) 책에서 23가지로 체계화됐습니다. 지금은 그보다 훨씬 많아졌습니다. 여기서는 이 프로젝트에서 **자주 만나게 될 것들** 만 소개합니다.

### 5.1 Repository 패턴

"DB에 접근하는 로직을 따로 빼 두는 것." 비즈니스 로직(서비스)은 DB가 PostgreSQL인지 MySQL인지 몰라도 되도록.

```python
# 비즈니스 로직이 쓰는 '추상적' 인터페이스
class UserRepository(Protocol):
    def find_by_email(self, email: str) -> User | None: ...

# 실제 구현(이걸 바꾸면 DB 종류 교체 가능)
class SqlUserRepository:
    def find_by_email(self, email: str) -> User | None:
        ...
```

### 5.2 Service / Use Case 패턴

"한 번의 비즈니스 행위"를 하나의 함수·클래스로 모음. 예: `create_meeting_room()` 은 '검증 → 저장 → 알림 보내기' 를 내부에서 실행.

### 5.3 Observer 패턴 (이벤트 버스)

"누군가 변경을 발표하면, 관심 있는 구독자들이 반응한다." 우리 프로젝트의 Celery + Redis 큐가 이 패턴의 일종입니다.

### 5.4 Strategy 패턴

"같은 작업을 여러 방식 중 하나로 한다." 예: 음성 인식을 Qwen-ASR로 할지 Whisper로 할지 런타임에 고르는 것(워커의 `ASR_ENGINE` 설정).

### 5.5 Dependency Injection (DI)

"필요한 물건을 스스로 만들지 말고, **밖에서 받아라**." FastAPI가 `Depends()` 로 이 패턴을 언어 레벨에서 지원합니다.

```python
@router.get("/me")
def me(user: User = Depends(current_user)):
    return user
```
→ `me` 함수는 "누가 user를 가져오는지" 모름. 그래서 테스트할 때 가짜 user를 쉽게 주입할 수 있음.

### 5.6 CQRS와 Event Sourcing (언급만)

"읽기 모델과 쓰기 모델을 분리한다"는 고급 패턴. 대형 시스템에서 유용하지만 우리 프로젝트는 아직 필요 없습니다. 용어만 알아 두세요.

## 6. ADR — 설계 결정을 기록한다

**ADR(Architecture Decision Record)** 은 **"왜 이 기술/패턴을 선택했는가"를 한 쪽짜리 문서로 남기는 관행** 입니다. 포맷은 대략:

```
# ADR 0001: 제목

## 상태
Accepted / Superseded / Deprecated

## 맥락
어떤 문제가 있었나?

## 결정
무엇을 선택했나?

## 근거
왜 그 선택인가?

## 결과
장점·단점·영향

## 대안
고려했지만 기각한 선택지들
```

우리 프로젝트의 ADR:

- `adr/0001-ai-platform-extensibility.md` — AI 플랫폼을 확장 가능하게 설계.
- `adr/0002-mcp-capability-platform.md` — MCP를 **"first-class capability"** 로 삼기로 결정.

ADR이 중요한 이유는 간단합니다. **3개월 뒤 새로 합류한 사람(또는 바이브 코딩하는 AI)에게 "왜 이렇게 됐는지" 설명해 주는 것** 이 ADR입니다. 여러분도 큰 결정을 할 때마다 ADR을 쓰는 습관을 들이세요.

---

## 7. 함수형 프로그래밍의 좋은 습관 (참고)

순수 함수형 언어로 바꾸자는 뜻은 아닙니다. 그러나 **다음 습관들은 TS/Python 어느 쪽에서도 유효** 합니다.

- **순수 함수 선호** — 같은 입력에는 같은 출력. 외부 상태를 건드리지 않음.
- **불변 데이터 선호** — 기존 객체를 고치지 말고 새 객체를 만들어 반환.
- **부수 효과 격리** — DB 쓰기, 파일 저장 같은 "세상에 영향 주는 일"은 경계에 몰아두기.

React(함수형 UI), Python의 `dataclass(frozen=True)` 등이 이 흐름의 실천입니다.

## 8. 실수하기 쉬운 점 — "원칙의 과잉"

초보자가 가장 자주 빠지는 함정은 **"모든 원칙을 동시에 지키려다 코드를 과하게 추상화하는 것"** 입니다. 이를 **오버 엔지니어링(over-engineering)** 이라 합니다.

규칙:

1. 처음엔 **KISS + YAGNI** 만 지킨다. 직관적으로 쓴다.
2. 같은 코드가 **세 번 반복되면** DRY 원칙을 적용해 추출한다.
3. 파일이 너무 커져서 **인지가 힘들어지면** DDD/SRP로 분리한다.
4. 문제가 생기면 그때 **SOLID의 해당 원칙** 을 펼친다.

"원칙은 목적이 아니라 도구"입니다.

---

## 9. 핵심 요약

- **DRY, KISS, YAGNI** 만 제대로 지켜도 코드 품질 70%는 잡힌다.
- **SOLID** 는 객체지향 설계의 5대 원칙. 감각적으로 알면 충분.
- **DDD** 는 "도메인 중심 폴더 구조". 우리 프로젝트의 `domains/` 배치가 그 실천.
- **디자인 패턴** 중 이 프로젝트에서 자주 만나는 것: Repository, Service, Observer/이벤트, Strategy, DI.
- **ADR** 로 설계 결정을 기록하는 관행이 있다. 우리 `adr/0001`, `adr/0002` 참조.
- 원칙은 **도구**이다. 과하게 지키려다 오버엔지니어링에 빠지지 않기.
