# 07. 설계 원칙과 디자인 패턴 — SOLID, DDD, ADR

> **한 줄 요약.** 설계 원칙은 "코드를 어떻게 나눠야 나중에 후회가 적은가"에 대한 **경험의 압축**이다. 외울 필요는 없고, **왜 그런 원칙이 생겼는지**만 감각하면 충분하다.

---

## 1. 왜 원칙이 필요한가

코드를 "일단 돌아가게만" 쓰면 한 달은 편합니다. 그러나 3개월이 지나면 코드가 스파게티가 되어 있고, **한 줄 고치면 다른 열 군데가 깨지는** 상태가 됩니다. 이런 코드를 **"레거시(legacy, 이전 세대가 남긴 유산)"** 라고 부르고, 많은 개발자가 평생의 업무 시간 대부분을 레거시 처리에 씁니다.

설계 원칙은 **"스파게티를 만들지 않기 위한 예방 규칙"** 입니다.

### 1.1 왜 원칙이 필요한지 빠르게 정리

- 책임이 다른 코드를 섞어 두면 초기 속도는 빨라도 유지보수 비용이 급격히 증가합니다. 설계 원칙은 이 비용을 선제적으로 줄이기 위한 규칙입니다.
- 역할별 분리는 단일 책임 원칙의 핵심입니다. 기능 수정 시 영향을 예측하기 쉬워지고 리뷰 품질이 올라갑니다.
- 폴더 구조가 일관되면 코드 탐색 시간이 줄고 팀 온보딩 속도가 빨라집니다.

### 1.2 ⚠️ 짚고 갈 오해들

- **"좋은 설계는 처음부터 완벽해야 한다."**
  좋은 설계는 **리팩토링(refactoring, 동작은 그대로 두고 구조만 다듬기)** 을 통해 조금씩 자라는 것에 가깝습니다.
- **"원칙을 많이 알수록 좋은 코드가 나온다."**
  원칙 과잉(오버엔지니어링)은 오히려 더 나쁜 코드를 만듭니다. 원칙은 필요할 때만 꺼내 쓰는 도구입니다.
- **"레거시 = 오래된 코드."**
  레거시의 실체는 "**테스트가 없어 손대기 두려운 코드**"에 가깝습니다. 일주일 전에 쓴 코드도 레거시가 될 수 있습니다.

## 2. DRY, KISS, YAGNI — 이름이 재미있는 3대 원칙

가장 자주 들리는 원칙들입니다.

### 2.1 DRY (Don't Repeat Yourself)

"같은 지식을 두 군데에 써 두지 말라." 같은 규칙이 두 군데에 있으면 한쪽만 바꿀 때 **두 코드가 거짓말을 하는 상태** 가 됩니다.

예: "회의실 예약 시간 단위는 30분"이라는 규칙이 프런트에도, 백에도 따로 하드코딩되어 있으면 정책이 바뀔 때 실수가 생깁니다. 한 군데에 **상수**나 **설정**으로 두어야 합니다.

### 2.2 KISS (Keep It Simple, Stupid)

"바보가 봐도 이해할 만큼 단순하게 유지하라." 똑똑한 코드보다 **읽기 쉬운 코드** 가 낫습니다. 성능 최적화는 **문제가 생겼을 때만** 합니다. 이를 "**premature optimization** 은 악의 근원" (도널드 크누스)이라고도 합니다.

### 2.3 YAGNI (You Aren't Gonna Need It)

"당장 필요하지 않은 기능은 미리 만들지 마라." 많은 개발자가 "언젠가 쓰겠지"라며 과하게 일반화된 코드를 짜는데, 대부분의 경우 그 "언젠가"는 오지 않습니다.

이 세 가지를 몸에 붙이면 코드 품질의 70%가 잡힙니다.

### 2.4 🏢 현장에서 본 두 장면

**케이스 A — 회의실 요금표 하드코딩의 저주.**
예약 시스템에서 "평일 시간당 1만 원"이라는 숫자가 프런트(예약 화면)·백(영수증 계산)·관리자(리포트) 세 군데에 흩어져 있었다. 법인카드 정책이 바뀌어 1만 2천 원으로 조정할 때 한 곳을 빠뜨려 **영수증과 리포트가 다른 금액**으로 찍혔다. DRY를 지켰다면 `config/pricing.yml` 한 줄 수정으로 끝났을 일이다.

**케이스 B — "나중에 쓸 수도 있어서" 만든 기능이 2년 동안 아무도 안 씀.**
결재 시스템에 "예비 결재자" 필드를 미리 추가했는데, 도입 논의조차 없었다. 그 필드 때문에 마이그레이션·UI·교육 자료가 모두 늘어났다. YAGNI를 지켰다면 피할 수 있었다.

### 2.5 ⚠️ 헷갈리기 쉬운 것들

- **"DRY는 중복 코드 제거다."**
  DRY의 핵심은 "**같은 지식의 중복 제거**"입니다. 겉모양이 비슷해도 **이유가 다른** 두 코드는 각자 두는 편이 맞습니다.
- **"KISS는 짧은 코드가 답이다."**
  KISS가 말하는 단순함은 "**읽는 사람의 인지 비용이 낮은 코드**"입니다. 때로는 길게 쓰는 쪽이 더 단순할 수 있습니다.

## 3. SOLID — 객체지향 설계의 5대 원칙

로버트 C. 마틴(Uncle Bob)이 정리한 원칙입니다. 이름은 외우기 어렵지만 **감만** 잡으면 됩니다.

| 글자 | 원칙 | 한 줄 요약 |
|---|---|---|
| **S** | Single Responsibility | 한 클래스·함수는 **한 가지 책임** 만 진다. |
| **O** | Open/Closed | 기능 추가에는 열려 있고, 수정에는 닫혀 있어야 한다(상속·확장으로 늘리기). |
| **L** | Liskov Substitution | 자식 클래스는 부모를 **대체 가능** 해야 한다. |
| **I** | Interface Segregation | 큰 인터페이스 하나보다 **작게 쪼갠 여러 개** 가 낫다. |
| **D** | Dependency Inversion | 구체적 구현이 아니라 **추상(약속)에 의존** 하라. |

### 3.1 SOLID를 실무 문장으로 다시 정리

- **SRP(S)**: 함수/클래스는 하나의 변경 이유만 갖도록 분리한다. 예: 로그인 검증과 이메일 발송 로직을 분리한다.
- **OCP(O)**: 신규 기능은 확장 지점으로 추가하고, 검증된 기존 코어 로직 수정은 최소화한다.
- **LSP(L)**: 하위 타입은 상위 타입이 약속한 동작을 깨지 않아야 한다.
- **ISP(I)**: 인터페이스는 작고 명확하게 분리해 불필요한 메서드 의존을 줄인다.
- **DIP(D)**: 구체 구현이 아니라 추상 인터페이스에 의존해 교체 비용을 낮춘다.

SOLID는 객체지향에 뿌리를 두지만, 함수형·TypeScript·Python 어디에서도 **감각의 층위에서** 유효합니다.

### 3.2 ⚠️ 바로잡고 싶은 오해

- **"SOLID는 객체지향(OOP)에서만 쓸모가 있다."**
  Python 함수, React 컴포넌트, 심지어 Excel 함수에도 **단일 책임** 과 **의존성 역전** 감각은 그대로 유효합니다.
- **"단일 책임이란 함수가 한 줄이어야 한다는 뜻이다."**
  한 함수가 **"바뀔 이유가 하나뿐(one reason to change)"** 이면 됩니다. 코드 줄 수와는 무관합니다.

### 3.3 🏢 엑셀 매크로의 교훈

**케이스 — 엑셀 매크로가 "양식 생성 + 이메일 전송 + 로그 기록"을 한 함수에 몰아서 수행하는 경우.**
양식이 바뀌자 매크로 전체가 꼬이면서 이메일까지 안 나갔다. 이를 3개 함수로 쪼개면(SRP), 양식 수정이 이메일 로직을 건드리지 않는다. AI에게 "이 매크로를 책임별로 쪼개 줘"라고 요청하는 것이 바이브 코딩의 첫 리팩토링 훈련으로 좋다.

## 4. DDD (Domain-Driven Design)

Eric Evans가 2003년 책에서 체계화한 방법론입니다. 핵심 한 줄:

> **"코드를 기술이 아니라 비즈니스 도메인 중심으로 나누라."**

### 4.1 전통적 구조 vs DDD 구조

**전통적 구조(기술 기반):**
```
src/
  controllers/
    LoginController.py
    PmsController.py
    DocsController.py
  services/
    LoginService.py
    PmsService.py
    ...
  models/
    ...
```
→ "같은 종류끼리 모아두기". 기능 하나 고칠 때 **여러 폴더를 오가야** 합니다.

**DDD 구조(도메인 기반):**
```
domains/
  auth/
    router.py
    service.py
    models.py
  pms/
    router.py
    service.py
    models.py
  docs/
    ...
```
→ "한 기능에 필요한 것은 한 폴더에". **인지 비용** 이 훨씬 낮음.

### 4.2 우리 프로젝트는?

당연히 **DDD형**입니다. 실제 폴더 구조:

```
apps/api/src/aidoo_api/domains/
  ai/         ← AI 에이전트, 채팅, 도구 호출
  auth/       ← 로그인, 세션
  admin/      ← 관리자 콘솔
  calendar/   ← 일정
  conversations/
  docs/       ← 위키 문서, 실시간 협업
  documents/
  drafts/
  media/
  meeting/
  ocr/
  planner/
  pms/        ← 프로젝트 관리
  plm/
  wiki_pms/
```

프런트(`apps/web/src/domains/`)도 같은 구조로 거울상을 이룹니다. 프런트와 백의 도메인 이름이 같으면 **두 세계를 넘나들 때 길 찾기가 쉬워집니다.**

### 4.3 DDD의 핵심 개념

- **Ubiquitous Language (보편 언어)** — 비즈니스 쪽과 개발 쪽이 **같은 용어** 를 써야 한다. "예약"을 한쪽에서 reservation, 다른쪽에서 booking이라고 쓰면 안 됨.
- **Bounded Context** — 도메인의 경계. 이 경계를 넘어서는 공유는 신중하게.
- **Entity / Value Object** — 정체성이 있는 것(사용자) vs 값 자체가 중요한 것(주소).
- **Aggregate** — 하나처럼 묶여 있는 여러 엔티티(주문과 주문아이템은 "주문" 단위로 묶임).
- **Repository** — 영속성(DB) 접근을 추상화한 인터페이스.

비개발자 단계에서는 **"도메인별 폴더 구조가 왜 편한가"** 만 감각하면 충분합니다.

### 4.4 DDD 구조가 주는 실무 이점

- 도메인 기준 구조는 기능 변경 시 탐색 범위를 줄여 수정·리뷰·테스트를 빠르게 만듭니다.
- 기술 계층 기준 폴더보다 도메인 기준 폴더가 책임 경계를 명확히 하므로 팀 간 커뮤니케이션 비용이 낮아집니다.

### 4.5 ⚠️ 자주 하는 오해

- **"DDD는 대기업 시스템에서나 쓴다."**
  5명짜리 팀의 사내 포털에서도 "도메인별 폴더"만 지켜도 DDD의 핵심 이득은 대부분 얻을 수 있습니다.
- **"도메인 이름은 개발자가 정하면 된다."**
  도메인 이름은 **현업에서 쓰는 용어** 를 그대로 가져오는 것이 원칙입니다(Ubiquitous Language). 예약을 한쪽에서는 `reservation`, 다른 쪽에서는 `booking`이라고 부르면 의사소통 비용이 급격히 증가합니다.
- **"폴더만 잘 나누면 DDD다."**
  DDD의 본질은 **비즈니스 언어로 모델을 짜는 것** 입니다. 폴더 구조는 그 결과물에 해당합니다.

### 4.6 🛠️ 5분 실습

- `apps/api/src/aidoo_api/domains/` 를 열어 각 폴더 이름을 소리 내어 읽어 본다.
- 본인 업무에서 반복적으로 등장하는 **명사 5개**를 적어 본다 (예: "결재", "출장", "발주", "교육", "평가").
- 이 중 지금 당장 포털에 추가한다면 **어떤 이름의 도메인 폴더**가 될지 상상한다. → 이것이 DDD식 사고의 출발이다.

## 5. 디자인 패턴 — 반복되는 문제의 정형 해법

디자인 패턴은 1994년 *Design Patterns* (Gang of Four, GoF) 책에서 23가지로 체계화됐습니다. 지금은 그보다 훨씬 많아졌습니다. 여기서는 이 프로젝트에서 **자주 만나게 될 것들** 만 소개합니다.

### 5.1 Repository 패턴

"DB에 접근하는 로직을 따로 빼 두는 것." 비즈니스 로직(서비스)은 DB가 PostgreSQL인지 MySQL인지 몰라도 되도록.

```python
# 비즈니스 로직이 쓰는 '추상적' 인터페이스
class UserRepository(Protocol):
    def find_by_email(self, email: str) -> User | None: ...

# 실제 구현(이걸 바꾸면 DB 종류 교체 가능)
class SqlUserRepository:
    def find_by_email(self, email: str) -> User | None:
        ...
```

### 5.2 Service / Use Case 패턴

"한 번의 비즈니스 행위"를 하나의 함수·클래스로 모음. 예: `create_meeting_room()` 은 '검증 → 저장 → 알림 보내기' 를 내부에서 실행.

### 5.3 Observer 패턴 (이벤트 버스)

"누군가 변경을 발표하면, 관심 있는 구독자들이 반응한다." 우리 프로젝트의 Celery + Redis 큐가 이 패턴의 일종입니다.

### 5.4 Strategy 패턴

"같은 작업을 여러 방식 중 하나로 한다." 예: 음성 인식을 Qwen-ASR로 할지 Whisper로 할지 런타임에 고르는 것(워커의 `ASR_ENGINE` 설정).

### 5.5 Dependency Injection (DI)

"필요한 물건을 스스로 만들지 말고, **밖에서 받아라**." FastAPI가 `Depends()` 로 이 패턴을 언어 레벨에서 지원합니다.

```python
@router.get("/me")
def me(user: User = Depends(current_user)):
    return user
```
→ `me` 함수는 "누가 user를 가져오는지" 모름. 그래서 테스트할 때 가짜 user를 쉽게 주입할 수 있음.

### 5.6 CQRS와 Event Sourcing (언급만)

"읽기 모델과 쓰기 모델을 분리한다"는 고급 패턴. 대형 시스템에서 유용하지만 우리 프로젝트는 아직 필요 없습니다. 용어만 알아 두세요.

### 5.7 ⚠️ 짚고 갈 오해들

- **"디자인 패턴은 다 외워야 한다."**
  자주 만나는 5~6개만 **감각적으로** 잡아 두면 충분합니다. 나머지는 필요할 때 AI에게 "이 경우에 어울리는 패턴이 뭐야?"라고 물으면 됩니다.
- **"패턴을 쓴 코드가 더 좋은 코드다."**
  패턴은 **해결해야 할 문제** 가 있을 때만 꺼내는 도구입니다. 문제가 없는데 패턴을 끼워 넣으면 그대로 오버엔지니어링이 됩니다.

## 6. ADR — 설계 결정을 기록한다

**ADR(Architecture Decision Record)** 은 **"왜 이 기술/패턴을 선택했는가"를 한 쪽짜리 문서로 남기는 관행** 입니다. 포맷은 대략:

```
# ADR 0001: 제목

## 상태
Accepted / Superseded / Deprecated

## 맥락
어떤 문제가 있었나?

## 결정
무엇을 선택했나?

## 근거
왜 그 선택인가?

## 결과
장점·단점·영향

## 대안
```

우리 프로젝트의 ADR:

- `adr/0001-ai-platform-extensibility.md` — AI 플랫폼을 확장 가능하게 설계.

ADR이 중요한 이유는 간단합니다. **3개월 뒤 새로 합류한 사람(또는 바이브 코딩하는 AI)에게 "왜 이렇게 됐는지" 설명해 주는 것** 이 ADR입니다. 여러분도 큰 결정을 할 때마다 ADR을 쓰는 습관을 들이세요.

### 6.1 ADR을 반드시 남겨야 하는 이유

- ADR은 "왜 A안이 아니라 B안을 선택했는지"를 미래 팀원에게 전달하는 공식 기록입니다.
- ADR이 있으면 기술 교체 검토 시 과거 제약과 의사결정 근거를 빠르게 재검증할 수 있습니다.

### 6.2 🏢 업무 시나리오

3년 전에 회사가 **"메일 서버를 왜 MS 365로 갔는가"** 를 기록하지 않은 탓에, 이번에 **Google Workspace**로 바꿀지 검토할 때 근거 자료가 전무했다. 당시 의사결정의 제약(예: 외부 감사 요건)이 아직 유효한지 판단 불가. 결국 재조사에만 2주가 들었다. ADR 한 페이지가 그 2주를 절약해 줬을 것이다.

## 7. 함수형 프로그래밍의 좋은 습관 (참고)

순수 함수형 언어로 바꾸자는 뜻은 아닙니다. 그러나 **다음 습관들은 TS/Python 어느 쪽에서도 유효** 합니다.

- **순수 함수 선호** — 같은 입력에는 같은 출력. 외부 상태를 건드리지 않음.
- **불변 데이터 선호** — 기존 객체를 고치지 말고 새 객체를 만들어 반환.
- **부수 효과 격리** — DB 쓰기, 파일 저장 같은 "세상에 영향 주는 일"은 경계에 몰아두기.

React(함수형 UI), Python의 `dataclass(frozen=True)` 등이 이 흐름의 실천입니다.

## 8. 실수하기 쉬운 점 — "원칙의 과잉"

초보자가 가장 자주 빠지는 함정은 **"모든 원칙을 동시에 지키려다 코드를 과하게 추상화하는 것"** 입니다. 이를 **오버 엔지니어링(over-engineering)** 이라 합니다.

규칙:

1. 처음엔 **KISS + YAGNI** 만 지킨다. 직관적으로 쓴다.
2. 같은 코드가 **세 번 반복되면** DRY 원칙을 적용해 추출한다.
3. 파일이 너무 커져서 **인지가 힘들어지면** DDD/SRP로 분리한다.
4. 문제가 생기면 그때 **SOLID의 해당 원칙** 을 펼친다.

"원칙은 목적이 아니라 도구"입니다.

---

## 9. 핵심 요약

- **DRY, KISS, YAGNI** 만 제대로 지켜도 코드 품질 70%는 잡힌다.
- **SOLID** 는 객체지향 설계의 5대 원칙. 감각적으로 알면 충분.
- **DDD** 는 "도메인 중심 폴더 구조". 우리 프로젝트의 `domains/` 배치가 그 실천.
- **디자인 패턴** 중 이 프로젝트에서 자주 만나는 것: Repository, Service, Observer/이벤트, Strategy, DI.
- **ADR** 로 설계 결정을 기록하는 관행이 있다. 우리 `adr/0001`, `adr/0002` 참조.
- 원칙은 **도구**이다. 과하게 지키려다 오버엔지니어링에 빠지지 않기.

## 10. 이해도 체크

1. DRY, KISS, YAGNI를 본인이 생각하는 쉬운 예로 하나씩 설명해 보세요.
2. SOLID의 "S(단일 책임)"는 왜 중요한가요? 회의실 예약 로직을 예로 들어 보세요.
3. 기술 기반 폴더 구조와 DDD식 도메인 기반 구조의 차이를 한 문장으로 정리하세요.
4. Dependency Injection이 왜 테스트를 쉽게 하는지 설명해 보세요.
5. ADR이 없는 팀에서 3개월 뒤 새 동료가 입사했다고 상상해 보세요. 그 동료가 겪을 가장 큰 불편은?
6. "오버 엔지니어링"이란 무엇이며, 본인 업무 경험에서 비슷한 사례(지나친 양식·규정 등)가 있다면 떠올려 적어 보세요.
7. 본인 업무에서 **도메인 명사 3개**를 골라 DDD식 폴더 이름으로 지어 보세요(예: `approval/`, `travel/`).
