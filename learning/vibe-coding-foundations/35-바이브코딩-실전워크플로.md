# 35. 바이브 코딩 실전 워크플로 — AI-DO Portal 개발 루프

> **한 줄 요약.** AI에게 맡기는 건 "놔두는 것"이 아니라 **맥락을 주고 작게 짧게 확인하는 습관**이다. 이 장은 비개발자 TF가 AI-DO Portal을 실제로 발전시킬 때 따를 **표준 개발 루프**를 제안한다.

> 🔑 **한 마디로.** 여러분의 역할은 **AI 작업의 감독관**이다. 타이핑 속도보다, **맥락을 설계하고 결과를 검수하는 능력**이 더 중요하다.

### 감독관 역할을 이해하는 3가지 포인트

1. 사람은 스펙과 품질 기준을 정의하고, 에이전트는 구현을 수행하며, 사람은 중간 결과를 반복 검토합니다.
2. AI가 초안을 빠르게 생산하더라도 최종 검수·승인은 사람 책임이라는 원칙이 유지됩니다.
3. 특히 운영 반영 코드는 작성 주체와 무관하게 머지 승인자가 결과 책임을 집니다.

### ⚠️ 바이브 코딩 실전에서 자주 듣는 오해

1. **"바이브 코딩 = 아무렇게나 시키기"** — 정반대입니다. **스펙이 좋을수록** AI 결과가 좋아집니다. 느슨한 프롬프트는 느슨한 코드를 낳습니다.
2. **"AI가 다 해 주니까 엔지니어링 원칙은 몰라도 된다"** — 테스트·타입·리뷰 같은 기본 원칙은 오히려 더 중요해집니다. AI가 만든 결과도 같은 기준으로 검증해야 합니다.
3. **"도구만 좋은 걸 쓰면 된다"** — 도구는 계속 바뀝니다. 이 장에서 고정해야 할 것은 특정 제품명이 아니라 **작업을 작게 쪼개고 검증하는 루프**입니다.
4. **"처음부터 완벽한 프롬프트를 써야 한다"** — 좋은 결과는 한 번의 주문이 아니라 **계획 요청, 중간 확인, 수정 요청**을 반복하면서 나옵니다.
5. **"프롬프트가 전부"** — 프롬프트보다 넓은 것이 **작업 맥락**입니다. 관련 파일, 규칙, 성공 기준, 금지 사항을 함께 관리해야 합니다.

## 1. 바이브 코딩의 재정의

12장에서 이미 봤지만 실전 맥락에서 다시 정리합니다.

- **코딩 파트너**: AI 코딩 도구가 IDE나 터미널에서 코드·테스트·문서 작업을 돕습니다.
- **사람은 감독**: 무엇을·왜 만들지 결정, 결과를 검수.
- **AI는 생산**: 코드·테스트·문서·리팩토링을 실행.

"바이브"라는 단어가 모호해 보이지만, **느슨한 자연어 의사소통 + 즉각 검증**이 핵심입니다.

## 2. 도구 선택 기준 — 도구보다 루프가 먼저다

AI 코딩 도구의 이름과 기능은 계속 바뀝니다. 교재에서 고정해야 할 것은 특정 제품 비교가 아니라 **어떤 기준으로 도구를 고르고, 어떤 절차로 결과를 검증할지**입니다.

### 2.1 도구를 고를 때 보는 5가지 질문

| 질문 | 왜 중요한가 |
|---|---|
| 프로젝트 폴더 전체를 안전하게 읽을 수 있는가 | 관련 파일을 모르면 그럴듯한 추측을 하기 쉽습니다. |
| 변경 전 계획을 보여 주고 멈출 수 있는가 | 비개발자는 구현보다 **변경 범위 확인**이 먼저 필요합니다. |
| 테스트·린트·타입 검사를 실행할 수 있는가 | AI의 말이 아니라 실행 결과로 검증해야 합니다. |
| 민감 정보와 권한 범위를 통제할 수 있는가 | `.env`, 고객 데이터, 운영 DB 접근은 별도 승인 대상입니다. |
| 변경 내용을 사람이 리뷰하기 쉽게 보여 주는가 | diff가 읽히지 않으면 수정을 승인할 수 없습니다. |

### 2.2 이 프로젝트에서의 기본 원칙

- AI 도구는 항상 **프로젝트 루트**에서 실행합니다.
- 작업 시작 전 `git status`로 기존 변경이 있는지 확인합니다.
- 이 저장소의 활성 규칙 원본은 루트 `agents.md` 하나입니다. 도구별 별도 규칙 파일을 새로 만들지 않습니다.
- 큰 작업은 바로 구현하지 않고 **수정할 파일 목록·순서·검증 방법**을 먼저 받습니다.
- 새 의존성, DB 변경, 운영 데이터 수정, 대량 파일 삭제는 AI가 제안해도 바로 실행하지 않고 사람이 승인합니다.

### 2.3 셋업 체크리스트

- Node.js, pnpm, Python, Docker가 프로젝트 요구 버전에 맞는지 확인.
- Git 이름·이메일·SSH 키 설정.
- 에디터 플러그인: ESLint, Prettier, Ruff, Python, TypeScript.
- `.env.example` 을 복사해 로컬 `.env` 생성. 실제 시크릿은 커밋하거나 프롬프트에 붙이지 않음.
- `docker compose up -d` 로 로컬 인프라가 뜨는지 확인.
- AI 도구에 연결된 MCP 서버나 외부 계정 권한을 확인하고, 쓰지 않는 연결은 끕니다.

## 3. 표준 개발 루프 — "7단계"

이 프로젝트에 맞춘 **표준 루프**를 익혀 두면, 무엇을 고쳐야 할 때든 같은 흐름을 반복하면 됩니다.

### 3.1 1단계 — 이슈 작성

"뭘 할 건지"를 PMS나 GitHub Issue에 적습니다. **한 줄 요약 + 기대 결과 + 검증 기준**. AI에게 이 텍스트를 그대로 던질 수 있도록 정제.

### 3.2 2단계 — 브랜치 생성

```bash
git checkout -b feat/calendar-filter
```

브랜치 이름 규칙: `feat/` `fix/` `chore/` `docs/` 등(4장).

### 3.3 3단계 — 맥락 주기

AI에게 첫 프롬프트를 던집니다. **좋은 프롬프트의 4요소**:

1. **무엇을 할지** (목표)
2. **왜 하는지** (배경)
3. **관련 파일 경로**
4. **제약**(테스트 통과, 기존 스타일 준수, 시간 제약 등)

예시 프롬프트:

```
목표: 캘린더 화면에 "한국 공휴일만 보기" 토글을 추가해 줘.
배경: 현재 @hyunbinseo/holidays-kr 이벤트가 항상 섞여서 팀 스케줄이 묻힘.
경로: apps/web/src/domains/calendar/
제약: Mantine Switch로 UI 구성, 선호값을 localStorage에 저장, Vitest 테스트도 추가.
```

### 3.4 4단계 — 작게 요청

한 번에 거대한 덩어리 대신 **작은 단위**로 요청:

- "먼저 훅 `useHolidayToggle` 만 만들어 줘."
- "이제 캘린더 페이지에 Switch 붙여 줘."
- "테스트 하나 써 줘."

각 단계 후 **결과 확인 → 커밋 → 다음 단계**.

### 3.5 5단계 — 실행·검증

- 로컬에서 `pnpm dev` 로 직접 보기.
- `pnpm test` / `pnpm lint` 로 자동 확인.
- **눈으로** 상태를 체크. AI의 설명만 믿지 말 것.

### 3.6 6단계 — 커밋·푸시

- Conventional Commits 규칙대로(4장).
- 실패한 상태로 커밋하지 말기. 워킹(동작) + 테스트 통과 상태만.

### 3.7 7단계 — PR과 리뷰

- PR 본문에 **무엇을 / 왜 / 어떻게 검증했는지**.
- CI가 자동으로 돌며 피드백.
- 팀원 한 명 이상의 리뷰 후 머지.

## 4. 프롬프트 노하우 — 이 프로젝트에서 자주 쓰는 패턴

### 4.1 "테스트부터 쓰게 하기"

```
먼저 apps/web/src/lib/date/format.spec.ts 에 실패하는 테스트 세 개를 써 줘.
그다음 format.ts를 구현해 그 테스트를 통과시켜 줘.
```

AI가 **요구 사항을 테스트로 명문화**하므로 결과가 안정적.

### 4.2 "변경 계획부터 제시"

```
이 기능을 넣기 전에, 어떤 파일을 어떤 순서로 수정할지 계획만 먼저 말해 줘.
내가 OK하면 수정을 시작해 줘.
```

실수·과잉 변경 방지. 바이브 코딩의 **세이프가드**.

### 4.3 "스크립트 기반 리팩토링"

```
아래 조건을 충족하는 codemod 스크립트(ts-morph 기반)를 만들어 줘:
- 모든 `useState<string>('')` 호출을 `useInputState('')` 훅으로 치환
- 이 훅은 apps/web/src/lib/hooks.ts 에 추가
```

수십 파일을 일관되게 바꿀 때.

### 4.4 "로그/에러부터 보여주기"

```
테스트가 실패했어. 아래가 전체 로그야. (붙여넣기) 원인 찾고 최소 수정으로 고쳐 줘.
```

오류 메시지는 가장 강력한 프롬프트.

### 4.5 하위 에이전트에 위임 ("격리 조사")

일부 AI 도구는 **하위 에이전트**나 별도 작업 세션을 지원합니다. 메인 세션을 어지럽히지 않고 독립 컨텍스트로 조사·리팩토링을 시킬 때 좋습니다.

```
Subagent로 apps/api/src/ai_do_api/domains/docs 전체를 탐색해
Alembic 마이그레이션이 없는 모델 필드가 있는지 조사해 줘.
결과만 요약으로 보고.
```

메인 세션의 컨텍스트는 그대로 유지됩니다.

### 4.6 Plan-and-Execute — "계획부터 먼저"

```
이 기능을 구현하기 전에, 먼저 10단계 이하의 실행 계획을 마크다운 체크리스트로만 써 줘.
내가 승인한 단계만 실제로 실행해 줘.
```

실수·과잉 변경을 막는 가장 효과적인 단일 프롬프트.

### 4.7 Reflection — "네 답을 스스로 검증해 봐"

```
방금 구현에 대해, 다음 기준을 스스로 체크리스트로 검증해 줘:
- 요구사항 A/B/C를 모두 만족하는가
- 기존 테스트를 깨지 않는가
- 추가 에지 케이스가 있는가
문제가 있으면 수정도 같이.
```

한 번의 추가 호출로 품질이 체감될 만큼 오릅니다.

### 4.8 Human-in-the-Loop 체크포인트

```
DB 스키마를 바꾸는 단계에 도달하면 실행 직전에 반드시 멈춰서
변경 내용을 diff로 보여 주고 내 승인을 기다려.
```

부작용이 큰 단계(DB, 외부 API, 파일 대량 삭제)에는 항상 체크포인트를.

## 5. 나쁜 바이브 코딩의 증상

- **커다란 변경 한 덩어리**: 200줄짜리 diff 한 번에 통과시키려 함 → 리뷰 불가능.
- **테스트 없이 "잘 됩니다"**: 돌려보지 않고 AI의 설명에만 의존.
- **비밀값 유출**: AI 프롬프트에 `.env` 전체를 붙여넣음(이러면 안 됨!).
- **이유 없는 새 의존성**: AI가 별 이유 없이 npm install X. 검토 후 최소 도입.
- **영혼 없는 PR 제목**: `update stuff` — 훗날 여러분도 자기 코드를 못 찾음.

해독제 — **작게, 자주, 눈으로 확인, 커밋 메시지는 진심으로**.

## 6. AI-DO Portal에 특화된 작업 시나리오

### 6.1 버그 수정

```
증상: /w/:slug/docs 페이지에서 새로고침 시 타이틀이 1초간 "undefined"로 보인다.
대상: apps/web/src/domains/docs/pages/DocsListPage.tsx 및 useLoaderData 관련 파일.
목표: 로딩 상태 UI로 교체. 테스트 추가.
```

### 6.2 새 도메인 기능

```
목표: "메모장(notes)" 도메인을 추가. 간단한 텍스트 노트 CRUD.
스펙:
- URL: /w/:slug/notes (목록), /w/:slug/notes/:id (상세)
- 백엔드: apps/api .../domains/notes/{router,service,models,schemas}.py
- Alembic 마이그레이션 포함
- 프런트: apps/web .../domains/notes/
- 관리자 화면에 최근 작성 노트 카운트 위젯
- 테스트: 백엔드 pytest, 프런트 Vitest
```

### 6.3 리팩토링

```
목표: apps/web/src/domains/docs 내의 fetch 함수를 lib/http 클라이언트로 통일
제약: 모든 기존 테스트 통과, 네트워크 에러 공통 처리(toast) 추가
```

### 6.4 운영 이슈 대응

```
상황: 운영 로그에 "openai.RateLimitError" 가 오늘 300건.
원인 가설: 요약 태스크가 배치 폭주.
목표: Celery 태스크에 exponential backoff + rate limiter(queue) 적용.
```

## 6.5 스펙 먼저 쓰기 — 스펙을 영구적 프롬프트로

스펙은 AI에게 반복해서 줄 수 있는 **기준 문서**입니다. 한 번 잘 쓴 스펙은 구현, 리팩토링, 디버깅, PR 설명, 테스트 체크리스트에 계속 재사용됩니다.

### 6.5.1 왜 필요한가

- 프롬프트는 **일회용**이 되기 쉽지만, 스펙은 **영구적**입니다.
- 스펙이 있으면 AI를 바꿔도, 팀원이 바뀌어도 같은 방향으로 갑니다.
- PR 설명·테스트 체크리스트·문서가 스펙을 근거로 일관성 있게 생산됩니다.

### 6.5.2 스펙으로 쓸 수 있는 문서

- **이슈 본문**: 왜 필요한지, 완료 기준이 무엇인지 남깁니다.
- **PR 본문**: 실제로 무엇을 바꿨고 어떻게 검증했는지 남깁니다.
- **ADR**: 구조나 정책처럼 오래 유지될 결정을 남깁니다.
- **테스트 이름**: 사용자가 기대하는 동작을 실행 가능한 문장으로 남깁니다.

중요한 것은 특정 도구가 아니라 **한 기준 문서를 계속 참조하면서 작업을 진행하는 습관**입니다.

### 6.5.3 좋은 스펙의 5가지 구성 요소

1. **목표** — 무엇을 달성하려 하는가.
2. **배경** — 왜 지금 필요한가, 어떤 사용자 페인을 푸는가.
3. **제약** — 기술 스택, 성능 목표, 호환성, 데드라인.
4. **성공 기준** — "완료"를 어떻게 판별하는가. 테스트·메트릭·사용자 시나리오.
5. **관련 파일·문서** — 기존 코드, ADR, 디자인, 데이터 모델.

### 6.5.4 AI-DO Portal에서 스펙 실전 사용

```
(이슈 본문 = 스펙)
목표: "캘린더에 공휴일 토글 추가"
배경: 팀 일정이 공휴일 이벤트에 묻혀 보임
제약: Mantine Switch 사용, localStorage 선호 저장, Vitest 테스트 추가
성공 기준:
- 토글 ON 시 공휴일 이벤트만 필터
- 새로고침 후 이전 선택 유지
- Vitest 테스트 2개 이상 그린
관련 파일:
- apps/web/src/domains/calendar/
- packages/docs/adr/0007-calendar-filters.md (가상의 예)
```

이 이슈 본문 그대로를 **AI에게 초기 프롬프트**로 투입하면 아주 잘 동작합니다. 이게 SDD의 본질입니다.

### 6.5.5 승인 후 구현 원칙

- 스펙은 **구현 전에 리뷰**를 받아야 합니다.
- AI가 스펙에서 벗어나려 하면 **"스펙 §3 성공 기준을 다시 읽고 맞춰"** 라고 지시.
- 스펙이 바뀌면 **스펙부터 고치고** 구현으로 간다(반대 방향 금지).

## 7. 컨텍스트 창 관리

AI는 한 번에 읽고 쓸 수 있는 **컨텍스트 한도**가 있습니다. 한도를 크게 넘으면 맥락을 놓치거나 부정확한 응답이 늘어납니다. 대처:

- 작업과 무관한 파일은 일일이 붙여넣지 않기.
- "관련 파일만 읽어 줘" 지시.
- 긴 회의록·로그는 **요약 후** 넘기기.
- 세션이 길어져 산만해지면 새 세션을 시작, 요점만 간단히 재투입.
- 컨텍스트가 큰 모델을 쓰더라도 "모든 걸 붙여 넣어도 된다"는 뜻은 아닙니다. 관련 없는 맥락은 **답 품질을 오히려 떨어뜨립니다**.

## 8. 안전장치

### 8.1 브랜치 보호

`main` 브랜치는 직접 push 금지. PR + 리뷰 + CI 통과만 허용.

### 8.2 환경 분리

- **로컬**: 내 컴퓨터. 실수해도 영향 0.
- **dev 서버**: 팀 공용 개발 환경.
- **staging**: 운영과 동일 구성 점검용.
- **production**: 실제 사용자 데이터.

AI가 시키는 대로 무심코 `production` 에 직접 DB 명령을 치는 일은 절대 없어야 합니다.

### 8.3 비밀값

- 절대 Git 커밋하지 말 것.
- AI 프롬프트에 붙여넣지 말 것(가명 값으로 바꿔 설명).
- 팀 단위는 시크릿 매니저 이용.

### 8.4 데이터 변경

운영 DB에서 레코드를 수정해야 할 땐 **트랜잭션** + **백업 확인** + **두 명 승인**. AI가 만든 스크립트를 바로 운영에 돌리지 않기.

### 8.5 MCP 서버 신뢰도 평가

AI-DO Portal에 외부 MCP 서버를 붙이면 AI가 실제 도구와 데이터에 접근할 수 있습니다. 편리하지만 권한이 커지는 만큼, 설치 전에는 아래 항목을 확인합니다.

1. **발행자 확인**: 공식 벤더·사내 관리 주체인지, 익명 커뮤니티 배포물인지 확인.
2. **권한 범위**: 이 서버가 어떤 데이터를 읽고/쓰는가. 최소 권한인가.
3. **코드 공개·감사**: 저장소가 공개돼 있는가. 최근 커밋·이슈 활동이 정상인가.
4. **네트워크 격리**: 사내 데이터를 다루는 MCP 서버는 **외부망 접속을 차단**하고 돌린다.
5. **승인 체크포인트**: 부작용이 있는 호출은 사용자 확인을 받도록 설정.

"MCP라고 해서 다 믿지 않는다"가 핵심입니다.

### 8.6 스펙 승인 → 구현 시작

6.5절의 원칙입니다. 스펙이 리뷰·승인되기 전에 구현을 시작하지 않습니다. AI가 "바로 짜 볼게요"라고 해도 **"스펙 먼저"** 라고 제어하는 습관이 품질을 지킵니다.

### 8.7 민감 데이터·시크릿

- `.env`는 **절대** AI 프롬프트에 붙이지 않음. 샘플 값으로 바꿔 설명.
- 사용자 PII(주민번호, 연락처)가 포함된 쿼리 결과를 AI에 넘기지 않음.
- 커밋 직전 시크릿 검출 도구(예: `git-secrets`, `trufflehog`)를 자동 실행.
- 팀은 시크릿 매니저(Doppler, 1Password, Vault) 사용.

### 🏢 AI-DO 기능 개발 한 바퀴 돌려보기

1. PM: "워크스페이스 대시보드에 '이번 주 내 할 일' 위젯이 필요해요"라고 이슈 생성.
2. AX TF 멤버가 이슈 본문을 **스펙 5요소**에 맞춰 정제(§6.5).
3. 브랜치 `feat/dashboard-myweek-widget` 생성.
4. AI 도구에 이슈 본문 투입 → **Plan-and-Execute** 요청(§4.6).
5. 계획 승인 후 1단계부터 실행. 서브에이전트(§4.5)로 기존 위젯 구조 조사.
6. 각 단계 후 `pnpm test`, `pnpm lint`, `pytest`.
7. Reflection 프롬프트(§4.7)로 자기 검증.
8. 커밋 → PR → 리뷰 → CI 통과 → 머지.
9. 스테이징 배포 확인 → 운영 배포.

한 기능이 **스펙 → 계획 → 실행 → 검증 → PR → 배포** 의 한 사이클로 돌아갑니다. 이 사이클이 **"감독관으로서의 바이브 코딩"** 의 전형입니다.

### 🛠️ 5분 실습 — 작업 규칙을 프롬프트에 넣어 보기

아래 규칙을 AI에게 첫 프롬프트로 붙여 넣고, 같은 수정 요청을 해 보세요.

```markdown
## 규칙: 테스트 우선
기능 추가나 수정 시, 먼저 실패하는 테스트를 작성하고

```

AI가 계획과 테스트를 먼저 말하는지 확인합니다. 이것이 **작업 맥락을 설계하는 가장 작은 실습**입니다.

## 10. 용어보다 중요한 역할 변화

### 10.1 비개발자에게 중요한 변화

바이브 코딩이라는 말은 가볍게 들리지만, 실무에서는 책임이 가볍지 않습니다. 비개발자가 코드를 직접 다 쓰지 않더라도 다음 세 가지를 맡게 됩니다.

- **문제 정의**: 무엇을 해결해야 하는지 설명합니다.
- **맥락 제공**: 관련 파일, 기존 규칙, 금지 사항, 성공 기준을 전달합니다.
- **결과 검수**: 테스트 결과, 화면 동작, 보안 영향, 운영 리스크를 확인합니다.

### 10.2 역할을 한 문장으로 정리하면

사람은 **방향과 기준을 정하고**, AI는 **초안을 만들고**, 사람은 다시 **검증하고 승인**합니다.

이 흐름을 지키면 비개발자도 개발팀과 같은 언어로 협업할 수 있습니다. 반대로 이 흐름이 없으면 AI가 만든 결과는 빨라 보여도 리뷰하기 어렵고, 운영에 반영하기 위험합니다.

### 10.3 이 교육 자료의 입장

이 자료는 "AI에게 자연어로 시킨다"에서 멈추지 않습니다. 목표는 **AI가 만든 결과를 업무 기준으로 판단할 수 있는 사람**을 만드는 것입니다.

## 11. 작업 맥락 설계 — 프롬프트보다 넓은 것

좋은 프롬프트는 한 문장이 아니라 **AI가 참고해야 할 정보 묶음**입니다. 같은 요청이라도 어떤 파일을 보여 주는지, 어떤 규칙을 알려 주는지, 무엇을 금지하는지에 따라 결과가 크게 달라집니다.

### 11.1 개념

작업 맥락 설계 = **AI에게 주어지는 모든 정보의 선택과 정리**.

- 시스템 프롬프트
- 도구 목록·도구 설명
- 대화 기록 요약
- 관련 파일·데이터
- 사용자가 지금 무엇을 보고 있는지
- `agents.md`·스펙·ADR 같은 장기 지식
- 메모리(지식 그래프)

"무엇을 포함하고, 무엇을 제외하고, 어떻게 정리할지"가 **성능의 가장 큰 레버**임이 드러났습니다.

### 11.2 실무 원칙

1. **관련 있는 것만 넣는다**: 컨텍스트가 많아도 무관한 정보는 품질을 떨어뜨림.
2. **구조화한다**: 마크다운 헤딩·표·체크리스트 등으로 AI가 파싱하기 쉽게.
3. **장기 지식은 승인된 파일로**: 이 프로젝트에서는 루트 `agents.md`, ADR, 스펙을 기준으로 삼음.
4. **정기 갱신**: 프로젝트가 진화하면 컨텍스트도 갱신. 죽은 규칙은 삭제.
5. **경계 설정**: 민감 데이터·비밀값은 컨텍스트에서 제외 규칙을 만든다.

### 11.3 AI-DO Portal의 컨텍스트 스택

- **프로젝트 규칙**: 루트 `agents.md`
- **구조 결정**: `adr/*.md`
- **이슈/PR 본문**: 이번 작업 스펙
- **파일 첨부**: 관련 코드·로그·디자인

AI 성능이 아쉽다면 **모델부터 바꾸지 말고 컨텍스트부터 점검**하세요. 열 중 여덟은 컨텍스트 문제입니다.

## 12. 핵심 요약

- 바이브 코딩의 본질은 **맥락 주기 + 작게 반복 + 즉각 검증**.
- **7단계 루프**(이슈 → 브랜치 → 맥락 → 작게 요청 → 검증 → 커밋 → PR)를 몸에 붙이면 대부분의 작업이 안전.
- **스펙 먼저 쓰기**로 스펙을 영구적 프롬프트로 삼는다.
- 프롬프트보다 넓은 **작업 맥락**을 의식적으로 관리한다.
- 테스트·린터·타입 검사가 있을 때 AI 결과를 신뢰할 수 있다.
- 운영 환경엔 **안전장치**(브랜치 보호, 환경 분리, 비밀값, 승인, MCP 신뢰도)가 반드시.
- 도구 선택은 제품명이 아니라 **계획, 검증, 권한 통제, diff 리뷰 가능성**을 기준으로 한다.
