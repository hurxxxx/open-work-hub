# 35. 바이브 코딩 실전 워크플로 — Claude Code · Cursor · AIDOO Portal 개발 루프

> **한 줄 요약.** AI에게 맡기는 건 "놔두는 것"이 아니라 **맥락을 주고 작게 짧게 확인하는 습관**이다. 이 장은 비개발자 TF가 AIDOO Portal을 실제로 발전시킬 때 따를 **표준 개발 루프**를 제안한다.

> 🔑 **한 마디로.** 2026년의 여러분은 **"자율 에이전트를 지휘하는 감독관"** 이다. 타이핑 속도가 아니라, **맥락을 설계하고 결과를 검수하는 능력**이 새 직무 기술이다.

### 감독관 역할을 이해하는 3가지 포인트

1. 사람은 스펙과 품질 기준을 정의하고, 에이전트는 구현을 수행하며, 사람은 중간 결과를 반복 검토합니다.
2. AI가 초안을 빠르게 생산하더라도 최종 검수·승인은 사람 책임이라는 원칙이 유지됩니다.
3. 특히 운영 반영 코드는 작성 주체와 무관하게 머지 승인자가 결과 책임을 집니다.

### ⚠️ 바이브 코딩 실전에서 자주 듣는 오해

1. **"바이브 코딩 = 아무렇게나 시키기"** — 정반대입니다. **스펙이 좋을수록** AI 결과가 좋아집니다. 느슨한 프롬프트는 느슨한 코드를 낳습니다.
2. **"AI가 다 해 주니까 엔지니어링 원칙은 몰라도 된다"** — 2024~2026 실패 사례의 공통점은 **원칙(테스트·타입·리뷰) 결여**입니다. 원칙은 오히려 더 중요해집니다.
3. **"Claude Code든 Cursor든 아무거나"** — 도구 특성이 다릅니다(§2). 대형 리팩토링은 Claude Code, 빠른 UI 편집은 Cursor, 자동 완성은 Copilot처럼 **상황별 전문 도구**가 있습니다.
4. **"용어가 '바이브 코딩'에서 끝난 줄"** — 2026년 초부터 업계는 **"agentic engineering"** 용어로 옮겨 가고 있습니다(§10). 개념은 연속적이지만 무게 중심이 "분위기 코딩"에서 "에이전트 지휘"로 이동하는 중입니다.
5. **"프롬프트가 전부"** — **컨텍스트가 전부**입니다. 프롬프트 엔지니어링의 상위 개념인 **컨텍스트 엔지니어링**이 2026년의 프레임입니다(§11).

## 1. 바이브 코딩의 재정의

12장에서 이미 봤지만 실전 맥락에서 다시 정리합니다.

- **코딩 파트너**: Claude Code(또는 Cursor · GitHub Copilot · Windsurf 등)가 IDE/터미널에 상주.
- **사람은 감독**: 무엇을·왜 만들지 결정, 결과를 검수.
- **AI는 생산**: 코드·테스트·문서·리팩토링을 실행.

"바이브"라는 단어가 모호해 보이지만, **느슨한 자연어 의사소통 + 즉각 검증**이 핵심입니다.

## 2. 도구 선택 가이드 — 2026.04 최신

**이 프로젝트 권장**: **Claude Code를 메인**, Cursor/VS Code를 보조. 큰 작업은 Claude Code, 작은 UI 수정은 Cursor, 자동 완성은 Copilot.

### 2.2 Claude Code의 7개 핵심 개념

AIDOO Portal 개발의 기본 도구이므로 이 7개는 머릿속에 상주시켜 두세요.

1. **CLAUDE.md** — 프로젝트·사용자·조직별 상시 컨텍스트 파일. "이 저장소에서 Claude가 알고 있어야 할 규칙"을 적어 둠.
2. **Skills** — `/command` 형태로 호출 가능한 재사용 스킬. 공통 워크플로(예: PR 리뷰, 릴리스 노트 생성)를 패키징.
3. **Subagents** — 격리된 컨텍스트로 독립 조사·리팩토링을 수행하는 하위 에이전트. 메인 세션을 어지럽히지 않음.
4. **Agent Teams** — 여러 서브에이전트를 역할 분담으로 구성.
5. **Plugins** — 외부 기능 확장. 예: `openproject` 플러그인으로 이슈 트래커 통합.
6. **Hooks** — 특정 이벤트(커밋 직전, 대화 압축 직전 등)에 자동 실행되는 스크립트. **자동화 행동**("매번 X를 하라")은 메모리가 아니라 hooks로 구현해야 실제로 동작.
7. **MCP Servers** — 외부 도구·데이터를 MCP 표준으로 연결.

**2026.04 업데이트 하이라이트**:

- **worktree 전환 지원**: 여러 브랜치를 병렬로 작업.
- **PreCompact hook**: 대화 압축 직전에 훅 실행(중요 컨텍스트 지키기).
- **`monitors` manifest**: 백그라운드 프로세스 모니터링 선언.
- **`/proactive` 별칭**: 프로액티브 제안 모드.
- **IDE 확장**: VS Code, JetBrains, Zed 공식 확장.

### 2.3 Cursor 3 — 2026.04.02 출시 요점

- **Agents Window**: Composer가 별도 워크스페이스로 분리됨. 에이전트 다중 실행·모니터링이 깔끔.
- **어디서나 시작**: 모바일·웹·데스크톱·Slack·GitHub·Linear에서 에이전트를 시작해 결과를 데스크톱에서 받기.
- **Composer 모델**: **5시간마다 체크포인트 RL 학습**. 사용 패턴을 반영해 지속 개선.
- **Design Mode**: 디자인 변주 여러 개를 병렬 생성 후 비교.
- **Cloud Agents on your network**: 코드·빌드·시크릿이 사용자 머신 밖으로 나가지 않도록 구성 가능. **보안 요구 맞춤**.

### 2.4 Zed + ACP — 2026.01 제안

Agent Client Protocol(ACP)은 "**에디터와 에이전트 사이의 표준**"을 노리는 시도입니다. MCP가 "AI와 도구"를 표준화했다면, ACP는 "에디터와 AI"를 표준화. 아직 초기지만, **Claude Opus 4.7 1M 컨텍스트 BYOK**과 **Agent Metrics 대시보드**로 실무 사용이 가능.

### 2.5 셋업 체크리스트

- Node.js 22, pnpm 10, Python 3.12, Docker 최신.
- Git 설정(이름·이메일), SSH 키.
- 에디터 플러그인: ESLint, Prettier, Ruff, Python, TypeScript.
- `.env.example` 을 복사해 로컬 `.env` 생성.
- `docker compose up -d` 로 인프라 뜨는지 확인.
- Claude Code 설치 + 프로젝트 루트의 `CLAUDE.md` 숙지.
- Cursor(선택) 설치 + 로그인.

## 3. 표준 개발 루프 — "7단계"

이 프로젝트에 맞춘 **표준 루프**를 익혀 두면, 무엇을 고쳐야 할 때든 같은 흐름을 반복하면 됩니다.

### 3.1 1단계 — 이슈 작성

"뭘 할 건지"를 PMS나 GitHub Issue에 적습니다. **한 줄 요약 + 기대 결과 + 검증 기준**. AI에게 이 텍스트를 그대로 던질 수 있도록 정제.

### 3.2 2단계 — 브랜치 생성

```bash
git checkout -b feat/calendar-filter
```

브랜치 이름 규칙: `feat/` `fix/` `chore/` `docs/` 등(4장).

### 3.3 3단계 — 맥락 주기

AI에게 첫 프롬프트를 던집니다. **좋은 프롬프트의 4요소**:

1. **무엇을 할지** (목표)
2. **왜 하는지** (배경)
3. **관련 파일 경로**
4. **제약**(테스트 통과, 기존 스타일 준수, 시간 제약 등)

예시 프롬프트:

```
목표: 캘린더 화면에 "한국 공휴일만 보기" 토글을 추가해 줘.
배경: 현재 @hyunbinseo/holidays-kr 이벤트가 항상 섞여서 팀 스케줄이 묻힘.
경로: apps/web/src/domains/calendar/
제약: Mantine Switch로 UI 구성, 선호값을 localStorage에 저장, Vitest 테스트도 추가.
```

### 3.4 4단계 — 작게 요청

한 번에 거대한 덩어리 대신 **작은 단위**로 요청:

- "먼저 훅 `useHolidayToggle` 만 만들어 줘."
- "이제 캘린더 페이지에 Switch 붙여 줘."
- "테스트 하나 써 줘."

각 단계 후 **결과 확인 → 커밋 → 다음 단계**.

### 3.5 5단계 — 실행·검증

- 로컬에서 `pnpm dev` 로 직접 보기.
- `pnpm test` / `pnpm lint` 로 자동 확인.
- **눈으로** 상태를 체크. AI의 설명만 믿지 말 것.

### 3.6 6단계 — 커밋·푸시

- Conventional Commits 규칙대로(4장).
- 실패한 상태로 커밋하지 말기. 워킹(동작) + 테스트 통과 상태만.

### 3.7 7단계 — PR과 리뷰

- PR 본문에 **무엇을 / 왜 / 어떻게 검증했는지**.
- CI가 자동으로 돌며 피드백.
- 팀원 한 명 이상의 리뷰 후 머지.

## 4. 프롬프트 노하우 — 이 프로젝트에서 자주 쓰는 패턴

### 4.1 "테스트부터 쓰게 하기"

```
먼저 apps/web/src/lib/date/format.spec.ts 에 실패하는 테스트 세 개를 써 줘.
그다음 format.ts를 구현해 그 테스트를 통과시켜 줘.
```

AI가 **요구 사항을 테스트로 명문화**하므로 결과가 안정적.

### 4.2 "변경 계획부터 제시"

```
이 기능을 넣기 전에, 어떤 파일을 어떤 순서로 수정할지 계획만 먼저 말해 줘.
내가 OK하면 수정을 시작해 줘.
```

실수·과잉 변경 방지. 바이브 코딩의 **세이프가드**.

### 4.3 "스크립트 기반 리팩토링"

```
아래 조건을 충족하는 codemod 스크립트(ts-morph 기반)를 만들어 줘:
- 모든 `useState<string>('')` 호출을 `useInputState('')` 훅으로 치환
- 이 훅은 apps/web/src/lib/hooks.ts 에 추가
```

수십 파일을 일관되게 바꿀 때.

### 4.4 "로그/에러부터 보여주기"

```
테스트가 실패했어. 아래가 전체 로그야. (붙여넣기) 원인 찾고 최소 수정으로 고쳐 줘.
```

오류 메시지는 가장 강력한 프롬프트.

### 4.5 Subagent에 위임 ("격리 조사")

Claude Code의 **Subagent** 는 메인 세션을 어지럽히지 않고 독립 컨텍스트로 조사·리팩토링을 시킬 때 좋습니다.

```
Subagent로 apps/api/src/aidoo_api/domains/docs 전체를 탐색해
Alembic 마이그레이션이 없는 모델 필드가 있는지 조사해 줘.
결과만 요약으로 보고.
```

메인 세션의 컨텍스트는 그대로 유지됩니다.

### 4.6 Plan-and-Execute — "계획부터 먼저"

```
이 기능을 구현하기 전에, 먼저 10단계 이하의 실행 계획을 마크다운 체크리스트로만 써 줘.
내가 승인한 단계만 실제로 실행해 줘.
```

실수·과잉 변경을 막는 가장 효과적인 단일 프롬프트.

### 4.7 Reflection — "네 답을 스스로 검증해 봐"

```
방금 구현에 대해, 다음 기준을 스스로 체크리스트로 검증해 줘:
- 요구사항 A/B/C를 모두 만족하는가
- 기존 테스트를 깨지 않는가
- 추가 에지 케이스가 있는가
문제가 있으면 수정도 같이.
```

한 번의 추가 호출로 품질이 체감될 만큼 오릅니다.

### 4.8 Human-in-the-Loop 체크포인트

```
DB 스키마를 바꾸는 단계에 도달하면 실행 직전에 반드시 멈춰서
변경 내용을 diff로 보여 주고 내 승인을 기다려.
```

부작용이 큰 단계(DB, 외부 API, 파일 대량 삭제)에는 항상 체크포인트를.

## 5. 나쁜 바이브 코딩의 증상

- **커다란 변경 한 덩어리**: 200줄짜리 diff 한 번에 통과시키려 함 → 리뷰 불가능.
- **테스트 없이 "잘 됩니다"**: 돌려보지 않고 AI의 설명에만 의존.
- **비밀값 유출**: AI 프롬프트에 `.env` 전체를 붙여넣음(이러면 안 됨!).
- **이유 없는 새 의존성**: AI가 별 이유 없이 npm install X. 검토 후 최소 도입.
- **영혼 없는 PR 제목**: `update stuff` — 훗날 여러분도 자기 코드를 못 찾음.

해독제 — **작게, 자주, 눈으로 확인, 커밋 메시지는 진심으로**.

## 6. AIDOO Portal에 특화된 작업 시나리오

### 6.1 버그 수정

```
증상: /w/:slug/docs 페이지에서 새로고침 시 타이틀이 1초간 "undefined"로 보인다.
대상: apps/web/src/domains/docs/pages/DocsListPage.tsx 및 useLoaderData 관련 파일.
목표: 로딩 상태 UI로 교체. 테스트 추가.
```

### 6.2 새 도메인 기능

```
목표: "메모장(notes)" 도메인을 추가. 간단한 텍스트 노트 CRUD.
스펙:
- URL: /w/:slug/notes (목록), /w/:slug/notes/:id (상세)
- 백엔드: apps/api .../domains/notes/{router,service,models,schemas}.py
- Alembic 마이그레이션 포함
- 프런트: apps/web .../domains/notes/
- 관리자 화면에 최근 작성 노트 카운트 위젯
- 테스트: 백엔드 pytest, 프런트 Vitest
```

### 6.3 리팩토링

```
목표: apps/web/src/domains/docs 내의 fetch 함수를 lib/http 클라이언트로 통일
제약: 모든 기존 테스트 통과, 네트워크 에러 공통 처리(toast) 추가
```

### 6.4 운영 이슈 대응

```
상황: 운영 로그에 "openai.RateLimitError" 가 오늘 300건.
원인 가설: 요약 태스크가 배치 폭주.
목표: Celery 태스크에 exponential backoff + rate limiter(queue) 적용.
```

## 6.5 Spec-Driven Development (SDD) — 스펙을 영구적 프롬프트로

2025~2026년에 자리 잡은 실무 방식. **스펙을 한 번 쓰고, 그 스펙을 AI에게 반복적으로 투입**해 구현·리팩토링·디버깅 모두를 같은 기준으로 끌고 갑니다.

### 6.5.1 왜 필요한가

- 프롬프트는 **일회용**이 되기 쉽지만, 스펙은 **영구적**입니다.
- 스펙이 있으면 AI를 바꿔도, 팀원이 바뀌어도 같은 방향으로 갑니다.
- PR 설명·테스트 체크리스트·문서가 스펙을 근거로 일관성 있게 생산됩니다.

### 6.5.2 참고 도구·프레임워크

- **GitHub Spec Kit**: 이슈·PR 템플릿을 스펙 중심으로 구성하는 키트.
- **Microsoft SpecKit**: 스펙 작성·버전 관리·AI 연동을 위한 도구.
- AIDOO Portal에서는 별도 도구 없이도 **이슈/PR 본문 + 기존 ADR 문서**가 스펙 역할을 수행합니다.

### 6.5.3 좋은 스펙의 5가지 구성 요소

1. **목표** — 무엇을 달성하려 하는가.
2. **배경** — 왜 지금 필요한가, 어떤 사용자 페인을 푸는가.
3. **제약** — 기술 스택, 성능 목표, 호환성, 데드라인.
4. **성공 기준** — "완료"를 어떻게 판별하는가. 테스트·메트릭·사용자 시나리오.
5. **관련 파일·문서** — 기존 코드, ADR, 디자인, 데이터 모델.

### 6.5.4 AIDOO Portal에서 스펙 실전 사용

```
(이슈 본문 = 스펙)
목표: "캘린더에 공휴일 토글 추가"
배경: 팀 일정이 공휴일 이벤트에 묻혀 보임
제약: Mantine Switch 사용, localStorage 선호 저장, Vitest 테스트 추가
성공 기준:
- 토글 ON 시 공휴일 이벤트만 필터
- 새로고침 후 이전 선택 유지
- Vitest 테스트 2개 이상 그린
관련 파일:
- apps/web/src/domains/calendar/
- packages/docs/adr/0007-calendar-filters.md (가상의 예)
```

이 이슈 본문 그대로를 **AI에게 초기 프롬프트**로 투입하면 아주 잘 동작합니다. 이게 SDD의 본질입니다.

### 6.5.5 승인 후 구현 원칙

- 스펙은 **구현 전에 리뷰**를 받아야 합니다.
- AI가 스펙에서 벗어나려 하면 **"스펙 §3 성공 기준을 다시 읽고 맞춰"** 라고 지시.
- 스펙이 바뀌면 **스펙부터 고치고** 구현으로 간다(반대 방향 금지).

## 7. 컨텍스트 창 관리

AI는 한 번에 읽고 쓸 수 있는 **컨텍스트 한도**가 있습니다. 한도를 크게 넘으면 맥락을 놓치거나 부정확한 응답이 늘어납니다. 대처:

- 작업과 무관한 파일은 일일이 붙여넣지 않기.
- "관련 파일만 읽어 줘" 지시.
- 긴 회의록·로그는 **요약 후** 넘기기.
- 세션이 길어져 산만해지면 새 세션을 시작, 요점만 간단히 재투입.
- Claude Opus 4.7의 **1M 컨텍스트**는 "모든 걸 붙여 넣어도 된다"는 뜻이 아닙니다. 관련 없는 맥락은 **답 품질을 오히려 떨어뜨립니다**.

## 8. 안전장치

### 8.1 브랜치 보호

`main` 브랜치는 직접 push 금지. PR + 리뷰 + CI 통과만 허용.

### 8.2 환경 분리

- **로컬**: 내 컴퓨터. 실수해도 영향 0.
- **dev 서버**: 팀 공용 개발 환경.
- **staging**: 운영과 동일 구성 점검용.
- **production**: 실제 사용자 데이터.

AI가 시키는 대로 무심코 `production` 에 직접 DB 명령을 치는 일은 절대 없어야 합니다.

### 8.3 비밀값

- 절대 Git 커밋하지 말 것.
- AI 프롬프트에 붙여넣지 말 것(가명 값으로 바꿔 설명).
- 팀 단위는 시크릿 매니저 이용.

### 8.4 데이터 변경

운영 DB에서 레코드를 수정해야 할 땐 **트랜잭션** + **백업 확인** + **두 명 승인**. AI가 만든 스크립트를 바로 운영에 돌리지 않기.

### 8.5 MCP 서버 신뢰도 평가

2026 Nerq 리포트 기준, 공개 MCP 서버 중 "high trust"로 분류되는 비율은 **12.9%** 에 불과합니다. AIDOO Portal에 외부 MCP 서버를 붙일 때 필수 점검:

1. **발행자 확인**: 공식 벤더(Anthropic, GitHub, Cloudflare 등) vs 익명 커뮤니티.
2. **권한 범위**: 이 서버가 어떤 데이터를 읽고/쓰는가. 최소 권한인가.
3. **코드 공개·감사**: 저장소가 공개돼 있는가. 최근 커밋·이슈 활동이 정상인가.
4. **네트워크 격리**: 사내 데이터를 다루는 MCP 서버는 **외부망 접속을 차단**하고 돌린다.
5. **승인 체크포인트**: 부작용이 있는 호출은 사용자 확인을 받도록 설정.

"MCP라고 해서 다 믿지 않는다"가 핵심입니다.

### 8.6 스펙 승인 → 구현 시작

6.5절의 SDD 원칙. 스펙이 리뷰·승인되기 전에 구현을 시작하지 않습니다. AI가 "바로 짜 볼게요"라고 해도 **"스펙 먼저"** 라고 제어하는 습관이 품질을 지킵니다.

### 8.7 민감 데이터·시크릿

- `.env`는 **절대** AI 프롬프트에 붙이지 않음. 샘플 값으로 바꿔 설명.
- 사용자 PII(주민번호, 연락처)가 포함된 쿼리 결과를 AI에 넘기지 않음.
- Claude Code의 **hooks** 로 커밋 직전 시크릿 검출(예: `git-secrets`, `trufflehog`) 자동 실행.
- 팀은 시크릿 매니저(Doppler, 1Password, Vault) 사용.

### 🏢 AIDOO 기능 개발 한 바퀴 돌려보기

1. PM: "워크스페이스 대시보드에 '이번 주 내 할 일' 위젯이 필요해요"라고 이슈 생성.
2. AX TF 멤버가 이슈 본문을 **스펙 5요소**에 맞춰 정제(§6.5).
3. 브랜치 `feat/dashboard-myweek-widget` 생성.
4. Claude Code에 이슈 본문 투입 → **Plan-and-Execute** 요청(§4.6).
5. 계획 승인 후 1단계부터 실행. 서브에이전트(§4.5)로 기존 위젯 구조 조사.
6. 각 단계 후 `pnpm test`, `pnpm lint`, `pytest`.
7. Reflection 프롬프트(§4.7)로 자기 검증.
8. 커밋 → PR → 리뷰 → CI 통과 → 머지.
9. 스테이징 배포 확인 → 운영 배포.

한 기능이 **스펙 → 계획 → 실행 → 검증 → PR → 배포** 의 한 사이클로 돌아갑니다. 이 사이클이 **"감독관으로서의 바이브 코딩"** 의 전형입니다.

## 11. Context Engineering — 프롬프트 엔지니어링의 상위 개념

2023~2024년의 "프롬프트 엔지니어링"은 **한 번의 질문을 잘 던지는 법**에 집중했습니다. 2025~2026년 업계는 **컨텍스트 엔지니어링**으로 프레임을 확장했습니다.

### 11.1 개념

컨텍스트 엔지니어링 = **AI에게 주어지는 모든 정보의 설계**.

- 시스템 프롬프트
- 도구 목록·도구 설명
- 대화 기록 요약
- 관련 파일·데이터
- 사용자가 지금 무엇을 보고 있는지
- CLAUDE.md·스펙·ADR 같은 장기 지식
- 메모리(지식 그래프)

"무엇을 포함하고, 무엇을 제외하고, 어떻게 정리할지"가 **성능의 가장 큰 레버**임이 드러났습니다.

### 11.2 실무 원칙

1. **관련 있는 것만 넣는다**: 1M 컨텍스트라도 무관한 정보는 품질을 떨어뜨림.
2. **구조화한다**: 마크다운 헤딩·표·체크리스트 등으로 AI가 파싱하기 쉽게.
3. **장기 지식은 영구 파일로**: CLAUDE.md, ADR, 스펙. 대화마다 다시 붙이지 않도록.
4. **정기 갱신**: 프로젝트가 진화하면 컨텍스트도 갱신. 죽은 규칙은 삭제.
5. **경계 설정**: 민감 데이터·비밀값은 컨텍스트에서 제외 규칙을 만든다.

### 11.3 AIDOO Portal의 컨텍스트 스택

- **전역**: `~/.claude/CLAUDE.md` (사용자 개인 규칙·선호)
- **프로젝트**: `/Users/edward/projects/doowon/CLAUDE.md` (프로젝트 규칙·토폴로지)
- **도메인 스펙**: `adr/*.md`, `docs/*`
- **이슈/PR 본문**: 이번 작업 스펙
- **파일 첨부**: 관련 코드·로그·디자인

AI 성능이 아쉽다면 **모델부터 바꾸지 말고 컨텍스트부터 점검**하세요. 열 중 여덟은 컨텍스트 문제입니다.

## 12. 핵심 요약

- 운영 환경엔 **안전장치**(브랜치 보호, 환경 분리, 비밀값, 승인, MCP 신뢰도)가 반드시.
