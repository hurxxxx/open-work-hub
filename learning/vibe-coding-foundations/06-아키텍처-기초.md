# 06. 소프트웨어 아키텍처 기초

> **한 줄 요약.** 아키텍처는 소프트웨어의 구조 설계다. 구성 요소의 책임과 통신 경계를 정의하며, AIDOO Portal은 **클라이언트-서버 + 모노레포 + 다중 서비스** 조합을 사용한다.

---

## 1. 아키텍처란 무엇인가

아키텍처는 시스템 구조를 정의합니다.
- 프로그램을 어떤 단위로 분리할지
- 각 단위가 어떤 책임을 가질지
- 단위 간 통신 방식은 무엇인지
- 데이터 저장 위치와 흐름은 어떻게 설계할지
를 명확히 정하는 작업입니다.

아키텍처는 **나중에 바꾸기 어려운 결정** 입니다. 그래서 초반에 신중히 정하고, **ADR(Architecture Decision Record, 아키텍처 결정 기록)** 이라는 문서로 남깁니다. 우리 프로젝트에도 `adr/0001-ai-platform-extensibility.md`, `adr/0002-mcp-capability-platform.md` 두 개의 ADR이 있습니다(7장에서 자세히).

### 1.1 구조 설계에서 먼저 보는 기준

- **모듈 경계 품질**: 기능 분할 경계가 모호하면 확장할수록 변경 영향 범위가 커지고 팀 생산성이 급격히 떨어집니다.
- **교체 용이성**: 한 구성 요소를 바꿀 때 시스템 전체를 중단하지 않고 교체할 수 있어야 장기 유지보수가 가능합니다.

### 1.2 오해하기 쉬운 것들

- **"아키텍처 = 기술 스택 목록."**
  "React, FastAPI, Postgres를 씁니다"는 기술 선택일 뿐, 아키텍처 설명이 아닙니다. 아키텍처는 **"그 기술들이 어떻게 배치되고 어떻게 대화하는가"** 에 관한 이야기입니다.
- **"아키텍처는 시스템 설계 초기에만 정하고 끝이다."**
  시스템이 자라면서 아키텍처도 같이 **개정됩니다.** 그래서 ADR처럼 "언제, 왜 그렇게 바꿨는지"를 누적해서 기록해 둡니다.
- **"복잡한 아키텍처가 곧 좋은 아키텍처다."**
  단순한 구조로 충분한 문제에 복잡한 아키텍처를 덧씌우면 **비용만 불어납니다.** "필요한 만큼만 복잡하게"가 기본 원칙입니다.

## 2. 가장 기본 구조 — 클라이언트-서버

현대 웹 애플리케이션의 뼈대입니다.

- **클라이언트(Client)** — 요청하는 쪽. 여기서는 **사용자의 웹 브라우저.**
- **서버(Server)** — 응답하는 쪽. 여기서는 **우리 백엔드(FastAPI).**

예시 흐름:

1. 브라우저(클라이언트) → API 서버로 **HTTP 요청** 전송
2. API 서버 → 브라우저로 **HTTP 응답** 반환

**왜 클라이언트-서버로 나누는가?**

- 수백~수천 명의 브라우저가 동시에 접속해도 **공통 데이터는 서버에만** 있으면 되기 때문.
- 클라이언트는 사용자 디바이스에서 돌아가므로, 사용자마다 다른 환경에 대응.
- 보안: 민감한 데이터를 브라우저에 주지 않고 서버 안쪽에 둘 수 있음.

## 3. 3-Tier Architecture (3계층 아키텍처)

1990년대부터의 고전적 패턴이며, 지금도 웹 앱의 표준입니다.

| 계층 | 이름 | 역할 | 우리 프로젝트 |
|---|---|---|---|
| 1 | Presentation | UI 담당 | `apps/web` (React) |
| 2 | Application/Logic | 비즈니스 규칙 | `apps/api` (FastAPI) |
| 3 | Data | 영속성 | PostgreSQL + MinIO |

이 3개를 **분리** 하는 것이 핵심입니다. 분리되어 있으면
- UI만 바꾸고 싶을 때 서버를 안 건드려도 된다.
- 서버만 최적화하고 싶을 때 UI를 안 건드려도 된다.
- DB를 바꿀 때도 서버 로직만 수정하면 된다.

우리 프로젝트는 정확히 이 구조를 따르며, 여기에 추가로 **비동기 워커(Celery)** 와 **실시간 협업 서버(Yjs/y-websocket)** 가 덧붙은 형태입니다.

## 4. 모놀리식 vs 마이크로서비스

소프트웨어 아키텍처의 **가장 큰 분기점** 중 하나입니다.

### 4.1 모놀리식(Monolithic)

모든 기능이 **하나의 큰 서버 프로세스** 안에 있는 방식. 전통적이고 단순합니다. 구조는 "하나의 큰 서버 안에 로그인·결제·채팅·검색 모듈이 전부 들어 있음"이고, 디렉터리로 표현하면 아래와 같습니다.

```
거대한 서버 하나/
├── 로그인
├── 결제
├── 채팅
└── 검색
```

- **장점**: 배포 단순, 개발 단순, 디버깅 쉬움.
- **단점**: 커질수록 복잡해지고, 한 부분 문제로 전체가 죽을 수 있음.

### 4.2 마이크로서비스(Microservice Architecture, MSA)

각 기능을 **독립된 작은 서비스** 로 쪼개 여러 서버로 나누는 방식. 2010년대 후반 크게 유행. 브라우저는 보통 **API 게이트웨이(API Gateway)** 라는 단일 진입점으로 요청을 보내고, 게이트웨이가 뒤에 있는 각각의 전문 서비스(로그인·결제·채팅·검색...)로 라우팅합니다.

| 층 | 구성 |
| --- | --- |
| 사용자 | 브라우저 |
| 진입점 | API Gateway |
| 서비스 묶음 | 로그인 서비스 · 결제 서비스 · 채팅 서비스 · 검색 서비스 (각자 독립 프로세스·DB 가능) |

- **장점**: 서비스별 독립 배포, 서비스별 기술 선택 자유, 장애 격리.
- **단점**: 운영 복잡성이 매우 커짐(모니터링, 네트워크, 배포 파이프라인 × 서비스 수).

### 4.3 어느 쪽이 맞는가?

**90%의 프로젝트는 모놀리식으로 시작해야 합니다.** 이유는 마이크로서비스의 운영 비용이 초기에는 이득보다 크기 때문입니다. 업계에서는 이를 **"Monolith First"** 원칙이라 부릅니다(Martin Fowler).

우리 프로젝트도 **모놀리식** 입니다(`apps/api`가 단일 서버). 단, 비동기 작업은 **Celery 워커(apps/worker)** 로 분리했습니다. 이는 마이크로서비스라기보다 **"같은 모놀리스의 백그라운드 버전"** 입니다.

### 4.4 모듈러 모놀리스(Modular Monolith)

요즘 뜨는 중간 지점입니다. "내부는 잘 나눠진 모듈로 두고, 외부로는 하나의 서버로 배포" 방식. 필요할 때 특정 모듈만 마이크로서비스로 떼어낼 수 있음. 우리 프로젝트의 `aidoo_api/domains/` 구조가 바로 이 방향입니다.

### 4.5 어느 스타트업의 아키텍처 후회

> 가상의 스타트업 A사는 창업 6개월 차에 개발자 3명이 "미래에 대비해" 마이크로서비스 8개로 쪼개 서비스를 만들었습니다. 결과는? 각 서비스의 배포 파이프라인, 모니터링, 인증 공유, 로컬 개발 환경 세팅에 **팀의 80% 시간이 소모** 됐고, 정작 기능은 6개월 내내 5개밖에 만들지 못했습니다.
>
> 경쟁사 B사는 같은 기간에 **모놀리스 하나** 로 기능 40개를 출시했습니다. 1년 뒤 B사가 "이제 결제 부분만 떼어내자"고 결정했을 때는 이미 **무엇을 떼어낼지 몸으로 알고 있는** 상태였습니다.
>
> 이것이 Martin Fowler의 "Monolith First" 원칙이 말하는 교훈입니다.

### 4.6 오해하기 쉬운 것들

- **"마이크로서비스는 현대적이고 좋은 것이며, 모놀리스는 낡은 방식이다."**
  Shopify, Stack Overflow, Basecamp처럼 세계적 수준의 제품도 **모놀리스** 입니다. 정말 중요한 것은 "우리 팀 규모, 배포 빈도, 장애 허용 범위"에 맞는지 여부입니다.
- **"모듈러 모놀리스는 덜 나눈 마이크로서비스에 불과하다."**
  모듈러 모놀리스는 **코드 내부 경계는 엄격하게 지키되 배포 단위는 하나로** 두는 별개의 철학입니다. 운영 비용은 모놀리스와 동일하지만, 내부 정돈은 MSA 수준으로 유지합니다.
- **"서비스를 쪼개면 장애가 줄어든다."**
  네트워크, 배포, 인증의 복잡성이 더해지면서 **전에는 없던 종류의 장애** 가 더 자주 생깁니다. 쪼개기 전에 관측성(observability)에 대한 투자가 먼저입니다.

## 5. 모노레포(Monorepo) vs 다중 저장소

소스 코드 **저장소 배치** 에 대한 이야기입니다. 아키텍처와는 다른 층위지만 자주 함께 논의됩니다.

| 구분 | 모노레포 | 폴리레포(각 프로젝트별 저장소) |
|---|---|---|
| 정의 | 여러 앱·패키지를 **한 저장소** 에 | 프로젝트마다 저장소 분리 |
| 장점 | 공통 코드 공유 쉬움, 일괄 변경 가능, 전체 버전 관리 | 서비스 독립성, 권한 분리 쉬움 |
| 단점 | 저장소가 커짐, 도구 필요(Nx, Turborepo) | 공통 변경 시 여러 저장소 건드려야 함 |

**우리 프로젝트는 모노레포**입니다. 이유:
- 프런트(TS)와 백(Python)이 **한 저장소**에 있으면 타입·API 명세를 동기화하기 쉽다.
- 5명짜리 팀이라 여러 저장소는 오버헤드.
- Nx가 있어 효율적으로 관리 가능(21장).

Google, Meta, Uber 같은 대형 회사들도 내부적으로 거대 모노레포를 씁니다. "코드가 많아질수록 모노레포가 맞다"는 업계 흐름입니다.

## 6. 이벤트 드리븐 아키텍처(Event-Driven)

최근 10년간 중요해진 패턴입니다. "직접 호출" 대신 "이벤트를 발생시키고 누군가 듣는" 방식입니다. 회의 녹음 업로드 예시를 순서대로 따라가 봅시다.

1. 사용자가 회의 녹음을 업로드한다.
2. **API** 는 `recording_uploaded` 라는 **이벤트(event)** 를 **메시지 큐(message queue, 예: Redis)** 에 넣고 "접수했습니다"를 즉시 응답한다.
3. 백그라운드의 **워커(Worker, 예: Celery)** 가 큐를 지켜보다 이벤트를 꺼내 수신한다.
4. 워커가 실제 트랜스크립션(음성 받아쓰기)·요약을 수행한다.

장점:
- API는 응답을 바로 반환(사용자 대기 없음).
- 워커가 느리거나 죽어도 메시지는 큐에 남아 있어 안전.

우리 프로젝트의 **Celery + Redis** 조합이 이 패턴의 가장 단순한 형태입니다(30장).

### 6.1 메시지 큐를 쓰는 이유

메시지 큐를 쓰면 API는 요청을 빠르게 접수하고, 실제 시간이 오래 걸리는 작업은 워커가 비동기로 처리합니다. 이 구조는 사용자 대기 시간을 줄이고 트래픽 급증 시 안정성을 높입니다.

### 6.2 현대 트렌드 — 이벤트·메시지의 확장

이벤트 기반 패턴은 단순한 백그라운드 처리 수준을 넘어 **"서비스 간 통신 방식"** 으로도 자주 쓰입니다. AI 분야의 **MCP (Model Context Protocol, 모델 컨텍스트 프로토콜)** 도 비슷한 아이디어를 AI 도구 연결에 적용합니다. 이 자료 후반부(Part 4)에서 자세히 다룹니다.

## 7. AIDOO Portal의 전체 그림

세 층 + 부가 서비스를 모두 그리면 이렇습니다.

**최상위 레이어 — 진입점**

사용자 브라우저(HTTPS) 에서 들어오는 요청은 세 갈래로 나뉩니다.

| 엔드포인트 | 역할 |
| --- | --- |
| 정적 웹 호스팅 (Nginx + `dist/web`) | SPA 번들 전달 |
| API 서버 (FastAPI) | REST·SSE 로직 |
| WebSocket 서버 (Yjs relay) | 실시간 협업 스트림 |

**중간 레이어 — 상태 보관소**

세 서비스는 공통으로 아래 저장소·큐를 공유합니다.

| 서비스 | 역할 |
| --- | --- |
| PostgreSQL | 메인 데이터 |
| Redis | 큐 / 캐시 / Yjs 릴레이 |
| MinIO | 파일 · 객체 저장소 |

**외곽 레이어 — 비동기·외부 의존**

- **Celery 워커 프로세스** — Redis 큐에서 느린 작업을 꺼내 전담 처리
- **OpenAI API (외부)** — 워커 또는 API 서버에서 필요 시 호출

이 한 장을 머리에 그리면, 앞으로 나오는 모든 기술 이야기가 "이 그림의 어느 부분인가"로 자리 잡을 수 있습니다.

## 8. 아키텍처를 판단하는 기준 (NFR: 비기능 요구)

어떤 아키텍처가 좋은가는 맥락에 따라 다릅니다. 그 맥락을 결정하는 것이 **비기능 요구사항(Non-Functional Requirements, NFR)** 입니다.

- **Scalability(확장성)** — 사용자가 10배 늘어도 버티는가
- **Availability(가용성)** — 장애 시 얼마나 빨리 복구되는가
- **Performance(성능)** — 응답 속도
- **Security(보안)** — 인증·권한·암호화
- **Maintainability(유지보수성)** — 6개월 뒤에도 이해 가능한가
- **Observability(관측성)** — 문제가 생겼을 때 원인을 빨리 찾을 수 있는가

우리 포털은 사내용이라 확장성 요구가 높지 않고, **보안·유지보수성·관측성** 이 가장 중요한 NFR입니다. 이 가치관이 현재 아키텍처를 결정했습니다.

## 9. 핵심 요약

- 아키텍처는 **소프트웨어의 구조 정의**이며, **ADR**로 남긴다.
- 기본 골격은 **클라이언트-서버 + 3-Tier**.
- 모놀리식 vs 마이크로서비스는 **모놀리식으로 시작** 이 업계 정석. 중간이 **모듈러 모놀리스**.
- 우리 프로젝트는 **모듈러 모놀리스 + 모노레포 + 이벤트 드리븐 보조** 조합.
- 아키텍처 판단 기준은 **NFR**. 우리는 보안·유지보수성·관측성이 중심.
