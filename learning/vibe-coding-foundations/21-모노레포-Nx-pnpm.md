# 21. 모노레포 — Nx와 pnpm

> **한 줄 요약.** 모노레포는 "여러 앱과 라이브러리를 한 저장소에 두는 방식"이다. 이 프로젝트는 **pnpm 워크스페이스**로 패키지를 묶고 **Nx**로 빌드·테스트·캐싱을 최적화한다.

> 🔑 **한 마디로.** "**회사 본사 건물 하나**에 웹팀·API팀·워커팀 사무실을 다 넣되, **총무팀(Nx)** 이 공동 설비·비용·동선을 총괄한다"는 발상. 각 팀은 자기 문만 열면 자기 방이지만, 복도·엘리베이터·회의실은 공유한다.

### 일상 비유로 확장하기

- **아파트 단지**: 각 동(앱) = `apps/web`, `apps/api` 등. 관리사무소(Nx) = 공용 시설·공지·택배 수령 공동 처리. pnpm = 자재 창고를 한 군데 두고 **각 동엔 링크(전표)만** 둠 → 자재비 절감.
- **출판사의 단행본 시리즈**: 표지·판형·편집 규칙(공통 ESLint/TSConfig)은 시리즈 전체가 공유, 각 책의 원고(앱 코드)는 각자. 한 책의 오탈자 수정이 다른 책에 영향 없음.
- **공유 주방 푸드홀**: 여러 가게(앱)가 같은 주방 시설·식기세척기(공통 도구)를 쓰되 메뉴판(각 앱의 기능)은 독립.

## 1. 모노레포의 목적 (복습 + 심화)

6장에서 모노레포 vs 폴리레포의 개념 차이를 봤습니다. 여기서는 우리 프로젝트에서 모노레포가 **실제로 어떤 편의를 주는지** 구체적으로 봅니다.

### 1.1 공통 작업의 단순화

- **타입 공유**: 프런트(TS)와 백엔드 사이의 API 타입을 `packages/contracts` 같은 공용 패키지로 공유 가능.
- **UI 라이브러리 공유**: `packages/ui` 안의 공통 컴포넌트를 `apps/web`과 `apps/ops`가 모두 import 가능.
- **한 PR로 풀스택 변경**: "로그인 API 바꾸면서 프런트 화면도 같이 바꾸는" 일이 한 번의 커밋·리뷰·배포로 끝난다.

### 1.2 일관된 도구

하나의 ESLint 설정, 하나의 TypeScript 설정, 하나의 Prettier 설정으로 팀 전체가 같은 규칙을 따릅니다. 개발자마다 스타일이 엇갈리는 일이 줄어듭니다.

### 1.3 규모의 함정

모노레포는 **잘못 쓰면 저장소가 무거워지고 빌드가 느려질 수 있습니다**. 이 문제를 해결하기 위해 **Nx 같은 빌드 오케스트레이터** 가 필요합니다.

## 2. pnpm — 왜 npm/yarn이 아니라 pnpm인가

**pnpm**(**p**erformant **n**ode **p**ackage **m**anager, "성능 좋은 노드 패키지 관리자") 은 Node.js 생태계의 **패키지 매니저(외부 라이브러리를 내려받고 버전을 관리해 주는 프로그램)** 중 하나입니다. 세 가지 대표가 있습니다.

| 구분 | npm | yarn | pnpm |
|---|---|---|---|
| 출시 | 2010 | 2016 (FB) | 2017 |
| 디스크 사용 | 매 프로젝트 복사 | 매 프로젝트 복사 | **전역 저장소 + 하드링크** |
| 설치 속도 | 보통 | 빠름 | 가장 빠름 |
| 모노레포 지원 | 약함 | 워크스페이스 | 워크스페이스 (깔끔) |
| 엄격한 호이스팅 | 약함 | 중간 | **엄격** |

pnpm의 결정적 차이는 **전역 저장소(store)를 두고, 각 프로젝트의 `node_modules`에는 그 저장소로의 "링크"만 남긴다** 는 점입니다. 이로 인해:

- **디스크 절약**: 같은 라이브러리가 10번 복사되지 않는다.
- **속도**: 실제 복사가 아니라 링크라 거의 순간이다.
- **엄격성**: `package.json`에 선언하지 않은 의존성은 못 쓴다. 우연한 의존이 줄어든다.

### 2.1 pnpm-workspace.yaml

우리 프로젝트 루트의 이 파일이 "워크스페이스 구성"을 정합니다.

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
```

이 설정으로 `apps/web`, `apps/api`(※ 파이썬은 제외), `packages/ui` 등이 모두 같은 워크스페이스의 "내부 패키지"가 됩니다. 서로를 `@aidoo/ui` 같은 이름으로 import 할 수 있습니다.

### 2.2 package.json의 `packageManager`

루트 `package.json`에 `"packageManager": "pnpm@10.33.0"` 이 명시돼 있습니다. 이 줄 덕분에 팀원들의 pnpm 버전이 **자동으로 통일** 됩니다(**Corepack**, Node.js에 내장된 "패키지 매니저 버전 자동 맞추기" 기능).

### 2.3 ⚠️ 흔한 오해 (pnpm 편)

- **오해:** "pnpm이든 npm이든 결과물은 같으니 아무거나 써도 된다."  
  **실제:** 모노레포에서 pnpm과 npm을 섞어 쓰면 `node_modules`가 엉켜 **"방금까지 되던 게 안 되는"** 재앙이 생긴다. 팀은 반드시 하나로 통일.
- **오해:** "`pnpm install` 이 오래 걸리니까 pnpm이 느린 것이다."  
  **실제:** 최초 1회 설치(글로벌 저장소 채우기) 이후로는 **새 프로젝트마다 거의 순간**이다. 디스크·네트워크 절약분이 크다.
- **오해:** "하드링크라 파일을 지우면 원본도 사라진다."  
  **실제:** 반대다. 여러 프로젝트가 **같은 파일을 공유**할 뿐, 한 쪽을 지워도 다른 쪽은 멀쩡하다.

## 3. Nx — 모노레포 오케스트레이터

**Nx** 는 Nrwl(현재는 Nx사)이 만든 **모노레포 오케스트레이터(monorepo orchestrator, 여러 프로젝트의 빌드·테스트 순서를 지휘하는 도구)** 입니다. Angular 진영에서 출발해 지금은 React/Node/Python까지 지원합니다. 업계에서는 **Turborepo**(Vercel)와 함께 양대 산맥입니다. 이 프로젝트는 **Nx 22.6 + pnpm 10.33** 조합을 사용합니다.

### 3.1 Nx가 하는 일

1. **프로젝트 그래프 인식**: "`apps/web`이 `packages/ui`에 의존한다"를 자동 파악.
2. **증분 빌드**: 바뀐 패키지와 그 영향 범위만 다시 빌드·테스트. 전체 모노레포가 커져도 속도가 안 느려진다.
3. **캐싱**: 같은 입력이면 결과를 캐시에서 꺼냄. 같은 테스트를 두 번 돌리지 않음.
4. **태스크 러너**: `nx run-many -t test --all` 같이 여러 프로젝트에 일괄 실행.
5. **플러그인 생태계**: `@nx/react`, `@nx/vite`, `@nx/eslint` 등. 템플릿·제너레이터 지원.

### 3.2 nx.json

이 프로젝트의 `nx.json`에 있는 주요 설정:

- **namedInputs**: 캐시 키 계산 시 포함할 파일 패턴. 테스트 파일은 `production` 입력에서 제외해 "소스 파일 변경 없이는 빌드 캐시 히트"가 됨.
- **targetDefaults**: `build`, `test`, `lint`의 기본 동작. 예: `build`는 `^build`(의존성 빌드 먼저)에 의존.
- **plugins**: `@nx/vite/plugin`, `@nx/eslint/plugin`, `@nx/vitest/plugin` 등이 자동으로 프로젝트의 타겟을 감지.

### 3.3 자주 쓰는 명령

```bash
# 특정 프로젝트만
pnpm nx run web:build
pnpm nx run api:test

# 전체 프로젝트에 일괄
pnpm lint          # nx run-many -t lint --all
pnpm test          # nx run-many -t test --all

# 영향 받는 것만 (Git diff 기반)
pnpm nx affected -t test

# 의존성 그래프 시각화
pnpm nx graph
```

`pnpm nx graph`는 진짜 유용합니다. **어떤 패키지가 어떤 걸 의존하는지** 브라우저로 볼 수 있습니다.

### 3.4 🛠️ 5분 실습

1. 터미널에서 `pnpm nx graph`를 실행하면 브라우저가 뜨고 그래프가 보인다.
2. `apps/web` 노드를 클릭 → "이 앱이 무엇에 의존하는지" 화살표로 확인.
3. `apps/api`와 `apps/worker`가 **서로 직접 연결**되어 있지 않아야 정상(둘은 HTTP/Redis로만 대화).
4. 아무 파일 하나를 저장만 한 뒤 `pnpm nx affected -t lint` → "바뀐 거 없으니 캐시에서 즉시 통과"가 뜨면 캐싱 체감.

## 3.5 ⚠️ 흔한 오해 (Nx 편)

- **오해:** "Nx를 써야만 모노레포가 된다."  
  **실제:** pnpm 워크스페이스만 있어도 모노레포다. Nx는 **속도·일관성 최적화 도구**일 뿐. 다만 규모가 커질수록 Nx 없이는 빌드가 고통스러워진다.
- **오해:** "Nx 캐시가 이상하게 굴면 `rm -rf node_modules`로 풀어야 한다."  
  **실제:** `pnpm nx reset` 한 줄이면 Nx 캐시만 깨끗이 비워진다.
- **오해:** "Nx는 Angular 전용 도구다."  
  **실제:** 과거엔 그랬지만 현재는 React·Vite·Python·Go까지 플러그인이 있다. 우리도 **파이썬 앱(`apps/api`, `apps/worker`)까지 Nx 타겟으로 관리**한다.
- **오해:** "affected 빌드는 마법이라 내가 뭘 바꿨는지 몰라도 알아서 한다."  
  **실제:** Nx는 **Git diff** 를 기준으로 "어느 파일이 바뀌었는지"를 본다. 커밋이 엉망이면 affected 판단도 엉망이 된다. 커밋 위생이 전제다.

## 4. 우리 모노레포의 구성 (최종 상세)

```
apps/web/         React 프런트
  ├── package.json  (name: "web", private)
  ├── vite.config.mts
  ├── project.json  (Nx 타겟 정의)
  ├── playwright.config.ts
  └── src/
      ├── main.tsx
      ├── App.tsx
      ├── domains/
      ├── components/
      └── lib/

apps/api/         Python FastAPI
  ├── pyproject.toml   (Python 의존성)
  ├── project.json     (Nx에서는 Python도 관리 가능)
  ├── alembic/
  └── src/aidoo_api/
      └── domains/...

apps/worker/      Python Celery 워커
  ├── pyproject.toml
  └── src/aidoo_worker/
      └── tasks/

apps/ops/         운영 도구 (초기 단계)

packages/ui/      공통 UI 컴포넌트
  ├── package.json  (name: "@aidoo/ui")
  ├── src/index.tsx
  └── src/styles.css

packages/contracts/  (예정) 공통 타입·스키마
```

Python 앱 두 개는 pnpm-workspace에 넣지 않고(파이썬은 자체 패키지 매니저 `uv` 를 씁니다), **Nx project.json** 으로만 관리합니다. 즉 **Nx는 TypeScript뿐 아니라 Python 프로젝트도 태스크 관리에 포함** 시킵니다.

## 5. 내부 패키지 import의 실제

`apps/web/src/App.tsx` 안에서 공통 UI를 쓸 때:

```ts
import { AppShell } from '@aidoo/ui';
```

이렇게 되려면 `packages/ui/package.json`의 `name` 이 `@aidoo/ui`여야 하고, `apps/web/package.json`이 그걸 `dependencies`(or `workspace:*` 참조)로 포함해야 합니다. pnpm 워크스페이스가 이 연결을 자동으로 처리합니다.

## 6. 왜 Nx인가 — 대안과 비교

| 도구 | 비개발자도 알 만한 특징 | 비교 |
|---|---|---|
| **Nx** | **기능이 많고 플러그인이 풍부**. 설정 초기 학습은 있지만 큰 팀·다언어에 안정. Angular 기원. | 우리 선택. Python까지 태스크 관리. |
| **Turborepo** | **설정이 매우 단순**, JS 전용 색깔 강함. Next.js 중심 팀에서 인기. | Python 통합이 약함. 우리 구조엔 부족. |
| **Lerna** | **옛날에 유행한 도구**. 지금은 Nx가 인수해 유지 중. | 레거시. 새 프로젝트엔 비추천. |
| **Bazel** | Google 사내 도구 공개판. **극도로 강력하지만 설정이 장편 소설**. | 스타트업엔 오버킬. |
| **Rush** | Microsoft 발 도구. 대규모 JS에 최적화. **설정이 세밀한 만큼 복잡**. | 우리 규모엔 과함. |

**Nx를 고른 결정적 이유**:

1. TypeScript + Python 혼합 모노레포에서 **태스크 관리까지 일원화** 가능.
2. 캐싱·affected 빌드가 훌륭해 모노레포가 커져도 속도를 유지.
3. 플러그인(@nx/react, @nx/vite 등)이 성숙해 설정 부담이 적다.

> 📝 **비개발자용 힌트.** "**Turborepo는 가볍고 빠른 세단, Nx는 옵션 풀세트 SUV, Bazel은 장거리 대형 트럭**" 정도로 비유할 수 있습니다. 우리는 짐(다언어 코드·Python)이 많으니 SUV를 골랐습니다.

## 7. 모노레포 운영의 규칙

초보자가 흔히 실수하는 것들과 팀 차원의 권장 규칙.

### 7.1 경계 규칙 (module boundaries)

`@nx/eslint-plugin`에는 **"프로젝트 A는 프로젝트 B를 import 못 하게 막는"** 규칙이 있습니다. 예: `apps/ops`가 `apps/web`의 내부 코드를 직접 쓰면 안 됨. `packages/ui`를 통해서만 공유.

이 규칙이 없으면 모노레포가 빠르게 스파게티가 됩니다.

### 7.2 루트에 공통 도구, 각 프로젝트에 특화 도구

- 루트: ESLint, Prettier, TypeScript, Vitest 공통 설정.
- 앱별: Vite 설정, Playwright 설정, Python pyproject 등 특화.

### 7.3 버전 통일

같은 라이브러리(예: React)를 여러 앱이 써야 할 때, pnpm이 **한 버전만 쓰도록** 강제됩니다. 이게 **이중 설치** 로 인한 "두 개의 React" 같은 재앙을 막습니다.

### 7.4 의존성 추가의 기본값

- 앱의 의존성 → 그 앱의 `package.json`에만.
- 여러 앱이 쓰는 것 → `packages/ui` 같은 공용 패키지에 추가.
- 빌드·개발 도구 → 루트 `package.json`의 `devDependencies`.

## 7.5 🏢 업무 시나리오 — "관리자 콘솔에 Excel 다운로드 버튼"

**상황:** 인사팀이 관리자 콘솔에서 "사용자 목록 엑셀로 내보내기" 기능을 요구했다.

- 이 기능은 **프런트 버튼(apps/web)** 과 **백엔드 엔드포인트(apps/api)** 가 둘 다 필요.
- **모노레포의 힘:** 한 브랜치에 프런트 변경 + 백엔드 변경 + 공유 타입(`packages/contracts`에 `UserExportRow` 추가)을 **한 PR로 묶어** 리뷰·배포.
- **Nx의 힘:** `pnpm nx affected -t test` 를 돌리면 **바뀐 두 앱만 테스트**, 나머지 앱(`worker`, `ops`)은 건너뛴다. CI 시간 절약.
- **pnpm의 힘:** 두 앱이 같이 쓰는 **엑셀 라이브러리(예: xlsx)** 는 `packages/ui`나 공용 유틸에 한 번만 설치 → 이중 설치 방지.

폴리레포(저장소가 나뉘어 있는 구조)였다면 "프런트 저장소 PR, 백 저장소 PR, 타입 저장소 PR"을 **따로 열고 배포 순서까지 맞춰야** 했을 일입니다.

## 7.6 프로젝트 구조 재정리 (버전 포함)

- **Nx 22.6** — 태스크 오케스트레이션·캐시.
- **pnpm 10.33** 워크스페이스 — 패키지 관리.
- 앱: **`apps/web`(프런트), `apps/api`(FastAPI), `apps/worker`(Celery), `apps/ops`(운영 도구)**.
- 공유 라이브러리 위치: **`libs/`**(원칙: **공유 코드만** 여기에 둔다. 앱 전용 코드는 각 앱 아래로).
- 기존 문서에서 `packages/ui` 같은 표현은 **공통 UI 패키지**의 포괄적 지칭이며, 실제 공유 모듈은 점진적으로 `libs/` 구조로 정리된다.

> 💡 **실무 팁.** "이 코드 공유일까?" 질문이 들면 **"두 앱 이상이 쓰면 `libs/`, 한 앱만 쓰면 해당 앱 내부"** 라는 단순한 규칙을 따른다.

## 8. 핵심 요약

- 모노레포 = **여러 앱·패키지를 한 저장소에**. 장점은 공유·일관성, 단점은 도구 필요.
- **pnpm** 을 패키지 매니저로 쓴다. 디스크·속도·엄격성 모두 우위.
- **Nx** 가 모노레포의 빌드·테스트·캐시를 오케스트레이션. Python도 타겟으로 관리.
- 우리 구조: `apps/{web,api,worker,ops}` + `packages/{ui,contracts}`.
- 규칙: **경계 규칙 + 버전 통일 + 의존성 위치 원칙**.
