# 25. 라우팅과 도메인 구조 — React Router v7 + `domains/` 레이아웃

> **한 줄 요약.** SPA에서 URL은 "화면의 주소"다. **React Router v7**이 URL ↔ 화면 매핑을 담당하고, 이 프로젝트는 코드 자체를 **도메인별 폴더**로 나눠 기능 단위로 이동하기 쉽게 만들었다.

> 🔑 **한 마디로.** 라우터는 URL을 해당 화면 컴포넌트로 매핑하고, 코드 구조는 도메인 단위로 분리해 기능별 탐색과 변경을 쉽게 만든다.

### URL 설계와 도메인 구조 읽기

- URL은 화면 상태를 표현하는 식별자이고, Gate 컴포넌트는 렌더링 전에 권한 조건을 검사합니다.
- 도메인 폴더(`docs/`, `pms/`, `ai/`)를 분리하면 기능 탐색 범위가 줄어 유지보수가 쉬워집니다.
- `/w/:workspaceSlug/docs/123` 같은 URL은 워크스페이스와 리소스 식별자를 동시에 담아 맥락 파악에 유리합니다.
- 도메인별 하위 구조(`pages`, `api`, `hooks`)를 통일하면 신규 기능 추가 시 팀 합의 비용이 줄어듭니다.

이 프로젝트는 **React Router v7**을 사용합니다. v6에서 v7로 통합되며, 파일 기반 라우팅도 옵션으로 지원되지만 우리는 **코드 기반 라우팅(Library 모드)** 를 채택했습니다.

---

## 1. 라우팅이란

"라우팅(routing)"은 URL과 화면을 **연결하는 규칙** 입니다.

- `/` → 홈 화면
- `/w/abc/docs` → 워크스페이스 `abc`의 문서 목록
- `/w/abc/docs/123` → 문서 `123` 상세
- `/w/abc/admin/users` → 관리자 사용자 관리

전통적 웹은 서버가 URL마다 다른 HTML을 보냅니다. SPA는 **브라우저가 URL 변화를 감지해 자체적으로 화면을 바꿉니다**. 이를 처리하는 핵심 구성 요소가 라우터입니다.

---

## 2. React Router — 역사와 v7

React Router는 2014년부터 존재한 가장 표준적인 React 라우팅 라이브러리입니다. 2024년의 **v7** 은 과거 Remix 프레임워크의 일부 철학을 흡수해 크게 바뀌었습니다.

### 2.1 v7의 두 가지 모드

- **Library 모드** (우리 선택 추정): `<BrowserRouter>`로 감싸고 `<Route>`를 쓰는 전통적 방식.
- **Framework 모드**: Remix처럼 파일 기반 라우팅, 서버 렌더링, 데이터 로더를 갖춘 풀 프레임워크.

우리 프로젝트는 Library 모드로 React를 사용하며 SSR은 하지 않습니다. 사내 포털이라 SEO가 필요 없고, 빠른 첫 로딩도 중요도가 낮기 때문입니다.

### 2.2 v7의 핵심 기능

- **Data APIs (loader/action)**: 라우트에 **"이 화면이 뜨기 전 필요한 데이터를 받아오는 함수"** 를 선언적으로 등록. React Query 없이도 페이지별 데이터 로딩이 깔끔해짐.
- **Nested routes**: 부모/자식 라우트 + 공통 레이아웃. 우리 `/w/:workspaceSlug/...` 패턴이 그 예.
- **Route-level error boundaries**: 화면별로 에러 UI.
- **Forms Actions**: React 19의 Actions와 궁합.

### 2.3 우리 라우트의 뼈대 (개념적)

```
/
├─ /login
├─ /w/:workspaceSlug
│   ├─ /ai
│   ├─ /docs
│   │   ├─ /                   (목록)
│   │   └─ /:docId             (상세)
│   ├─ /pms
│   │   ├─ /boards/:boardId
│   │   ├─ /issues
│   │   └─ /milestones
│   ├─ /calendar
│   ├─ /meeting
│   └─ /admin
│       ├─ /users
│       ├─ /workspaces
│       └─ /security
```

`:workspaceSlug`는 **동적 파라미터**입니다. `/w/doowon-hq/docs` 라면 `workspaceSlug = "doowon-hq"`로 읽힙니다.

### 2.4 Gate(게이트) 컴포넌트

라우트가 실제로 그려지기 전에 **권한을 검사하는 층**입니다. 예를 들어 `WorkspaceGate` 는 로그인 상태 + 워크스페이스 멤버십을 확인하고, 실패 시 로그인 페이지나 에러 페이지로 리다이렉트합니다. `AdminGate` 는 관리자 여부까지 확인합니다.

게이트 패턴은 권한·세션 체크를 **라우트 정의 옆에 명시** 해 두는 관행으로, 권한 누락 사고를 줄이는 데 매우 효과적입니다.

### 2.5 ⚠️ 라우팅에서 자주 듣는 오해

- **"SPA에서 F5를 누르면 로그인이 풀린다"** — 세션 쿠키는 브라우저가 유지한다. 단, 화면 **메모리 상태**(입력 중이던 폼 등)는 사라질 수 있다.
- **"URL에 있는 `/w/doowon-hq/docs/123` 같은 경로는 실제 디렉터리다"** — SPA에서는 **라우터가 해석하는 문자열**일 뿐이다. Nginx가 **모든 경로를 `index.html`로 되돌려** React에게 넘기고, 라우터가 "아, docs 상세구나"라고 판단한다.
- **"권한 체크는 백엔드만 하면 된다"** — 백엔드 검증이 **최종 방패**지만, 프런트도 **Gate**로 미리 막아야 **잘못된 화면이 잠깐 보였다 사라지는**(flash) 사고를 피할 수 있다.
- **"Redux를 안 쓰면 대형 프로젝트가 안 된다"** — 상태의 종류(서버/클라이언트/URL)를 나눠 **도구를 분산**하는 것이 2025~2026의 주류다. 우리도 React Query 스타일 loader + Context + URL 조합이면 충분하다.
- **"코드 스플리팅은 고급 기법이라 나중에 붙이면 된다"** — 도메인이 늘수록 번들이 커져 첫 로딩이 눈에 띄게 느려진다. **`React.lazy`** 를 도메인 경계에 걸어 두는 것이 기본값이다.

## 3. 주요 훅과 API

### 3.1 `useNavigate`

프로그램적으로 URL을 바꿉니다.

```tsx
const navigate = useNavigate();
navigate('/w/doowon-hq/docs');
navigate(-1);  // 뒤로가기
```

### 3.2 `useParams`

URL의 동적 파라미터를 읽습니다.

```tsx
const { workspaceSlug, docId } = useParams();
```

### 3.3 `useSearchParams`

쿼리 스트링(`?search=hello&page=2`) 관리.

```tsx
const [sp, setSp] = useSearchParams();
const q = sp.get('search');
setSp({ search: 'new', page: '1' });
```

### 3.4 `useLocation`

현재 경로·쿼리·상태를 다 포함한 객체.

### 3.5 `<Link>` / `<NavLink>`

일반 `<a>` 대신 이걸 씁니다. 새로고침 없이 SPA 내부 이동.

```tsx
<Link to={`/w/${workspaceSlug}/docs`}>문서</Link>
<NavLink to="/admin" className={({ isActive }) => isActive ? 'font-bold' : ''}>관리자</NavLink>
```

### 3.6 🛠️ 5분 실습 — 라우팅 관찰

1. 포털에서 문서 목록 → 문서 상세 → 이슈 보드를 차례로 열어 **URL이 어떻게 바뀌는지** 관찰.
2. 브라우저 **주소창에서 직접 URL을 복사** 해 새 탭에 붙여 넣기 → 같은 화면이 뜨는지 확인(딥 링크 지원 체감).
3. 문서 목록에서 검색어를 입력하면 **`?search=...`** 가 URL에 붙는지 확인(`useSearchParams` 활용 흔적).

## 4. 도메인 주도 폴더 구조 — 이 프로젝트의 설계 기둥

### 4.1 왜 `domains/` 인가

7장에서 DDD(Domain-Driven Design, **도메인 주도 설계** — "업무 영역 단위로 코드를 묶자"는 설계 원칙)를 이미 봤습니다. 실제로 `apps/web/src/domains/<domain>/` 아래에는 `routes/pages/components/api/hooks` 식으로 파일이 배치됩니다.

```
domains/
├── admin/
│   ├── components/
│   ├── pages/
│   ├── api/
│   ├── hooks/
│   └── types.ts
├── ai/
│   ├── components/
│   ├── pages/
│   ├── stream/         (SSE 스트리밍 로직)
│   ├── hooks/
│   └── types.ts
├── auth/
├── calendar/
├── docs/
│   ├── collab/         (Yjs 협업 로직)
│   └── ...
├── drafts/
├── meeting/
├── pms/
├── planner/
├── workspaces/
└── ...
```

**한 도메인 = 한 폴더** 원칙이 지켜집니다. 한 기능을 수정할 때 그 폴더 안의 서너 파일만 열면 됩니다.

### 4.2 각 도메인 폴더의 내부

대부분 이런 구조로 통일되어 있습니다.

- `pages/` — 라우트 엔트리 컴포넌트.
- `components/` — 도메인 내부에서만 쓰는 UI 조각.
- `hooks/` — 커스텀 훅(데이터 페치, 상태 관리).
- `api/` — HTTP 요청 함수들.
- `types.ts` — 이 도메인의 타입.
- `utils.ts` — 도메인 유틸.

이 규칙은 "**인지 비용**"을 낮춰줍니다. "드래프트 기능 고치려면 drafts 폴더만 보면 됨".

### 4.3 공용 컴포넌트는 어디에?

여러 도메인이 공유하는 것은 `components/`(프로젝트 상위) 또는 `packages/ui`에 둡니다. **"두 도메인 이상이 쓰면 승격"** 이 규칙입니다.

### 4.4 상위 공용 폴더

```
apps/web/src/
├── App.tsx
├── main.tsx
├── constants.ts
├── app-shell.ts / .spec.ts
├── index.css
├── assets/
├── components/     (공용 UI)
├── domains/        (위)
├── lib/            (도메인에 속하지 않는 공용 로직. HTTP 클라이언트 등)
└── styles/
```

## 5. 상태 관리 — Redux를 왜 안 쓰나

2015~2020년엔 **Redux**가 React 상태 관리의 표준이었습니다. 지금은 상황이 바뀌었습니다.

### 5.1 현대의 분할

- **서버 상태(Server State — 백엔드가 진실을 가진 데이터)**: React Query, SWR, TanStack Query, 혹은 React Router v7 loader → **이 프로젝트는 대체로 loader + 직접 fetch 조합으로 보임**.
- **클라이언트 상태** (UI 상태 — 폼 입력값·토글·탭): `useState`, `useReducer`, Context. 필요하면 **Zustand(간단한 전역 스토어 라이브러리)**, **Jotai(원자 단위 상태 관리)**.
- **URL 상태**: React Router의 **searchParams(쿼리 스트링 관리)**. 북마크·공유에 유리.

Redux 하나에 다 욱여넣는 대신, **상태의 종류에 맞게 도구를 나눠 쓰는 것** 이 현대 스타일입니다.

> 📝 **상태 분리 원칙.** 서버 상태/클라이언트 상태/URL 상태를 구분해 각각 맞는 도구로 관리하면 전역 상태 과부하를 막을 수 있습니다.

### 5.2 이 프로젝트의 상태 패턴 (관찰된 것)

- 인증/세션: 아마 React Context로 상위에서 제공(`WorkspaceGate` 등과 연계).
- AI 채팅: 복잡한 스트림 상태 → 도메인 내부의 커스텀 훅(`useChatStream` 같은 것).
- 폼 상태: Mantine form / React Router Actions.
- 글로벌 토스트: Mantine Notifications.

실무에서 여러분이 상태 관리를 늘릴 일이 생기면, **"진짜 전역이 맞나?"** 를 먼저 물어보세요. 대부분 한 도메인 안의 커스텀 훅이면 충분합니다.

## 6. 라우팅과 데이터 로딩의 모범 패턴

### 6.1 페이지 단위 데이터 로더

```tsx
// v7 data router 스타일
export const docListRoute = {
  path: '/w/:workspaceSlug/docs',
  element: <DocList />,
  loader: async ({ params }) => {
    return fetchDocs(params.workspaceSlug);
  }
};

function DocList() {
  const data = useLoaderData();
  return <DocListView docs={data} />;
}
```

### 6.2 낙관적 업데이트(optimistic update)

"일단 UI 먼저 반영 → 서버 응답 오면 최종 동기화" 패턴. React 19의 `useOptimistic` 훅이 이걸 쉽게 만들어 줍니다.

## 7. 주의점과 실전 팁

### 7.1 딥 링크를 지원한다

브라우저 새로고침·북마크로도 같은 화면이 열려야 합니다. 상태가 URL에 충분히 담기는지 확인.

### 7.2 코드 스플리팅

모든 도메인 코드를 한 번에 로드하지 않고, **필요할 때만** 받도록. `React.lazy` + `Suspense` 로 구현. 번들을 크게 줄여 줍니다.

```tsx
const AdminPage = React.lazy(() => import('./domains/admin/pages/AdminPage'));
```

### 7.3 404 처리

정의되지 않은 경로로 들어왔을 때 예쁜 "페이지 없음" 화면을 보이기. 라우트 맨 끝에 `*` (와일드카드) 라우트를 둡니다.

### 7.4 로그인 유지

세션이 살아 있어도 라우트가 재로딩되면 로그인 상태를 잃지 않도록, 인증 Context를 **App 최상위**에 둡니다.

## 8. 대안 — 왜 Next.js/Remix가 아닌가

Next.js는 **SSR(Server-Side Rendering, 서버에서 HTML을 미리 그려 보내는 방식)**, 자동 이미지 최적화, **SEO(Search Engine Optimization, 검색엔진 최적화)** 강화 등을 제공합니다. 우리 프로젝트가 SPA만 쓰는 이유:

1. **사내 포털** 이라 SEO가 무관.
2. 사용자가 로그인한 뒤 **오래 머무는** 앱이라 첫 로딩 시간의 손해를 신경 쓸 가치가 낮음.
3. Python 백엔드와 분리된 **정적 SPA + API** 구조가 운영이 훨씬 단순.
4. Vite + React Router의 **학습 난이도**가 Next.js보다 낮음.

| 대안 | 비개발자도 알 만한 특징 | 우리와 안 맞는 이유 |
|---|---|---|
| **React Router v7** (현재) | **URL ↔ 화면**만 담당, 가볍고 파이썬 백과 궁합 좋음. | — |
| Next.js | **풀 프레임워크** — SSR·이미지 최적화·SEO까지 통짜. Vercel 생태계. | Node 서버 추가 필요, 파이썬 백과 중복. |
| Remix | **데이터 로더 중심**의 프레임워크(현재 v7에 흡수). | 풀 프레임워크 오버헤드. |
| TanStack Router | **타입 안전**을 강조한 신흥 라우터. 경로까지 TypeScript 체크. | 생태계·문서화가 아직 얇음. |

현재 선택이 합리적이며, 필요해지면 마이그레이션 경로가 열려 있습니다.

## 8.5 🏢 인사팀 전용 탭 신설해 보기

**상황:** 인사팀이 관리자 콘솔 아래 **"조직도" 탭**을 새로 요구. 일반 관리자에게는 보이면 안 되고 **HR 권한자**만 봐야 한다.

1. `apps/web/src/domains/admin/routes/` 아래에 새 라우트 정의 추가 → 경로 `/w/:workspaceSlug/admin/org`.
2. 기존 `AdminGate` 외에 **`HrGate`** 를 추가로 감싸 "HR 역할"만 진입 허용.
3. 페이지 컴포넌트는 `domains/admin/pages/OrgChartPage.tsx` 한 파일만 만들면 된다.
4. 데이터 로딩은 페이지 내부의 커스텀 훅(`useOrgTree`)이 `domains/admin/api/org.ts`를 호출.

**도메인 폴더 구조 덕분에** 신규 기능 하나 추가하는 동안 건드리는 파일이 4~5개로 제한된다. 이것이 **인지 비용을 낮추는 설계**의 실전 효과.

---

## 8.6 "이 기술을 고른 이유와 대안" — 비개발자 관점 보강

**React Router v7을 고른 이유** (비개발자 언어로):

1. **"라우터만 하고 다른 건 안 간섭한다"** — 백엔드·빌드 도구와 분리, 파이썬 FastAPI와 궁합 좋음.
2. **"v6에서 v7로 자연 승계"** — 이미 React를 쓰는 팀이 적은 비용으로 업그레이드 가능.
3. **"Nested route + Gate"** 패턴으로 **권한 누락** 을 구조적으로 막아 준다.

**비개발자가 Next.js를 지지하고 싶어할 수 있는 오해**:

- "Next.js를 쓰면 더 빠르다고 들었어요" → **첫 페이지 로딩**은 빠르지만, 사내 포털처럼 **로그인 후 오래 머무는** 앱에선 체감 차이가 적다.
- "Next.js는 업계 표준이잖아요" → 공개 웹(블로그·커머스)의 표준이지 **사내 SPA의 유일 해답**은 아니다.

---

## 8.7 🏢 문서 상세에서 이슈로 바로 이동하기

**상황:** 사용자들이 "회의록에서 논의한 액션 아이템을 PMS 이슈로 **즉시 전환**" 요구.

1. 문서 에디터(`domains/docs/`) 에서 블록을 선택 → "이슈로 전환" 클릭.
2. 내부적으로 **`useNavigate`** 가 `/w/${slug}/pms/issues/new?from=doc&blockId=...` 로 이동.
3. 이슈 신규 페이지(`domains/pms/pages/IssueNewPage.tsx`) 가 `useSearchParams` 로 **`from`과 `blockId`** 를 읽어 초기값 세팅.
4. 사용자가 뒤로가기를 눌러도 **원래 문서로 복귀** — 브라우저 히스토리가 라우터와 자연스럽게 이어지기 때문.

**URL에 상태를 담는** 덕분에: ① 링크 복사·공유 가능, ② 북마크 가능, ③ 다음 단계로 돌아갔을 때 맥락 유지.

---

## 9. 핵심 요약

- SPA 라우팅은 URL ↔ 화면의 매핑. **React Router v7** 이 이 프로젝트의 라우터.
- 주요 API: `useNavigate`, `useParams`, `useSearchParams`, `<Link>`, data loader.
- 권한 검사는 **Gate 컴포넌트**(WorkspaceGate, AdminGate)로 집중.
- 코드 구조는 **도메인별 폴더**. 기능 단위로 이동하기 쉬움.
- 상태 관리는 **서버/클라이언트/URL** 로 분할해 적절한 도구 선택. Redux는 현재 불필요.
