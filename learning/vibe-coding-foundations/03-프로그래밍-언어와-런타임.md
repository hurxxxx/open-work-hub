# 03. 프로그래밍 언어와 런타임

> **한 줄 요약.** 프로그래밍 언어는 문제 영역별로 강점이 다른 실행 도구다. 우리 프로젝트는 TypeScript(화면)와 Python(서버)을 함께 쓴다.

---

## 1. 언어마다 쓰이는 자리가 다르다

프로그래밍 언어는 용도별로 선택합니다. 브라우저 화면, AI 백엔드, 고성능 시스템처럼 문제 유형이 다르면 적합한 언어도 달라집니다.

- **JavaScript / TypeScript** — 브라우저 화면을 다룰 때 사실상 "유일한 언어".
- **Python** — 데이터·AI·서버에서 강한 언어.
- **Go / Rust** — 대규모·고성능이 필요한 시스템에서.
- **Java / C#** — 전통적 대기업 백엔드에서.
- **SQL** — 데이터베이스 질의용 전용 언어.

이 중 어느 하나를 "최고"라고 고를 수는 없습니다. 우리 프로젝트도 **두 언어(TypeScript + Python)를 함께 씁니다.** 이 조합은 요즘 AI 제품을 만들 때 가장 흔히 선택되는 짝입니다.

### 1.1 언어 선택 기준을 빠르게 정리

- 언어 선택은 문제 특성으로 결정합니다. 빠른 실험은 Python, 고성능 처리 계층은 Go/Rust, 브라우저 실행 코드는 TypeScript가 자연스러운 선택입니다.
- 같은 기능을 여러 언어로 구현할 수는 있지만, 생산성·성능·생태계의 균형점은 언어마다 다릅니다.

### 1.2 자주 듣는 오해들

- **"가장 좋은 언어가 하나 있다."**
  분야마다 강점이 다릅니다. 한 팀에서 **여러 언어를 함께 쓰는 것이** 오히려 일반적입니다.
- **"한 언어를 배우면 다른 언어도 바로 쓸 수 있다."**
  기초 문법은 비슷하지만 **생태계, 관용적 표현, 도구 체인** 이 서로 달라서 실무에서 제 몫을 하기까지는 시간이 걸립니다. 다만 AI가 거들어 주는 요즘은 이 간극이 꽤 좁아졌습니다.
- **"Python은 쉽고 느린 언어라 진지한 프로젝트에는 맞지 않는다."**
  Instagram, Dropbox, Netflix, OpenAI 모두 핵심 부분에 Python을 쓰고 있습니다. 언어 선택보다 **"어디가 병목인지"** 가 훨씬 중요합니다.

## 2. 언어가 컴퓨터와 통하는 방법 — 컴파일 vs 인터프리터

사람이 쓴 코드는 그대로는 컴퓨터가 못 읽습니다. 컴퓨터는 **0과 1** 만 압니다. 그래서 "번역기"가 필요합니다. 두 가지 방식이 있습니다.

### 2.1 컴파일(Compile)

코드를 **한 번에 통째로** 0/1로 번역해 놓고, 그 번역된 파일을 실행합니다. 예: C, C++, Rust, Go.

- 장점: 실행 속도가 빠르다.
- 단점: 번역 과정에 시간이 걸리고, 수정할 때마다 다시 번역해야 한다.

### 2.2 인터프리터(Interpret)

코드를 **한 줄씩 읽으면서** 그때그때 번역·실행합니다. 예: Python, JavaScript(기본적으로), Ruby.

- 장점: 빨리 실행해 볼 수 있다(수정 → 바로 확인).
- 단점: 통째로 번역된 언어보다 살짝 느리다(요즘은 JIT 같은 기법으로 많이 메움).

### 2.3 두 방식이 섞이기도 한다

TypeScript는 **사람이 TypeScript로 쓰고 → JavaScript로 번역(컴파일) → 브라우저가 인터프리터로 실행** 하는 독특한 흐름을 탑니다. 이렇게 "언어에서 언어로 번역"하는 과정을 **트랜스파일(transpile)** 이라고 부릅니다. 자세한 이야기는 22장에서 다룹니다.

## 3. "런타임"이라는 말

런타임(Runtime)이라는 말은 교육 내내 계속 나옵니다. 두 가지 의미로 쓰입니다.

1. **실행 중인 순간(run-time)** — "런타임에 오류가 났다" = "실행 도중 오류가 났다".
2. **실행 환경** — 언어 코드를 실제로 실행해 주는 **엔진 + 도구 모음**. 예: Node.js는 JavaScript 런타임, CPython은 Python 런타임.

이 프로젝트와 관련된 주요 런타임은 다음과 같습니다.

| 런타임 | 언어 | 역할 |
|---|---|---|
| **Node.js(노드제이에스)** | JavaScript/TypeScript | 프런트엔드 빌드 도구(Vite, Nx 등)를 돌림. |
| **브라우저 엔진** | JavaScript | 사용자 PC의 크롬·사파리가 우리 화면 코드를 실행함. |
| **CPython(씨파이썬)** | Python 3.12 | `apps/api`, `apps/worker` 서버 프로세스를 실행함. |

### 3.1 "내 맥북에선 되는데 서버에선 안 돼요"

흔히 벌어지는 상황입니다.

> 개발자 A가 "내 맥북에선 잘 되는데 서버에 올리면 에러가 난다"며 당황합니다. 확인해 보니 A의 맥북에는 Python 3.12가, 운영 서버에는 3.11이 깔려 있었습니다. Python 3.12에서 새로 생긴 문법을 썼기 때문에 3.11 런타임은 그 코드를 읽어내지 못한 것입니다.

그래서 "런타임 버전"은 언제나 **팀 전체가 맞춰야 할 약속** 입니다. 우리 프로젝트의 `pyproject.toml`, `package.json`, `.nvmrc`, `.python-version` 같은 파일들이 그 약속을 기록해 두는 문서 역할을 합니다.

### 3.2 헷갈리기 쉬운 것들

- **"'런타임에 오류가 났다'는 말은 런타임이라는 프로그램 자체의 오류라는 뜻이다."**
  대개는 **우리가 쓴 코드가 실행 도중에 터진** 경우를 가리킵니다. "컴파일 타임 오류(문법 오류)"와 대비되는 표현입니다.
- **"브라우저마다 JavaScript는 다 똑같이 돈다."**
  크롬의 V8, 사파리의 JavaScriptCore, 파이어폭스의 SpiderMonkey는 **같은 표준(ECMAScript)** 을 따르지만 최신 기능 지원 시점이나 속도가 조금씩 다릅니다. "크로스 브라우저 테스트"가 필요한 이유가 여기에 있습니다.
- **"Python이면 다 같은 Python이다."**
  표준인 CPython 외에도 속도가 빠른 PyPy, 소형 기기용 MicroPython 등 여러 구현체가 있습니다. 우리 프로젝트가 쓰는 것은 표준인 **CPython 3.12** 입니다.

## 4. 우리 프로젝트의 언어 선택

### 4.1 프런트엔드 = **TypeScript**

브라우저가 실행할 수 있는 언어는 사실상 JavaScript뿐입니다. TypeScript는 JavaScript에 **타입(데이터의 형태)** 을 더한 확장으로, 실수를 줄여 줍니다.

다른 선택지도 있었지만:
- **JavaScript(순수)** — 타입이 없어 자유롭지만 버그가 쉽게 스며든다.
- **Dart(Flutter)** — 모바일에 강점, 웹은 약점.
- **Elm / ReScript** — 안정적이지만 생태계가 작다.

→ 이 프로젝트처럼 **대규모·오래 유지할 웹앱** 에는 **TypeScript가 적합한 선택**입니다. 타입 정보가 코드 이해와 유지보수를 도와주기 때문입니다.

### 4.2 백엔드 = **Python 3.12**

백엔드 언어 선택지는 훨씬 다양합니다.

| 언어 | 대표 프레임워크 | 강점 | 약점 |
|---|---|---|---|
| **Python** | FastAPI, Django | AI/ML 생태계 최고, 문법이 쉬움 | 순수 성능은 중간 |
| Node.js | Express, NestJS | 프런트와 같은 언어로 통일 가능 | 대규모 타입 운영이 번거로움 |
| Go | Gin, Echo | 매우 빠르고 배포 단순 | AI 라이브러리가 빈약 |
| Java/Kotlin | Spring Boot | 대기업 전통 강자 | 설정이 무겁다 |
| Rust | Actix, Axum | 최상의 성능/안전성 | 학습 난이도 매우 높음 |

**이 프로젝트가 Python을 고른 이유:**

1. **AI 통합.** OpenAI-compatible LLM, MCP, embedding/rerank, 문서 변환, 음성 인식 등 AI 관련 라이브러리의 중심 언어가 Python이다.
2. **문법이 가장 쉽다.** 비개발자가 유지보수해야 하는 우리 상황에 결정적 장점.
3. **FastAPI가 매우 성숙하다.** 타입(Pydantic)과 비동기(asyncio)를 기본 지원해 TypeScript에 가까운 개발 경험을 준다.

반대급부로 **순수 CPU 처리 속도** 는 Go/Rust에 비해 느리지만, 우리 시스템의 병목은 "데이터베이스 I/O"와 "LLM/문서 처리 provider 호출 대기"라서 언어 성능은 사실상 문제가 안 됩니다.

### 4.3 데이터 질의 = **SQL**

데이터베이스와 대화할 때는 **SQL** 이라는 전용 언어를 씁니다. 이 프로젝트는 SQL을 직접 쓰지 않고 **SQLAlchemy라는 Python 도구를 통해 간접적으로** 씁니다(8장, 29장).

### 4.4 운영체제/스크립트 = **Bash**

`dev.sh`, `prod.sh`, `scripts/*.sh` 파일들이 있습니다. 이들은 **Bash 스크립트** 로, 리눅스/macOS에서 여러 명령을 한번에 실행하기 위한 언어입니다. 복잡한 로직은 없고, "도커 띄우고 → 서버 띄워라" 같은 **조립 지시서** 역할을 합니다.

## 5. "왜 한 언어로 통일 안 하나"에 대한 답

"Node.js로 프런트도 백도 통일하면 편하지 않나?"라는 생각이 들 수 있습니다. 실제로 어떤 회사들은 그렇게 합니다(예: Airbnb 초기).

하지만 현대적 선택은 대부분 **"적재적소 언어 혼용"** 입니다. 이유는:

- AI·데이터 분야는 Python 생태계가 압도적이다.
- 프런트는 브라우저 제약상 JS/TS를 피할 수 없다.
- 언어를 나눠도 서로 HTTP API로 통신하면 되므로 **강하게 결합되지 않는다.**

우리 프로젝트도 프런트(TS)와 백(Python)이 **API로만 대화** 하기 때문에, 두 언어가 서로 영향을 주고받지 않습니다. 이렇게 언어에 얽매이지 않고 **HTTP/JSON 같은 공용 약속을 통해 서로를 연결하는 방식** 을 업계에서 표준처럼 씁니다.

## 6. 이 프로젝트의 "언어 + 런타임" 지도

| 영역 | 언어 | 런타임 | 도구 | 실행 위치 |
|---|---|---|---|---|
| 화면 | TypeScript → JavaScript | 브라우저 | Vite + React | 사용자 PC의 브라우저 |
| 빌드/개발 도구 | TypeScript / JS | Node.js | Nx, Vite | 개발자 PC |
| API 서버 | Python 3.12 | CPython + Uvicorn | FastAPI | 서버 |
| 백그라운드 워커 | Python 3.12 | CPython | Celery | 서버 |
| DB 질의 | SQL | PostgreSQL | SQLAlchemy로 생성 | 서버 |
| 셸 스크립트 | Bash | /bin/bash | — | 서버·개발 PC |

이 표가 머릿속에 대략적으로라도 그려진다면 이 장에서 다룰 내용은 거의 짚은 셈입니다.

---

## 7. 핵심 요약

- 프로그래밍 언어는 외국어와 같아서, **각 분야에 맞는 언어** 가 있다.
- 코드는 **컴파일(통째 번역)** 이나 **인터프리터(한 줄씩 해석)** 방식으로 실행된다. TypeScript는 "번역해서 브라우저에서 인터프리트" 되는 혼합형이다.
- 런타임이란 **언어를 실제로 실행해 주는 환경** 이다. Node.js, 브라우저, CPython.
- 우리 프로젝트는 **TypeScript(프런트) + Python(백)** 의 업계 표준 조합을 쓴다.
- 이 선택의 결정적 이유는 **AI 생태계(Python)와 웹 생태계(TS)의 강점을 모두 쓰기 위해서** 다.
