# 08. 데이터베이스 — 영속성의 세계

> **한 줄 요약.** 데이터베이스는 소프트웨어의 **장기 기억**이다. 이 프로젝트는 관계형 DB(**PostgreSQL**)를 쓰고, 앱은 ORM(**SQLAlchemy**)으로 DB와 대화하며, 스키마 변경은 마이그레이션(**Alembic**)으로 안전하게 관리한다.

---

## 1. 왜 데이터베이스가 필요한가

프로그램이 메모리에만 데이터를 들고 있으면, 서버가 재시작되는 순간 **모든 것이 사라집니다**. 사용자 정보, 문서, 회의 기록—서버 재부팅 한 번에 날아가면 안 됩니다.

그래서 "전원이 꺼져도 남아 있는 저장소"가 필요합니다. 이것이 **영속성(persistence, 껐다 켜도 살아남는 성질)** 이며, 그 담당이 **데이터베이스(DB, Database)** 입니다.

### 1.1 캐비닛, 녹음기, 도서관 서가

- **회사 캐비닛과 책상의 차이**: 책상 위 서류(메모리)는 퇴근 전 캐비닛(DB)으로 옮겨 놓아야 다음날에도 존재한다.
- **녹음기의 저장 버튼**: 녹음만 되고 저장을 안 누르면 휘발된다. DB에 `commit`하는 행위가 저장 버튼을 누르는 것.
- **도서관 서가**: 책마다 **청구기호(기본키)** 가 있고, 저자·주제별 **색인(인덱스)** 이 있어 빠르게 찾는다.

### 1.2 ⚠️ 자주 하는 오해

- **"DB는 결국 '데이터 저장 폴더' 아닌가?"**
  DB는 **수백 명이 동시에 읽고 써도 깨지지 않도록** 만들어진 정교한 시스템입니다. 단순한 파일로는 해낼 수 없는 일입니다.
- **"엑셀 시트도 DB 아닌가?"**
  엑셀은 한 명이 열어 볼 때는 괜찮지만, 두 명이 동시에 수정하면 한쪽 작업이 날아갈 수 있습니다. DB는 바로 이 문제를 풀기 위해 만들어진 것입니다.
- **"DB가 하나 죽으면 모든 데이터가 사라진다."**
  운영 DB는 **백업** 과 **복제(replication, 실시간 복사본)** 로 여러 겹의 안전장치를 두고 돌립니다.

## 2. DB의 종류 — 2025년 기준 지도

DB는 크게 두 계열로 나뉩니다.

### 2.1 관계형(RDBMS, SQL)

데이터를 **표(table)** 에 넣고 표 사이에 관계를 맺는 방식. 1970년대 이론으로 만들어진 이래 50년간 업계 표준.

대표:
- **PostgreSQL** (오픈소스, 가장 강력)
- **MySQL / MariaDB** (오픈소스, 가장 널리 쓰임)
- **Oracle, SQL Server** (대기업용 상용)
- **SQLite** (단일 파일, 임베디드)

### 2.2 NoSQL

"관계형의 경직된 스키마가 싫어!"에서 시작. 종류가 많습니다.

- **Document DB** (MongoDB, CouchDB) — JSON 같은 문서 단위 저장
- **Key-Value Store** (Redis, DynamoDB) — 간단한 키-값 저장
- **Graph DB** (Neo4j) — 관계가 복잡할 때
- **Column-family** (Cassandra) — 대규모 분석용
- **Search Engine** (Elasticsearch, OpenSearch) — 검색 특화

### 2.3 이 프로젝트의 선택 — **PostgreSQL 18** + **Redis**

이 프로젝트는 관계형 DB인 **PostgreSQL**을 메인으로, **Redis**를 보조(캐시·큐)로 씁니다. 이유:

1. **복잡한 관계 데이터**: 사용자↔워크스페이스↔앱↔권한 같은 **여러 단계의 관계**를 다루기 좋다.
2. **ACID 보장**: 금융·회의록 같은 "잃으면 안 되는 데이터"에 강한 트랜잭션.
3. **JSON 컬럼도 지원**: PostgreSQL은 관계형인데 NoSQL의 JSON 저장까지 겸한다. "두 세계의 좋은 점"을 동시에.
4. **오픈소스**의 최강자: 성능·안정성·기능 모두 업계 1위급.

→ 결론적으로 **"모르면 PostgreSQL로 시작해라"** 가 2020년대 표준 조언입니다.

Redis는 28장과 30장에서 따로 다룹니다.

### 2.4 ⚠️ 바로잡고 싶은 오해

- **"NoSQL이 더 최신이니 성능도 무조건 좋다."**
  용도가 다를 뿐입니다. **복잡한 관계** 가 얽혀 있는 데이터에는 여전히 관계형 DB가 왕입니다. 중요한 것은 "우리 데이터에 맞는 DB" 를 고르는 일입니다.
- **"MongoDB 같은 Document DB는 스키마가 없어서 자유롭다."**
  스키마가 **코드 속에 숨어 있을 뿐** 이고, 규칙이 없으면 3개월 뒤 데이터가 뒤엉켜 버립니다.
- **"Redis를 메인 DB로 써도 된다."**
  Redis는 메모리 기반이라 **전원이 꺼지면 데이터가 유실될 위험** 이 있습니다. 영속성이 생명인 데이터에는 어울리지 않습니다.

## 3. 관계형 DB의 기본 개념

### 3.1 테이블(Table)

행과 열로 된 표. Excel 시트와 비슷합니다. 예:

**users 테이블**

| id | email | display_name | created_at |
| -- | ----- | ------------ | ---------- |
| 1  | a@doowon.co | 김과장 | 2026-01-01 |
| 2  | b@doowon.co | 이대리 | 2026-01-05 |

### 3.2 기본키(Primary Key) / 외래키(Foreign Key)

- **기본키** — 한 행을 유일하게 구분하는 컬럼. 보통 `id`.
- **외래키** — 다른 테이블의 기본키를 참조. 관계를 표현.

예: 회의 참석자는 `users.id`와 `meetings.id`를 외래키로 참조하는 **연결 테이블**.

**meeting_attendees 테이블**

| meeting_id | user_id |
| ---------- | ------- |
| 100 | 1 |
| 100 | 2 |

### 3.3 관계의 종류

- **1:1** — 하나-하나 (users ↔ profiles)
- **1:N** — 하나-여러 (workspaces ↔ workspace_members)
- **N:M** — 여럿-여럿 (meetings ↔ users, 연결 테이블 필요)

### 3.4 인덱스(Index)

"도서관의 색인"처럼 빠른 검색을 위한 **보조 자료구조**. 자주 쓰이는 컬럼(`email`, `created_at` 등)에 인덱스를 걸면 조회가 빨라집니다. 대신 쓰기가 조금 느려집니다.

### 3.5 트랜잭션(Transaction)과 ACID

여러 DB 변경을 **하나의 덩어리로 묶어** "전부 성공하거나 전부 실패"하게 하는 장치. 계좌 이체의 고전적 예: A에서 -10000, B에서 +10000. 이 둘이 **둘 다 돼야** 맞습니다.

ACID는 트랜잭션의 4가지 성질:

- **A**tomicity (원자성) — 전부 또는 전혀.
- **C**onsistency (일관성) — 규칙 위반 상태로 못 끝난다.
- **I**solation (격리성) — 동시에 돌아가는 트랜잭션들이 서로를 혼동시키지 않는다.
- **D**urability (지속성) — 성공했으면 전원이 꺼져도 남는다.

관계형 DB는 ACID를 **잘** 지키는 것이 강점. NoSQL 일부는 **속도를 위해 이 중 일부를 포기**합니다(CAP 이론). 우리 데이터는 ACID가 중요하므로 RDBMS가 맞습니다.

### 3.6 은행 창구로 다시 보는 ACID

- **원자성(Atomicity).** 이체 신청서를 찢으면 "출금"과 "입금"이 양쪽 모두 무효가 됩니다. 반쪽 상태는 없습니다.
- **일관성(Consistency).** 잔고가 마이너스가 되는 거래는 애초에 막혀 있습니다.
- **격리성(Isolation).** 두 창구에서 동시에 같은 계좌를 처리하더라도, 중간 상태가 서로에게 보이지 않습니다.
- **지속성(Durability).** 영수증을 출력한 거래는 은행이 정전돼도 기록이 남습니다.

### 3.7 ⚠️ 자주 하는 오해

- **"인덱스를 많이 걸수록 무조건 빠르다."**
  인덱스는 **조회 속도는 올려 주지만 쓰기 속도는 떨어뜨립니다.** 저장 공간도 적잖게 잡아먹습니다. **자주 조회되는 컬럼에만** 거는 것이 원칙입니다.
- **"외래키는 꼭 걸어야 한다."**
  **데이터 무결성(integrity, 모순 없는 상태)** 을 지키기 위해 거는 것이 표준이지만, 대규모 분산 시스템에서는 성능을 위해 일부러 빼 두는 경우도 있습니다.

### 3.8 🏢 회의실 예약 동시성

김 과장과 이 대리가 거의 동시에 "3층 A회의실, 오후 2시"를 예약합니다. 트랜잭션과 격리성이 없으면 **둘 다 "성공했다"는 화면** 을 보다가 오후 2시에 정면충돌합니다. DB가 격리성(Isolation)을 지키면 한쪽은 "이미 예약됨"이라는 에러를 받고 다른 시간을 고르게 됩니다.

## 4. SQL — DB와 대화하는 언어

SQL(Structured Query Language)은 모든 관계형 DB가 공통으로 쓰는 언어입니다. 4가지 기본 동사가 핵심입니다.

```sql
-- 조회
SELECT display_name FROM users WHERE email = 'a@doowon.co';

-- 추가
INSERT INTO users (email, display_name) VALUES ('c@doowon.co', '박주임');

-- 수정
UPDATE users SET display_name = '박차장' WHERE id = 3;

-- 삭제
DELETE FROM users WHERE id = 3;
```

**하지만 우리 프로젝트의 코드에는 이런 SQL이 거의 보이지 않습니다**. 왜? ORM을 쓰기 때문입니다.

---

## 5. ORM — Object-Relational Mapping

ORM은 **"DB의 테이블을 프로그래밍 언어의 객체처럼 다루게 해 주는 도구"** 입니다. 이 프로젝트는 **SQLAlchemy 2.x** 를 씁니다.

### 5.1 ORM이 없다면

```python
# 직접 SQL을 쓰는 경우
cursor.execute(
    "SELECT id, email FROM users WHERE email = %s",
    ('a@doowon.co',)
)
row = cursor.fetchone()
```

### 5.2 ORM을 쓰면

```python
# 객체지향적으로
user = session.query(User).filter_by(email='a@doowon.co').first()
print(user.display_name)
```

또는 SQLAlchemy 2.x 스타일:
```python
stmt = select(User).where(User.email == 'a@doowon.co')
user = session.execute(stmt).scalar_one_or_none()
```

### 5.3 ORM의 장·단점

장점:
- **보안**: SQL 인젝션(악의적 입력으로 DB를 탈취하는 공격)을 대부분 막아줌.
- **가독성**: 비즈니스 로직 옆에 자연스럽게 녹아듦.
- **DB 이식성**: PostgreSQL → MySQL 전환이 쉬워짐(이론상).

단점:
- **마법이 많음**: 생성되는 SQL이 최적이 아닐 수 있음.
- **복잡한 쿼리는 오히려 어려움**: 이럴 땐 Raw SQL을 쓰면 됨.

### 5.4 대안

| ORM | 언어 | 특징 |
|---|---|---|
| **SQLAlchemy** | Python | 가장 강력하고 유연. 우리가 씀. |
| Django ORM | Python | Django에 통합, 편리. |
| Peewee | Python | 가볍지만 제약 많음. |
| Prisma | TS/Node | 타입 자동 생성. 최신 인기. |
| TypeORM | TS/Node | 전통적, 문제 많음. |
| Drizzle | TS/Node | 경량, Type-safe. 최근 부상. |

백엔드가 Python이라 SQLAlchemy가 자연스러운 선택입니다.

### 5.5 ⚠️ 헷갈리기 쉬운 것들

- **"ORM을 쓰면 SQL을 몰라도 된다."**
  결국 성능 문제(N+1 쿼리 같은 것)는 **생성된 SQL을 읽어야** 풀립니다. ORM은 "SQL을 대신 써 주는 도구"일 뿐, SQL 이해 자체를 대체해 주지는 않습니다.
- **"ORM을 쓰면 DB 엔진을 언제든 갈아치울 수 있다."**
  단순한 경우에는 맞지만, PostgreSQL만의 기능(JSONB, 배열 컬럼, 풀텍스트 검색 등)을 쓰기 시작하면 이식성은 현실적으로 떨어집니다.

### 5.6 🛠️ 5분 실습

- `apps/api/src/aidoo_api/domains/` 아래에서 `models.py` 파일 하나를 연다 (예: `auth/models.py`).
- 파이썬 클래스 이름(예: `User`)과 필드 이름(예: `email`, `display_name`)이 **그대로 DB 컬럼**이 되는 감각을 눈으로 확인한다.
- "이 파일 한 줄 추가하면 DB에 컬럼 하나가 늘어난다"는 것이 ORM의 본질이다.

## 6. 마이그레이션(Migration) — 스키마 변경의 안전 장치

시간이 지나면 DB 구조도 바뀝니다. 컬럼이 추가되고, 테이블이 나뉘고, 인덱스가 생기고. 이 변경을 **SQL 파일로 기록**해 팀이 공유하는 것이 마이그레이션입니다.

우리 프로젝트는 **Alembic** 을 씁니다(SQLAlchemy의 공식 마이그레이션 도구).

### 6.1 실제 흐름

1. 개발자가 모델(Python 클래스)을 수정. 예: `User` 에 `phone_number` 컬럼 추가.
2. `alembic revision --autogenerate -m "add phone to user"` 로 마이그레이션 파일 자동 생성.
3. `apps/api/alembic/versions/2026xxxx_add_phone_to_user.py` 같은 파일이 생김.
4. 팀원들은 `alembic upgrade head` 로 자기 DB에 그 변경을 적용.
5. 운영 배포 시에도 같은 마이그레이션이 돌아감.

### 6.2 왜 이게 안전한가

- 변경 **역사** 가 파일로 남는다.
- 롤백(되돌리기)도 지원된다.
- 모든 환경(개발·스테이징·운영)이 **동일한 순서로** 변경된다.

마이그레이션 없이 DB를 직접 수정하는 것은 **매우 위험** 합니다. 팀원들 DB가 제각기 달라지기 때문입니다.

### 6.3 리모델링 설계도에 빗대어

- **건물 리모델링 설계도.** "벽을 언제, 어디서, 어떻게 텄는지"를 설계도에 남겨 두지 않으면 나중에 누수가 생겼을 때 원인을 못 찾습니다. 마이그레이션 파일은 "DB의 리모델링 일지"에 가깝습니다.
- **Word 문서의 변경 이력.** 한 파일에 누적된 수정 이력 같은 것. 특정 시점으로 되돌리는 롤백도 가능합니다.

### 6.4 ⚠️ 헷갈리기 쉬운 것들

- **"운영 DB에 `ALTER TABLE`을 직접 치면 빠르고 편하다."**
  며칠 뒤 다른 팀원의 환경과 **스키마가 달라지면서** 원인 모를 버그로 돌아옵니다. 무조건 마이그레이션 파일을 통해 바꿔야 합니다.
- **"마이그레이션은 한 번 만들면 나중에 수정해도 된다."**
  이미 다른 사람이 적용해 버린 마이그레이션을 수정하면 **히스토리가 꼬입니다.** 잘못했을 때는 **새 마이그레이션** 을 만들어서 되돌려야 합니다.

### 6.5 🏢 HR 테이블에 컬럼 하나 추가하기

HR 테이블에 "근무지 유형"(재택/출근/하이브리드) 컬럼을 추가하기로 했다고 해 봅시다. 개발자가 `alembic revision --autogenerate`로 마이그레이션 파일을 생성 → 리뷰 → 머지 → 개발·스테이징·운영 환경이 모두 같은 순서로 업그레이드됩니다. 팀원 누구도 "나만 그 컬럼이 없는데요?" 같은 사태를 겪지 않습니다.

## 7. 비관계형의 자리 — Redis

우리 프로젝트는 Redis도 씁니다. 하지만 Redis는 **"메인 데이터 저장소"가 아닙니다.** 보조 역할입니다.

- **캐시**: 자주 조회되는 결과를 잠시 저장해 DB 부담을 줄임.
- **메시지 큐**: Celery가 워커에 작업을 전달할 때 사용.
- **세션·임시 상태**: 로그인 토큰 블랙리스트, 유저별 임시 설정 등.
- **실시간 협업 릴레이**: Yjs WebSocket 메시지 중계에 Redis Pub/Sub.

Redis는 **메모리 위에서 돌아가므로 매우 빠르지만 영속성은 약하다** 는 특성이 있습니다. 그래서 "잃어도 재계산 가능한 데이터"만 넣는 것이 원칙입니다.

---

## 8. 이 프로젝트의 데이터 계층

**요청이 위에서 아래로 흐른다:**

1. **FastAPI 라우터** — `apps/api/.../router.py`
2. ↓ 호출
3. **서비스 / 유스케이스** — `.../service.py`
4. ↓ 쿼리
5. **SQLAlchemy 모델 + 세션** — `.../models.py`
6. ↓ SQL
7. **PostgreSQL 18**

> 스키마 변경은 별도 트랙으로 흐른다: **Alembic 마이그레이션** (`apps/api/alembic/versions/`).

---

## 9. 실전에서 주의할 점

1. **N+1 쿼리 문제**: 반복문 안에서 DB를 호출하면 쿼리가 수백 번 나감. ORM은 `joinedload`, `selectinload` 같은 기법으로 해결.
2. **트랜잭션 경계**: "이 작업은 다 성공하거나 다 실패해야 한다"는 것을 명확히. FastAPI + SQLAlchemy는 `async with` / 요청 스코프로 처리.
3. **인덱스를 너무 많이 걸지 않기**: 인덱스 = 쓰기 느려짐 + 저장공간 증가. 필요한 것에만.
4. **민감 정보 암호화**: 비밀번호는 **절대** 평문 저장 금지. bcrypt, argon2 같은 **해시 함수**로 변환해 저장.

---

## 10. 핵심 요약

- DB는 **영속성** 을 담당하는 장기 기억.
- 우리는 **PostgreSQL 18 + Redis** 조합. PostgreSQL이 메인, Redis는 캐시/큐.
- 관계형 DB의 핵심: 테이블·키·관계·인덱스·트랜잭션·ACID.
- 앱은 **SQLAlchemy ORM** 을 통해 DB와 대화. 직접 SQL은 거의 안 씀.
- 스키마 변경은 **Alembic 마이그레이션** 으로 안전하게 추적.
