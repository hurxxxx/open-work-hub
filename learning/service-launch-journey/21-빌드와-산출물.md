# 21. 빌드와 산출물 관리

> **한 줄 요약.** 빌드는 "코드를 실행 가능한 형태로 바꾸는 과정" 이다. **언어마다 산출물의 모양이 다르고**, 그 형태에 따라 배포 방식이 결정된다.

---

## 들어가며

지금까지 우리는 코드를 짜고 테스트했습니다. 그런데 그 코드를 운영 서버에 그대로 올려도 동작할까요? 보통은 **그대로는 안 됩니다.** 코드가 실제로 실행 가능한 형태가 되려면 한 단계 변환이 필요한데, 그 단계가 **빌드**입니다.

처음 만드는 분이 빌드 단계에서 자주 막히는 자리:

- React 의 "build" 명령이 무엇을 하는지 흐릿.
- Docker 이미지·압축 파일·정적 파일 같은 산출물 종류가 헷갈림.
- 환경 변수가 빌드 시점에 박히는지, 실행 시점에 읽는지 모호.
- 로컬에서는 잘 도는데 빌드한 결과물이 운영에서 깨짐.

이 레슨은 **언어·프레임워크별 빌드 산출물의 모양**과 그것을 어떻게 관리하는지를 정리합니다.

이 레슨을 다 읽으면:

- 소스 코드와 산출물의 차이를 명확히 안다.
- 주요 언어·프레임워크의 빌드 결과물 형태를 안다.
- Docker 이미지가 무엇이고 왜 사실상 표준이 되었는지 안다.
- 환경 변수의 빌드 시점 vs 실행 시점 처리를 구분할 수 있다.
- CI/CD 파이프라인의 큰 그림을 안다.

## 1. 핵심 개념 — 소스 코드와 산출물

### 1.1 두 단계의 코드

| 단계 | 무엇 | 어디 |
|---|---|---|
| **소스 코드 (Source)** | 사람이 읽고 쓰는 형태 | 깃 저장소 |
| **산출물 (Build Artifact)** | 기계가 실행하는 형태 | 별도 저장소·배포 시스템 |

빌드는 이 둘 사이의 변환 과정입니다.

### 1.2 빌드가 하는 일

언어·프레임워크에 따라 다르지만, 대체로 다음 중 일부 또는 전부.

- **컴파일** — 소스를 기계어·바이트코드로.
- **번들링** — 여러 파일을 하나로 묶기.
- **트랜스파일** — 한 언어를 다른 형태로 변환 (TS → JS, JSX → JS).
- **압축 (Minify)** — 공백·주석 제거, 변수명 축약.
- **트리 셰이킹** — 안 쓰는 코드 제거.
- **자산 처리** — 이미지·CSS 최적화.
- **소스맵 생성** — 운영 디버깅용.

### 1.3 빌드의 두 가지 출력

| 출력 | 무엇 |
|---|---|
| **실행 가능한 산출물** | 운영 환경에 올릴 형태 |
| **메타데이터** | 버전 정보·빌드 시각·커밋 해시 |

메타데이터는 운영 중 어느 버전이 돌고 있는지 추적하는 데 핵심.

## 2. 언어·프레임워크별 산출물

### 2.1 정적 사이트·SPA — 정적 파일

React·Vue·Svelte 같은 SPA 의 빌드 결과는 **정적 파일 묶음** 입니다.

```
dist/
├── index.html
├── assets/
│   ├── index-a1b2c3.js
│   ├── index-d4e5f6.css
│   └── logo-g7h8i9.png
└── favicon.ico
```

이 파일들을 **CDN·정적 호스팅** 에 올리면 끝. Vercel·Netlify·Cloudflare Pages·S3+CloudFront 가 잘 어울립니다.

### 2.2 Node.js 서버

Node 는 **소스 코드를 그대로** 또는 트랜스파일된 JS 를 직접 실행.

```
dist/        ← TypeScript → JavaScript 변환된 코드
node_modules/  ← 의존성
package.json
```

`node dist/main.js` 같은 명령으로 실행. 보통 Docker 이미지로 포장.

### 2.3 Python 서버

Python 도 소스 그대로 실행. 의존성을 명세한 파일이 필수.

```
app/                       ← 소스
requirements.txt 또는 pyproject.toml
```

`uvicorn app.main:app` 또는 `gunicorn` 같은 WSGI/ASGI 서버로 실행.

### 2.4 Java / Kotlin

`.jar` 또는 `.war` 파일로 빌드. 단일 jar 안에 모든 의존성 포함 가능 (fat jar).

```
target/myapp-1.0.0.jar
```

`java -jar myapp.jar` 로 실행.

### 2.5 Go / Rust

단일 실행 파일로 컴파일. 의존성 따로 없음. 가장 가벼움.

```
./myapp        ← Linux 실행 파일
./myapp.exe    ← Windows
```

서버에 그대로 올려 실행.

### 2.6 모바일 앱

| 플랫폼 | 산출물 |
|---|---|
| iOS | `.ipa` (App Store 업로드용) |
| Android | `.apk` (직접 배포) 또는 `.aab` (Play Store 업로드용) |

자세한 내용 레슨 25.

### 2.7 한 표 비교

| 언어 | 산출물 | 실행 방식 |
|---|---|---|
| React/Vue/Svelte | 정적 파일 (HTML+JS+CSS) | 정적 호스팅·CDN |
| Node.js | JS 파일 + node_modules | Node 런타임 |
| Python | .py 파일 + 의존성 | Python 런타임 |
| Java | .jar | JVM |
| Go/Rust | 단일 바이너리 | 직접 실행 |
| 모바일 | .ipa/.aab | 스토어 |

## 3. Docker — 사실상의 표준

### 3.1 Docker 이미지란

소스·런타임·의존성·설정을 모두 한 박스에 담은 형태. **"내 컴퓨터에선 되는데" 문제**를 해결.

```dockerfile
# Dockerfile
FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```bash
docker build -t myapp:v1.0.0 .
docker run -p 8000:8000 myapp:v1.0.0
```

### 3.2 왜 거의 모든 곳에서 쓰나

- **환경 일관성** — 로컬·staging·운영이 같은 이미지.
- **의존성 격리** — 호스트 OS 와 분리.
- **이식성** — Docker 가 도는 곳 어디서나.
- **확장성** — Kubernetes·ECS 같은 오케스트레이션과 결합.

### 3.3 멀티 스테이지 빌드 — 이미지 크기 줄이기

빌드용 이미지와 실행용 이미지를 분리해 산출물만 옮김.

```dockerfile
# 1단계: 빌드
FROM node:20 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 2단계: 실행
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
```

빌드 도구(Node·npm) 는 최종 이미지에 안 들어감. 이미지 크기 1/10 으로 줄어듦.

### 3.4 이미지 레지스트리

빌드된 이미지를 저장·공유하는 곳.

| 레지스트리 | 무엇 |
|---|---|
| **Docker Hub** | 가장 흔한 공개 |
| **GitHub Container Registry** | GitHub 통합 |
| **AWS ECR** | AWS 통합 |
| **Google Artifact Registry** | GCP 통합 |
| **Harbor** | 셀프 호스팅 |

푸시·풀 명령:

```bash
docker push registry.example.com/myapp:v1.0.0
docker pull registry.example.com/myapp:v1.0.0
```

## 4. 환경 변수 — 빌드 시점 vs 실행 시점

### 4.1 빌드 시점 (Build-Time)

빌드할 때 코드에 박힘. 빌드 후에는 못 바꿈.

- 정적 사이트의 `import.meta.env.VITE_API_URL` (Vite).
- React 의 `process.env.REACT_APP_XXX`.

같은 코드를 다른 환경에 배포하려면 **환경별 별도 빌드** 필요.

```bash
# 운영 빌드
VITE_API_URL=https://api.app.com npm run build

# Staging 빌드
VITE_API_URL=https://api-staging.app.com npm run build
```

### 4.2 실행 시점 (Runtime)

서버가 시작될 때 환경 변수 읽음. 같은 빌드를 여러 환경에 배포 가능.

- Node.js·Python 서버.
- Docker 컨테이너 환경 변수.

```bash
docker run -e DATABASE_URL=postgres://... -e API_KEY=... myapp:v1.0.0
```

이 차이를 모르면, **운영 변수를 빌드한 정적 코드에 박은 채 staging 에 올려** 깨지는 사고가 자주 납니다.

### 4.3 시크릿 관리

환경 변수도 안전한 저장소에 두어야.

| 도구 | 무엇 |
|---|---|
| **AWS Secrets Manager / Parameter Store** | AWS |
| **GCP Secret Manager** | GCP |
| **HashiCorp Vault** | 멀티 클라우드 |
| **Doppler** | SaaS, 다국 환경 통합 관리 |
| **GitHub Secrets** | CI 변수 |

코드·.env 에 절대 박지 않고, 위 저장소에서 빌드·실행 시점에 주입.

## 5. CI/CD 파이프라인

### 5.1 무엇

코드 변경이 들어오면 자동으로 **빌드·테스트·배포** 까지 수행하는 파이프라인.

| 단어 | 무엇 |
|---|---|
| **CI (Continuous Integration)** | 변경마다 자동 빌드·테스트 |
| **CD (Continuous Delivery / Deployment)** | 자동 배포 |

CD 의 두 변형:
- **Continuous Delivery** — 자동으로 staging 까지, 운영은 수동 승인.
- **Continuous Deployment** — 자동으로 운영까지.

처음에는 Continuous Delivery 가 안전.

### 5.2 도구

| 도구 | 특징 |
|---|---|
| **GitHub Actions** | GitHub 통합, 가장 흔함 |
| **GitLab CI** | GitLab 통합 |
| **CircleCI** | 빠름, 무료 티어 |
| **Jenkins** | 오래됨, 셀프 호스팅 |
| **Drone, Buildkite** | 가벼움 |

### 5.3 GitHub Actions 예시

```yaml
# .github/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install dependencies
        run: npm ci

      - name: Test
        run: npm test

      - name: Build
        run: npm run build
        env:
          VITE_API_URL: ${{ secrets.API_URL }}

      - name: Build Docker image
        run: docker build -t myapp:${{ github.sha }} .

      - name: Push to registry
        run: |
          docker tag myapp:${{ github.sha }} registry.example.com/myapp:${{ github.sha }}
          docker push registry.example.com/myapp:${{ github.sha }}

      - name: Deploy to staging
        run: kubectl set image deployment/myapp myapp=registry.example.com/myapp:${{ github.sha }}
```

### 5.4 파이프라인의 단계

권장 단계 순서:

```
1. 코드 받기 (Checkout)
2. 의존성 설치
3. Lint·Format 검사
4. 단위 테스트
5. 통합 테스트
6. 빌드
7. (선택) E2E 테스트
8. 보안 스캔
9. 산출물 푸시 (Docker 이미지·정적 파일)
10. Staging 배포
11. (선택) Smoke 테스트
12. 운영 배포 (수동 승인 또는 자동)
```

## 6. 버전 관리

### 6.1 산출물에 버전을 박자

운영 중 "지금 무슨 버전이 돌고 있지?" 의 답이 즉시 나와야 합니다.

방법:
- **Git commit hash** — `myapp:abc1234`
- **Semantic version + commit** — `myapp:v1.0.0-abc1234`
- **빌드 시간** — `myapp:2026-04-25-1430`

이미지 태그·환경 변수·로그에 모두 일관 표시.

### 6.2 시맨틱 버저닝 (SemVer)

`MAJOR.MINOR.PATCH` 형식.

| 부분 | 언제 올림 |
|---|---|
| MAJOR | 호환성 깨는 변경 |
| MINOR | 호환성 유지하는 새 기능 |
| PATCH | 버그 수정 |

### 6.3 latest 태그의 함정

`myapp:latest` 만 쓰면 어느 버전이 돌고 있는지 추적 불가. 항상 명시적 버전.

## 7. 자주 빠지는 함정

### 함정 1. 로컬 빌드를 직접 운영에 올린다

"내 노트북에서 빌드한 게 deploy 됐다" → 다른 컴퓨터에서 다시 빌드하면 다른 결과. **CI 가 빌드** 하는 것이 표준.

### 함정 2. node_modules 를 git 에 올린다

거대한 디렉토리가 저장소를 망침. `.gitignore` 에 추가, CI 가 매번 `npm ci`.

### 함정 3. .env 를 git 에 올린다

시크릿 유출. **`.env` 는 절대 커밋 금지**. `.env.example` 만 올려서 키 이름만 공유.

### 함정 4. 환경 변수의 시점 혼동

빌드 시점 변수를 운영에 바꾸려고 하지만 안 바뀜 (이미 코드에 박힘). 변수의 성격을 정확히.

### 함정 5. 빌드가 비결정적

같은 커밋을 빌드해도 결과가 다름. 의존성을 lock 파일(`package-lock.json`·`requirements.txt`·`go.sum`)로 고정.

### 함정 6. 이미지가 너무 큼

Node.js 이미지가 1GB 를 넘는 등. 멀티 스테이지·Alpine 베이스 이미지 사용.

### 함정 7. 시크릿이 빌드 로그에 노출

CI 로그에 환경 변수 값이 그대로 출력. **GitHub Secrets** 같은 도구를 쓰면 자동 마스킹. 직접 echo 하지 않기.

### 함정 8. 빌드 산출물의 추적성 없음

운영에서 버그 발견했는데 어느 커밋의 결과인지 모름. **이미지 태그 = 커밋 해시** 로 매핑.

### 함정 9. 빌드 시간이 너무 오래

10분·30분 빌드는 개발자 피로. 캐싱 (의존성·Docker 레이어) 으로 1~3분으로.

### 함정 10. CI 만 통과하면 끝

CI 가 그린이라도 운영에서 깨질 수 있음. Staging 에서 한 번 더 검증.

## 8. 한 셜 더

### 8.1 모노레포 빌드

여러 패키지가 한 저장소에 있을 때, 변경된 부분만 빌드. **Nx·Turborepo·Bazel** 같은 도구.

```bash
nx affected:build  # 변경된 패키지만 빌드
```

### 8.2 빌드 캐시

같은 입력에 대해 빌드 결과 재사용.

- **GitHub Actions cache**
- **Turborepo Remote Cache**
- **Bazel Remote Cache**
- **Docker BuildKit cache**

CI 빌드 시간이 30 분 → 3 분으로 줄어드는 일이 흔함.

### 8.3 SBOM (Software Bill of Materials)

산출물에 들어간 모든 의존성 명세. 보안·라이선스 추적에 필수.

```bash
syft myapp:v1.0.0 -o spdx-json
```

### 8.4 Reproducible Builds

같은 입력 → 정확히 같은 산출물(바이너리 일치). 보안·신뢰의 근거. 어렵지만 의미 있는 목표.

### 8.5 추가 키워드

- **GitOps** — 운영 상태를 git 으로 선언, 자동 동기화 (ArgoCD·Flux).
- **Blue-Green / Canary 배포** — 무중단 배포 패턴 (다음 레슨).
- **Artifact Promotion** — 같은 산출물을 staging → 운영으로 승격.
- **Trusted Build / Sigstore** — 빌드 산출물 서명·검증.
