# 13. 프론트엔드 개발 한 바닥

> **한 줄 요약.** 프론트엔드는 "화면을 그리는 일" 이 아니라 **"사용자 입력 → 서버 호출 → 결과 표시" 라는 끊임없는 사이클을 매끄럽게 만드는 일** 이다.

---

## 들어가며

설계가 끝나면 가장 먼저 만져지는 영역이 보통 프론트엔드입니다. 사용자에게 가장 먼저 보이는 부분이고, 결과가 화면에 즉시 떠서 만족도가 빠르기 때문입니다.

처음 만드는 분이 프론트엔드에서 자주 막히는 자리:

- HTML·CSS·JavaScript 가 무엇이고 어떻게 협력하는지 흐릿함.
- React·Vue·Svelte 같은 프레임워크 중 무엇을 골라야 할지 막막함.
- 화면을 그렸지만 데이터가 화면에 흘러 들어가는 흐름을 모름.
- 상태 관리·라우팅·폼 같은 단어 앞에서 멈춤.

이 레슨은 프론트엔드의 **큰 그림**을 잡는 데 집중합니다. 한 프레임워크의 문법을 외우는 게 아니라, "프론트엔드가 무엇을 책임지고 어떻게 흘러가는지" 의 감각을 만드는 것이 목표입니다.

이 레슨을 다 읽으면:

- 프론트엔드의 책임 4가지(렌더·상호작용·통신·상태)를 안다.
- 웹·모바일 프론트엔드 옵션을 이해하고 선택할 수 있다.
- React 생태계의 핵심 개념(컴포넌트·상태·이펙트·라우팅)을 짧게 안다.
- 프론트엔드 폴더 구조를 어떻게 잡을지 안다.
- 처음 만드는 사람이 빠지는 함정을 안다.

---

## 1. 핵심 개념 — 프론트엔드의 책임 4가지

### 책임 1. 렌더 (Render)

데이터를 받아 **화면 요소** 로 그립니다. 사용자 목록 데이터가 있으면 그것을 카드 리스트로, 거래 데이터가 있으면 차트로.

웹의 렌더는 **HTML + CSS** 입니다.

- HTML — 구조 (이 자리에 어떤 요소가)
- CSS — 모양 (그 요소가 어떻게 보이는지)

### 책임 2. 상호작용 (Interaction)

사용자의 입력에 반응합니다. 버튼 클릭·텍스트 입력·스크롤·드래그.

웹에서 상호작용은 **JavaScript** 가 담당.

```js
button.addEventListener('click', () => {
  // 사용자가 버튼을 눌렀을 때 실행
});
```

### 책임 3. 통신 (Communication)

서버에 데이터를 요청하고 받아옵니다. 레슨 11 의 API 를 호출하는 일입니다.

```js
const response = await fetch('/transactions', {
  headers: { Authorization: `Bearer ${token}` },
});
const data = await response.json();
```

### 책임 4. 상태 (State)

화면에 표시될 데이터를 메모리에 들고 있습니다. 사용자가 입력한 값, 서버에서 받은 결과, "지금 로딩 중인가" 같은 플래그.

상태가 바뀌면 화면이 다시 그려집니다 — 이것이 모던 프론트엔드 프레임워크의 핵심 동작 원리입니다.

### 4책임의 흐름

```
① 사용자가 화면을 본다       → 렌더
② 사용자가 입력·클릭한다     → 상호작용
③ 그 동작으로 서버를 호출    → 통신
④ 받은 데이터를 상태에 저장 → 상태 변경
⑤ 상태가 바뀌면 화면 다시 그림 → 렌더
```

이 사이클이 끊임없이 도는 게 프론트엔드입니다.

## 2. 웹 프론트엔드 — 무엇으로 만들까

### 2.1 가장 단순한 형태 — 순수 HTML/CSS/JS

작은 정적 사이트라면 프레임워크 없이 HTML·CSS·JS 파일 몇 개로 충분합니다.

```
index.html
style.css
script.js
```

랜딩 페이지·소개 페이지 정도라면 이걸로 충분. 빠르고 가볍습니다.

### 2.2 SPA 프레임워크

화면이 5개 이상이고 상호작용이 많다면 **SPA(Single Page Application)** 프레임워크를 씁니다.

| 프레임워크 | 특징 | 학습 곡선 |
|---|---|---|
| **React** | 가장 많이 쓰임, 생태계 거대 | 중간 |
| **Vue** | 진입 장벽 낮음, 한국에서 인기 | 낮음 |
| **Svelte** | 컴파일러 기반, 코드 양 적음 | 낮음 |
| **Solid** | React 비슷한 문법, 빠름 | 중간 |
| **Angular** | 풀 스택 솔루션, 대기업 | 높음 |

처음 만드는 분이 가장 무난한 선택은 **React** 또는 **Vue** 입니다. 자료가 가장 많고, AI 도구도 가장 잘 만들어 줍니다.

### 2.3 메타 프레임워크

SPA 프레임워크 위에 라우팅·SSR·번들링까지 묶은 도구.

| 메타 프레임워크 | 기반 |
|---|---|
| **Next.js** | React 기반. 가장 인기. |
| **Remix / React Router v7** | React 기반. 데이터 흐름 강조. |
| **Nuxt** | Vue 기반. |
| **SvelteKit** | Svelte 기반. |
| **Astro** | 다중 프레임워크. 콘텐츠 사이트에 강함. |

단순 SPA 대신 메타 프레임워크로 시작하면 SEO·성능에 유리합니다.

### 2.4 무엇을 골라야 하나

| 상황 | 추천 |
|---|---|
| 정적 페이지 (랜딩·블로그) | Astro / Next.js |
| SPA 웹 앱 | Next.js / Vite + React |
| 빠른 학습·작은 팀 | Vue / Svelte |
| 디자이너와 같이 일하는 콘텐츠 사이트 | Astro |
| AI 도구로 빠르게 만들기 | React + Vite + Tailwind + shadcn |

처음 만드는 분이라면 **Vite + React + Tailwind + shadcn/ui** 조합이 가장 무난한 시작입니다.

## 3. React 의 핵심 개념 짧게

React 를 선택했다면 다음 4가지만 잡으면 시작할 수 있습니다.

### 3.1 컴포넌트 (Component)

화면의 한 조각. 함수처럼 만들고 호출합니다.

```tsx
function Button({ children, onClick }) {
  return (
    <button className="rounded bg-primary px-4 py-2 text-white" onClick={onClick}>
      {children}
    </button>
  );
}

// 사용
<Button onClick={() => alert('clicked')}>저장</Button>
```

컴포넌트는 **재사용 단위**. 한 번 만들고 여러 화면에서 사용.

### 3.2 상태 (State)

컴포넌트 내부의 데이터. 바뀌면 컴포넌트가 다시 렌더됩니다.

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button onClick={() => setCount(count + 1)}>
      클릭 {count}번
    </button>
  );
}
```

`useState` 가 React 의 가장 기본 도구.

### 3.3 이펙트 (Effect)

렌더 외부의 작업 (서버 호출·구독·타이머).

```tsx
function Profile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch(`/users/${userId}`).then(r => r.json()).then(setUser);
  }, [userId]);

  if (!user) return <p>로딩 중...</p>;
  return <p>{user.name}</p>;
}
```

다만 데이터 페칭은 직접 `useEffect` 보다 **TanStack Query (React Query)** 같은 라이브러리를 쓰는 것이 훨씬 깔끔합니다.

### 3.4 라우팅 (Routing)

URL 에 따라 다른 화면을 보여주는 작업.

| 도구 | 사용 |
|---|---|
| **React Router** | 가장 많이 쓰임 |
| **TanStack Router** | 타입 안전 |
| **Next.js App Router** | Next.js 내장 |

```tsx
<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/transactions" element={<TransactionList />} />
  <Route path="/transactions/:id" element={<TransactionDetail />} />
</Routes>
```

## 4. 프론트엔드 폴더 구조

처음 시작할 때 권장되는 구조:

```
src/
├── app/                  ← 라우트, 레이아웃
├── components/           ← 재사용 가능한 UI 컴포넌트
│   ├── ui/              ← 디자인 시스템 (Button, Input, ...)
│   └── layout/          ← Header, Sidebar, Footer
├── domains/              ← 도메인별 모듈
│   ├── auth/
│   ├── transactions/
│   └── couples/
├── hooks/               ← 커스텀 훅
├── lib/                  ← 외부 SDK 래퍼, 유틸
├── api/                  ← API 클라이언트
└── styles/               ← 전역 스타일
```

핵심은 **도메인별 분리**. 기능이 늘어나면서 한 폴더에 몰리지 않게.

### 도메인 한 폴더 안의 구조

```
domains/transactions/
├── api.ts               ← API 호출 함수
├── hooks.ts             ← 커스텀 훅 (useTransactions 등)
├── types.ts             ← 타입 정의
├── components/          ← 이 도메인의 컴포넌트
└── pages/               ← 라우트 페이지
```

처음에는 단순하게, 도메인이 늘면서 패턴을 굳힘.

## 6. 컴포넌트 설계 원칙

### 6.1 작게, 한 가지만

한 컴포넌트는 한 가지 일만 합니다. 길어지면 분리.

```tsx
// 나쁨: 한 컴포넌트가 너무 많이 함
function TransactionPage() {
  // 100줄의 로직...
}

// 좋음: 작게 분리
function TransactionPage() {
  return (
    <Layout>
      <TransactionFilters />
      <TransactionList />
      <TransactionPagination />
    </Layout>
  );
}
```

### 6.2 Props 로 데이터를 받음

부모 컴포넌트가 자식에게 데이터를 props 로 전달.

```tsx
function TransactionItem({ transaction, onEdit }) {
  return (
    <li>
      {transaction.merchant} — {transaction.amount}
      <button onClick={() => onEdit(transaction.id)}>수정</button>
    </li>
  );
}
```

### 6.3 비즈니스 로직과 UI 분리

데이터 처리 로직은 훅 (`useTransactions`) 으로, UI 는 컴포넌트로 분리.

```tsx
function useTransactions(filters) {
  return useQuery({
    queryKey: ['transactions', filters],
    queryFn: () => fetchTransactions(filters),
  });
}

function TransactionList() {
  const filters = useFilters();
  const { data, isLoading } = useTransactions(filters);

  if (isLoading) return <Skeleton />;
  return <ul>{data.map(t => <TransactionItem key={t.id} transaction={t} />)}</ul>;
}
```

## 7. 자주 빠지는 함정

### 함정 1. 프레임워크 선택에 며칠 보낸다

React vs Vue vs Svelte 의 끝없는 비교. 처음 출시에는 **둘 중 하나** 골라서 시작하면 됩니다. 자료가 많은 React 가 무난.

### 함정 2. 모든 상태를 전역으로 관리

처음에 모든 데이터를 Redux 나 Zustand 에 몰아넣는 함정. **컴포넌트 안에서 처리되는 상태는 안에서**, 정말 여러 곳에서 공유되는 것만 전역.

### 함정 3. `useEffect` 남발

데이터 페칭·구독·이벤트 처리에 `useEffect` 만 쓰면 코드가 복잡해집니다. **TanStack Query** 같은 데이터 페칭 라이브러리, 또는 라이브러리에 맞는 훅을 우선 사용.

### 함정 4. 에러 처리 없이 시작

API 가 실패할 수 있다는 가정이 빠진 코드. 모든 페칭에 **로딩·에러·성공 3상태**를 처리.

### 함정 5. 화면을 한 번 그리고 반응형 안 함

처음에 PC 만 그렸다가 모바일에서 깨지는 사고. **모바일 먼저, PC 는 확장**. 자세한 내용 레슨 18.

### 함정 6. 디자인 시스템 없이 매 화면 새 색·간격

같은 결정을 매번 다시 하면 일관성이 깨집니다. 레슨 12 의 토큰을 만들어 두고 그것만 사용.

### 함정 7. 빌드 사이즈 폭증

라이브러리를 너무 많이 가져다 쓰면 번들이 무거워져 첫 로딩이 느립니다. **불필요한 라이브러리 제거 + 코드 스플리팅**.

### 함정 8. 폼 검증을 직접 짠다

폼은 보기보다 까다롭습니다. **React Hook Form + Zod** 조합이 검증 로직의 90% 를 처리해 줍니다.

## 8. 한 셜 더

### 8.1 SSR / SSG / CSR

- **CSR (Client-Side Rendering)** — 브라우저가 JS 실행해 화면 생성. 일반 SPA.
- **SSR (Server-Side Rendering)** — 서버가 HTML 만들어 보냄. 첫 페이지 빠름, SEO 좋음.
- **SSG (Static Site Generation)** — 빌드 시점에 HTML 미리 생성. 가장 빠름.
- **ISR (Incremental Static Regeneration)** — SSG + 일정 시점에 재생성.

Next.js 같은 메타 프레임워크는 이 모두를 지원합니다. 첫 출시는 **CSR 또는 SSG** 가 단순.

### 8.2 컴포넌트 카탈로그 — Storybook

컴포넌트를 격리된 환경에서 보여주는 도구. 디자이너·개발자가 같은 화면을 보고 합의할 수 있습니다.

처음 출시에는 Storybook 까지는 과할 수 있지만, 컴포넌트가 30개 넘어가면 도입 검토.

### 8.3 접근성 (A11y) 기본

- 의미 있는 HTML 태그 사용 (`button` 을 `div` 대신).
- `alt` 속성 (이미지).
- 라벨이 폼 입력과 연결.
- 키보드만으로 모든 기능 도달.
- 스크린 리더 호환 (`aria-*` 속성).

shadcn/ui 같은 라이브러리는 접근성을 기본으로 지원하므로 가져다 쓰면 자동.

### 8.4 추가 키워드

- **Hydration** — SSR 후 JS 가 활성화되는 과정.
- **Code Splitting** — 번들을 페이지별로 쪼개기.
- **Lazy Loading** — 필요할 때만 로드.
- **Web Vitals** — Google 의 사용자 경험 핵심 지표 (LCP·FID·CLS).
- **PWA** — 웹 앱을 모바일 앱처럼 설치·오프라인 지원.
