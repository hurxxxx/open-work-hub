# 16. 프론트-백 연동의 실제

> **한 줄 요약.** 프론트와 백이 따로 잘 도는 것과, 둘이 연결되어 잘 도는 것은 **다른 문제**다. CORS·환경별 base URL·에러 처리·재시도 — 이 4가지가 첫 연동의 디버깅 시간을 결정한다.

---

## 들어가며

프론트엔드도 만들었고 백엔드 API도 동작합니다. 따로따로는 잘 돕니다. 그런데 막상 둘을 연결하려는 순간 새로운 종류의 문제들이 등장합니다.

처음 연동에서 자주 마주치는 모습:

- "CORS 에러" 라는 빨간 메시지가 콘솔에 가득.
- 로컬에서는 잘 되는데 운영에 올리니 API 호출이 실패.
- 토큰을 어디에 저장해야 하는지 헷갈림.
- 네트워크가 잠깐 끊기면 화면이 텅 비어버림.

이 모든 문제는 따로따로 보면 별거 아닌데, 처음에는 한꺼번에 닥쳐 시간을 잡아먹습니다. 이 레슨은 그 시간을 줄여 줍니다.

이 레슨을 다 읽으면:

- CORS 가 무엇이고 어떻게 푸는지 안다.
- 환경별(로컬·staging·운영) base URL 관리 패턴을 안다.
- API 클라이언트를 한 곳으로 모으는 구조를 잡을 수 있다.
- 토큰 저장·갱신·전송의 기본 패턴을 안다.
- 에러·로딩·재시도를 일관되게 처리하는 법을 안다.

---

## 1. CORS — 가장 많이 부딪히는 첫 벽

### 1.1 CORS 가 뭔가

브라우저는 보안상 **다른 출처(origin)** 의 자원에 접근할 때 제약을 둡니다. 출처는 `protocol + host + port` 의 조합.

| 두 URL | 출처가 같은가? |
|---|:-:|
| `https://app.com` ↔ `https://app.com/anything` | ✓ |
| `http://app.com` ↔ `https://app.com` | ✗ (protocol 다름) |
| `https://app.com` ↔ `https://api.app.com` | ✗ (host 다름) |
| `localhost:3000` ↔ `localhost:8000` | ✗ (port 다름) |

다른 출처에 요청을 보내려면 서버가 **CORS 헤더**로 명시적으로 허용해야 합니다.

### 1.2 CORS 에러의 모습

브라우저 콘솔에 빨갛게:

```
Access to fetch at 'https://api.app.com/users' from origin 'https://app.com'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is
present on the requested resource.
```

### 1.3 백엔드에서 CORS 허용

각 프레임워크에 CORS 미들웨어가 있습니다.

**FastAPI:**
```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.com", "http://localhost:3000"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**Express:**
```ts
import cors from 'cors';
app.use(cors({ origin: ['https://app.com', 'http://localhost:3000'], credentials: true }));
```

### 1.4 CORS 의 함정

- **Preflight 요청** — `PUT`·`DELETE`·커스텀 헤더가 있는 요청은 본 요청 전에 `OPTIONS` 요청을 자동 발송. 백엔드가 OPTIONS 도 처리해야.
- **`allow_credentials=True` 일 때** `allow_origins=["*"]` 안 됨. 명시적 origin 나열 필요.
- **Wildcard subdomain** — `*.app.com` 식의 와일드카드는 직접 처리 (정규식·함수).

## 2. 환경별 Base URL 관리

### 2.1 환경마다 API 주소가 다르다

| 환경 | 프론트 URL | API URL |
|---|---|---|
| Local | `http://localhost:3000` | `http://localhost:8000` |
| Staging | `https://staging.app.com` | `https://api-staging.app.com` |
| Production | `https://app.com` | `https://api.app.com` |

코드에 base URL 을 박지 않습니다. **환경 변수**로 주입.

### 2.2 Vite 환경 변수 예시

```bash
# .env.local
VITE_API_BASE_URL=http://localhost:8000

# .env.production
VITE_API_BASE_URL=https://api.app.com
```

```ts
const API_BASE = import.meta.env.VITE_API_BASE_URL;
```

### 2.3 Next.js 환경 변수

```bash
# .env.local
NEXT_PUBLIC_API_BASE_URL=http://localhost:8000
```

`NEXT_PUBLIC_` 접두어가 있으면 클라이언트 코드에 노출됩니다 (그래서 비밀이 아닌 값에만 사용).

### 2.4 빌드 시점 vs 런타임 환경 변수

- **빌드 시점** — 빌드할 때 값이 코드에 박힘. 빌드 후엔 못 바꿈. 일반 정적 사이트.
- **런타임** — 실행할 때 환경 변수를 읽음. 같은 빌드를 다른 환경에 배포 가능. 컨테이너·서버.

처음에는 **빌드 시점**으로 시작. 환경마다 별도 빌드.

## 3. API 클라이언트 — 한 곳으로 모으기

각 컴포넌트마다 `fetch` 를 직접 부르면 인증·에러·재시도 코드가 흩어집니다. **API 클라이언트** 한 군데에 모으세요.

### 3.1 라이브러리 선택

| 라이브러리 | 특징 |
|---|---|
| **fetch** | 브라우저·Node 기본. 간단. |
| **ky** | fetch 위의 가벼운 wrapper. 좋은 기본값. |
| **axios** | 가장 인기. 인터셉터·취소·진행률. |
| **TanStack Query** | 데이터 페칭 + 캐싱 + 상태. 위 셋과 같이 사용. |

처음에는 **ky 또는 axios + TanStack Query** 조합 권장.

### 3.2 클라이언트 예시 (axios)

```ts
import axios from 'axios';

export const api = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 10_000,
  headers: { 'Content-Type': 'application/json' },
});

// 요청 인터셉터: 토큰 자동 첨부
api.interceptors.request.use((config) => {
  const token = getAccessToken();
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// 응답 인터셉터: 401 시 자동 갱신
api.interceptors.response.use(
  (response) => response,
  async (error) => {
    if (error.response?.status === 401) {
      await refreshToken();
      return api(error.config); // 재시도
    }
    return Promise.reject(error);
  }
);
```

### 3.3 도메인별 호출 함수

```ts
// domains/transactions/api.ts
export async function fetchTransactions(filters: Filters) {
  const { data } = await api.get('/transactions', { params: filters });
  return data;
}

export async function createTransaction(body: CreateTransactionInput) {
  const { data } = await api.post('/transactions', body);
  return data;
}
```

이제 컴포넌트는 함수만 호출:

```tsx
const { data, isLoading, error } = useQuery({
  queryKey: ['transactions', filters],
  queryFn: () => fetchTransactions(filters),
});
```

## 4. 토큰 저장·전송·갱신

### 4.1 어디에 저장하나

| 위치 | 장점 | 단점 |
|---|---|---|
| **localStorage** | 간단 | XSS 에 취약 |
| **sessionStorage** | 탭 닫으면 사라짐 | XSS 에 취약 |
| **HttpOnly 쿠키** | XSS 안전 | CSRF 신경 써야 |
| **메모리 (state)** | 가장 안전 | 새로고침 시 사라짐 |

가장 안전한 패턴:
- **Access Token** — 짧은 수명, 메모리.
- **Refresh Token** — 긴 수명, HttpOnly 쿠키.

처음에는 단순하게 localStorage 도 OK. XSS 가 터지지 않도록 React 의 자동 escape 를 신뢰하고, 어떤 경우에도 `dangerouslySetInnerHTML` 에 사용자 입력을 넣지 않습니다.

### 4.2 자동 갱신 (Refresh)

Access Token 이 만료되면 자동으로 Refresh Token 을 사용해 새 Access Token 을 받습니다.

```ts
async function refreshToken() {
  const { data } = await api.post('/auth/refresh');
  setAccessToken(data.access_token);
}
```

응답 인터셉터에서 401 받으면 자동 갱신 → 원래 요청 재시도. (위 axios 예시 참조.)

### 4.3 동시 갱신 문제

여러 요청이 동시에 401 을 받으면 갱신이 중복 호출. 한 번만 갱신하도록 락을 걸어야:

```ts
let refreshPromise: Promise<void> | null = null;

async function refreshOnce() {
  if (!refreshPromise) {
    refreshPromise = doRefresh().finally(() => { refreshPromise = null; });
  }
  return refreshPromise;
}
```

## 5. 에러·로딩·재시도 — 일관된 처리

### 5.1 응답 상태 3종 — 모든 호출에 적용

| 상태 | 화면 |
|---|---|
| Loading | 스피너 또는 스켈레톤 |
| Error | 에러 메시지 + 재시도 버튼 |
| Success | 데이터 표시 |

`useQuery` 가 이 3종을 자동 제공:

```tsx
const { data, isLoading, error, refetch } = useQuery({ ... });

if (isLoading) return <Skeleton />;
if (error) return <ErrorMessage onRetry={() => refetch()} />;
return <List data={data} />;
```

### 5.2 에러 분류

```ts
function describeError(error: unknown): string {
  if (axios.isAxiosError(error)) {
    if (!error.response) return '네트워크 연결을 확인해 주세요.';
    if (error.response.status === 401) return '로그인이 필요합니다.';
    if (error.response.status === 403) return '권한이 없습니다.';
    if (error.response.status === 404) return '데이터를 찾을 수 없습니다.';
    if (error.response.status >= 500) return '서버에 문제가 있어요. 잠시 후 다시.';
    return error.response.data?.error?.message ?? '요청을 처리하지 못했어요.';
  }
  return '알 수 없는 문제가 발생했어요.';
}
```

이 함수를 통해 일관된 메시지.

### 5.3 자동 재시도

네트워크 에러 같은 일시적 오류는 자동 재시도. TanStack Query 는 기본으로 3번 재시도.

```ts
useQuery({
  queryKey: [...],
  queryFn: ...,
  retry: 3,           // 3번 재시도
  retryDelay: (i) => Math.min(1000 * 2 ** i, 30_000), // 지수 백오프
});
```

POST·PATCH·DELETE 같은 변경 요청은 재시도가 위험할 수 있음 (중복 처리). 멱등키(`Idempotency-Key`) 가 있을 때만 재시도.

### 5.4 글로벌 에러 경계

예상 못한 에러가 발생해도 화면이 통째로 죽지 않도록.

```tsx
import { ErrorBoundary } from 'react-error-boundary';

<ErrorBoundary fallback={<ErrorScreen />}>
  <App />
</ErrorBoundary>
```

## 6. 개발 편의 — 프록시·Mocking

### 6.1 Vite Dev Proxy

로컬 개발에서 CORS 를 우회하려면 Vite 의 프록시 설정.

```ts
// vite.config.ts
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8000',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
    },
  },
});
```

이제 프론트가 `/api/transactions` 호출 → Vite 가 `http://localhost:8000/transactions` 로 프록시. CORS 신경 안 씀.

### 6.2 Mock Service Worker (MSW)

백엔드가 아직 준비 안 됐을 때, 가짜 응답으로 프론트 개발 진행.

```ts
import { rest, setupWorker } from 'msw';

const worker = setupWorker(
  rest.get('/api/transactions', (req, res, ctx) => {
    return res(ctx.json([{ id: 1, amount: 4500, merchant: '스타벅스' }]));
  }),
);

worker.start();
```

API 가 완성되기 전에 화면 작업을 끝낼 수 있음.

### 6.3 OpenAPI 클라이언트 자동 생성

레슨 11 에서 OpenAPI 명세를 만들어 두면 클라이언트 코드를 자동 생성 가능.

```bash
npx openapi-typescript-codegen --input openapi.yaml --output src/api/generated
```

타입 안전 클라이언트가 자동으로 만들어집니다.

## 7. 자주 빠지는 함정

### 함정 1. CORS 를 프론트에서 풀려 한다

CORS 는 **서버**가 푸는 문제. 프론트에서는 풀 수 없습니다. 백엔드 미들웨어로.

### 함정 2. base URL 을 코드에 박는다

```ts
// 나쁨
const API = 'http://localhost:8000';
```

운영에 올리면 깨짐. 환경 변수 사용.

### 함정 3. 모든 컴포넌트에서 직접 fetch

흩어진 fetch 호출은 디버깅이 어려움. **API 클라이언트 한 곳**으로.

### 함정 4. 토큰을 코드에 노출

GitHub 에 시크릿이 올라가는 사고. 환경 변수 + `.gitignore`.

### 함정 5. 에러 처리 안 함

성공 케이스만 그린 화면. 네트워크 끊김·5xx 에러에서 사용자가 어떻게 해야 할지 모름. **항상 3상태 처리**.

### 함정 6. 무한 재시도

401 → refresh → 또 401 → refresh ... 무한 루프. 재시도 횟수 제한·인터셉터에서 재진입 막기.

### 함정 7. 토큰 만료 처리 빼먹음

Access Token 이 만료되면 모든 요청이 401. 자동 갱신 또는 로그인 화면으로.

### 함정 8. 프록시·CORS 를 둘 다 동시에

dev proxy 를 쓰면 CORS 가 안 보이지만, 운영에 올리면 진짜 CORS 가 등장. **둘 다 미리 점검**.

### 함정 9. 응답 형식이 환경마다 다름

로컬은 `{data: [...]}` 이고 운영은 `[...]` 인 식. 백엔드의 응답 형식을 한 가지로 통일.

### 함정 10. 캐시를 신경 안 씀

같은 데이터를 매번 새로 호출. TanStack Query 의 `staleTime` 으로 적절히 캐시.

## 8. 한 셜 더

### 8.1 SSE (Server-Sent Events) — 서버 → 클라이언트 스트림

진행률 표시·실시간 알림·AI 응답 스트리밍에 자주 쓰임.

```ts
const eventSource = new EventSource('/api/notifications');
eventSource.onmessage = (event) => {
  const data = JSON.parse(event.data);
  // 처리
};
```

### 8.2 WebSocket — 양방향 실시간

채팅·실시간 협업에 필수. Socket.IO 같은 라이브러리가 일반.

### 8.3 GraphQL 클라이언트

GraphQL 을 쓴다면 Apollo Client·urql·Relay 같은 클라이언트.

### 8.4 BFF (Backend for Frontend)

프론트가 여러 백엔드 마이크로서비스를 호출해야 할 때, 그 사이에 BFF 를 두어 한 번만 호출. Next.js 의 API Routes 가 BFF 역할 가능.

### 8.5 추가 키워드

- **Optimistic Update** — 응답 오기 전에 화면을 미리 업데이트.
- **Suspense** — React 의 비동기 처리 패턴.
- **Streaming SSR** — 서버가 응답을 점진적으로 보냄.
- **Service Worker** — 브라우저에서 네트워크 가로채기.
- **CDN** — 정적 자산 글로벌 캐싱.
