# 10. 데이터 설계 (테이블·ERD)

> **한 줄 요약.** 데이터 설계는 한 번 굳으면 풀기 어렵다. **첫 ERD에서 테이블 분리를 잘 잡는 것**이 운영 6개월 뒤의 마이그레이션 며칠을 살린다.

---

## 들어가며

화면과 시나리오까지 손에 들어왔다면, 이제 그 화면들 뒤에서 **데이터가 어떤 모양으로 저장될지**를 결정할 차례입니다. 사용자에게 보이지 않는 영역이지만, 이 결정은 향후 운영의 안정성·성능·보안을 모두 좌우합니다.

레슨 02의 사례 2를 떠올려 보세요. 처음에 사용자 테이블 하나에 모든 정보를 몰아넣었던 사례. 6개월 뒤 큰 마이그레이션으로 며칠을 통째로 잃은 그 사례입니다. 이런 일은 데이터 설계의 첫 단추가 잘못 끼워졌을 때 거의 예외 없이 일어납니다.

이 레슨은 화면과 시나리오에서 결정된 정보들을 **테이블의 형태로 옮기는** 작업입니다. 거창한 데이터베이스 이론을 다 익힐 필요는 없습니다. 다만 **테이블 분리·관계 설정·키 결정** 의 세 가지만 잘 잡으면 출시 후 한참 동안 큰 사고 없이 굴러갑니다.

이 레슨을 다 읽으면:

- 테이블·열·행의 관계를 명확히 이해한다.
- 화면에서 데이터 모델을 추출하는 4단계 절차를 안다.
- ERD의 1:1·1:N·N:M 관계를 표현할 수 있다.
- 정규화의 1·2·3 단계를 경량 버전으로 적용할 수 있다.
- 자주 빠지는 함정(JSON 컬럼 남발·NULL 처리·시간대) 을 안다.

## 1. 핵심 개념 — 테이블·행·열·키

### 1.1 테이블·행·열

데이터베이스의 가장 작은 단위는 **테이블** 입니다. 엑셀 한 시트와 같습니다.

| 요소 | 비유 | 무엇 |
|---|---|---|
| **테이블 (table)** | 엑셀 시트 | 같은 종류의 데이터를 모은 집합. 예: `users`, `posts` |
| **행 (row)** | 엑셀 한 줄 | 한 개의 데이터. 예: 사용자 1명 |
| **열 (column)** | 엑셀 한 칸 (헤더) | 데이터의 속성. 예: 이름, 이메일 |

예시 — `users` 테이블:

| id | email | name | created_at |
|---|---|---|---|
| 1 | jiyoung@example.com | 김지영 | 2026-01-15 09:23 |
| 2 | husband@example.com | 이남편 | 2026-01-15 12:01 |
| 3 | friend@example.com | 박친구 | 2026-01-16 18:42 |

이 테이블은 3명의 사용자를 가지고 있고, 각 사용자에 대해 4개의 속성을 저장합니다.

### 1.2 키 (Key) — 행을 구별하는 단서

테이블의 각 행은 **유일하게 구별** 되어야 합니다. 그 구별의 단서가 **키(key)** 입니다.

| 키 종류 | 의미 |
|---|---|
| **기본 키 (Primary Key, PK)** | 한 행을 유일하게 식별. 보통 `id` |
| **외래 키 (Foreign Key, FK)** | 다른 테이블의 PK를 참조. 테이블 간 관계의 표시 |
| **유니크 키 (Unique Key)** | 중복 안 되는 값. PK는 아니지만 유일해야 함 (예: 이메일) |

예시:

- `users.id` 는 PK.
- `users.email` 은 유니크 키. 한 이메일에 두 사용자 가입 안 됨.
- `posts.user_id` 는 FK. `users.id` 를 참조해 "이 글을 누가 썼는가" 를 표현.

### 1.3 자료형

각 열은 **자료형(type)** 을 가집니다. 처음 자주 쓰는 것들:

| 자료형 | 무엇 | 예시 |
|---|---|---|
| `BIGINT` / `INTEGER` | 정수 | id, count |
| `VARCHAR(N)` / `TEXT` | 문자열 | 이름, 본문 |
| `BOOLEAN` | 참/거짓 | is_active |
| `DATE` / `TIMESTAMP` | 날짜·시간 | created_at |
| `DECIMAL(p,s)` | 정확한 소수 | 금액 |
| `JSON` / `JSONB` | JSON 문서 | 유연한 메타데이터 |

자료형은 처음 정한 것을 나중에 바꾸기 어렵습니다 (특히 데이터가 많이 쌓인 후). 처음에 신중히 결정.

## 2. 실무 흐름 — 화면에서 데이터 모델 추출 4단계

### 단계 1. 화면에서 명사 뽑아내기 (15분)

각 화면에서 등장하는 **명사**를 모두 뽑아 적습니다. 이 명사가 곧 테이블 후보입니다.

예시 — 부부 가계부 앱:

화면 1: "둘이 같이 보는 가계부 — 가입"
- 명사: **사용자**, 이메일, 이름

화면 2: "남편 초대"
- 명사: **사용자**, **초대**, 코드

화면 3: "정산 화면"
- 명사: **거래(transaction)**, **카드**, **카테고리**, 금액, 날짜

명사를 모두 모으면:

```
사용자 (user)
초대 (invitation)
거래 (transaction)
카드 (card)
카테고리 (category)
부부 그룹 (couple)  ← 두 사용자가 묶이는 단위
```

이 6개가 첫 테이블 후보입니다.

### 단계 2. 각 테이블의 속성 적기 (20분)

각 테이블에 어떤 열이 들어갈지 적습니다. 이 단계에서는 빠짐없이 다 적기.

예시:

**users**
- id (PK)
- email (unique)
- name
- created_at

**couples**  ← 두 사용자가 함께 가계를 본다는 관계 자체를 테이블로
- id (PK)
- name (예: "지영·남편")
- created_at

**couple_members**  ← couples ↔ users 의 N:M 관계 (한 사람이 두 그룹에 속할 수도 있음)
- id (PK)
- couple_id (FK → couples.id)
- user_id (FK → users.id)
- joined_at

**invitations**
- id (PK)
- couple_id (FK → couples.id)
- inviter_user_id (FK → users.id)
- code (unique)
- expires_at
- accepted_user_id (FK → users.id, nullable)

**cards**
- id (PK)
- user_id (FK → users.id)
- card_number_masked (앞 4자리 + 뒤 4자리만)
- nickname (예: "내 신한카드")
- created_at

**transactions**
- id (PK)
- card_id (FK → cards.id)
- amount (DECIMAL)
- merchant (가맹점)
- category_id (FK → categories.id, nullable)
- transacted_at (TIMESTAMP)
- created_at

**categories**
- id (PK)
- couple_id (FK → couples.id, nullable for global defaults)
- name (예: "식비", "교통")
- color
- created_at

### 단계 3. 관계 표시 (15분)

테이블 사이의 관계를 ERD(Entity Relationship Diagram) 로 그립니다. 관계는 세 가지뿐입니다.

| 관계 | 의미 | 예시 |
|---|---|---|
| **1:1** | 한 행이 다른 한 행에만 대응 | 사용자 ↔ 사용자 프로필 |
| **1:N** | 한 행이 여러 행에 대응 | 사용자 ↔ 글들 |
| **N:M** | 양쪽 모두 여러 | 사용자 ↔ 부부 그룹 (이론상) |

### ERD 예시 (텍스트로)

```
users (1) ─── (N) cards
users (1) ─── (N) transactions  (카드 거래자)
cards (1) ─── (N) transactions
couples (1) ─── (N) couple_members (N) ─── (1) users
couples (1) ─── (N) invitations
couples (1) ─── (N) categories
categories (1) ─── (N) transactions
```

(실제 ERD는 [Mermaid](https://mermaid.live), [dbdiagram.io](https://dbdiagram.io), Figma 같은 도구에서 시각적으로 그립니다.)

### 단계 4. 정합성·확장성 점검 (10분)

다음 질문에 모두 "예" 라고 답할 수 있는지 확인.

- 모든 테이블에 PK 가 있는가?
- 다른 테이블을 참조하는 모든 열이 FK 로 표현되었는가?
- 한 테이블의 속성이 너무 많지 않은가? (보통 10~15개 이상이면 분리 검토)
- 같은 정보가 두 테이블에 중복 저장되지 않는가?
- 출시 후 6개월 안에 추가될 만한 정보가 끼어들 자리가 있는가?

## 3. 정규화 — 가벼운 버전

데이터베이스 책에는 1정규형·2정규형·3정규형·BCNF 같은 단어가 등장하지만, 처음 만드는 분에게는 다음 3가지만 챙기면 충분합니다.

### 정규화 1. 한 칸에 한 값

한 셀에 콤마로 여러 값을 넣지 않습니다.

❌ 나쁜 예:

| user_id | hobbies |
|---|---|
| 1 | "독서, 영화, 운동" |

✅ 좋은 예 — 별도 테이블로:

| user_id | hobby |
|---|---|
| 1 | 독서 |
| 1 | 영화 |
| 1 | 운동 |

### 정규화 2. 같은 정보는 한 곳에만

같은 정보를 여러 테이블에 중복 저장하지 않습니다.

❌ 나쁜 예: `transactions` 테이블에 `user_name` 을 직접 저장. 사용자 이름이 바뀌면 모든 거래 행을 업데이트해야 함.

✅ 좋은 예: `transactions.user_id` 만 저장하고, 이름은 `users` 테이블에서 조회.

### 정규화 3. 한 테이블은 한 가지를 표현

한 테이블에 여러 종류의 정보를 섞지 않습니다.

❌ 나쁜 예: `users` 테이블에 개인 정보 + 결제 정보 + 활동 로그를 모두 저장.

✅ 좋은 예: `users`, `payment_methods`, `activity_logs` 로 분리.

## 4. 자주 결정해야 하는 것들

### 4.1 PK 를 무엇으로?

가장 흔한 두 선택지:

| 방식 | 장점 | 단점 |
|---|---|---|
| **자동 증가 정수 (`id BIGINT auto_increment`)** | 단순, 빠름 | 외부에 노출 시 추측 가능 ("/users/123" 다음에 124가 있겠지) |
| **UUID** | 추측 불가, 분산 시스템에 유리 | 조금 느림, 더 큼 |

처음에는 자동 증가 정수로 시작해도 됩니다. 외부 노출이 걱정된다면 UUID 또는 짧은 토큰(`nanoid`)을 따로 발급.

### 4.2 NULL 을 허용할 것인가?

각 열에 대해 "이 값이 없을 수도 있는가" 결정.

- 항상 있어야 하는 값 (예: `email`) → `NOT NULL`
- 있을 수도 없을 수도 (예: `accepted_user_id` 초대 수락 전엔 NULL) → 허용

NULL 이 너무 많은 열은 다른 테이블로 분리하는 게 깔끔할 때도 있습니다.

### 4.3 시간 정보 — 시간대 (Timezone)

시간 관련 데이터는 항상 골치입니다. 출시 후 사용자가 해외에 살거나, 서버가 다른 지역에 있을 때 시간 표시가 어긋납니다.

**원칙:**
- 데이터베이스에는 항상 **UTC** 로 저장.
- 사용자에게 보여줄 때만 해당 사용자의 시간대로 변환.
- 자료형은 `TIMESTAMP WITH TIME ZONE` (Postgres) 또는 `TIMESTAMP` (MySQL, UTC 기준).

### 4.4 삭제 vs 비활성화 (Soft Delete)

사용자가 게시글을 "삭제" 했을 때 행을 진짜 지울지, 아니면 `deleted_at` 만 표시할지.

| 방식 | 장점 | 단점 |
|---|---|---|
| **하드 삭제** | 깔끔, 용량 적음 | 복구 불가 |
| **소프트 삭제 (`deleted_at`)** | 복구 가능, 통계용 | 모든 쿼리에 `WHERE deleted_at IS NULL` 추가 |

처음에는 사용자 데이터는 소프트 삭제, 로그성 데이터는 하드 삭제가 무난합니다.

### 4.5 JSON 컬럼 — 언제 쓸까

`JSONB` (Postgres) 같은 자료형은 유연한 메타데이터 저장에 편리합니다. 하지만 **남발하면 결국 후회**합니다.

**JSON 컬럼이 적합한 경우:**
- 스키마가 자주 바뀌는 메타데이터.
- 검색이 필요 없는 부가 정보 (예: UI 설정 저장).

**JSON 컬럼을 피해야 할 경우:**
- 자주 검색·필터링되는 정보.
- 핵심 비즈니스 데이터.

## 5. 자주 빠지는 함정

### 함정 1. 테이블 하나에 다 몰아넣기

레슨 02의 사례. `users` 테이블에 모든 정보를 다 넣으면 6개월 뒤 통째로 풀어야 합니다. **분리할 만한 것은 처음부터 분리** 하세요.

### 함정 2. FK 를 안 쓴다

테이블 사이 관계를 코드에서만 관리하고 데이터베이스 차원의 FK 제약을 안 거는 경우. 결과: 고아 데이터가 쌓임. 사용자가 삭제됐는데 그 사용자의 거래 데이터가 남는 식.

### 함정 3. 인덱스 없는 검색 컬럼

자주 검색되는 컬럼에 **인덱스(index)** 가 없으면 데이터가 쌓일수록 느려집니다. PK 와 FK 는 보통 자동으로 인덱스가 만들어지지만, 그 외 검색용 컬럼(예: `email`, `created_at`) 에는 명시적으로 추가.

### 함정 4. 시간대 무시

`TIMESTAMP` 만 쓰고 시간대 처리를 미루면 사용자에게 "오전 9시 게시글" 이 "오후 3시" 로 보이는 사고가 납니다. **출시 전에** 시간대 정책을 정하세요.

### 함정 5. 비밀번호를 평문 저장

회원 비밀번호를 그대로 저장하는 사고. 절대 하지 마세요. 항상 **해시** (bcrypt, argon2) 로 저장. 자세한 내용은 레슨 17(인증)에서.

### 함정 6. JSON 컬럼 남발

처음에는 편하지만, 검색·집계가 필요한 시점에 후회합니다. 핵심 데이터는 정상 컬럼으로.

### 함정 7. 마이그레이션 계획 없음

데이터 모델은 결국 변합니다. 변경을 어떻게 관리할지 처음부터 정해 두세요. 마이그레이션 도구(예: Flyway, Liquibase, Alembic, Knex, Prisma Migrate) 를 골라 두면 변경의 부담이 작아집니다.

## 6. 한 셜 더

### 6.1 NoSQL — RDB 가 아닌 선택

지금까지 다룬 것은 관계형 데이터베이스(RDB) 입니다. 다른 선택지로 NoSQL 이 있습니다.

| 종류 | 예시 | 적합한 상황 |
|---|---|---|
| **문서 DB** | MongoDB, DynamoDB | 스키마가 유연해야 할 때 |
| **Key-Value** | Redis | 빠른 캐시·세션 |
| **그래프 DB** | Neo4j | 관계가 매우 복잡할 때 |
| **시계열 DB** | InfluxDB, TimescaleDB | 로그·메트릭 |

처음 만드는 일반 서비스에는 **RDB(Postgres·MySQL)** 가 거의 항상 정답입니다. NoSQL 은 명확한 이유가 있을 때만.

### 6.2 인덱스의 종류

인덱스는 검색 속도를 빠르게 하지만, 쓰기 속도를 느리게 합니다. 종류:

- **B-Tree 인덱스** — 가장 흔한 형태. 범위 검색·정렬에 좋음.
- **Hash 인덱스** — 정확 일치 검색에 빠름.
- **Composite 인덱스** — 여러 컬럼을 묶은 인덱스. 자주 같이 쓰이는 컬럼.
- **부분 인덱스 (Partial Index)** — 조건을 만족하는 행만 인덱싱.

처음에는 PK + 자주 검색하는 컬럼에 B-Tree 만 충분합니다. 운영 중 느려지는 쿼리가 발견되면 그때 인덱스 추가.

| 도구 | 무엇 |
|---|---|
| **dbdiagram.io** | 텍스트로 ERD 그리기 무료 |
| **DBeaver** | 데이터베이스 클라이언트, ERD 자동 생성 |
| **draw.io / Excalidraw** | 가벼운 다이어그램 |
| **Mermaid** | 마크다운에 ERD 코드로 임베드 |
| **Figma + 플러그인** | 디자인 도구 안에서 |

### 6.4 추가 키워드

- **ACID / BASE** — 트랜잭션의 두 모델. RDB 는 ACID, NoSQL 은 BASE.
- **Sharding** — 한 테이블을 여러 서버로 분할. 대규모 서비스의 영역.
- **Read Replica** — 읽기 전용 복제본. 읽기 부하 분산.
- **CAP Theorem** — Consistency, Availability, Partition tolerance 의 트레이드오프.
- **Migration** — 스키마 변경 관리.
