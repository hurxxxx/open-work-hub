# 27. 장애 대응과 모니터링

> **한 줄 요약.** 장애는 일어난다. 좋은 운영은 **장애를 안 일으키는 것이 아니라 빨리 알아채고 빨리 복구하는 것**이다. 모니터링·알람·런북 — 이 셋이 그 능력을 만든다.

---

## 들어가며

운영을 하다 보면 어느 날 새벽 3시에 알림이 옵니다. "API 응답 시간이 5초를 넘었습니다." 부랴부랴 노트북을 열고, 어디서부터 봐야 할지 막막합니다. 로그는 어디에 있는지, 무엇이 정상이고 무엇이 비정상인지 분간이 안 됩니다.

이 풍경은 모니터링·관찰성을 미리 갖추지 않은 팀의 풍경입니다. 갖춘 팀의 풍경은 다릅니다. 알림이 어떤 메트릭에서 왔는지·연관 로그가 어디에 있는지·비슷한 사고의 과거 회고는 무엇인지 — 모두 한 화면에서 보입니다.

이 레슨은 그 차이를 만드는 도구·절차를 정리합니다. 처음 만드는 분이 출시 직후부터 갖출 수 있는 **현실적 최소 세트**.

이 레슨을 다 읽으면:

- 모니터링의 4가지 축(메트릭·로그·트레이스·알람)을 안다.
- 처음 도입할 도구를 결정할 수 있다.
- 알람의 신호 대 노이즈 비율을 관리할 수 있다.
- 장애 대응의 단계별 절차를 안다.
- 사후 회고(Post-mortem)의 표준 형식을 안다.

---

## 1. 핵심 개념 — 관찰성의 3대 기둥

### 1.1 메트릭 (Metrics)

수치 시계열 데이터. CPU 사용률·요청 수·응답 시간·에러율 같은 것.

```
api.requests.count = 1234 (분당)
api.response_time.p95 = 350ms
db.connections.active = 12
```

특징: 가볍고 빠름. 시간에 따른 추이·이상치 탐지에 적합.

### 1.2 로그 (Logs)

이벤트의 텍스트 기록. "사용자 X 가 Y 를 했다" 같은 문장.

```json
{
  "timestamp": "2026-04-25T14:32:00Z",
  "level": "ERROR",
  "service": "api",
  "request_id": "abc-123",
  "user_id": 456,
  "message": "Failed to charge card",
  "error": "Card declined"
}
```

특징: 풍부한 정보. 특정 사용자·요청의 흐름 추적에 적합.

### 1.3 트레이스 (Traces)

한 요청이 여러 서비스를 거치는 흐름. 각 단계의 시간·결과.

```
[GET /transactions]              420ms
├─ auth.verify_token             5ms
├─ db.query_transactions         180ms ⚠ 오래
└─ db.query_categories           20ms
```

특징: 분산 시스템의 디버깅. 어느 단계가 느린지 즉시 보임.

### 1.4 알람 (Alerts)

위 셋을 기반으로 사람을 깨우는 신호.

```
"API p95 > 1초가 5분간 지속" → Slack 알림
"에러율 > 1%가 3분간 지속" → PagerDuty 호출
```

알람의 품질 = 운영 품질.

## 2. 처음 도입할 도구

### 2.1 무료 / 저비용 시작

| 영역 | 도구 | 무료 한도 |
|---|---|---|
| **에러 추적** | **Sentry** | 5K 이벤트/월 |
| **로그 + 메트릭** | **Better Stack** (Logtail+Better Uptime) | 1GB/월 |
| **APM·트레이스** | **DataDog**·**New Relic** 무료 티어 | 제한적 |
| **간단한 메트릭** | **Grafana Cloud** | 10K 시리즈 |
| **업타임 모니터링** | **UptimeRobot**·**Better Uptime** | 무료 50 모니터 |

### 2.2 처음 출시 권장 스택

작은 팀·MVP 에 권장:

- **에러 추적: Sentry** — 처음 5K 이벤트 무료.
- **업타임: UptimeRobot** — 5분 간격 핑.
- **로그·메트릭: PaaS 내장 + Better Stack** — 부족한 부분만 외부.
- **알람: Sentry → Slack 채널**.

이 정도로 시작에 충분.

### 2.3 본격 모니터링 — 옵션

성장 단계에서 검토:

- **DataDog** — 가장 풍부, 가장 비쌈.
- **New Relic** — APM 강함.
- **Grafana + Prometheus + Loki** — 오픈소스 셀프 호스팅.
- **Honeycomb** — 분산 트레이스 특화.

## 3. 메트릭 — 무엇을 볼까

### 3.1 RED 메트릭 — 서비스 핵심 3 지표

| 약자 | 무엇 |
|---|---|
| **R**ate | 초당 요청 수 |
| **E**rrors | 실패한 요청 수 / 비율 |
| **D**uration | 응답 시간 (p50·p95·p99) |

이 3개가 핵심. 어느 하나라도 비정상이면 즉시 조사.

### 3.2 USE 메트릭 — 자원 3 지표

| 약자 | 무엇 |
|---|---|
| **U**tilization | 자원이 얼마나 사용 중 (CPU 사용률) |
| **S**aturation | 처리 못 하고 쌓인 양 (큐 길이) |
| **E**rrors | 자원의 에러 (디스크 I/O 실패) |

서버·DB·큐 같은 인프라의 건강.

### 3.3 비즈니스 메트릭

기술 메트릭 외에 비즈니스 핵심 지표.

- 분당 가입 수
- 분당 결제 수
- 동시 접속자 수
- 핵심 기능 사용 횟수

이런 지표가 갑자기 0 이 되면 사고 신호 (로그인 깨짐 등).

### 3.4 대시보드

핵심 메트릭을 한 화면에. 매일 아침 1분만 봐도 큰 신호 잡힘.

권장 대시보드 구성:
- 위: RED 메트릭 (현재 + 최근 1시간 추이).
- 중: 비즈니스 핵심 지표.
- 하: 인프라 USE.

## 4. 로그 — 좋은 로그의 조건

### 4.1 구조화 로그 (JSON)

평문 대신 JSON 으로. 검색·필터링·집계가 쉬워집니다.

```json
{
  "timestamp": "2026-04-25T14:32:00Z",
  "level": "INFO",
  "service": "api",
  "request_id": "req-abc-123",
  "user_id": 456,
  "endpoint": "/transactions",
  "method": "POST",
  "status": 201,
  "duration_ms": 145
}
```

### 4.2 Request ID — 흐름 추적의 핵심

한 요청이 여러 서비스·로그를 거칠 때, 같은 ID 로 묶어 보기. 진입점에서 ID 발급, 모든 로그·다른 서비스 호출에 전달.

```
프론트 → request_id: req-abc-123
   ↓
API 게이트웨이 → req-abc-123
   ↓
백엔드 서비스 → req-abc-123
   ↓
DB 쿼리 → req-abc-123
```

이 ID 로 검색하면 한 사용자의 한 요청이 모든 시스템을 어떻게 흘렀는지 한눈에.

### 4.3 로그 레벨

| 레벨 | 언제 |
|---|---|
| **DEBUG** | 개발 시 디버깅용 |
| **INFO** | 정상 동작 (가입·로그인 등) |
| **WARN** | 비정상이지만 동작 가능 (재시도 후 성공) |
| **ERROR** | 실패한 작업 |
| **FATAL/CRITICAL** | 프로세스 종료 수준 |

운영에서는 보통 **INFO 이상**만 기록. DEBUG 는 개발 환경에만.

### 4.4 무엇을 로그에 남기지 말아야

- **비밀번호·토큰** — 절대 평문.
- **신용카드 번호** — 마스킹 (뒤 4자리만).
- **개인정보** — 이름·전화번호·이메일.
- **API 키·시크릿** — 절대.

실수로 로그에 들어가면 즉시 회수·키 회전.

## 5. 알람 — 신호 대 노이즈

### 5.1 좋은 알람의 조건

- **사람이 행동해야 함** — 알람이 오면 무엇을 할지 분명.
- **신호가 분명함** — 노이즈 없음.
- **빠른 도착** — 사고 후 1분 이내.
- **컨텍스트 풍부** — 어디서·언제·무엇이.

### 5.2 알람 피로 (Alert Fatigue)

알람이 너무 많거나 노이즈가 많으면 사람이 무시하기 시작. 진짜 사고를 놓침.

해결:
- **임계값 정확히** — 너무 민감하지 않게.
- **합치기 (Grouping)** — 같은 사고의 알람 한 번만.
- **정기 정리** — 무시되는 알람 삭제·조정.

### 5.3 알람 채널

| 우선순위 | 채널 | 언제 |
|---|---|---|
| **즉시 깨움** | PagerDuty·Opsgenie·전화 | SEV1 |
| **빠른 알림** | Slack·Discord 채널 | SEV2 |
| **참고** | 이메일·대시보드 | 추세 |

처음에는 Slack 채널 하나만 있어도 충분.

### 5.4 알람 예시

**API 에러율:**
```
조건: 5분간 에러율 > 1%
대응: Sentry 확인 + 최근 배포 확인
```

**응답 시간:**
```
조건: 5분간 p95 > 2초
대응: DB 슬로우 쿼리 확인 + 외부 의존 확인
```

**사용자 영향:**
```
조건: 분당 가입 수가 평소의 10% 미만
대응: 가입 흐름 직접 시도해 보기
```

## 6. 장애 대응 절차

장애가 일어났을 때의 표준 절차.

### 6.1 단계 1. 인지 (Detection)

알람 수신 또는 사용자 신고.

- "정말 사고인가" — 알람의 진위 확인.
- 영향 범위 가늠 — 일부 사용자? 전체?

### 6.2 단계 2. 알림 (Notification)

팀 내 공유. 작은 팀이라도 다음 채널.

- Slack 사고 채널 — 한 곳에 정보 모음.
- 상태 페이지 (statuspage.io 등) — 사용자에게 공지.

### 6.3 단계 3. 진단 (Diagnosis)

원인 추적.

- 최근 배포 확인 — 가장 흔한 원인.
- 메트릭 대시보드.
- 로그 (request_id 또는 시간 범위).
- 외부 의존 (PaaS·DB·외부 API) 상태.

### 6.4 단계 4. 완화 (Mitigation)

빠른 복구. 근본 원인 수정은 나중.

- 롤백 (이전 버전 재배포).
- 트래픽 차단 (rate limit).
- 기능 토글 OFF.
- 인프라 확장 (수평 확장).

**완화가 우선, 근본 수정은 나중.** 사용자 영향 최소화.

### 6.5 단계 5. 복구 (Recovery)

서비스 정상화 확인.

- 메트릭이 정상 범위로.
- 사용자 신고 멎음.
- 상태 페이지 업데이트.

### 6.6 단계 6. 회고 (Post-mortem)

24~48 시간 안에 회고 문서. 비난 없이.

```markdown
## YYYY-MM-DD: API 응답 시간 폭증 사고

### 영향
- 14:32 ~ 15:18 (46분간)
- 사용자 약 5,200명 (전체 트래픽의 23%)

### Timeline
- 14:32 — 알람 수신 (p95 > 2초)
- 14:35 — 엔지니어 인지, 사고 채널 공지
- 14:42 — DB 슬로우 쿼리 발견
- 14:55 — 인덱스 추가 마이그레이션 결정
- 15:10 — 인덱스 적용
- 15:18 — 정상 복귀

### 근본 원인
새 기능 (월별 거래 검색) 이 user_id + transacted_at 인덱스 없이 배포됨.
사용자 데이터가 누적되며 쿼리가 느려져 임계 도달.

### 잘한 점
- 알람이 5분 내 동작.
- 빠른 진단 (10분).

### 개선 점
- PR 리뷰에서 인덱스 검토 누락.
- staging 의 데이터 양이 운영과 너무 달라 사전 발견 못 함.

### 액션 아이템
- [ ] PR 리뷰 체크리스트에 "인덱스 검토" 추가
- [ ] staging 에 운영의 5% 데이터 자동 동기화
- [ ] 새 기능 출시 후 성능 메트릭 모니터링 강화
```

## 7. 자주 빠지는 함정

### 함정 1. 모니터링을 출시 후에 시작

출시 첫날의 사고가 가장 위험. **출시 전에** Sentry·기본 알람 설정.

### 함정 2. 알람이 너무 많음

매일 50개 알람 → 사람이 무시. 정기 정리.

### 함정 3. 알람이 하나도 없음

사고를 사용자가 먼저 발견. 사용자보다 먼저 알아야.

### 함정 4. 로그가 평문

검색·집계 어려움. **JSON 구조화 로그**.

### 함정 5. 시크릿 로그 노출

비밀번호·카드 번호 로그에 박힘. 마스킹·필터링.

### 함정 6. 사고 시 패닉 → 무엇이든 시도

명확한 절차 없이 여러 변경 동시에 시도 → 더 큰 사고. **롤백 우선**.

### 함정 7. 회고 안 함

같은 사고 재발. 짧아도 회고 필수.

### 함정 8. "비난" 회고

사람을 공격하는 회고는 정직한 보고를 막음. 항상 시스템·절차 관점.

### 함정 9. 외부 상태 공지 안 함

사용자가 우리 서비스 상태를 모름. 상태 페이지·SNS 공지.

### 함정 10. 운영 중 새 기능 배포

장애 도중 다른 변경을 같이 적용. 원인 파악 어려움. **사고 시 freeze**.

## 8. 한 셜 더

### 8.1 OpenTelemetry

벤더 중립 관찰성 표준. 같은 코드로 어떤 도구든 데이터 보낼 수 있음.

```python
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

with tracer.start_as_current_span("create_transaction") as span:
    span.set_attribute("user_id", user.id)
    # ...
```

### 8.2 SLO 와 Error Budget

99.9% 가용성 목표 → 월 43분의 다운타임 허용.
- Error Budget 다 쓰면 새 기능 출시 freeze, 안정화에 집중.
- 다 안 쓰면 더 공격적 출시 가능.

### 8.3 Chaos Engineering

의도적으로 시스템에 장애 주입해 회복력 검증. Netflix 의 Chaos Monkey 가 시작. 안정 단계에서.

### 8.4 On-call Rotation

24/7 운영을 위해 팀원들이 돌아가며 대기. 1주 단위가 흔함.

처음 1인 팀이라면 본인이 24/7. 휴가·부재 시 대안 마련.

### 8.5 추가 키워드

- **Synthetic Monitoring** — 가짜 사용자 시나리오로 정기 점검.
- **Real User Monitoring (RUM)** — 실제 사용자 측정.
- **Distributed Tracing** — Jaeger·Zipkin·Tempo.
- **APM (Application Performance Monitoring)** — DataDog·New Relic·Dynatrace.
- **SLI / SLO / SLA** — 측정·목표·약속의 세 단계.

## 마치며

오늘 한 일:

- 관찰성의 **3대 기둥** (메트릭·로그·트레이스) + 알람.
- 처음 출시에 권장하는 **저비용 모니터링 스택** (Sentry + UptimeRobot).
- **RED·USE 메트릭** + 비즈니스 메트릭.
- **구조화 로그·Request ID** 의 가치.
- 알람 피로 관리 + 채널 우선순위.
