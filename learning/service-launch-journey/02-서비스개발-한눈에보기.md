# 02. 서비스 개발 한눈에 보기

> **한 줄 요약.** 본격 여정에 들어가기 전, 9단계 전체 윤곽을 한 편으로 미리 둘러본다. 단계의 이름·순서·서로 어떻게 이어지는지를 먼저 잡아 두면 이후 레슨이 훨씬 잘 들어온다.

---

## 들어가며

지도를 펼쳐 본 적 있으시죠. 어느 도시에 처음 가더라도 지도를 5분만 들여다보면, 막상 골목에 들어갔을 때 방향 감각이 다릅니다. 지도를 안 보고 출발하면 한 골목 한 골목이 미로처럼 느껴지지만, 한 번 윤곽을 잡고 나면 같은 골목도 "아, 여기가 그 골목이구나" 하는 식으로 보입니다.

서비스 개발도 똑같습니다. 본격 단계에 들어가기 전에 **9단계 전체 윤곽**을 한 번 잡아 두면, 나중에 한 단계를 깊이 다룰 때 "이게 어디쯤이고, 앞뒤로 무엇이 붙어 있는지" 가 자연스럽게 떠오릅니다.

이 레슨은 코스 전체의 **요약본 1편** 입니다. 깊이는 의도적으로 얕게 갑니다. 대신 **단계 사이의 흐름**과 **한 단계의 결정이 다른 단계에 어떻게 도착하는지** 의 사슬을 미리 깔아 둡니다. 이 흐름 감각이 다음 26개 레슨을 읽는 데 가장 큰 도움이 됩니다.

---

## 1. 9단계 윤곽 — 한 줄씩 미리 보기

서비스 하나를 처음부터 끝까지 끌고 가는 일은 다음 9단계로 펼쳐집니다. 단계마다 **무엇을 정하는가**, **무엇을 산출물로 남기는가**, **다음 단계에 무엇을 넘기는가** 만 한 줄로 잡아 봅니다.

| # | 단계 | 무엇을 정하나 | 다음 단계로 넘기는 것 |
|---:|---|---|---|
| 1 | **기획** | 누구에게, 어떤 문제를, 어떤 최소 기능으로 풀지 | 기능 목록, 페르소나, MVP 정의 |
| 2 | **설계** | 화면·데이터·API·디자인의 구체적 모양 | 화면 정의서, ERD, API 스펙, 디자인 시안 |
| 3 | **개발** | 프론트·백·DB의 실제 구현 | 동작하는 소스 코드 |
| 4 | **테스트** | 무엇을 검증하고 무엇을 보장할지 | 테스트 통과 결과, 발견된 결함 목록 |
| 5 | **빌드·소스 관리** | 산출물 형태와 코드 관리 전략 | 배포 가능한 빌드 파일, 깔끔한 브랜치 이력 |
| 6 | **배포** | 어디에·어떻게 띄울지 | 서버에 올라간 실행 환경, 도메인·HTTPS |
| 7 | **출시** | 사용자에게 어떻게 도달할지 | 앱 스토어 등록, 공개 URL |
| 8 | **운영·유지보수** | 살아 있는 서비스를 어떻게 굴릴지 | 안정성·개선 사이클 |
| 9 | **수익화** | 어떻게 돈이 들어오게 할지 | 매출 모델, 결제 구조 |

표가 가로로 길어 보이지만, 핵심은 **세 번째 컬럼**입니다. 각 단계는 다음 단계에 **무언가를 넘기기 위해** 존재합니다. 그 "무언가" 가 부실하면 다음 단계가 절뚝거립니다.

### 1.1 단계 순서가 이렇게 짜인 이유

순서가 단순한 우연은 아닙니다. 각 단계는 **앞 단계의 산출물 없이는 시작하기 어려운** 의존 관계로 묶여 있습니다.

- 설계는 기획의 **기능 목록과 페르소나**가 있어야 시작됩니다. 누구를 위해 무엇을 만드는지 모르면 화면을 그릴 수 없습니다.
- 개발은 설계의 **화면·데이터·API**가 있어야 본격적인 코드를 칠 수 있습니다.
- 테스트는 개발의 **동작하는 코드**가 있어야 검증할 대상이 생깁니다.
- 배포는 빌드의 **실행 가능한 산출물**이 있어야 서버에 올릴 것이 있습니다.
- 운영은 출시의 **사용자에게 도달한 서비스**가 있어야 운영할 대상이 됩니다.

다만 현실에서는 단계가 칼같이 한 방향으로만 흐르지 않습니다. 개발 도중에 설계가 바뀌고, 테스트 중에 기획이 흔들리는 일이 잦습니다. 그렇더라도 **순서의 의도는 유지하는 것이 좋습니다**. 뒤집어서 진행하면 비용이 기하급수적으로 늘어납니다.

## 2. 단계별 한 단락 둘러보기

각 단계가 무엇을 다루는지를 한 단락 분량으로 미리 살펴봅니다. 깊이 있는 다룸은 해당 Part에서 합니다.

### 2.1 기획 — 만들 것을 정한다

기획은 **"무엇을 만들지" 를 정하는 단계**입니다. 거창하게 들리지만 시작은 단순합니다. 어느 날 떠오른 아이디어 하나, 평소에 불편했던 일 하나가 출발점입니다. 거기서부터 누가 이 서비스를 쓸 사람인지(페르소나), 그 사람의 어떤 문제를 푸는지, 그 문제를 풀려면 최소한 어떤 기능이 필요한지(MVP)를 차례로 좁혀 갑니다.

기획에서 가장 자주 빠지는 함정은 **욕심**입니다. 아이디어 단계에서는 머릿속에 기능이 50개씩 떠오릅니다. 하지만 처음 출시할 서비스에 그 50개를 다 넣으면 어느 것도 제대로 안 됩니다. **MVP는 기능을 더하는 작업이 아니라 빼는 작업**입니다. 카카오톡의 첫 버전이 채팅 하나였고, 당근마켓의 첫 버전이 동네 거래 하나였던 것이 그래서입니다.

이 단계의 산출물은 화려할 필요 없습니다. 노트 한 장에 그린 그림, 한 줄로 적은 페르소나, 5개 안쪽의 핵심 기능 목록 — 이 정도면 다음 단계로 넘어가기에 충분합니다.

### 2.2 설계 — 그림을 그린다

설계는 기획의 단어들을 **눈에 보이는 형태**로 바꾸는 단계입니다. 네 가지 그림을 그립니다.

| 설계 종류 | 무엇을 그리나 |
|---|---|
| **화면 설계** | 사용자가 보게 될 화면의 흐름과 각 화면의 구성 |
| **UX 시나리오** | 일반 사용자·어드민·비로그인 사용자가 각각 어떻게 서비스를 이용할지의 줄거리 |
| **데이터 설계 (ERD)** | 어떤 데이터를 어떤 테이블에 저장하고, 테이블 사이의 관계는 어떻게 잡을지 |
| **API 설계** | 프론트와 백엔드가 주고받을 인터페이스의 모양 |

설계는 코드를 한 줄도 짜지 않은 채 **모든 결정을 미리 내리는** 단계입니다. 이 단계에서 흐릿하게 지나간 결정은 모두 개발 단계에서 비싸게 청구됩니다.

설계의 또 한 축은 **디자인**입니다. 색·타이포·컴포넌트 시스템을 잡고, 디자이너와 협업해 비주얼 시안을 만듭니다. 작은 팀에서는 디자이너 없이 개발자가 겸업하기도 하지만, 그래도 **어떤 룩앤필을 추구할지** 는 명시적으로 결정해 두는 것이 좋습니다.

### 2.3 개발 — 코드를 짠다

개발은 설계서를 **실제로 동작하는 코드**로 옮기는 단계입니다. 크게 세 영역으로 나뉩니다.

- **프론트엔드** — 사용자가 직접 보고 만지는 화면. 웹은 HTML·CSS·JavaScript로, 앱은 안드로이드·iOS의 각 언어 또는 React Native·Flutter 같은 크로스 플랫폼 프레임워크로 만듭니다.
- **백엔드** — 화면 뒤에서 돌아가는 API 서버. 회원·상품·결제 같은 데이터를 처리하고, 비즈니스 로직을 담습니다.
- **데이터베이스** — 데이터가 영구적으로 저장되는 곳. MySQL·PostgreSQL 같은 관계형 DB, MongoDB 같은 문서형 DB 중에서 골라 씁니다.

이 셋은 따로 만들어지지만, 결국 **연동되어 한 서비스로 합쳐져야** 합니다. 프론트가 백엔드 API를 호출하고, 백엔드가 DB에 데이터를 쓰고 읽는 흐름이 막힘없이 흐를 때 비로소 "동작하는" 서비스가 됩니다.

개발 단계에는 **회원가입·로그인·소셜 인증** 같은 공통 기능 구현, 그리고 **모바일 대응**(반응형 웹·네이티브 앱) 같은 결정도 포함됩니다.

### 2.4 테스트 — 검증한다

"동작함" 과 "맞음" 은 다른 이야기입니다. 테스트는 그 둘 사이의 간격을 좁히는 단계입니다. 테스트의 종류는 다양하지만, 처음에는 다음 두 가지만 잡아도 큰 진전입니다.

- **단위 테스트** — 함수 하나·모듈 하나가 기대한 대로 동작하는지 검증.
- **통합 테스트** — 여러 모듈을 함께 돌렸을 때 시나리오대로 흐르는지 검증.

여기에 더해 **성능 테스트**(부하를 주었을 때 견디는지), **보안 테스트**(악의적 입력에 뚫리는지), **설치/회귀 테스트**(새 기능이 기존 기능을 망가뜨리지 않는지) 가 단계가 진행되며 추가됩니다.

테스트는 "넣을까 말까" 의 영역이 아닙니다. 사용자가 늘수록, 코드가 커질수록 **테스트 없이는 변경이 불가능해지는 임계점**이 옵니다. 시작 단계부터 작게라도 들여놓는 것이 결국 가장 빠른 길입니다.

### 2.5 빌드·소스 관리 — 산출물과 이력

개발이 끝났다고 바로 서버에 올릴 수는 없습니다. 코드는 **빌드(build)** 라는 변환 과정을 거쳐 실행 가능한 형태가 됩니다. 자바라면 jar 파일, React라면 번들된 정적 파일, Node.js라면 그대로의 소스가 산출물이 됩니다.

같은 단계의 다른 축은 **소스 관리**입니다. 거의 모든 팀이 **Git** 을 씁니다. 그 안에서 특히 중요한 것이 **브랜치 전략**입니다. 개발용 브랜치(`develop`)와 운영용 브랜치(`main`)를 분리하고, 기능마다 별도 브랜치(`feature/...`)에서 작업한 뒤 검토를 거쳐 합치는 방식이 일반적입니다.

브랜치 전략은 단순한 절차가 아니라 **출시 속도와 안정성을 동시에 결정하는 장치**입니다. main 한 줄로만 굴리는 팀과 잘 분리한 팀의 출시 사고 빈도는 차원이 다릅니다.

### 2.6 배포 — 세상으로 보낸다

배포는 빌드된 산출물을 **서버에 올려 실행 가능한 상태로 만드는** 작업입니다. 어디에 올릴지부터 결정해야 합니다.

| 선택지 | 적합한 상황 |
|---|---|
| **클라우드 (AWS·Azure·GCP)** | 사용자 규모가 클 가능성, 다양한 서비스 조합 필요, 인프라 자유도 중요 |
| **PaaS/Serverless (Vercel·Cloudflare·Netlify)** | 단순한 웹 서비스, 빠른 시작, 인프라 학습 부담 줄이기 |

배포에 따라오는 것들이 줄줄이 있습니다.

- **도메인 구매와 연결** — IP 주소 대신 사람이 읽을 수 있는 주소(`example.com`)로 접근할 수 있게.
- **HTTPS / SSL 인증서** — 통신을 암호화. 요즘은 거의 필수.
- **환경 변수와 시크릿 관리** — DB 비밀번호, API 키 같은 민감 정보를 안전하게 보관.

이 모든 작업이 끝나야 비로소 **누구나 접근 가능한 서비스**가 됩니다.

### 2.7 출시 — 사용자에게 도달한다

웹 서비스라면 도메인 연결로 출시가 사실상 끝나지만, **모바일 앱**이라면 한 단계가 더 있습니다. 앱 스토어와 구글 플레이에 등록하고 **심사**를 받아야 합니다. 심사는 짧으면 하루, 길면 일주일 이상 걸리고, 정책 위반으로 리젝(거절)되는 경우도 흔합니다.

출시는 의외로 **한 번의 이벤트가 아닙니다**. 처음 출시 후에도 새로운 버전을 계속 올리며 같은 절차를 반복합니다. 그래서 출시 절차를 자동화해 두는 것이 장기적으로 큰 효율을 줍니다.

출시 시점의 또 다른 작업은 **마케팅·홍보**입니다. 이 코스에서는 깊이 다루지 않지만, "만들었다고 사람들이 자동으로 오는 것은 아니다" 라는 사실은 이 단계에서 가장 뼈저리게 느낍니다.

### 2.8 운영·유지보수 — 살아 있게 한다

흔히 출시를 골인 지점으로 여기지만, **출시는 시작점**입니다. 그 뒤로 본격적인 운영이 시작됩니다.

- **장애 대응** — 서버가 죽었을 때, DB가 느려졌을 때, 외부 API가 응답하지 않을 때 무엇을 어떻게 복구할지.
- **모니터링** — 무엇이 잘 돌고 있고 무엇이 위험한지를 항상 보이게 만드는 작업. 로그·메트릭·알람.
- **추가 기능 개발과 개선** — 사용자 피드백을 반영해 기능을 추가하거나 다듬기.
- **이슈 관리** — 발견된 버그·요청을 누락 없이 추적.

운영 단계에서 일어나는 모든 일은 결국 **앞 단계로 다시 흘러갑니다**. 발견된 버그는 개발로, 사용자 요청은 기획으로 돌아가 다음 사이클을 시작합니다. 한 서비스의 라이프사이클은 직선이 아니라 **순환**입니다.

### 2.9 수익화 — 돈의 흐름

수익화는 코스의 마지막 레슨이지만, 실제로는 **기획 단계부터** 고민해야 하는 주제입니다. 어떤 수익 모델을 선택하는지에 따라 서비스의 첫 화면, 가입 흐름, 데이터 수집 항목이 통째로 바뀌기 때문입니다.

수익 모델의 대표적 종류:

| 모델 | 예시 | 특징 |
|---|---|---|
| **광고** | 무료 앱·콘텐츠 사이트 | 사용자 규모가 클수록 유리. 사용자 경험과 트레이드오프. |
| **구독** | SaaS, OTT | 안정적 매출. 가치 인식이 분명해야 작동. |
| **건당 결제** | 이커머스, 콘텐츠 판매 | 거래 빈도와 단가가 변수. |
| **수수료** | 마켓플레이스, 결제 플랫폼 | 거래 양쪽을 모두 모아야 작동. |
| **프리미엄/Freemium** | 도구 SaaS | 무료로 시작해 고급 기능을 유료화. 전환율이 핵심. |

이 중 무엇을 선택하든 **기획 단계의 페르소나·MVP 결정**과 정합성이 맞아야 합니다. 페르소나에게 무료가 자연스러운데 구독을 강요하면 가입조차 안 일어납니다.

## 3. 단계 간 의사결정 사슬 — 사례 4개

이론은 이쯤에서 멈추고, 실제로 **앞 단계의 결정이 뒷 단계에 어떻게 도착하는지** 를 사례 4개로 보겠습니다. 이 코스를 끝까지 듣고 나면 이런 사례를 자기 머릿속에서 술술 짚어낼 수 있게 되는 것이 목표입니다.

### 사례 1. MVP의 칼질이 운영의 부담을 정한다

**상황** — 동네 카페 리뷰 앱을 만들기로 했습니다. 기획 단계에서 "리뷰", "사진", "지도", "친구 팔로우", "DM", "이벤트", "쿠폰", "방문 예약" 8개 기능을 모두 넣었습니다.

**개발·출시까지** — 8개 기능 구현으로 출시 일정이 4개월에서 9개월로 늘어납니다. 가까스로 출시.

**운영에서 청구되는 비용** — 출시 직후 8개 기능 모두에서 동시다발적 버그가 터집니다. 한 사람이 모두 대응할 수 없어 어떤 기능은 방치됩니다. 사용자는 "이 앱은 뭘 하는 앱이지?" 라며 이탈합니다.

**되감기** — 만약 기획 단계에서 **"리뷰 + 사진 + 지도"** 3개로 좁혔다면? 출시는 4개월에 가능했고, 3개 기능을 안정화하는 데 운영 자원을 집중할 수 있었습니다. 사용자도 "동네 카페 리뷰 앱" 이라는 정체성을 분명히 인식했을 겁니다.

**교훈** — MVP의 칼질은 단지 출시 일정만 좌우하는 게 아닙니다. **출시 후 운영의 면적**을 결정합니다.

### 사례 2. 흐릿한 ERD가 6개월 뒤 마이그레이션을 부른다

**상황** — 설계 단계에서 데이터 모델을 그릴 때 "사용자" 테이블 하나에 개인 정보·결제 정보·활동 로그를 모두 몰아넣었습니다. "어차피 한 사용자에 대한 정보니까."

**개발·출시까지** — 별 문제없이 진행됩니다. 단순한 구조가 처음에는 오히려 편합니다.

**운영 6개월 후 청구되는 비용** — 사용자가 늘면서 활동 로그가 폭증, 사용자 테이블이 무거워져 로그인조차 느려집니다. 결제 정보를 별도로 분리해 보안 감사를 받아야 하는데 분리할 수가 없습니다. 결국 큰 마이그레이션을 진행하느라 며칠을 통째로 소비하고, 그 사이에 일부 데이터가 유실됩니다.

**되감기** — 설계 단계에서 **사용자(`users`) / 결제(`payments`) / 활동 로그(`activity_logs`)** 를 분리만 했다면 모두 피할 수 있었던 비용입니다.

**교훈** — 데이터 설계는 한 번 굳으면 풀기 어렵습니다. 처음부터 **분리할 만한 것은 분리해 두는 것**이 결국 가장 싸게 먹힙니다.

### 사례 3. 브랜치 전략이 출시 속도를 정한다

**상황** — 개발자 두 명이 main 브랜치 한 줄로만 작업합니다. "둘이서 굳이 브랜치까지?" 라는 판단이었습니다.

**개발·출시까지** — 처음에는 빠릅니다. 작은 변경은 바로 반영됩니다.

**출시 후 청구되는 비용** — 한 명이 미완성 기능을 main에 올린 채 퇴근. 같은 시각 다른 한 명이 긴급 핫픽스를 배포합니다. 그 결과 **미완성 기능이 동반 출시**됩니다. 사용자가 깨진 화면을 보고 항의가 쏟아집니다. 롤백하려 했더니 어떤 커밋까지 되돌려야 하는지조차 분간이 안 됩니다.

**되감기** — `main`은 항상 배포 가능 상태로 유지하고, `develop`에서 통합한 뒤 검토를 거쳐 `main`으로 합치는 흐름이었다면 **미완성과 핫픽스가 섞일 수 없는 구조**가 됐을 겁니다.

**교훈** — 브랜치 전략은 단순 절차가 아니라 **사고를 구조적으로 막는 장치**입니다.

### 사례 4. 수익 모델이 첫 화면을 바꾼다

**상황** — 학습 앱을 기획합니다. "일단 무료로 만들고 사용자 모은 뒤에 수익화 고민하자" 로 시작합니다.

**개발·출시까지** — 첫 화면은 강의 카탈로그, 가입은 이메일만, 광고는 어디에도 없습니다.

**6개월 후, 구독 모델 도입** — 사용자가 어느 정도 모이고 광고로는 매출이 안 나와 구독 모델을 붙이려고 합니다. 그런데 첫 화면이 카탈로그라 "유료" 라는 신호가 어디에도 없습니다. 가입 흐름에 결제 단계도 없고, 이메일만 받았으니 결제 정보 수집도 처음부터 다시 해야 합니다. **기존 사용자의 70%가 결제 화면 직전에 이탈**합니다.

**되감기** — 기획 단계에서 "이 서비스는 구독" 이 정해져 있었다면, 첫 화면은 **무료 체험 + 가격 안내**, 가입은 처음부터 결제 정보 동의를 포함했을 겁니다. 사용자도 "이 서비스는 유료" 라는 인식을 가지고 들어왔겠죠.

**교훈** — 수익 모델은 **기획 단계의 결정**이지 출시 후 추가하는 부속이 아닙니다.

## 4. 시간 분포 — 어디에 얼마나 쓸까

처음 서비스를 만들면 시간 배분을 잘못 잡기 쉽습니다. 단계마다 대략 어떤 비중으로 시간이 들어가는지 미리 감을 잡아 둡니다. (서비스 종류·팀 구성에 따라 차이가 큽니다. 어디까지나 **시작점을 위한 거친 가이드**입니다.)

| 단계 | 첫 출시까지의 비중 | 출시 후 1년의 비중 |
|---|---:|---:|
| 기획 | 5–10% | 10% |
| 설계 | 10–15% | 5% |
| 개발 | 40–50% | 25% |
| 테스트 | 10–15% | 15% |
| 빌드·배포·출시 | 10–15% | 5% |
| 운영·유지보수 | — | 30% |
| 추가 기능·개선 | — | 10% |

처음 만드는 분이 가장 자주 빠지는 함정 두 가지:

1. **개발에 80% 이상의 시간을 쓴다** — 기획·설계·테스트가 빈약해진다. 결과적으로 출시 후 운영 비용이 폭증.
2. **출시 후를 0%로 가정한다** — 출시를 마지막으로 보고 그 후의 시간을 계획에 안 넣는다. 막상 출시 다음 날부터 "이제 뭘 하지?" 가 시작.

운영·유지보수가 1년 비중에서 **가장 큰 덩어리**라는 점을 기억해 두세요. 이것이 "출시는 시작" 이라는 말의 실체입니다.

## 5. 자주 빠지는 함정

### 함정 1. 단계를 칼같이 한 방향으로만 가려 한다

이상적으로는 기획→설계→개발→테스트→배포→운영 순서로 한 번 흐르고 끝납니다. 현실은 다릅니다. **개발 도중에 설계가 바뀌고**, 테스트 중에 기획이 흔들리고, 운영 중에 핵심 기능이 재정의됩니다. 이걸 "잘못된 일" 로 보면 매번 좌절합니다. 정상이라고 받아들이고, 대신 **변경 비용을 줄이는 도구**(브랜치 전략, 자동화된 테스트, 명확한 설계 문서)를 갖춰 두세요.

### 함정 2. 한 단계만 잘하려 한다

"나는 개발은 잘하니까 그쪽에 집중한다" 같은 자세는 종종 함정입니다. 한 단계만 잘하는 사람은 **앞뒤 단계의 산출물을 받아들이는 안목**이 떨어져, 결과적으로 자기 단계마저 잘 안 됩니다. **9단계의 윤곽을 모두 가지고 있는 사람**이 가장 강합니다. 그 위에 한 단계 깊이를 더하세요.

### 함정 3. 기획·설계를 "낭비" 로 본다

빨리 코드를 치고 싶은 마음은 자연스럽지만, 기획·설계에 들인 시간은 **개발·테스트 단계의 시간을 절약**합니다. 비유하자면, 길을 먼저 그리고 차를 모는 것과 무작정 출발해서 헤매는 것의 차이입니다. 처음 만드는 분일수록 기획·설계의 비중을 의식적으로 늘려 보세요.

### 함정 4. 출시를 골인 지점으로 본다

이건 워낙 자주 나오는 함정이라 한 번 더 강조합니다. 출시는 **시작점**입니다. 출시 후의 운영·개선이 사실 가장 긴 시간이고, 가장 큰 가치를 만들어 내는 구간입니다. 출시까지의 일정만 잡고 그 후를 계획하지 않으면 출시 다음 날부터 길을 잃습니다.

### 함정 5. 수익화를 마지막에 붙이려 한다

수익 모델은 **기획 단계의 결정**입니다. 사례 4에서 봤듯이 마지막에 붙이려 하면 첫 화면부터 가입 흐름까지 통째로 다시 짜야 합니다. 기획서에 "수익 모델: 미정" 이라고 적혀 있다면 위험 신호입니다. 한 줄이라도 가설을 적어 두세요.

## 6. 한 셜 더

### 6.1 다른 단계 분류법들

이 코스는 **9단계** 로 정리하지만, 다른 자료에서는 다르게 나눕니다.

- **소프트웨어 공학 교과서** — 요구사항 분석 → 설계 → 구현 → 검증 → 유지보수 (5단계 워터폴).
- **애자일 관점** — 단계가 아니라 **반복(스프린트)** 으로 본다. 한 스프린트 안에 기획·설계·개발·테스트·배포가 모두 들어간다.
- **DevOps 관점** — Plan → Code → Build → Test → Release → Deploy → Operate → Monitor 의 8단계 무한 루프.

이 코스의 9단계는 워터폴에 가까운 분류이지만, 사례 분석 곳곳에 애자일·DevOps 관점도 섞여 있습니다. 어느 분류가 정답이라기보다, **하나를 잘 익히면 다른 분류로 옮겨 가기 쉬워집니다**.

### 6.2 단계마다의 직무 매핑

큰 회사에서는 단계마다 다른 직무가 들어갑니다. 작은 팀에서는 한 사람이 여러 직무를 겸업하지만, 누가 어느 단계의 주된 책임자인지 미리 알아 두면 좋습니다.

| 단계 | 주된 직무 |
|---|---|
| 기획 | PO(Product Owner), 기획자, PM |
| 설계 | UX 디자이너, UI 디자이너, 백엔드 아키텍트 |
| 개발 | 프론트엔드·백엔드·모바일 개발자 |
| 테스트 | QA 엔지니어 |
| 빌드·배포 | DevOps, SRE |
| 운영 | 운영팀, 고객 지원 |
| 수익화 | 비즈니스, 마케팅, 데이터 분석 |

### 6.3 사이클의 빠르기 — 출시 빈도

성숙한 조직일수록 **출시 사이클이 짧습니다**. 한 달에 한 번 출시하던 팀이 일주일에 한 번, 그 다음에는 하루에 여러 번 출시하는 식으로 빨라집니다. 출시 빈도가 빨라지려면 **테스트·빌드·배포의 자동화**가 뒷받침되어야 합니다. 처음에는 한 달에 한 번도 어렵지만, 운영을 굴려 가며 점진적으로 짧아지는 방향이 정상입니다.

### 6.4 권할 만한 키워드

이 레슨에서는 짧게만 짚었지만, 자기 프로젝트에서 마주칠 만한 키워드들:

- **CI/CD (Continuous Integration / Continuous Deployment)** — 빌드·테스트·배포의 자동화. Part 6에서 다시 등장.
- **MAU / DAU** — 월간·일간 활성 사용자. 출시 후 가장 먼저 보는 지표.
- **Cohort 분석** — 사용자를 가입 시점별로 묶어 행동을 비교. 운영의 핵심 도구.
- **NPS (Net Promoter Score)** — "이 서비스를 친구에게 추천할 의향이 있는가" 로 만족도 측정.

## 마치며

오늘 한 일을 다시 정리합니다.

- 서비스 개발의 **9단계**(기획·설계·개발·테스트·빌드/소스·배포·출시·운영·수익화)와 그 순서가 짜인 이유를 잡았다.
- 각 단계가 다음 단계에 무엇을 **넘기는지**, 그 산출물의 모양이 무엇인지를 한 줄씩 봤다.
- **단계 간 사슬** 의 사례 4개로, 앞 단계의 결정이 뒷 단계에 어떤 비용으로 도착하는지 미리 감을 잡았다.
- 단계별 **시간 비중**과 자주 빠지는 함정들을 짚었다.

이제부터의 26개 레슨은 이 윤곽을 **하나씩 펼쳐서** 깊이 들어갑니다. 혹시 중간에 길을 잃은 느낌이 들면 언제든 이 레슨으로 돌아와 지도를 다시 펼쳐 보세요. 이 한 편이 코스 전체의 **나침반** 역할을 합니다.
