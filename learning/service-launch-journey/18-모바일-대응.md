# 18. 모바일 대응 (반응형·네이티브)

> **한 줄 요약.** 모바일 대응은 **"PC 화면을 줄이는 것"** 이 아니라 **"한정된 화면에서 무엇을 보여주고 무엇을 숨길지 결정하는 것"** 이다. 반응형 웹·네이티브 앱·하이브리드 — 셋 중 자기 상황에 맞는 하나를 골라야 한다.

---

## 들어가며

오늘날 사용자의 **70~80%** 가 모바일로 서비스에 접근합니다. 모바일 대응 없이 출시하는 것은 사용자의 4분의 3을 잃고 시작하는 것과 같습니다. 동시에 모바일은 PC 와 화면 크기·입력 방식·사용 맥락이 모두 다르기 때문에, 단순히 PC 화면을 작게 줄여서는 좋은 경험이 안 나옵니다.

처음 만드는 분이 모바일에서 자주 막히는 자리:

- 반응형 웹·네이티브 앱·하이브리드 중 무엇을 골라야 할지.
- 같은 기능을 PC·모바일에 모두 구현하려니 시간이 두 배.
- 화면이 좁아서 모든 정보를 다 보여줄 수 없음.
- 터치·드래그·핀치 줌 같은 입력 방식이 PC 와 다름.

이 레슨은 그 결정 지점들을 짚습니다.

이 레슨을 다 읽으면:

- 반응형 웹·PWA·네이티브·하이브리드의 차이를 안다.
- 자기 서비스에 맞는 옵션을 결정할 수 있다.
- 모바일 우선(Mobile First) 디자인의 실제 의미를 안다.
- 터치 인터페이스 기본 가이드라인을 안다.
- 모바일 성능·접근성 체크 포인트를 안다.

---

## 1. 모바일 대응의 4가지 옵션

### 1.1 옵션 A. 반응형 웹

같은 웹 코드가 화면 크기에 따라 모양을 바꿈. CSS 미디어 쿼리·flexbox·grid 로 구현.

**장점:**
- 코드 한 벌. 유지보수 부담 적음.
- 즉시 배포. 앱 스토어 심사 없음.
- SEO·검색 가능.

**단점:**
- 푸시 알림·카메라·하드웨어 접근 제한.
- 첫 로딩이 앱보다 느림.
- 오프라인 동작 어려움.

**적합한 경우:**
- 콘텐츠 중심 (블로그·뉴스·문서).
- B2B SaaS.
- 자주 사용하지 않는 도구.

### 1.2 옵션 B. PWA (Progressive Web App)

반응형 웹 + 앱처럼 설치·알림·오프라인 지원. 매니페스트·서비스 워커 추가.

**장점:**
- 반응형 웹의 모든 장점.
- 홈 화면에 설치 가능.
- 푸시 알림 (iOS Safari 16.4+ 부터).
- 오프라인 동작.

**단점:**
- iOS 의 PWA 지원이 제한적.
- 앱 스토어 노출 안 됨.
- 일부 하드웨어 접근 제약.

**적합한 경우:**
- 자주 쓰는 도구지만 앱 스토어가 굳이 필요 없을 때.
- 콘텐츠·도구 혼합형.

### 1.3 옵션 C. 네이티브 앱

iOS·Android 각 플랫폼의 언어로 개발.

| 플랫폼 | 언어 |
|---|---|
| iOS | Swift, SwiftUI |
| Android | Kotlin, Jetpack Compose |

**장점:**
- 가장 빠르고 부드러운 사용 경험.
- 모든 하드웨어·OS 기능 접근.
- 앱 스토어 노출.

**단점:**
- iOS·Android 코드 두 벌.
- 개발 시간 길고 인력 두 배.
- 출시 시 심사 필요.

**적합한 경우:**
- 사용자 경험이 핵심 차별화인 서비스.
- 게임·카메라·AR 같이 하드웨어 의존.
- 큰 사용자 기반이 예상되는 B2C.

### 1.4 옵션 D. 크로스 플랫폼 (하이브리드)

한 코드로 iOS·Android 양쪽 앱 생성.

| 도구 | 언어 |
|---|---|
| **React Native** | JavaScript/TypeScript |
| **Flutter** | Dart |
| **Capacitor** | 웹 → 앱 컨테이너 |
| **.NET MAUI** | C# |

**장점:**
- 한 코드로 두 플랫폼.
- 네이티브에 가까운 성능.
- 앱 스토어 노출.

**단점:**
- 네이티브보다 약간 느림.
- 일부 OS 기능은 네이티브 모듈 필요.
- 도구·라이브러리 생태계가 네이티브보다 작음.

**적합한 경우:**
- 작은 팀이 양 플랫폼 노출 필요.
- 웹 개발자가 모바일도 만들고 싶을 때 (React Native).

### 1.5 4옵션 비교 표

| 옵션 | 개발 비용 | 사용자 경험 | OS 기능 | 배포 |
|---|---|---|---|---|
| 반응형 웹 | 낮음 | 보통 | 제한적 | 즉시 |
| PWA | 낮음~중간 | 좋음 | 일부 | 즉시 |
| 네이티브 (Native) | 매우 높음 | 매우 좋음 | 모두 | 심사 필요 |
| 크로스 플랫폼 | 중간 | 좋음 | 거의 모두 | 심사 필요 |

### 1.6 처음 만드는 분의 권장

| 상황 | 권장 |
|---|---|
| MVP, 빠른 검증 | **반응형 웹** |
| 자주 쓰는 도구, 앱 스토어 굳이 안 필요 | **PWA** |
| 양 플랫폼 앱 필요, 작은 팀 | **React Native 또는 Flutter** |
| 게임·하드웨어 의존, 큰 팀 | **네이티브** |

처음에는 **반응형 웹 → 검증 후 PWA 또는 크로스 플랫폼** 이 가장 안전한 길.

## 2. 반응형 웹 — 실무

### 2.1 모바일 우선 (Mobile First)

레슨 12 에서 짧게 언급한 원칙. CSS 를 모바일 기준으로 먼저 쓰고, 화면이 커질 때 추가 스타일을 얹습니다.

```css
/* 모바일 (기본) */
.container {
  padding: 16px;
}

/* 태블릿 이상 */
@media (min-width: 768px) {
  .container {
    padding: 32px;
    display: grid;
    grid-template-columns: 1fr 2fr;
  }
}

/* PC 이상 */
@media (min-width: 1024px) {
  .container {
    max-width: 1200px;
    margin: 0 auto;
  }
}
```

Tailwind 라면 모바일이 기본, `md:`·`lg:` 접두사가 큰 화면용.

```html
<div class="p-4 md:p-8 md:grid md:grid-cols-3 lg:max-w-6xl lg:mx-auto">
```

### 2.2 표준 브레이크포인트

| 이름 | 범위 | 대상 |
|---|---|---|
| sm | 0–639px | 모바일 |
| md | 640–767px | 큰 모바일·작은 태블릿 |
| lg | 768–1023px | 태블릿 |
| xl | 1024–1279px | 작은 PC |
| 2xl | 1280px+ | 큰 PC |

이 표를 따로 외우지 말고 **Tailwind 기본값**을 쓰는 것이 무난합니다.

### 2.3 우선순위 결정

좁은 화면에서 무엇을 보이고 무엇을 숨길지 결정. 레슨 08 의 4영역 중 모바일에서:

- **헤더** — 메뉴를 햄버거 ☰ 아래로.
- **본문** — 가장 중요한 한 가지.
- **보조** — 보통 숨김 또는 하단으로.
- **CTA** — 화면 하단 고정 또는 본문 끝.

PC 에서는 사이드바·여러 칼럼이 가능하지만, 모바일에서는 **세로 스크롤 한 줄** 이 기본입니다.

### 2.4 터치 영역 크기

iOS HIG: **최소 44pt × 44pt**. Material Design: **최소 48dp × 48dp**.

너무 작은 버튼은 누르기 어렵습니다. 디자인 시스템의 버튼 컴포넌트가 이 크기를 만족하는지 확인.

### 2.5 폰트 크기

- 본문: **16px 이상** 권장. 작으면 모바일에서 자동 줌.
- 입력: **16px 이상** 권장 (iOS 가 16px 미만이면 자동 줌인).

### 2.6 이미지 — `srcset` 과 `picture`

화면 크기·해상도에 따라 다른 이미지 제공.

```html
<img
  src="hero-800.jpg"
  srcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1600.jpg 1600w"
  sizes="(max-width: 768px) 100vw, 50vw"
  alt="..."
/>
```

작은 화면에는 작은 이미지를 보내 데이터·로딩 시간 절약.

### 2.7 viewport 메타 태그

모든 모바일 웹 페이지에 필수.

```html
<meta name="viewport" content="width=device-width, initial-scale=1" />
```

빠뜨리면 모바일에서 PC 크기로 렌더 후 줌 아웃 — 텍스트가 작아 못 읽음.

## 3. PWA 만들기

### 3.1 필수 3요소

1. **HTTPS** — PWA 는 HTTPS 필수 (localhost 제외).
2. **Web App Manifest** — 앱 정보·아이콘·시작 URL 정의.
3. **Service Worker** — 오프라인 캐시·푸시 알림 처리.

### 3.2 Manifest 예시

`public/manifest.json`:

```json
{
  "name": "둘이 가계부",
  "short_name": "둘가",
  "start_url": "/",
  "display": "standalone",
  "theme_color": "#4F46E5",
  "background_color": "#FFFFFF",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}
```

`<link rel="manifest" href="/manifest.json" />` 로 연결.

### 3.3 Service Worker

기본 캐시 전략:

```js
// public/sw.js
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open('app-v1').then((cache) =>
      cache.addAll(['/', '/index.html', '/main.js', '/main.css'])
    )
  );
});

self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((response) => response || fetch(event.request))
  );
});
```

Vite·Next.js 에는 PWA 플러그인이 있어 직접 안 짜도 됩니다 (`vite-plugin-pwa`, `next-pwa`).

### 3.4 PWA 체크리스트

- HTTPS ✓
- Manifest 연결 ✓
- Service Worker 등록 ✓
- 192px·512px 아이콘 ✓
- viewport 메타 ✓
- 오프라인에서 적어도 시작 화면이 보여야 ✓

Lighthouse (Chrome DevTools) 의 PWA 점검으로 빠진 항목 확인.

## 4. 크로스 플랫폼 — React Native·Flutter 짧게

### 4.1 React Native

Facebook(Meta) 이 만든 크로스 플랫폼. JavaScript/TypeScript 로 작성, 네이티브 컴포넌트로 변환.

**특징:**
- 웹 React 와 비슷한 문법.
- Expo 라는 도구로 빠르게 시작 가능.
- 네이티브 모듈 작성 시 Swift·Kotlin 일부 필요할 수 있음.

**시작:**
```bash
npx create-expo-app my-app
```

### 4.2 Flutter

Google 의 크로스 플랫폼. Dart 언어. 자체 렌더링 엔진(Skia·Impeller).

**특징:**
- 디자인이 두 플랫폼에서 똑같이 보임.
- 성능이 React Native 보다 약간 좋다는 평.
- Dart 학습 부담.

**시작:**
```bash
flutter create my_app
```

### 4.3 둘의 비교

| 항목 | React Native | Flutter |
|---|---|---|
| 언어 | JS/TS | Dart |
| 렌더링 | 네이티브 컴포넌트 | 자체 엔진 |
| 학습 곡선 | 웹 개발자에게 낮음 | Dart 학습 필요 |
| 디자인 일관성 | 플랫폼에 따라 미묘하게 다름 | 통일 |
| 생태계 | 매우 큼 | 빠르게 성장 |
| 채용 풀 | 큼 | 중간 |

웹 개발자 출신은 보통 **React Native (Expo)** 가 자연스럽습니다.

## 5. 모바일 특유 함정

### 함정 1. 데스크톱 디자인을 모바일에 그대로

PC 의 사이드바·다단 레이아웃을 모바일에 그대로 두면 답답합니다. **모바일 전용 우선순위** 결정.

### 함정 2. 터치 영역 너무 작음

링크·버튼이 작으면 손가락으로 누르기 어렵습니다. 44pt 이상.

### 함정 3. 호버 의존

PC 의 hover 효과만으로 정보를 표시하면 모바일에서 안 보임 (터치 디바이스에 hover 없음). **클릭·롱프레스로 대체**.

### 함정 4. 폰트 16px 미만 입력

iOS 가 자동 줌인해서 사용자 경험 깨짐. **input·textarea 의 font-size 16px 이상**.

### 함정 5. 거대 이미지

PC 용 4K 이미지를 모바일에도 그대로 보내면 데이터·로딩 시간 폭증. `srcset` 또는 CDN 의 이미지 변환.

### 함정 6. 가로 스크롤

모바일에서 의도치 않은 가로 스크롤은 큰 사용성 문제. `overflow-x: hidden`·요소 너비 100vw 주의.

### 함정 7. 키보드가 화면 가림

모바일 키보드가 올라오면 입력 필드가 가려질 수 있음. 키보드 등장 시 입력으로 자동 스크롤.

### 함정 8. 푸시 알림 남발

매일 푸시 보내면 사용자가 알림 끔. **의미 있는 알림만**.

### 함정 9. 배터리·데이터 무관심

위치 추적·계속 polling 같은 작업이 배터리·데이터를 갉아먹음. 필요할 때만.

### 함정 10. 앱 스토어 가이드라인 무시

iOS 는 특히 까다로움. 결제는 In-App Purchase 강제, 인종·정치 콘텐츠 제한 등. 자세한 내용 레슨 25.

## 6. 모바일 성능 체크

### 6.1 측정 도구

| 도구 | 무엇 |
|---|---|
| **Lighthouse (Chrome)** | 종합 점수 |
| **PageSpeed Insights** | Lighthouse + 실제 사용자 데이터 |
| **WebPageTest** | 다양한 디바이스·네트워크 시뮬레이션 |
| **Real User Monitoring (RUM)** | 실제 사용자 측정 (DataDog·NewRelic) |

### 6.2 Core Web Vitals

Google 이 제시하는 핵심 지표.

| 지표 | 의미 | 좋은 값 |
|---|---|---|
| **LCP (Largest Contentful Paint)** | 가장 큰 요소가 보일 때까지 | < 2.5s |
| **INP (Interaction to Next Paint)** | 상호작용 후 화면 반응까지 | < 200ms |
| **CLS (Cumulative Layout Shift)** | 화면 흔들림 | < 0.1 |

이 셋이 모두 좋으면 사용자가 빠르고 안정적이라고 느낍니다.

### 6.3 자주 쓰는 최적화

- **이미지 최적화** — WebP·AVIF 포맷, 적절한 크기.
- **코드 스플리팅** — 페이지별로 번들 분할.
- **Lazy Loading** — 보이지 않는 이미지·컴포넌트 지연 로드.
- **CDN** — 정적 자산을 사용자 가까이.
- **Brotli/Gzip 압축** — 서버 응답 압축.

## 7. 한 셜 더

### 7.1 Capacitor / Tauri — 웹 → 앱

이미 만든 웹앱을 모바일·데스크톱 앱으로 포장하는 도구.

- **Capacitor** — Ionic 의 후속. iOS·Android 앱 생성.
- **Tauri** — Rust 기반 데스크톱(macOS·Windows·Linux) 앱.

기존 웹 코드 재사용에 유리.

### 7.2 Apple App Tracking Transparency (ATT)

iOS 에서 다른 앱·웹사이트의 사용자 추적 시 별도 동의 필요. 광고 SDK 사용 시 영향.

### 7.3 Android Navigation·iOS Tab Bar

플랫폼별 표준 패턴.

- iOS — 화면 하단 Tab Bar 가 일반.
- Android — 화면 상단 Top Bar + 하단 Bottom Navigation.

크로스 플랫폼 도구는 보통 두 패턴을 모두 지원.

### 7.4 다크 모드

OS 설정에 따라 자동. CSS:

```css
@media (prefers-color-scheme: dark) {
  :root { --bg: #0F172A; --text: #F8FAFC; }
}
```

처음 출시에 다크 모드를 무리해서 만들 필요는 없지만, 디자인 토큰을 색 변수로 잡아 두면 나중에 추가가 쉬워집니다.

### 7.5 추가 키워드

- **Adaptive Layout** — 화면 크기 외에 디바이스 능력별 다른 UI.
- **Container Queries** — 부모 컨테이너 크기에 반응 (CSS 신기능).
- **Safe Area** — iPhone 노치·홈 인디케이터 영역 회피.
- **Haptic Feedback** — 진동·햅틱 피드백.
- **Offline-First** — 오프라인 동작을 기본 가정으로 설계.
