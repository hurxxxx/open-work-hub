# 26. 운영·유지보수 — 출시는 시작

> **한 줄 요약.** 출시는 결승선이 아니라 **출발선**이다. 출시 후 1년의 시간 비중이 출시까지의 시간보다 크고, 그 시간이 서비스의 생사를 결정한다.

---

## 들어가며

길고 길었던 여정 끝에 마침내 출시. 사용자가 첫 가입을 합니다. 이때 처음 만드는 분들이 가장 자주 겪는 감정은 **"이제 뭘 하지?"** 입니다. 출시까지의 모든 준비는 했지만, 그 후를 위한 준비는 거의 안 했기 때문입니다.

이 레슨은 출시 직후부터 시작되는 운영 단계를 안내합니다. 거대한 운영 노하우를 모두 다루는 것은 불가능하지만, **첫 1년을 큰 사고 없이 보내는 데 필요한 기본** 을 잡아 봅니다.

이 레슨을 다 읽으면:

- 운영의 4축(안정성·개선·소통·관찰) 을 안다.
- 운영 사이클(피드백 → 결정 → 배포)을 이해한다.
- 추가 기능과 개선의 균형을 잡을 수 있다.
- 사용자 지원 채널을 처음 어떻게 마련하는지 안다.
- 기술 부채와 리팩터링 시점을 안다.

---

## 1. 핵심 개념 — 운영의 4축

### 1.1 4축

| 축 | 무엇 | 시간 비중 |
|---|---|---|
| **안정성** | 서비스가 계속 동작 | 30~40% |
| **개선·새 기능** | 기존 기능 다듬기·새 기능 | 30~40% |
| **사용자 소통** | 문의·피드백·지원 | 10~20% |
| **관찰·학습** | 데이터·트렌드·다음 결정 준비 | 10~20% |

비율은 서비스 성격에 따라 다르지만, 4축이 모두 있어야 균형. 한 축에 치우치면 다른 축에서 사고가 납니다.

### 1.2 운영 사이클 — 피드백·결정·배포

운영은 다음 사이클의 반복:

```
사용자 신호 (지표·문의·리뷰)
    ↓
패턴 발견 (무엇이 문제인가)
    ↓
결정 (수정·개선·새 기능·놔두기)
    ↓
구현·테스트
    ↓
배포 (점진 또는 전체)
    ↓
다시 사용자 신호 관찰
```

이 사이클의 속도가 곧 서비스의 적응 능력입니다. 처음에는 사이클이 길지만, 도구·자동화가 쌓이며 빨라집니다.

## 2. 안정성 운영

### 2.1 무엇이 깨지면 안 되는가

서비스의 핵심 흐름이 무엇인지 명확히 해 두세요. 그 흐름이 막히면 즉시 대응.

| 우선순위 | 무엇 |
|---|---|
| **P0** | 결제·로그인·핵심 기능. 깨지면 즉시 대응. |
| **P1** | 일부 기능. 24시간 안에 대응. |
| **P2** | UI 깨짐·소수 사용자 영향. 다음 배포 주기에. |
| **P3** | 사소한 개선. 백로그. |

이 분류가 사전에 합의되어 있어야 새벽 3시에 무엇을 깨워서 고칠지 결정 가능.

### 2.2 SLA·SLO·Error Budget

**SLA (Service Level Agreement)** — 사용자에게 약속한 가용성. 보통 99.9% (월 약 43분 다운).

**SLO (Service Level Objective)** — 내부 목표. SLA 보다 약간 높게.

**Error Budget** — 허용된 다운타임. 다 쓰면 새 기능 출시 멈추고 안정화에 집중.

처음에는 거창한 SLA 없이 시작해도 됩니다. 다만 "**얼마나 다운되면 사용자가 떠나는가**" 를 의식.

### 2.3 정기 점검

매주·매월 점검할 항목:

- 자동 백업이 동작하는가
- 인증서 만료 임박은 없는가
- 도메인 갱신 임박은 없는가
- 오래된 의존성 (보안 취약점) 없는가
- 디스크·메모리·DB 용량 여유는?
- 비용이 예상 대비 어떤가

이 점검을 잊으면 **갑작스런 사고**로 돌아옵니다. 캘린더에 정기 일정으로.

## 3. 개선과 새 기능 — 균형 잡기

### 3.1 출시 직후 최우선

처음 출시 후 1~2개월은 **새 기능보다 안정화**.

- 발견된 버그 수정.
- 사용자 피드백에서 반복되는 불만 해결.
- 성능 문제 발견 시 개선.
- 첫 페르소나 외 다른 사용자 행동 관찰.

이 시기에 새 기능을 마구 추가하면 기존 기능까지 흔들립니다.

### 3.2 그 후의 균형

성장이 시작되면 다음 균형:

| 작업 | 비중 |
|---|---|
| **버그 수정·기술 부채** | 20~30% |
| **기존 기능 개선** | 30~40% |
| **새 기능** | 30~40% |
| **인프라·관찰성** | 10~20% |

**70-20-10 원칙** — 검증된 영역 70%, 인접 영역 20%, 도전적 시도 10%.

### 3.3 새 기능 결정 — 페르소나로 돌아가기

새 기능을 추가할지 망설일 때 페르소나(레슨 06) 로 돌아가세요.

- "김지영 씨가 이 기능을 매주 쓸까?" — YES 면 검토.
- "안티 페르소나(박철수 씨) 가 원하는 기능은 아닌가?" — YES 면 빠지기.
- "이 기능이 가치 제안 한 문장과 맞는가?" — NO 면 빠지기.

페르소나가 등대. 기능 폭증을 막는 안전장치.

### 3.4 기술 부채

빠른 출시를 위해 미뤄둔 일들. 출시 후 슬슬 갚아야:

- 테스트 미흡한 영역.
- 임시방편으로 깔린 코드.
- 처음 잡았던 데이터 모델의 한계.
- 리팩터링이 필요한 영역.

**모두 갚을 필요는 없습니다.** 다만 **개선 비용이 그 영역의 변경 비용을 줄이는지** 가 기준. 자주 변경되는 영역의 부채만 갚으세요.

## 4. 사용자 소통

### 4.1 채널 마련

처음 출시 시 최소한 다음 중 한 가지:

- **이메일** (`support@couple-budget.com`).
- **인앱 문의 폼** — 사용자가 앱 안에서.
- **카카오 채널** — 한국 사용자에게 친숙.
- **디스코드·슬랙 커뮤니티** — 활발한 사용자에게.

이메일이 가장 무난한 시작점.

### 4.2 응답 시간 목표

| 우선순위 | 목표 |
|---|---|
| 결제·로그인 같은 핵심 문의 | 24시간 |
| 일반 사용 문의 | 48시간 |
| 기능 요청·피드백 | 1주일 |

응답이 늦어도 **"받았습니다, 살펴보고 답변드리겠습니다"** 한 줄 자동 회신은 즉시.

### 4.3 흔한 문의 정리 (FAQ)

같은 문의가 반복되면 FAQ 페이지·인앱 도움말로. 시간을 크게 절약합니다.

### 4.4 사용자 인터뷰

문의 응답 외에, **능동적으로 사용자에게 묻는 시간**도 만드세요. 분기에 한 번이라도.

- 핵심 사용자 5명을 30분씩 인터뷰.
- "최근 우리 앱을 쓰면서 답답했던 일은?"
- "다른 도구로 옮긴다면 어떤 이유?"

이 인터뷰가 다음 분기 우선순위를 결정합니다.

## 5. 데이터 기반 의사결정

### 5.1 핵심 지표 (North Star Metric)

서비스의 건강을 한 지표로 표현. 모든 결정의 등대.

| 서비스 종류 | NSM 후보 |
|---|---|
| SaaS 도구 | 주간 활성 사용자 (WAU) |
| 이커머스 | 주간 거래액 (GMV) |
| SNS | 일간 게시글 수 |
| 학습 앱 | 주간 학습 시간 |
| 부부 가계부 | 월간 활성 부부 그룹 수 |

NSM 이 정해지면 모든 새 기능·개선이 그것을 올리는지 확인.

### 5.2 보조 지표

- **DAU / MAU 비율 (Stickiness)** — 매일 쓰는 비율. 0.2 이상이면 강함.
- **Retention** — 가입 후 1주·1개월 후 다시 들어오는 비율.
- **Activation Rate** — 가입자 중 핵심 가치를 받은 비율.
- **Conversion Rate** — 결제 모델이라면 결제 전환율.

### 5.3 Cohort 분석

가입 시점별로 사용자를 묶어 행동 비교. 1월 가입자와 4월 가입자의 retention 이 다르면 그 사이에 무엇이 바뀐 것.

### 5.4 도구

| 도구 | 무엇 |
|---|---|
| **Google Analytics 4** | 무료, 일반 트래픽 |
| **Mixpanel** | 이벤트 분석 |
| **Amplitude** | 동일, 무료 티어 큼 |
| **PostHog** | 오픈소스, 셀프 호스팅 가능 |
| **Plausible** | 가벼운 분석 |

처음에는 GA4 + 한 가지 이벤트 분석 도구.

## 6. 운영 자동화

수동 작업이 많을수록 사람이 지치고 사고 위험이 큽니다. 다음을 자동화.

### 6.1 자동화할 것들

- **CI/CD** — 머지하면 자동 빌드·배포 (레슨 21).
- **백업** — 매일 자동.
- **모니터링·알람** — 임계 넘으면 자동 알림 (레슨 27).
- **인증서 갱신** — Let's Encrypt 자동.
- **의존성 업데이트** — Dependabot.
- **테스트** — PR 마다 자동 (레슨 19).
- **에러 추적** — Sentry.

### 6.2 자동화의 ROI

처음에는 자동화 셋업에 시간이 들지만, 한 번 들이면 매일 절약. 며칠 분량의 셋업이 한 달 안에 회수.

## 7. 자주 빠지는 함정

### 함정 1. 출시 후 일주일 휴식

출시는 시작. 첫 1~2주가 가장 중요. 사용자 첫 반응을 놓치지 마세요.

### 함정 2. 정기 점검 안 함

도메인 갱신·인증서 만료·백업 동작 같은 기본을 잊어서 사고. 캘린더에 정기 일정.

### 함정 3. 새 기능에 매몰

새 기능을 매주 추가하지만 기존 기능의 버그는 방치. 사용자가 떠납니다.

### 함정 4. 모든 사용자 의견을 따름

목소리 큰 한 사용자가 안 어울리는 기능을 강하게 요청. 페르소나·NSM 으로 판단.

### 함정 5. 기술 부채를 다 갚으려 함

코드 베이스 전체 리팩터링 같은 큰 일에 한 분기를 보냄. **자주 변경되는 영역만**.

### 함정 6. 사용자 소통 채널 무관심

이메일·문의 답변이 며칠 늦어짐. 사용자 평이 빠르게 깨짐.

### 함정 7. 데이터 없이 결정

"느낌으로" 새 기능 결정. 지표 보고 결정.

### 함정 8. 운영을 한 사람이 도맡음

특정 인원이 휴가·퇴사하면 운영이 멈춤. 문서화·교차 훈련.

### 함정 9. 사고 후 회고 안 함

같은 사고가 반복. 매번 사고 후 짧은 포스트모템 (Post-mortem).

### 함정 10. 비용·자원에 무관심

트래픽이 늘면서 비용이 폭증. 매월 비용 점검·최적화.

## 8. 한 셜 더

### 8.1 Postmortem 문화

사고 후 다음 형식으로 회고 문서.

```
## YYYY-MM-DD 사고 회고

### 무엇이 일어났는가 (timeline)

### 영향
- 영향받은 사용자 수
- 다운타임 길이

### 원인
- 직접 원인
- 근본 원인 (5 Whys)

### 무엇을 잘했는가

### 무엇이 부족했는가

### 액션 아이템
- [ ] 같은 사고를 막을 변경
- [ ] 모니터링·알람 추가
- [ ] 문서화
```

비난 없는 (blameless) 분위기로. 사람이 아니라 시스템·절차의 문제로.

### 8.2 Runbook — 자주 일어나는 운영 작업

특정 상황에서 무엇을 어떻게 할지의 절차서.

```
## DB 마이그레이션 절차
1. staging 에서 마이그레이션 적용
2. staging 에서 통합 테스트
3. 운영 트래픽이 적은 시간 (새벽 3시)
4. 백업 스냅샷 확인
5. 운영 마이그레이션 적용
6. 5분간 모니터링
7. 이상 시 롤백
```

이게 있으면 누가 하든 같은 결과.

### 8.3 SaaS Metrics

B2B SaaS 라면 추가로 챙겨야 할 지표.

- **MRR (Monthly Recurring Revenue)**
- **Churn Rate** (해지율)
- **LTV (Lifetime Value)**
- **CAC (Customer Acquisition Cost)**
- **NPS (Net Promoter Score)**

### 8.4 Incident Severity

장애 심각도 등급으로 대응 우선순위 결정.

- **SEV1** — 핵심 기능 다운. 즉시 대응. 대표·임원에게 알림.
- **SEV2** — 일부 기능. 영업시간 내 대응.
- **SEV3** — 사소함. 다음 주.

### 8.5 추가 키워드

- **SRE (Site Reliability Engineering)** — 운영을 코드·엔지니어링으로.
- **DevOps Culture** — 개발과 운영의 결합.
- **GitOps** — git 으로 운영 상태 관리.
- **Chaos Engineering** — 의도적 장애 주입.
- **MTTR / MTTF / MTBF** — 평균 복구·장애·고장 간격.
