# 15. 데이터베이스 구축과 운영

> **한 줄 요약.** 처음에는 **Postgres 한 대**면 충분하다. DB 의 진짜 어려움은 SQL 이 아니라 **마이그레이션·백업·인덱스** 의 운영에 있다.

---

## 들어가며

레슨 10 에서 데이터 모델(ERD)을 그리고, 레슨 14 에서 백엔드가 그 데이터를 다루는 흐름을 봤습니다. 이제 그 데이터가 실제로 살아 있는 곳 — **데이터베이스 자체**를 구축하고 굴리는 일이 남았습니다.

처음 만드는 분이 DB 단계에서 자주 막히는 자리:

- MySQL·Postgres·MongoDB 중 무엇을 골라야 할지 막막.
- 로컬에서는 잘 도는데 운영에 어떻게 올릴지 모름.
- 스키마 변경할 때마다 데이터가 깨질까봐 두려움.
- "백업이 중요하다" 는 말은 들었지만 어떻게 시작할지 모름.

이 레슨은 처음 출시하는 서비스의 DB 운영을 **무난하고 안전한 형태**로 시작하는 데 집중합니다. 거대한 분산 DB·고급 튜닝은 다음 단계.

이 레슨을 다 읽으면:

- DB 종류(RDB·NoSQL·캐시) 의 차이를 안다.
- 처음 시작에 무난한 선택과 그 이유를 안다.
- 마이그레이션 도구의 작동 원리와 첫 도입을 안다.
- 인덱스를 언제 추가하는지, 백업을 어떻게 시작하는지.
- 자주 빠지는 함정 (커넥션 풀·시간대·정합성) 을 피한다.

---

## 1. DB 종류 — 무엇이 무엇인가

### 1.1 관계형 DB (RDB)

행·열 테이블, 외래 키 관계, SQL 쿼리. 거의 모든 비즈니스 서비스의 기본.

| 제품 | 특징 |
|---|---|
| **PostgreSQL** | 기능 풍부, 표준 준수, JSON 지원 우수, 무료 |
| **MySQL** | 속도 빠름, 호스팅 옵션 많음, 무료 |
| **MariaDB** | MySQL 의 포크, 호환성 |
| **SQLite** | 파일 기반, 임베디드, 단일 사용자 |
| **Microsoft SQL Server** | 윈도우·기업 |
| **Oracle** | 금융·대기업 |

### 1.2 NoSQL — 비관계형 DB

스키마가 유연하고 분산이 쉬운 대신, 관계·트랜잭션이 약함.

| 종류 | 제품 | 적합한 상황 |
|---|---|---|
| **문서 DB** | MongoDB, DynamoDB | 스키마가 자주 바뀌거나 중첩 깊음 |
| **Key-Value** | Redis (캐시), DynamoDB | 빠른 단순 조회 |
| **컬럼 패밀리** | Cassandra | 거대 분산 |
| **그래프 DB** | Neo4j | 관계 위주 |
| **시계열 DB** | InfluxDB, TimescaleDB | 로그·메트릭 |

### 1.3 캐시·검색

DB 가 아니지만 함께 쓰임.

| 도구 | 역할 |
|---|---|
| **Redis / Valkey** | 캐시, 세션, 큐, pub/sub |
| **Memcached** | 단순 캐시 |
| **Elasticsearch / OpenSearch** | 풀 텍스트 검색 |
| **Meilisearch / Typesense** | 가벼운 검색 |

## 2. 처음 시작에 무난한 선택

### 2.1 권장 — PostgreSQL 한 대 + Redis (선택)

처음 출시하는 서비스에 가장 무난한 조합:

- **메인 DB: PostgreSQL** — RDB 의 표준. 기능이 풍부하고 JSON 도 잘 다룸. 무료. 클라우드 어디서나 매니지드 옵션 있음.
- **캐시·세션·큐: Redis** — 필요할 때 추가. 처음에는 없어도 됨.

이 조합이 작은 서비스부터 수만 사용자까지 무난히 견딥니다.

### 2.2 왜 Postgres 인가

| 이유 | 설명 |
|---|---|
| **표준 SQL 준수** | 다른 DB 로 옮기기 쉬움 |
| **JSON·JSONB** | 유연한 메타데이터 저장 |
| **확장 가능** | PostGIS(지리), pgvector(임베딩) 등 |
| **트랜잭션 강함** | 데이터 정합성 |
| **활발한 생태계** | 매니지드 호스팅·도구 풍부 |

MySQL 도 좋은 선택입니다. 단, 새로 시작한다면 Postgres 의 기능 풍부함이 유리합니다.

### 2.3 왜 NoSQL 부터 시작하지 않나

처음 만드는 분이 MongoDB 등으로 시작하는 경우가 있는데, 보통 후회합니다. 이유:

- 비즈니스 데이터의 90% 는 관계가 있음. RDB 가 더 자연스러움.
- 트랜잭션 정합성이 RDB 가 강함.
- SQL 로 데이터를 보는 도구·쿼리가 풍부.

NoSQL 이 적합한 경우는 명확합니다 — **거대한 비정형 데이터**, **유연한 스키마가 필수**, **수평 확장 절대 필요**. 이 셋 중 하나가 아니면 RDB.

## 3. 로컬 ↔ 운영 — 환경 분리

### 3.1 환경 3단계

대부분의 서비스가 다음 3개 환경을 굴립니다.

| 환경 | 용도 |
|---|---|
| **Local (개발자 노트북)** | 개인 개발 |
| **Staging / Dev** | 팀 공유 테스트 |
| **Production (운영)** | 실제 사용자 |

각 환경마다 별도의 DB. 데이터는 절대 섞지 않음.

### 3.2 로컬 DB — native PostgreSQL

AI-DO 서버의 dev/prod DB는 Docker가 아니라 native PostgreSQL service를 사용합니다. 데이터베이스와 role을 환경별로 분리하고, 애플리케이션은 DSN으로 접속합니다.

```bash
sudo systemctl enable --now postgresql
sudo -u postgres createuser app
sudo -u postgres createdb -O app app_dev
```

AI-DO dev/prod 서버에서는 PostgreSQL을 `127.0.0.1:5432`에 묶고, Docker Compose에는 DB 서비스를 넣지 않습니다.

### 3.3 운영 DB — 매니지드 서비스 추천

운영 환경에서 DB 를 직접 EC2 같은 서버에 설치하지 마세요. 관리 부담이 너무 큽니다. **매니지드 서비스**를 쓰세요.

| 서비스 | 무엇 |
|---|---|
| **AWS RDS** | Postgres·MySQL 매니지드 |
| **Google Cloud SQL** | 동일 |
| **Azure Database** | 동일 |
| **Supabase** | Postgres + Auth + Storage 통합 |
| **Neon, Render** | Postgres 서버리스 |
| **PlanetScale** | MySQL 서버리스 (현재는 더 이상 무료 없음) |

처음 시작에는 **Supabase** 또는 **Neon** 이 무료 티어가 있어 가볍게 시작 가능. 본격 운영은 AWS RDS 같은 안정적 매니지드.

### 3.4 환경 변수로 연결 정보 관리

DB 접속 정보를 코드에 박지 말고 환경 변수로.

```bash
# .env (로컬, git 에 올리지 않음)
DATABASE_URL=postgresql://app:localdev@localhost:5432/app_dev

# 운영은 클라우드의 secret manager 또는 배포 환경 변수
```

## 4. 마이그레이션 — 스키마 변경 관리

### 4.1 마이그레이션이란

데이터베이스 스키마(테이블·컬럼·인덱스) 를 변경하는 작업을 **버전 관리** 하는 것. 변경마다 한 파일을 만들고, 그 파일들을 순서대로 적용·롤백할 수 있게 합니다.

```
migrations/
├── 001_create_users.sql
├── 002_add_email_to_users.sql
├── 003_create_transactions.sql
└── ...
```

### 4.2 도구

| 언어 | 도구 |
|---|---|
| Python | Alembic, Django Migrations |
| Node.js | Prisma Migrate, Knex, TypeORM Migrations |
| Ruby | ActiveRecord Migrations |
| Go | golang-migrate, goose |
| 언어 무관 | Flyway, Liquibase |

### 4.3 첫 마이그레이션 예시 (Alembic)

```python
"""create users

Revision ID: 001
"""

def upgrade():
    op.create_table(
        'users',
        sa.Column('id', sa.BigInteger, primary_key=True),
        sa.Column('email', sa.String(255), unique=True, nullable=False),
        sa.Column('name', sa.String(100)),
        sa.Column('created_at', sa.TIMESTAMP, server_default=sa.func.now()),
    )

def downgrade():
    op.drop_table('users')
```

`alembic upgrade head` — 모든 미적용 마이그레이션 적용.
`alembic downgrade -1` — 한 단계 롤백.

### 4.4 마이그레이션 원칙

- **한 변경 = 한 마이그레이션 파일.** 큰 변경을 한 파일에 몰아넣지 않음.
- **항상 `down` 도 작성.** 롤백 가능해야.
- **운영에 적용 전에 staging 에서 검증.**
- **데이터 삭제·컬럼 삭제는 신중.** 두 단계 (deprecate → 실제 삭제) 가 안전.
- **거대 테이블의 변경은 락 주의.** 운영 중 락이 길게 걸리면 서비스 영향.

### 4.5 deprecate-then-delete 패턴

운영 중인 컬럼을 삭제할 때 안전한 패턴:

1. 새 코드 배포: 그 컬럼을 더 이상 안 씀.
2. 일정 기간 (며칠) 모니터링: 정말 안 쓰는지 확인.
3. 컬럼 삭제 마이그레이션 적용.

이 단계를 건너뛰고 한 번에 컬럼을 지우면 구버전 코드가 깨집니다.

## 5. 인덱스 — 성능의 친구

### 5.1 인덱스란

테이블의 특정 컬럼에 대해 빠른 검색을 위한 **별도 자료구조**. 책 뒤의 색인과 같습니다.

```sql
CREATE INDEX idx_transactions_user_id ON transactions(user_id);
```

이 인덱스 덕에 `WHERE user_id = 123` 검색이 100배 빨라집니다.

### 5.2 자동으로 생기는 인덱스

- **Primary Key** — 자동.
- **Unique 제약** — 자동.
- **Foreign Key** — Postgres 는 자동 안 생김. 수동 추가 권장.

### 5.3 언제 인덱스 추가?

다음 조건에서 인덱스를 추가합니다.

- 자주 `WHERE` 절에 등장하는 컬럼.
- 자주 `ORDER BY` 에 쓰이는 컬럼.
- 자주 `JOIN` 키로 쓰이는 컬럼.

처음에는 PK + FK + 명백한 검색 컬럼(`email`, `user_id`)에 인덱스. 운영하며 느려지는 쿼리가 보이면 그 시점에 추가.

### 5.4 합성 인덱스 (Composite Index)

여러 컬럼을 묶은 인덱스. 자주 같이 검색되는 조합에.

```sql
CREATE INDEX idx_transactions_user_date ON transactions(user_id, transacted_at DESC);
```

이 인덱스는 `WHERE user_id = ? AND transacted_at > ?` 쿼리에 강력. 컬럼 순서가 중요 (앞 컬럼 우선).

### 5.5 인덱스의 비용

인덱스가 무료가 아닙니다.

- **공간** — 데이터 외에 별도 저장.
- **쓰기 속도** — INSERT·UPDATE 시 인덱스도 업데이트.

지나치게 많으면 쓰기가 느려짐. 자주 쓰는 검색에만 인덱스.

### 5.6 EXPLAIN — 쿼리가 인덱스를 쓰는지 확인

```sql
EXPLAIN ANALYZE SELECT * FROM transactions WHERE user_id = 123;
```

`Index Scan` 이 보이면 인덱스 사용. `Seq Scan` 이 보이면 전체 테이블 스캔 — 인덱스가 없거나 옵티마이저가 인덱스를 안 씀.

## 6. 백업과 복구

### 6.1 백업의 3원칙

- **자동화** — 사람이 잊어버리면 안 됨.
- **여러 시점** — 매일·매주·매월.
- **다른 위치** — DB 서버와 다른 지역에.

### 6.2 매니지드 DB 라면

AWS RDS·Cloud SQL 등은 자동 백업 옵션이 있음. 사용 시:

- 매일 자동 스냅샷.
- 보관 기간 설정 (보통 7~35일).
- 다른 리전에 복제 (재해 복구).

이걸 켜는 게 첫 번째 작업.

### 6.3 직접 운영 시

```bash
# Postgres 백업
pg_dump -U app -d app_prod -F c -f backup_2026-04-25.dump

# 복구
pg_restore -U app -d app_prod backup_2026-04-25.dump
```

크론으로 매일 자동, S3 같은 객체 저장소에 업로드.

### 6.4 복구 연습

백업이 진짜로 작동하는지 확인하려면 **복구를 한 번 해 보세요**. 운영 중에는 못 하니, staging 에 복구해서 확인.

복구 안 되는 백업은 백업이 아닙니다.

## 7. 자주 빠지는 함정

### 함정 1. DB 를 직접 EC2 에 설치

운영 부담이 너무 큽니다. 매니지드 사용.

### 함정 2. 시간대 무관 컬럼

`TIMESTAMP WITHOUT TIME ZONE` 으로 한국 시간을 저장. 사용자가 미국에 있을 때 8시간 어긋남. **항상 `TIMESTAMP WITH TIME ZONE` (timestamptz)** 로 UTC 저장.

### 함정 3. 비밀번호·민감 정보를 평문 저장

비밀번호는 항상 해시. 결제 정보는 가능한 토큰화 (PG 사 측 토큰).

### 함정 4. 커넥션 풀 무관

DB 커넥션은 비싼 자원. 매 요청마다 새 커넥션을 만들면 DB 가 죽음. **커넥션 풀** 사용 (SQLAlchemy 기본·PgBouncer).

### 함정 5. 인덱스 없이 쿼리

운영 데이터가 쌓이면 갑자기 모든 화면이 느려짐. **개발 시점에 인덱스를 미리** 챙기세요.

### 함정 6. 마이그레이션을 운영에 직접

로컬에서만 돌려 보고 운영에 바로 적용하면 사고. **staging → 운영** 순서. 큰 마이그레이션은 트래픽 적은 시간대에.

### 함정 7. 백업 안 함

"매니지드라 알아서 되겠지" 라고 백업 옵션을 안 켜는 함정. **매니지드여도 명시적으로** 자동 백업을 활성화하세요.

### 함정 8. 운영 DB 에 직접 SQL

급한 일에 운영 DB 에서 `UPDATE` 를 직접 치면 사고 위험. 가능하면 항상 마이그레이션 또는 운영 도구를 통해.

### 함정 9. 데이터 정합성을 코드만 믿는다

NULL·UNIQUE·FK 같은 제약을 DB 차원에서도 걸어 두면 코드 버그가 나도 데이터가 깨지지 않음. **DB 제약 + 코드 검증** 둘 다.

## 8. 한 셜 더

### 8.1 Read Replica — 읽기 부하 분산

운영 DB 옆에 읽기 전용 복제본을 두고 SELECT 트래픽을 분산. 매니지드 서비스에서 클릭 한 번으로 추가 가능.

```
              (write) → Master
App ─┤
              (read)  → Replica 1, Replica 2
```

대규모 트래픽이 오기 시작할 때 도입.

### 8.2 샤딩 (Sharding)

테이블을 여러 서버로 분할. 거대 서비스의 영역. 처음 출시에는 절대 필요 없습니다.

### 8.3 모니터링 — 무엇을 볼까

운영 시작 후 다음을 모니터링.

- **CPU·메모리** — DB 서버 자원.
- **연결 수** — 커넥션 풀 부족 신호.
- **쿼리 시간** — 느린 쿼리 (`pg_stat_statements`).
- **디스크 사용량** — 가득 차면 즉시 장애.
- **레플리케이션 지연** — replica 가 master 를 따라가는지.

### 8.4 ACID·CAP·BASE

데이터베이스 이론의 큰 단어들.

- **ACID** — Atomicity, Consistency, Isolation, Durability. 트랜잭션의 4보장.
- **CAP** — Consistency, Availability, Partition tolerance. 분산 시스템의 트레이드오프.
- **BASE** — Basically Available, Soft state, Eventually consistent. NoSQL 의 보장 수준.

처음에는 ACID 만 의식해도 충분.

### 8.5 추가 키워드

- **Connection Pooler (PgBouncer)** — 커넥션 재사용.
- **Materialized View** — 자주 조회되는 집계를 미리 계산.
- **Partitioning** — 한 테이블을 여러 파티션으로.
- **Vacuum (Postgres)** — 불필요한 행 청소.
- **WAL (Write-Ahead Log)** — 트랜잭션 로그.
