# 23. 배포 인프라 — 클라우드 vs Vercel/CF

> **한 줄 요약.** 처음에는 **AWS·GCP 같은 큰 클라우드보다 Vercel·Render·Fly 같은 PaaS** 가 빠르고 안전하다. 인프라를 학습하지 않고도 출시할 수 있게 해 준다.

---

## 들어가며

빌드 산출물이 손에 있다면 이제 **그것을 어디에 띄울지** 결정합니다. 이 결정이 출시 일정과 운영 부담을 모두 좌우합니다.

처음 만드는 분이 인프라 단계에서 자주 막히는 자리:

- AWS·Azure·GCP 의 단어들 (EC2·S3·VPC·IAM…) 앞에서 어지러움.
- 클라우드를 안 쓰고 싶은데 안 써도 되는지 모름.
- Vercel·Netlify·Cloudflare 같은 옵션이 진짜 충분한지 모름.
- 처음에 어디 띄웠다가 나중에 옮기는 비용이 무서움.

이 레슨은 서비스 규모·복잡도에 맞는 **합리적 선택**을 짚습니다.

이 레슨을 다 읽으면:

- IaaS·PaaS·Serverless·BaaS 의 차이를 안다.
- 처음 출시에 권장되는 옵션들을 안다.
- 큰 클라우드(AWS·GCP)와 PaaS의 트레이드오프를 안다.
- 컨테이너 오케스트레이션이 언제 필요한지 안다.
- 비용·확장성·이식성의 트레이드오프를 안다.

## 1. 핵심 개념 — 인프라 추상화의 4단계

### 1.1 IaaS (Infrastructure as a Service)

가상 머신·네트워크 같은 **하드웨어 추상화**만 제공. 운영체제·런타임·앱은 다 사용자가.

| 제품 | 무엇 |
|---|---|
| AWS EC2 | 가상 서버 |
| GCP Compute Engine | 동일 |
| Azure VM | 동일 |
| DigitalOcean Droplets | 단순한 가상 서버 |
| Hetzner | 저렴한 VPS |

**장점:** 자유도 최대.
**단점:** 모든 것을 직접 — OS 패치·보안·모니터링 등.

### 1.2 PaaS (Platform as a Service)

런타임·OS 까지 제공. 코드만 올리면 됨.

| 제품 | 무엇 |
|---|---|
| **Heroku** | 원조. 비싸짐. |
| **Render** | Heroku 후속. 가성비. |
| **Railway** | 빠른 시작. |
| **Fly.io** | 글로벌 분산. |
| **Vercel** | 프론트엔드·Serverless 함수 특화. |
| **Netlify** | 정적 사이트·함수. |
| **Cloudflare Pages/Workers** | 엣지 컴퓨팅. |

**장점:** 인프라 학습 부담 없음. 빠른 출시.
**단점:** 자유도 제한. 베이스 가격 비쌀 수 있음.

### 1.3 Serverless / FaaS (Function as a Service)

코드 단위로 실행. 호출될 때만 자원 사용.

| 제품 | 무엇 |
|---|---|
| AWS Lambda | 가장 흔함 |
| Cloudflare Workers | 엣지 |
| Google Cloud Functions | GCP |
| Vercel Edge Functions | Next.js 통합 |

**장점:** 사용한 만큼만 과금. 자동 확장.
**단점:** 콜드 스타트. 실행 시간 제한. 디버깅 어려움.

### 1.4 BaaS (Backend as a Service)

DB·인증·스토리지·실시간까지 포함된 백엔드.

| 제품 | 무엇 |
|---|---|
| **Supabase** | Postgres + Auth + Storage |
| **Firebase** | NoSQL + Auth + Realtime |
| **Appwrite** | 오픈소스 BaaS |
| **AWS Amplify** | AWS 의 BaaS |

**장점:** 백엔드 코드 거의 없이 출시 가능.
**단점:** 락인. 비즈니스 로직 한계.

## 2. 처음 출시 권장 옵션

### 2.1 가장 단순한 시작 — Vercel + Supabase

작은 팀·MVP·웹 서비스에 가장 빠른 시작.

| 영역 | 도구 |
|---|---|
| 프론트엔드 (Next.js) | **Vercel** |
| 백엔드 API | **Vercel Serverless Functions** 또는 **Supabase Edge Functions** |
| DB + Auth + Storage | **Supabase** |

이 조합으로 **하루 안에** 첫 배포 가능. 도메인 연결·HTTPS 자동.

### 2.2 백엔드 따로 — Render / Fly / Railway

백엔드를 컨테이너로 굴리고 싶다면:

| 영역 | 도구 |
|---|---|
| 프론트엔드 | Vercel·Netlify·Cloudflare Pages |
| 백엔드 (Docker) | **Render**·**Railway**·**Fly.io** |
| DB | Render Postgres·Neon·Supabase |
| 캐시·큐 | Render Redis·Upstash |

이 조합도 며칠 안에 배포 가능.

### 2.3 큰 클라우드 (AWS·GCP) — 언제

다음에 해당하면 큰 클라우드 검토.

- 매우 특수한 인프라 요구 (멀티 리전·VPC 격리 등).
- 큰 팀·DevOps 인력 보유.
- 규제·보안 요구사항이 강함 (금융·의료).
- 비용이 PaaS 보다 명백히 유리한 규모.

작은 팀 출시 단계에는 **거의 필요 없습니다**. 1~2년 운영 후에도 PaaS 만으로 충분한 경우가 많음.

### 2.4 옵션 비교

| 옵션 | 시작 시간 | 자유도 | 비용 (저트래픽) | 학습 |
|---|---|---|---|---|
| Vercel + Supabase | 하루 | 중 | 무료~$20 | 낮음 |
| Render + Supabase | 며칠 | 중·상 | $7~$20 | 낮음 |
| Fly.io + Postgres | 며칠 | 상 | $5~$20 | 중간 |
| AWS ECS + RDS | 1~2주 | 매우 상 | $30~$100 | 높음 |
| AWS EKS (Kubernetes) | 2주~ | 최상 | $100~ | 매우 높음 |

처음에는 **위에서 두세 번째** 옵션이 거의 항상 정답.

## 3. 컨테이너와 오케스트레이션

### 3.1 Docker — 거의 모든 곳의 표준

레슨 21 에서 다룬 Docker 이미지가 배포의 표준 단위. PaaS 들도 대부분 Docker 이미지를 받음.

### 3.2 컨테이너 한 대 vs 오케스트레이션

**컨테이너 한 대로 충분한 경우** (대부분의 출시 단계):
- 트래픽 적음.
- 단일 서비스.
- 간단한 무중단 배포.

→ Render·Fly·ECS Fargate·Cloud Run 같은 매니지드.

**오케스트레이션이 필요한 경우** (성장 후):
- 수십 개 마이크로서비스.
- 복잡한 자동 확장.
- 멀티 리전.

→ Kubernetes (EKS·GKE·AKS).

### 3.3 Kubernetes 의 함정

처음 만드는 분이 "큰 회사들이 쓰니까 우리도 Kubernetes 로" 시작하는 함정. 학습 곡선이 매우 높고, 작은 팀에 운영 부담이 큼. **자기 서비스 규모에서 정말 필요한지** 확인.

대부분의 출시 단계에서는 **Cloud Run / ECS Fargate / Render** 같은 매니지드 컨테이너 서비스가 K8s 의 모든 가치를 제공하면서 학습·운영 부담이 1/10.

## 4. 무중단 배포 패턴

새 버전을 배포할 때 사용자가 끊김 없이 이어서 쓰게 만드는 패턴들.

### 4.1 Rolling Update

기존 인스턴스를 하나씩 새 버전으로 교체. 가장 흔함.

```
[v1] [v1] [v1] [v1]    ← 시작
[v2] [v1] [v1] [v1]    ← 첫 인스턴스 교체
[v2] [v2] [v1] [v1]
[v2] [v2] [v2] [v1]
[v2] [v2] [v2] [v2]    ← 완료
```

대부분의 PaaS·Kubernetes 가 기본.

### 4.2 Blue-Green Deployment

새 환경(green) 을 통째로 띄우고, 트래픽을 한 번에 전환.

```
Blue (v1) ← 100% 트래픽
Green (v2) ← 준비 중
↓
Blue (v1) ← 0% (대기)
Green (v2) ← 100% 트래픽
```

문제 발생 시 즉시 Blue 로 전환. 인프라 비용은 잠시 두 배.

### 4.3 Canary Deployment

새 버전을 일부 트래픽에만 노출, 단계적으로 확대.

```
v1 90% / v2 10%   ← 일부에 노출
↓ 모니터링 OK
v1 50% / v2 50%
↓
v1 0% / v2 100%
```

가장 안전. 문제를 일찍 발견.

### 4.4 Feature Flag — 코드 배포와 사용자 노출 분리

코드는 배포돼 있되 사용자에겐 OFF 인 채. 플래그로 ON/OFF 조절.

자세한 내용 레슨 22 참고.

## 5. 자동 확장 (Auto Scaling)

트래픽에 따라 인스턴스 수를 자동 조절.

### 5.1 수직 vs 수평

| 종류 | 무엇 | 한계 |
|---|---|---|
| **Vertical (수직)** | 한 서버를 더 큰 것으로 | 한 대의 한계 |
| **Horizontal (수평)** | 서버 대수를 늘림 | 거의 무한 |

수평 확장이 표준. 단, 앱이 **stateless** 이어야 (세션·상태가 서버 간 공유되지 않으면 깨짐).

### 5.2 트리거

- **CPU·메모리 사용률** — 가장 흔함.
- **응답 시간** — p95 가 임계 넘으면 확장.
- **큐 길이** — 처리 대기 작업 수.
- **시간 기반** — 출퇴근 시간 미리 확장.

### 5.3 Stateless 만들기

세션·임시 파일을 메모리에 두지 말고 외부에.

| 데이터 | 어디에 |
|---|---|
| 세션 | Redis·DB·JWT |
| 업로드 파일 | S3·MinIO·R2 |
| 캐시 | Redis·CDN |
| 백그라운드 작업 | 큐 (Celery·BullMQ) |

이래야 어떤 인스턴스가 죽거나 새 인스턴스가 뜨거나 사용자 영향 없음.

## 6. 비용 관리

### 6.1 처음 출시의 현실적 비용

월 트래픽 1만 명 미만 기준 대략:

| 옵션 | 월 비용 |
|---|---|
| Vercel + Supabase 무료 | $0 |
| Render Starter + Postgres | $14~$20 |
| Fly.io + Neon | $5~$20 |
| AWS Lightsail | $10~$20 |
| AWS EC2 + RDS (직접 운영) | $30~$80 |

대부분의 MVP 는 **$20 / 월 미만** 으로 출시 가능.

### 6.2 트래픽 증가 시

월 10만 사용자 ~ 월 100만 사용자 구간에서 비용이 빠르게 증가합니다. 이 구간에서 옵션을 다시 검토 — PaaS 의 비용이 큰 클라우드보다 비싸지는 지점이 옵니다.

### 6.3 비용 폭탄 방지

처음 만드는 분이 가끔 겪는 "예상 못한 청구서" 사고.

- **AWS Free Tier 만료** — 1년 후 갑자기 청구.
- **데이터 전송 비용** — 의외로 큼 (외부로 나가는 트래픽).
- **로드 테스트 실수** — 실수로 운영에 부하 걸기.
- **무한 루프 람다** — 1초당 수천 번 실행.

대책:
- **결제 알람** — 일정 금액 넘으면 알림.
- **예산 한도 설정** — 가능하다면 자동 차단.
- **사용량 모니터링** — 매주 한 번 확인.

## 7. 자주 빠지는 함정

### 함정 1. AWS 부터 시작

학습 곡선이 매우 높고, 처음 만드는 분에게 과도. **PaaS 부터 시작**, 필요할 때 옮기기.

### 함정 2. Kubernetes 부터 시작

같은 함정. K8s 가 진짜 필요한 시점은 보통 대규모 운영 단계.

### 함정 3. 락인 무시

특정 클라우드에 너무 결합된 코드(AWS Lambda·DynamoDB 등)는 옮기기 어려움. 이식성 있는 도구(Docker·Postgres) 를 우선.

### 함정 4. 단일 장애 지점

DB 한 대만 두면 그것이 죽으면 모두 죽음. 백업·읽기 복제·다중 가용 영역(AZ) 검토.

### 함정 5. 백업 안 함

매니지드 서비스라도 자동 백업 명시 활성화. 자세한 내용 레슨 15.

### 함정 6. 환경 변수 관리 부실

운영 비밀번호가 staging 에 들어 있는 사고. 환경별 시크릿 분리.

### 함정 7. 무중단 배포 가정만 하고 검증 안 함

"무중단" 이라 광고하는 도구도 설정 잘못하면 끊김. 한 번은 staging 에서 실제 검증.

### 함정 8. Stateful 앱을 수평 확장

세션을 메모리에 둔 앱을 2대로 띄우면 사용자가 무작위로 두 서버에 분산되며 세션이 깨짐. **Stateless 필수**.

### 함정 9. 모든 것을 컨테이너에

DB 까지 직접 컨테이너로 운영하려는 함정. DB 는 매니지드 서비스가 거의 항상 정답.

### 함정 10. 인프라 코드 (IaC) 무시

수동 클릭으로 만들어진 인프라는 재현·롤백 어려움. **Terraform·Pulumi·CDK** 같은 IaC 로 코드화.

## 8. 한 셜 더

### 8.1 인프라 코드 (IaC)

인프라를 코드로 정의해 git 으로 관리.

```hcl
# Terraform 예시
resource "aws_ecs_service" "api" {
  name            = "api"
  cluster         = aws_ecs_cluster.main.id
  task_definition = aws_ecs_task_definition.api.arn
  desired_count   = 2
}
```

장점: 재현 가능·리뷰·롤백.

### 8.2 GitOps

운영 상태를 git 저장소로 표현, 자동 동기화. **ArgoCD·Flux**.

main 에 머지 → 운영 클러스터가 자동으로 그 상태로 수렴.

### 8.3 멀티 리전

지리적으로 분산된 사용자에게 빠른 응답. CDN 으로 시작, 본격 멀티 리전은 큰 운영 부담.

### 8.4 엣지 컴퓨팅

코드를 사용자 가까운 엣지 노드에서 실행. **Cloudflare Workers·Vercel Edge**. 글로벌 서비스에 효과적.

### 8.5 추가 키워드

- **Service Mesh** — 마이크로서비스 간 통신 관리 (Istio·Linkerd).
- **Observability** — 로그·메트릭·트레이스 (다음 레슨).
- **Incident Response** — 장애 대응 절차 (다음 레슨).
- **Cost Optimization** — Reserved Instance·Spot Instance.
- **Multi-Cloud** — 여러 클라우드 동시 사용.
