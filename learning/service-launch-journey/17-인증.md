# 17. 회원가입·로그인·소셜 인증

> **한 줄 요약.** 인증은 **"누구인가"** 를, 인가는 **"무엇을 할 수 있는가"** 를 결정한다. 직접 만들면 함정 30개, 외부 서비스를 쓰면 함정 5개로 줄어든다.

---

## 들어가며

거의 모든 서비스에 들어가는 기능이 **회원가입·로그인** 입니다. 동시에 가장 잘못 만들기 쉬운 영역이기도 합니다. 비밀번호를 평문 저장한다거나, 토큰을 잘못 다뤄 모든 사용자가 다른 사람으로 로그인되는 사고는 잊을 만하면 한 번씩 뉴스에 등장합니다.

이 레슨은 인증을 **안전하게**, 그리고 **가능하면 직접 만들지 않는** 방향으로 안내합니다. 0부터 만드는 것은 거의 항상 나쁜 선택입니다.

이 레슨을 다 읽으면:

- 인증(Authentication)과 인가(Authorization)의 차이를 안다.
- 비밀번호 저장의 표준 방법을 안다.
- 세션 vs JWT 의 트레이드오프를 안다.
- OAuth·소셜 로그인의 흐름을 안다.
- 외부 인증 서비스(Auth0·Clerk·Supabase Auth) 를 쓸지 직접 만들지 결정할 수 있다.

---

## 1. 핵심 개념 — 인증과 인가

### 1.1 인증 (Authentication, "AuthN")

"이 요청자가 누구인가" 를 확인. 보통 **로그인** 절차로 한 번 검증한 뒤, 이후 요청에는 그 신원을 증명하는 토큰을 첨부.

```
사용자 → [이메일/비밀번호 또는 OAuth] → 인증 통과 → 토큰 발급
사용자 → [요청 + 토큰] → 서버가 토큰 검증 → "아, 김지영이구나"
```

### 1.2 인가 (Authorization, "AuthZ")

"이 사람이 이 작업을 할 수 있는가" 를 확인.

- 김지영 씨가 자기 거래 정보를 조회 — OK
- 김지영 씨가 다른 사용자의 거래를 조회 — 거부
- 일반 사용자가 어드민 페이지 접근 — 거부

인증된 다음에 인가가 따라옵니다.

### 1.3 둘은 다른 단계

| 단계 | 결과가 없으면 응답 |
|---|---|
| 인증 | 401 Unauthorized |
| 인가 | 403 Forbidden |

상태 코드를 정확히 구분해 사용.

## 2. 비밀번호 — 절대 평문 저장 금지

### 2.1 해시 함수

비밀번호를 단방향 해시로 변환해 저장. 같은 비밀번호는 같은 해시가 되지만, 해시에서 원본을 복원할 수 없음.

**❌ 나쁜 해시:**
- MD5, SHA-1, SHA-256 — 너무 빠름. GPU로 무차별 대입 공격 가능.

**✅ 좋은 해시 (느린 해시):**
- **bcrypt** — 가장 흔히 쓰임. work factor 조정 가능.
- **argon2** — 최신 표준. 메모리·시간 모두 비용.
- **scrypt** — argon2 이전 표준.

```python
# bcrypt 예시
import bcrypt

# 저장
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt())

# 검증
bcrypt.checkpw(password.encode(), hashed)
```

### 2.2 Salt 와 Pepper

- **Salt** — 각 비밀번호마다 다른 랜덤 값. 해시 함수 자체가 자동으로 처리 (bcrypt·argon2 모두).
- **Pepper** — 모든 비밀번호에 공통으로 추가하는 비밀 값. 코드 또는 환경 변수에 저장.

bcrypt·argon2 의 기본 사용으로 salt 까지는 자동. pepper 는 선택.

### 2.3 비밀번호 정책

- **최소 길이** — 8자 이상 (NIST 권장 8~12).
- **복잡도 요구사항을 강요하지 마세요.** "특수문자 1개·대문자 1개·숫자 1개" 같은 룰은 사용자가 더 약한 비밀번호를 만들게 합니다 (예: "Password1!").
- **유출된 비밀번호 차단.** Have I Been Pwned API 등으로 흔한 유출 비밀번호를 거르기.
- **2단계 인증(2FA·TOTP) 옵션** 제공.

## 3. 세션 vs JWT — 어느 방식을 쓸까

로그인 후 토큰을 어떻게 표현하는지 두 가지 방식.

### 3.1 세션 (Session)

서버가 **세션 ID** 를 발급하고, 서버 메모리·DB·Redis 에 세션 데이터를 저장. 클라이언트는 쿠키로 세션 ID 를 들고 다님.

```
로그인 → 서버가 세션 생성 (Redis에 user_id 저장) → Set-Cookie: sid=abc123
요청 → Cookie: sid=abc123 → 서버가 Redis 조회 → user_id 발견
```

**장점:**
- 서버에서 즉시 무효화 가능 (Redis 에서 삭제).
- 토큰 자체에 정보가 없어 안전.

**단점:**
- 서버에 상태가 있음 (확장 시 공유 저장소 필요).
- 분산 서버에서 세션 공유 필요.

### 3.2 JWT (JSON Web Token)

서버가 **서명된 JSON 토큰**을 발급. 토큰 자체에 정보가 들어 있고 서버는 서명만 검증.

```
JWT 구조: header.payload.signature
{ "user_id": 123, "exp": 1714050000 }
```

**장점:**
- 무상태(stateless). 서버 메모리·DB 부하 없음.
- 마이크로서비스 간 공유 쉬움.

**단점:**
- 무효화가 어려움 (만료 전엔 항상 유효).
- 토큰이 큼 (URL·헤더에 부담).
- 잘못 다루면 보안 사고.

### 3.3 비교 표

| 항목 | 세션 | JWT |
|---|---|---|
| 저장 위치 | 서버 (Redis) | 클라이언트 |
| 무효화 | 즉시 | 어려움 |
| 확장성 | 공유 저장소 필요 | 무상태 |
| 토큰 크기 | 작음 (32바이트) | 큼 (수백 바이트) |
| 분산 시스템 | 보통 | 잘 어울림 |

### 3.4 무엇을 골라야

- **단순 웹 서비스, 같은 도메인** → 세션 + 쿠키.
- **모바일 앱·여러 도메인·마이크로서비스** → JWT.
- **금융·보안 강한 서비스** → 세션.

처음 만드는 일반 웹 서비스는 **세션**, 모바일까지 있다면 **JWT** 가 무난.

### 3.5 JWT 사용 시 필수 수칙

- **HTTPS 만 사용.** 평문 HTTP 는 토큰 도난.
- **만료 시간 짧게** (15분~1시간) + Refresh Token 별도.
- **알고리즘 명시.** `alg: none` 공격 방지. RS256 또는 ES256 권장.
- **서명 키 안전 관리.** 환경 변수·Secret Manager.
- **민감 정보는 payload 에 넣지 않음.** payload 는 서명만 됐지 암호화 안 됨.

## 4. 회원가입·로그인의 표준 흐름

### 4.1 회원가입

```
1. 사용자: 이메일·비밀번호 입력
2. 클라이언트: POST /auth/signup
3. 서버:
   a. 이메일 형식·비밀번호 강도 검증
   b. 같은 이메일 중복 검사
   c. 비밀번호 해시 (bcrypt)
   d. users 테이블에 INSERT
   e. (선택) 이메일 인증 메일 발송
4. 응답: 가입 완료 또는 이메일 인증 안내
```

### 4.2 로그인

```
1. 사용자: 이메일·비밀번호 입력
2. 클라이언트: POST /auth/login
3. 서버:
   a. 이메일로 사용자 조회
   b. bcrypt.checkpw 로 비밀번호 검증
   c. 세션 생성 OR JWT 발급
4. 응답: 토큰 (또는 Set-Cookie)
```

### 4.3 로그아웃

- **세션:** 서버에서 세션 삭제 + 쿠키 만료.
- **JWT:** 클라이언트에서 토큰 삭제. (서버 측 무효화는 블랙리스트 필요.)

### 4.4 비밀번호 재설정

```
1. 사용자: 이메일 입력
2. 서버: 임의 토큰 생성, DB 에 저장 (만료시간 30분), 이메일 발송
3. 사용자: 이메일의 링크 클릭 → /reset?token=...
4. 사용자: 새 비밀번호 입력
5. 서버: 토큰 검증 → 비밀번호 해시 갱신
```

토큰은 한 번만 쓸 수 있게.

## 5. 소셜 로그인 — OAuth 2.0

### 5.1 왜 소셜 로그인

- 사용자가 새 비밀번호를 안 만들어도 됨.
- 가입 단계가 1번 클릭으로 줄어듦 (레슨 09 의 클릭 수 줄이기).
- 카카오·구글·애플 같은 신뢰된 제공자가 인증을 담당.

### 5.2 OAuth 2.0 흐름 (Authorization Code Flow)

```
1. 사용자가 "카카오로 로그인" 버튼 클릭
2. 우리 앱 → 카카오 인증 페이지로 리다이렉트
3. 사용자가 카카오에 로그인 + 권한 동의
4. 카카오 → 우리 앱의 callback URL로 리다이렉트 (with code)
5. 우리 백엔드가 카카오 API 에 code → access_token 교환
6. 우리 백엔드가 access_token 으로 카카오에서 사용자 정보 조회
7. 우리 DB 에 사용자 생성 또는 매칭 + 세션/JWT 발급
8. 우리 앱 사용자로 로그인 완료
```

### 5.3 주요 제공자

| 제공자 | 한국 사용자 친숙도 |
|---|---|
| **카카오** | 매우 높음 |
| **네이버** | 높음 |
| **Google** | 높음 |
| **Apple** | 필수 (iOS 앱) |
| **GitHub** | 개발자 대상 서비스 |
| **Facebook** | 감소 추세 |

처음에는 **카카오 + Google** 2개로 시작하면 대부분 커버. iOS 앱이라면 Apple Sign In 필수.

### 5.4 라이브러리

| 언어 | 라이브러리 |
|---|---|
| Python | Authlib, python-social-auth |
| Node.js | NextAuth.js, Passport.js |
| Go | goth |
| 프론트엔드 | next-auth (Next.js), Auth0 SDK |

직접 OAuth flow 를 구현하지 말고 라이브러리 사용. 보안 수칙이 자동으로 챙겨집니다.

## 6. 직접 만들까, 외부 서비스를 쓸까

### 6.1 외부 인증 서비스 옵션

| 서비스 | 특징 | 가격 |
|---|---|---|
| **Auth0** | 가장 유명, 풍부한 기능 | 부분 무료 |
| **Clerk** | React·Next.js 최적, UX 좋음 | 부분 무료 |
| **Supabase Auth** | DB + Auth 통합 | 무료 시작 |
| **Firebase Auth** | Google 생태계 | 무료 시작 |
| **AWS Cognito** | AWS 통합 | 부분 무료 |
| **Keycloak** | 오픈소스 셀프 호스팅 | 무료 |

### 6.2 외부 서비스의 장단점

**장점:**
- 보안 수칙·OAuth·2FA·이메일 인증 모두 자동.
- 사용자 관리 UI 자동 제공.
- 출시 시간 단축 (며칠 → 몇 시간).

**단점:**
- 외부 의존.
- 사용자 데이터의 일부가 외부에 저장.
- 가격 (사용자 수 기반 과금이 일반).

### 6.3 권장

처음 만드는 분 + 작은 팀이라면 **외부 서비스 사용 권장**. 인증을 직접 만드는 건 거의 항상 손해입니다.

```
[권장]
  소규모 SaaS·내부 도구 → Clerk 또는 Supabase Auth
  Next.js 프로젝트 → NextAuth.js (자체 + 소셜 모두)
  AWS 환경 → Cognito
  전체 자체 운영 필요 → Keycloak
```

### 6.4 직접 만들어야 하는 경우

다음에 해당하면 직접 만드는 것을 고려.

- 외부 서비스에 데이터를 절대 보낼 수 없는 규제 환경 (금융·의료).
- 매우 특수한 인증 요구사항 (생체 인식·하드웨어 키).
- 사용자 수가 매우 많아 외부 서비스 비용이 직접 운영보다 비쌈.

## 7. 인가 (Authorization) 패턴

인증된 사용자가 **무엇을 할 수 있는가** 결정.

### 7.1 자원 소유자 검사

가장 흔한 패턴. "이 자원의 소유자가 현재 사용자인가".

```python
def get_transaction(transaction_id, current_user):
    transaction = session.get(Transaction, transaction_id)
    if transaction.user_id != current_user.id:
        raise HTTPException(403, "Forbidden")
    return transaction
```

### 7.2 역할 기반 (RBAC)

사용자에 역할을 부여 (admin·user·guest), 역할별로 권한.

```python
def is_admin_or_owner(user, resource):
    return user.role == "admin" or resource.user_id == user.id
```

### 7.3 정책 기반 (ABAC)

더 복잡한 규칙. 시간·위치·자원 속성·환경 등을 종합. 큰 시스템에 필요.

### 7.4 권장

처음에는 **자원 소유자 검사 + 간단한 RBAC** 으로 시작. 복잡해지면 정책 라이브러리(Casbin·Oso) 도입.

## 8. 자주 빠지는 함정

### 함정 1. 비밀번호 평문 저장

가장 큰 사고. 한 번 데이터 유출되면 사용자가 다른 서비스에서도 쓰는 비밀번호가 노출. **반드시 bcrypt/argon2**.

### 함정 2. JWT Secret 을 코드에 박음

GitHub 에 시크릿이 올라가면 토큰 위조 가능. 환경 변수.

### 함정 3. 만료 없는 토큰

영구 토큰은 한 번 도난당하면 영영 사용. **15분~1시간 + Refresh Token**.

### 함정 4. HTTPS 안 씀

토큰이 평문 네트워크를 흐름. **반드시 HTTPS**. 자세한 내용 레슨 24.

### 함정 5. CSRF 무시

쿠키 기반 인증에서 CSRF (Cross-Site Request Forgery) 보호 빠뜨림. SameSite 쿠키 + CSRF 토큰.

### 함정 6. 사용자 입력을 신뢰

이메일 검증·비밀번호 강도 검증을 클라이언트에서만 하고 서버는 안 함. **서버에서 다시 검증**.

### 함정 7. 같은 비밀번호 다른 해시

salt 가 자동 처리되는지 확인. bcrypt·argon2 는 자동, 직접 해시는 별도 salt 처리.

### 함정 8. 무차별 대입 공격 무대응

같은 IP·계정에서 여러 번 로그인 실패 → 일정 시간 차단 (rate limit). 미구현 시 패스워드가 약하면 뚫림.

### 함정 9. 이메일 인증 없이 가입

가짜 이메일로 가입. 이메일 발송으로 인증 토큰 클릭 후 활성화하는 단계 권장.

### 함정 10. 로그아웃 시 토큰을 안 지움

클라이언트 메모리·localStorage 에서 토큰 삭제 잊음. 다음 사용자가 같은 디바이스에서 자동 로그인.

## 9. 한 셜 더

### 9.1 2단계 인증 (2FA / MFA)

비밀번호 외에 추가 검증.

| 방식 | 보안 | 사용성 |
|---|---|---|
| **TOTP (Google Authenticator·Authy)** | 높음 | 좋음 |
| **SMS 코드** | 중간 (SIM 스왑 위험) | 매우 좋음 |
| **Hardware Key (YubiKey)** | 매우 높음 | 보통 |
| **Email OTP** | 중간 | 좋음 |

처음에는 옵션으로 TOTP 제공. 금융·관리자 계정은 강제.

### 9.2 Passkey — 비밀번호 없는 미래

WebAuthn 표준 기반. 지문·Face ID·하드웨어 키로 인증. 2024 년 이후 빠르게 확산.

iOS·Android·주요 브라우저 모두 지원. 외부 인증 서비스는 대부분 Passkey 지원 시작.

### 9.3 SSO (Single Sign-On)

한 번 로그인으로 여러 서비스 접근. 기업 내부 도구·SaaS 에 자주 쓰임. SAML·OIDC 표준.

### 9.4 OAuth 와 OpenID Connect (OIDC)

- **OAuth 2.0** — 인가 (다른 서비스에 우리 자원 접근 권한 위임).
- **OIDC** — OAuth 위에 얹은 인증 표준.

소셜 로그인은 거의 OIDC 사용.

### 9.5 추가 키워드

- **JWT Best Practices** — RFC 8725.
- **Session Hijacking** — 세션 도난.
- **Refresh Token Rotation** — 갱신 시마다 토큰 변경.
- **Device Trust** — 디바이스 단위로 신뢰 관리.
- **Just-In-Time (JIT) Provisioning** — 최초 SSO 로그인 시 자동 사용자 생성.
