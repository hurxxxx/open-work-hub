# 20. 성능·보안·시나리오 테스트

> **한 줄 요약.** 단위·통합 테스트가 "코드가 맞게 동작하는가" 라면, 성능·보안 테스트는 "**스트레스와 공격에도 견디는가**" 를 검증한다. 출시 전에 한 번씩이라도 돌려 보면 운영 첫 달의 사고 절반은 사전에 방지된다.

---

## 들어가며

레슨 19 에서 다룬 단위·통합 테스트는 **"코드의 동작 정확성"** 을 검증합니다. 그런데 정확하게 동작한다고 해서 항상 안전한 것은 아닙니다.

- 사용자가 동시에 1만 명 몰리면? 응답이 30초 걸리고 결국 죽을 수도.
- 누가 SQL Injection 으로 DB 를 통째로 다운로드하면?
- 결제 화면에서 네트워크가 끊기면? 두 번 결제되거나 돈만 빠지고 주문은 안 들어갈 수도.

이 레슨은 그 "**예외 시나리오**" 를 다루는 테스트들입니다. 처음 만드는 분이라도 출시 전에 가벼운 형태로라도 한 번 돌려 보면 큰 사고를 피할 수 있습니다.

이 레슨을 다 읽으면:

- 성능 테스트의 4종류(Load·Stress·Spike·Soak)를 안다.
- 가벼운 부하 테스트를 자기 프로젝트에 적용할 수 있다.
- OWASP Top 10 의 핵심 취약점을 안다.
- 시나리오 테스트(설치·회귀·접근성) 의 위치를 안다.
- 출시 전 점검 체크리스트를 갖춘다.

## 1. 성능 테스트

### 1.1 4가지 종류

| 종류 | 무엇 | 언제 |
|---|---|---|
| **Load** | 예상 평균 부하에서 동작 확인 | 출시 전 기본 |
| **Stress** | 한계까지 부하 증가, 어디서 깨지는지 | 한계 파악 |
| **Spike** | 갑작스런 트래픽 폭증 | 마케팅·이벤트 전 |
| **Soak (Endurance)** | 장시간 부하 (몇 시간~며칠) | 메모리 누수·점진 저하 |

처음 출시에는 **Load + Stress** 만 돌려도 충분합니다.

### 1.2 측정 지표

| 지표 | 의미 |
|---|---|
| **응답 시간 (Latency)** | 요청 → 응답까지의 시간. p50·p95·p99 로 분포 본다. |
| **처리량 (Throughput / RPS)** | 초당 처리 요청 수. |
| **에러율 (Error rate)** | 실패한 요청 비율. |
| **자원 사용량** | CPU·메모리·DB 연결 수. |

p95·p99 가 중요합니다. 평균은 좋아 보여도 95퍼센타일이 5초면 사용자 5%가 5초 기다림.

### 1.3 도구

| 도구 | 특징 |
|---|---|
| **k6** | JavaScript 시나리오, CLI, CI 통합 좋음. 권장. |
| **Locust** | Python 시나리오, 웹 UI |
| **JMeter** | GUI 기반, 가장 오래됨 |
| **Artillery** | Node.js, 간단 |
| **Gatling** | Scala, 고성능 |

### 1.4 k6 예시

```js
// loadtest.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '1m', target: 100 },  // 1분간 100명까지 증가
    { duration: '3m', target: 100 },  // 3분간 100명 유지
    { duration: '1m', target: 0 },    // 1분간 0명으로 감소
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'], // p95 응답 < 500ms
    http_req_failed: ['rate<0.01'],   // 실패율 < 1%
  },
};

export default function () {
  const res = http.get('https://staging.app.com/api/transactions', {
    headers: { Authorization: 'Bearer test-token' },
  });
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1);
}
```

```bash
k6 run loadtest.js
```

### 1.5 어떤 시나리오를 부하 테스트?

- **가장 자주 호출되는 엔드포인트** — 보통 GET 리스트.
- **결정적 순간 흐름** — 가입·로그인·결제.
- **DB 부담이 큰 쿼리** — 집계·검색.

### 1.6 결과 해석

처음 측정한 결과는 보통 다음과 같이 보입니다.

```
http_req_duration:
  avg=120ms  min=20ms  med=80ms  max=4.2s  p(95)=350ms  p(99)=2.1s

http_req_failed: 0.5%
```

p95 가 500ms 이내면 무난. p99 가 너무 크면 (예: 5초) 일부 요청에서 무엇이 막히는지 조사.

### 1.7 어디서 부하 테스트하나

**절대 운영(Production) 에 직접 부하 주지 마세요.** 진짜 사용자가 영향받습니다. **Staging 환경**에 부하.

## 2. 보안 테스트 — OWASP Top 10

OWASP(Open Web Application Security Project)이 정리하는 가장 흔한 보안 취약점 10가지. 처음 만드는 분이 알아야 할 핵심.

### 2.1 OWASP Top 10 (2021)

| # | 취약점 | 짧은 설명 |
|---:|---|---|
| A01 | **Broken Access Control** | 권한 우회. 다른 사람의 자원에 접근 |
| A02 | **Cryptographic Failures** | 암호화 미흡·평문 저장 |
| A03 | **Injection** | SQL·OS·LDAP 인젝션 |
| A04 | **Insecure Design** | 설계 단계의 결함 |
| A05 | **Security Misconfiguration** | 설정 실수 (기본 비밀번호·디버그 모드) |
| A06 | **Vulnerable Components** | 취약한 라이브러리 사용 |
| A07 | **Authentication Failures** | 인증 우회·세션 도난 |
| A08 | **Data Integrity Failures** | 무결성 검증 안 함 (CI/CD 공급망 등) |
| A09 | **Logging & Monitoring Failures** | 사고 감지 안 됨 |
| A10 | **Server-Side Request Forgery (SSRF)** | 서버를 통해 내부 자원 접근 |

### 2.2 처음 만드는 분이 챙길 7가지

이 중에서 처음 출시 전에 반드시 점검할 것들.

**1. SQL Injection (A03)**

직접 문자열 SQL 만들지 말고 ORM·파라미터 바인딩.

```python
# ❌ 위험
session.execute(f"SELECT * FROM users WHERE email = '{email}'")

# ✅ 안전
session.execute("SELECT * FROM users WHERE email = :email", {"email": email})
```

**2. XSS (Cross-Site Scripting)**

사용자 입력을 HTML 에 직접 삽입하면 스크립트가 실행될 수 있음.

```jsx
// React 는 자동 escape 됨 — 안전
<div>{userInput}</div>

// ❌ dangerouslySetInnerHTML 에 사용자 입력 — 위험
<div dangerouslySetInnerHTML={{ __html: userInput }} />
```

**3. CSRF (Cross-Site Request Forgery)**

쿠키 기반 인증 시 다른 사이트가 우리 도메인에 요청을 강제.

방어:
- `SameSite=Strict` 또는 `Lax` 쿠키.
- CSRF 토큰.
- API 요청에는 `Authorization` 헤더 사용 (자동으로 다른 사이트가 안 보냄).

**4. 권한 검사 누락 (A01)**

자기 자원만 접근 가능한지 모든 엔드포인트에서 검사.

```python
def get_transaction(transaction_id, current_user):
    transaction = session.get(Transaction, transaction_id)
    if transaction.user_id != current_user.id:
        raise HTTPException(403)  # ← 빠뜨리면 큰 사고
    return transaction
```

**5. 비밀번호·시크릿 관리**

- 비밀번호: bcrypt/argon2.
- API 키·시크릿: 환경 변수·Secret Manager.
- `.env` 파일 git 에 안 올림 (`.gitignore`).

**6. 취약한 의존성 (A06)**

라이브러리에 알려진 취약점이 있는지 자동 점검.

| 도구 | 언어 |
|---|---|
| `pip-audit` | Python |
| `npm audit` | Node.js |
| `Dependabot` | GitHub 자동 |
| `Snyk` | 다언어 |

CI 에 통합하면 PR 마다 자동 검사.

**7. 입력 검증**

서버에서 모든 입력 검증. 클라이언트만 믿지 않음. Pydantic·Zod 같은 스키마 라이브러리 활용.

### 2.3 보안 테스트 도구

| 도구 | 무엇 |
|---|---|
| **OWASP ZAP** | 자동 취약점 스캔, 무료 |
| **Burp Suite** | 수동·자동, 업계 표준 |
| **Nikto** | 웹 서버 스캔 |
| **sqlmap** | SQL Injection 자동 탐지 |
| **Trivy** | 컨테이너 이미지 취약점 |

처음에는 **OWASP ZAP** 의 자동 스캔만 한 번 돌려 봐도 큰 가치.

### 2.4 헤더 보안

응답 헤더로 추가 보안 강화.

```
Content-Security-Policy: default-src 'self'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), camera=()
```

[securityheaders.com](https://securityheaders.com) 에서 자기 사이트 점수 확인 가능.

## 3. 시나리오 테스트

### 3.1 회귀 테스트 (Regression Test)

이미 동작하던 기능이 새 변경으로 깨지지 않는지. 단위·통합 테스트가 자동 회귀 테스트 역할.

**원칙:** 한 버그가 발견되면 그 버그를 잡는 테스트를 **반드시** 추가. 같은 버그가 다시 안 나오게.

### 3.2 설치 테스트

새 환경에서 처음부터 설치해 동작하는지. 보통 다음을 점검.

- README 의 설치 절차로 깨끗한 환경에서 동작하는가
- 환경 변수가 모두 문서화되어 있는가
- 데이터베이스 초기 마이그레이션이 한 번에 적용되는가

CI 에서 매번 클린 컨테이너로 빌드·실행하는 것이 자동 설치 테스트 역할.

### 3.3 호환성 테스트

다양한 브라우저·디바이스에서 동작하는지.

| 도구 | 무엇 |
|---|---|
| BrowserStack | 클라우드 브라우저·디바이스 |
| LambdaTest | 동일 |
| Playwright | 여러 브라우저 자동 테스트 |

처음에는 **Chrome + Safari + Firefox + iOS Safari + Android Chrome** 5종 정도면 90% 커버.

### 3.4 접근성 테스트

| 도구 | 무엇 |
|---|---|
| **axe-core** | 자동 접근성 점검, 라이브러리 형태 |
| **Lighthouse** | Chrome DevTools 내장 |
| **NVDA / VoiceOver** | 스크린 리더 수동 테스트 |

자동 도구로 70% 의 문제는 잡을 수 있습니다.

### 3.5 사용자 수용 테스트 (UAT)

실제 사용자(또는 QA 팀)가 가짜 시나리오로 직접 사용. 자동화 못 하는 영역. 출시 전에 5명 정도에게 핵심 시나리오를 직접 해 보게 하면 의외의 발견이 많음.

## 4. 출시 전 점검 체크리스트

처음 출시할 때 다음 항목을 모두 확인.

### 4.1 기능

- [ ] 단위·통합 테스트 통과
- [ ] Happy Path E2E 1개 통과
- [ ] 빈 상태·로딩·에러 화면 모두 동작
- [ ] 권한 검사가 모든 엔드포인트에 있음

### 4.2 성능

- [ ] 메인 페이지 LCP < 2.5s (3G 환경)
- [ ] API p95 < 500ms (정상 부하)
- [ ] 부하 테스트 100 동시 사용자 통과

### 4.3 보안

- [ ] HTTPS 적용
- [ ] 비밀번호 bcrypt/argon2 해시
- [ ] SQL Injection·XSS·CSRF 점검
- [ ] OWASP ZAP 자동 스캔 1회
- [ ] 의존성 취약점 스캔 (npm audit / pip-audit)
- [ ] 시크릿이 코드·git 에 없음
- [ ] 보안 헤더 설정

### 4.4 운영

- [ ] 로그가 구조화되어 있음 (JSON)
- [ ] 에러 추적 도구 연결 (Sentry 등)
- [ ] 모니터링 대시보드 설정
- [ ] 알람 (장애 발생 시)
- [ ] DB 자동 백업 활성화
- [ ] 롤백 절차 문서화

### 4.5 호환성

- [ ] Chrome·Safari·Firefox 동작
- [ ] iOS Safari·Android Chrome 동작
- [ ] 화면 320px ~ 1920px 동작
- [ ] 키보드만으로 핵심 기능 도달

이 체크리스트가 모두 ✓ 이면 출시 1차 준비 완료.

## 5. 자주 빠지는 함정

### 함정 1. 출시 후에 부하 테스트

운영에서 발견되는 성능 문제는 비싼 사고. 출시 전 staging 에서.

### 함정 2. 자기 컴퓨터에서만 부하 테스트

로컬은 다른 환경에 비해 다르게 동작. 운영과 같은 환경의 staging 에서.

### 함정 3. 평균 응답 시간만 본다

평균은 좋아도 p99 가 나쁘면 일부 사용자가 고통. **분포** 를 봐야.

### 함정 4. 보안을 "전문가 영역" 으로 미루기

OWASP Top 10 의 70%는 단순한 실수. 처음 만드는 분도 챙겨야.

### 함정 5. 의존성 업데이트 안 함

라이브러리 취약점이 발표돼도 업데이트 안 하면 무용지물. 자동 의존성 업데이트 도구(Dependabot·Renovate) 활용.

### 함정 6. 운영에 디버그 모드

`DEBUG=True` 가 운영에 켜져 있으면 에러 메시지·내부 정보가 노출. 환경별 설정 확인.

### 함정 7. 부하 테스트 시나리오가 비현실적

실제로 사용자가 안 하는 행동을 테스트. 실제 사용 패턴(가입 ~ 핵심 동작)을 시나리오로.

### 함정 8. "취약점은 우리 같은 작은 서비스엔 안 와"

자동 봇이 모든 사이트를 끊임없이 스캔합니다. 작아도 표적입니다.

### 함정 9. 접근성 무시

법적 요구사항이기도 합니다. 결함이 발견되면 소송·과징금 위험.

### 함정 10. 체크리스트만 채우고 안 본다

체크박스가 ✓ 인데 실제로는 안 한 경우. 누가 한 번 더 검증.

## 6. 한 셜 더

### 6.1 카오스 엔지니어링 (Chaos Engineering)

운영 시스템에 의도적으로 장애를 주입해 회복력 확인. Netflix 의 Chaos Monkey 가 시작.

처음 만드는 서비스에는 과도하지만, 안정 단계에 들어가면 고려.

### 6.2 모의 침투 테스트 (Penetration Testing)

전문 보안 팀(또는 화이트 햇 해커) 이 실제 공격 시나리오로 점검. 금융·의료 등 규제 산업은 거의 의무.

### 6.3 Compliance — 규제 준수

- **개인정보 보호법** (한국) — 사용자 동의·암호화·파기.
- **GDPR** (EU) — 더 엄격.
- **PCI DSS** — 결제 카드 데이터.
- **HIPAA** — 의료 정보 (미국).

자기 서비스에 해당하는 규제를 미리 파악.

### 6.4 보안·성능 문화

기술이 아니라 문화의 영역. 모든 팀원이 자기 영역에서 보안·성능을 고려하는 분위기. PR 리뷰 시 습관적으로 점검 항목 묻기.

### 6.5 추가 키워드

- **CIS Benchmarks** — 시스템 보안 설정 표준.
- **SBOM (Software Bill of Materials)** — 의존성 명세.
- **Bug Bounty** — 보안 연구자에게 포상.
- **Web Application Firewall (WAF)** — 네트워크 단의 공격 차단.
- **Secrets Scanning** — git 커밋의 시크릿 자동 검출.
