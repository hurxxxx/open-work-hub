# 12. 디자인 시스템과 비주얼 설계

> **한 줄 요약.** 디자인 시스템은 "예쁜 화면을 만드는 작업" 이 아니라 **"같은 결정을 두 번 하지 않게 만드는 약속"** 이다. 색 5개·폰트 3개·간격 4단계로도 충분히 시작할 수 있다.

---

## 들어가며

지금까지 우리는 화면(레슨 08)·시나리오(레슨 09)·데이터(레슨 10)·API(레슨 11)를 차례로 잡았습니다. 회색 와이어프레임이 손에 있고, 그 뒤의 데이터·API 가 모두 정리됐습니다. 이제 마지막으로 **그 회색 와이어프레임에 색을 입히는** 작업이 남았습니다.

처음 만드는 분이 디자인 단계에서 자주 막히는 자리:

- 색을 무엇으로 잡을지 모르겠어서 며칠을 보냄.
- 폰트를 고르다가 끝이 없어서 결정을 미룸.
- 한 화면을 잘 디자인했는데 다음 화면에서 그 결정이 흩어짐.
- 디자이너가 없는 팀에서 "디자인 어떻게 하지?" 막막함.

이 모든 어색함의 원인은 같습니다. **결정을 매번 새로 하기 때문**입니다. 디자인 시스템은 그 결정을 **한 번에 모아 약속해 두고**, 다음 모든 화면이 그 약속을 자동으로 따르게 만드는 도구입니다.

이 레슨을 다 읽으면:

- 디자인 시스템의 4구성 요소(색·타이포·간격·컴포넌트) 를 안다.
- 디자이너가 없어도 처음 디자인 시스템을 만들 수 있다.
- Tailwind·Material·shadcn 같은 기성 시스템을 가져다 쓰는 법을 안다.
- 비주얼 설계의 3원칙(시각 위계·일관성·여백) 을 적용할 수 있다.
- 디자이너가 합류했을 때 어떤 산출물을 받아야 하는지 안다.

## 1. 핵심 개념 — 디자인 시스템이란

### 1.1 정의 — 시각 결정의 라이브러리

디자인 시스템은 다음을 한 곳에 모은 것입니다.

- **디자인 토큰 (tokens)** — 색·폰트·간격·둥글기 등의 값.
- **컴포넌트 (components)** — 버튼·입력·카드 같은 재사용 단위.
- **패턴 (patterns)** — 폼·다이얼로그·리스트 같은 합성 단위.
- **가이드라인** — 언제 어떤 컴포넌트를 쓰는지의 규칙.

예시:

| 토큰 | 값 |
|---|---|
| `color.primary` | `#4F46E5` |
| `color.text` | `#1F2937` |
| `font.heading` | Pretendard 700 |
| `space.md` | `16px` |
| `radius.md` | `8px` |

이런 토큰을 정해 두면 새 화면을 만들 때 "어떤 보라색을 쓸까" 를 다시 고민하지 않습니다. `color.primary` 를 쓰면 됩니다.

### 1.2 디자인 시스템이 주는 가치

| 가치 | 설명 |
|---|---|
| **일관성** | 모든 화면이 같은 색·간격을 씀 |
| **속도** | 새 화면을 빠르게 조립 |
| **유지보수** | 하나만 바꾸면 모든 화면이 바뀜 |
| **협업** | 디자이너·개발자가 같은 단어로 대화 |

### 1.3 처음에는 작게 시작

대기업 같은 대규모 디자인 시스템 (Material, Polaris, Carbon) 을 처음부터 만들려고 하면 출시가 영영 미뤄집니다. **작게 시작해서 키우세요.**

처음 출시 시 충분한 디자인 시스템 규모:

- 색 5~7개
- 폰트 패밀리 1개, 사이즈 5단계
- 간격 4단계
- 둥글기 3단계
- 컴포넌트 5~8개 (버튼·입력·카드·모달·네비)

이 정도면 시작에 충분. 운영하며 필요한 것을 추가.

## 2. 실무 흐름 — 4구성 요소 결정 절차

### 구성 1. 색 (Color)

**1단계: 메인 색상 1개 결정 (15분)**

서비스의 정체성을 한 색으로 표현한다면 무엇일지. 이 한 색이 가장 중요합니다.

| 분위기 | 후보 색 |
|---|---|
| 신뢰·안정 | 파랑 |
| 친근·따뜻 | 주황·노랑 |
| 차분·고급 | 검정·진한 보라 |
| 자연·건강 | 초록 |
| 열정·에너지 | 빨강 |
| 창의·놀이 | 분홍·민트 |

가치 제안의 톤과 어울리는 색을 고릅니다. 이 색이 **primary** 입니다.

**2단계: 보조 색상 + 중립 색상 (15분)**

| 역할 | 예시 |
|---|---|
| Primary | `#4F46E5` (보라) |
| Secondary (선택) | `#10B981` (초록) — 강조 |
| Success | `#22C55E` (성공) |
| Warning | `#F59E0B` (주의) |
| Error | `#EF4444` (실패) |
| Background | `#FFFFFF` (밝은 모드) / `#0F172A` (다크) |
| Text — primary | `#1F2937` |
| Text — secondary | `#6B7280` |
| Border | `#E5E7EB` |

이 정도가 처음 출시 시 충분합니다.

**색 선택 도구:**
- [coolors.co](https://coolors.co) — 팔레트 추천
- [colorhunt.co](https://colorhunt.co) — 사례 모음
- [Tailwind 기본 팔레트](https://tailwindcss.com/docs/colors) — 검증된 50~900 단계

**3단계: 명도 단계 (Tints/Shades)**

각 색의 흐림·진함 단계를 미리 만들어 둡니다. Tailwind 의 50~900 단계가 좋은 참고입니다.

```
primary-50:  매우 밝음 (배경)
primary-500: 기본 (메인 사용)
primary-700: 어두움 (호버 상태)
primary-900: 매우 어두움 (강조)
```

### 구성 2. 타이포그래피 (Typography)

**1단계: 폰트 패밀리 1~2개 (10분)**

한국어 서비스라면:

| 폰트 | 무료 | 특징 |
|---|---|---|
| **Pretendard** | ✓ | 가장 무난, 모든 굵기 지원 |
| **Noto Sans KR** | ✓ (Google Fonts) | 표준적, 안정적 |
| **Spoqa Han Sans Neo** | ✓ | 깔끔함, 산세리프 |
| **NanumSquareNeo** | ✓ | 모던 |

**Pretendard** 가 가장 무난한 첫 선택입니다. 한 폰트만 써도 충분.

**2단계: 사이즈 단계 (10분)**

| 이름 | 크기 | 용도 |
|---|---|---|
| `xs` | 12px | 캡션, 보조 |
| `sm` | 14px | 본문 작은 |
| `base` | 16px | 본문 기본 |
| `lg` | 18px | 강조 본문 |
| `xl` | 20px | 소제목 |
| `2xl` | 24px | 제목 |
| `3xl` | 32px | 큰 제목 |

**3단계: 굵기 (Weight)**

| 굵기 | 용도 |
|---|---|
| 400 (Regular) | 본문 |
| 500 (Medium) | 약한 강조 |
| 700 (Bold) | 제목·강한 강조 |

이 정도가 시작에 충분.

### 구성 3. 간격 (Spacing)

여백·간격을 4~6 단계로 정합니다.

| 이름 | 크기 | 용도 |
|---|---|---|
| `xs` | 4px | 매우 좁은 |
| `sm` | 8px | 좁은 |
| `md` | 16px | 기본 |
| `lg` | 24px | 넓은 |
| `xl` | 32px | 매우 넓은 |
| `2xl` | 48px | 섹션 사이 |

이 단계만 쓰고 임의의 13px·19px 같은 값은 쓰지 않습니다. **일관된 리듬**이 만들어집니다.

### 구성 4. 컴포넌트 (Components)

처음 만들 5~8개:

| 컴포넌트 | 용도 |
|---|---|
| **Button** | 기본·보조·위험 (Primary·Secondary·Danger) |
| **Input** | 텍스트 입력 |
| **Card** | 정보 카드 |
| **Modal / Dialog** | 팝업 |
| **Top Navigation** | 상단 메뉴 |
| **List Item** | 리스트 한 줄 |
| **Toast / Snackbar** | 일시 알림 |
| **Empty State** | 빈 상태 |

각 컴포넌트마다 다음을 결정:

- 기본 상태
- 호버·포커스·활성 상태
- 비활성·로딩 상태
- 사이즈 변형 (small·medium·large)

## 3. 기성 시스템 — 처음부터 직접 만들지 말 것

처음 만드는 분이라면 디자인 시스템을 0부터 만들지 말고 **기성 시스템을 가져다 쓰세요**. 시간을 1개월 절약합니다.

### 3.1 무료·오픈소스

| 시스템 | 무엇 | 적합한 상황 |
|---|---|---|
| **Tailwind CSS + Tailwind UI** | 유틸리티 클래스 + 기본 컴포넌트 | 빠른 시작, 커스텀 자유 |
| **shadcn/ui** | 코드 복사형 React 컴포넌트 | React 프로젝트, 커스텀 자유 |
| **Material UI (MUI)** | Google 스타일 컴포넌트 라이브러리 | 익숙한 느낌, 한국 사용자에 친숙 |
| **Chakra UI** | 접근성 좋은 React 컴포넌트 | 빠른 프로토타입 |
| **Ant Design** | B2B 에 자주 쓰이는 컴포넌트 | 어드민·대시보드 |
| **DaisyUI** | Tailwind 기반 컴포넌트 | 가벼움 |

처음에는 **shadcn/ui + Tailwind** 가 자유도와 속도의 균형이 가장 좋습니다.

### 3.2 모바일

| 시스템 | 적합한 상황 |
|---|---|
| **iOS Human Interface Guidelines** | iOS 네이티브 |
| **Material Design** | Android 네이티브 |
| **React Native Paper** | RN 크로스 플랫폼 |
| **Flutter Material/Cupertino** | Flutter |

### 3.3 사용 패턴

기성 시스템을 가져다 쓰되, **자기 토큰만 덮어 씁니다**.

```ts
// tailwind.config.ts
export default {
  theme: {
    extend: {
      colors: {
        primary: {
          50: '#EEF2FF',
          500: '#4F46E5',
          700: '#3730A3',
        },
      },
      fontFamily: {
        sans: ['Pretendard', 'system-ui', 'sans-serif'],
      },
    },
  },
};
```

이 한 파일이 우리 디자인 시스템의 모든 토큰을 정의합니다.

## 4. 비주얼 설계의 3원칙

기성 시스템을 가져왔어도 화면을 잘 만들기 위한 시각 원칙은 알아 두어야 합니다.

### 원칙 1. 시각 위계 (Visual Hierarchy)

화면의 **가장 중요한 한 가지가 시각적으로도 가장 두드러져야** 합니다.

도구:
- **크기** — 큰 글씨가 더 중요해 보임.
- **색** — 채도 높은 색이 더 눈에 띔.
- **위치** — 위·왼쪽이 더 먼저 읽힘.
- **여백** — 주변에 여백이 많을수록 더 두드러짐.

❌ 모든 버튼이 같은 색·크기 → 사용자가 어디를 눌러야 할지 모름.
✅ 주된 CTA 만 진한 색·큰 크기 → 자연스럽게 거기로 시선이 감.

### 원칙 2. 일관성 (Consistency)

비슷한 요소는 비슷하게 보여야 합니다.

- 모든 버튼이 같은 둥글기.
- 모든 카드가 같은 그림자.
- 모든 본문이 같은 간격.

이게 디자인 시스템의 토큰이 만들어 주는 가치입니다.

### 원칙 3. 여백 (Whitespace)

처음 만드는 분이 가장 자주 빠뜨리는 것이 여백입니다. **여백은 비어 있는 공간이 아니라 콘텐츠를 돋보이게 하는 도구** 입니다.

- 본문 양옆에 충분한 여백 → 읽기 편함.
- 카드 사이에 여백 → 각 카드가 독립적으로 보임.
- 섹션 사이에 큰 여백 → 시선이 다음 섹션으로 자연스럽게.

이론보다 잘 만든 서비스를 자세히 보세요. 거의 항상 여백이 풍부합니다.

## 5. 디자이너와 협업 — 산출물 체크리스트

디자이너와 함께 일한다면 다음 산출물을 받아야 개발이 매끄럽습니다.

### 5.1 디자인 시스템

- 토큰(색·폰트·간격·둥글기) 명세
- 컴포넌트 라이브러리 (Figma 컴포넌트)
- 다크 모드 변형 (해당 시)

### 5.2 화면 시안

- 모든 핵심 화면의 고충실도 시안
- 빈 상태·로딩·에러 변형
- 모바일·태블릿·PC 변형 (반응형)

### 5.3 인터랙션 명세

- 호버·클릭·포커스 상태
- 전환 애니메이션
- 페이지 이동 효과

### 5.4 에셋 (Assets)

- 로고 (벡터 + PNG)
- 아이콘 세트
- 일러스트 (빈 상태용)
- 이미지 가이드라인

### 5.5 핸드오프

- Figma 의 Inspect 모드 또는 Zeplin
- 개발자가 픽셀 값·색·폰트를 직접 가져갈 수 있는 형태

## 6. 자주 빠지는 함정

### 함정 1. 색·폰트에 며칠을 쓴다

처음 결정에 너무 시간을 쓰면 출시가 미뤄집니다. **색 5개·폰트 1개** 1시간에 결정하고 시작. 안 어울리면 나중에 바꾸면 됩니다.

### 함정 2. 디자인 시스템부터 완벽하게 만든다

50개 컴포넌트·100개 토큰을 미리 만들려는 함정. **필요한 만큼만** 만들고 운영하며 키우세요.

### 함정 3. 기성 시스템을 너무 많이 커스터마이징

shadcn 가져와 놓고 모든 컴포넌트를 다 뜯어고치면, 차라리 처음부터 만드는 게 빠릅니다. **기성을 70~80% 그대로 쓰고, 토큰만 덮기.**

### 함정 4. 모바일·PC 한쪽만 디자인

요즘 사용자는 두 환경을 모두 씁니다. 모바일을 먼저 디자인하고 PC 로 확장 (반응형). 자세한 내용은 레슨 18.

### 함정 5. 다크 모드를 처음부터 신경

다크 모드는 출시 후 추가해도 늦지 않습니다. 첫 출시에 다크 모드까지 만들면 시간이 두 배. **밝은 모드 먼저, 안정화 후 다크.**

### 함정 6. 디자이너 없는데 욕심을 낸다

작은 팀에 디자이너가 없으면 기성 시스템에 의존하세요. **shadcn + Tailwind + 무료 아이콘 (Lucide·Phosphor)** 조합으로 충분히 시작 가능.

### 함정 7. 색을 RGB 로 직접 쓴다

`#4F46E5` 같은 값을 화면에 직접 박지 말고 **토큰** 으로. `bg-primary-500` 같은 식. 나중에 색을 한 번에 바꿀 수 있어야 합니다.

### 함정 8. 일러스트·이미지에 너무 많은 시간

빈 상태에 직접 그린 일러스트를 쓰려고 며칠 보내는 함정. **무료 일러스트 라이브러리** ([Storyset](https://storyset.com), [unDraw](https://undraw.co)) 또는 단순한 아이콘으로 시작.

## 7. 한 셜 더

### 7.1 Atomic Design

브래드 프로스트의 컴포넌트 분류 방법론. 디자인 시스템을 다음 단계로 분해:

- **Atoms** — 가장 작은 단위 (버튼·입력 한 칸)
- **Molecules** — Atom 의 조합 (검색 폼)
- **Organisms** — Molecule 의 조합 (헤더 전체)
- **Templates** — 페이지 뼈대
- **Pages** — 실제 데이터가 들어간 페이지

처음에는 Atom·Molecule 정도만 명확하면 충분합니다.

### 7.2 접근성 (Accessibility, A11y)

색만 가지고 정보를 전달하면 색맹·시각 장애 사용자가 못 알아챕니다. 텍스트·아이콘과 함께 표현하세요.

기본 점검:
- 본문과 배경의 명도 대비 4.5:1 이상.
- 클릭 가능 영역 최소 44px × 44px.
- 폼 입력에 라벨.
- 키보드만으로 모든 기능 도달 가능.

### 7.3 디자인 토큰 표준화

W3C Design Tokens Community Group 이 만드는 표준이 있습니다 (`design-tokens.json`). 토큰을 표준 형식으로 적어 두면 Figma·코드·문서 사이에서 자동 동기화 가능.

규모가 커지면 고려할 만하지만, 처음에는 Tailwind config 같은 단일 정의로 충분.

### 7.4 추가 키워드

- **Style Guide** — 디자인 시스템의 가벼운 형태.
- **Pattern Library** — 컴포넌트의 사용 패턴 모음.
