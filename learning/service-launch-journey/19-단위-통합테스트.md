# 19. 단위·통합 테스트

> **한 줄 요약.** 테스트는 "버그를 잡는 일" 이 아니라 **"코드를 안심하고 바꿀 수 있는 자유"** 를 만드는 일이다. 단위 5개·통합 2개 정도라도 시작하면, 출시 후 한 달 만에 그 가치를 깨닫는다.

---

## 들어가며

처음 만드는 분들에게 테스트는 종종 "여유 있을 때 추가하는 것" 으로 미뤄집니다. 출시까지 시간이 빠듯하니 일단 동작하는 것이 우선처럼 느껴집니다. 그런데 막상 출시 후 한 달이 지나면 같은 사람들이 거의 예외 없이 같은 후회를 합니다.

> "처음에 작은 테스트라도 깔아 둘 걸. 지금은 어디를 고쳐도 다른 데가 깨질까봐 무섭다."

테스트가 없으면 코드는 살아 있으되, **변경할 수 없는 박물관**이 됩니다. 작은 버튼 색을 바꾸는 것조차 위험한 결정이 됩니다.

이 레슨은 처음 만드는 분이 "여유 없이도" 도입할 수 있는 **최소한의 테스트 세트** 를 안내합니다. 거대한 테스트 피라미드를 처음부터 갖추는 게 아니라, 단위 5개·통합 2개로 시작해 점진적으로 키우는 길.

이 레슨을 다 읽으면:

- 단위·통합·E2E 테스트의 차이를 안다.
- 테스트 피라미드의 권장 비율을 안다.
- 처음 도입할 5개 단위·2개 통합 테스트를 자기 프로젝트에 적용할 수 있다.
- 무엇을 테스트하고 무엇을 안 할지 결정할 수 있다.
- CI 에 테스트를 자동 실행시키는 큰 그림을 안다.

## 1. 핵심 개념 — 테스트의 3계층

### 1.1 단위 테스트 (Unit Test)

함수 하나·클래스 하나·작은 모듈 하나가 **혼자서** 기대대로 동작하는지 검증.

```python
def test_calculate_discount():
    assert calculate_discount(price=10000, percent=10) == 9000
    assert calculate_discount(price=0, percent=10) == 0
```

특징:
- 빠름 (밀리초).
- 외부 의존 없음 (DB·네트워크 없음).
- 작은 단위 → 실패 시 원인이 명확.

### 1.2 통합 테스트 (Integration Test)

여러 모듈이 함께 동작하는지 검증. 보통 **DB·외부 API 까지 포함**.

```python
def test_create_transaction_via_api(client, db, user):
    response = client.post(
        "/transactions",
        json={"card_id": 1, "amount": 4500, "merchant": "스벅"},
        headers={"Authorization": f"Bearer {user.token}"},
    )
    assert response.status_code == 201
    assert db.query(Transaction).count() == 1
```

특징:
- 단위 테스트보다 느림 (수십 ms~수 초).
- 시나리오 단위로 작성.
- 모듈 사이 계약을 검증.

### 1.3 E2E 테스트 (End-to-End)

실제 브라우저·앱을 띄워 사용자처럼 동작.

```ts
// Playwright 예시
test('user can sign up and create transaction', async ({ page }) => {
  await page.goto('/signup');
  await page.fill('[name=email]', 'test@example.com');
  await page.fill('[name=password]', 'password123');
  await page.click('button:has-text("가입")');
  // ...
});
```

특징:
- 가장 느림 (초~분).
- 실제 사용자 경험에 가장 가까움.
- 깨지기 쉬움 (UI 변경에 민감).

### 1.4 테스트 피라미드

흔히 권장되는 비율:

```
    [E2E]       ← 5~10%
   [통합]      ← 20~30%
  [단위]       ← 60~70%
```

- 단위 테스트가 가장 많고 빠름.
- E2E 는 적게, 가장 중요한 흐름만.

처음 만드는 분이라면 **단위 5개·통합 2개·E2E 1개** 정도로 시작.

## 2. 무엇을 테스트하고 무엇을 안 할까

### 2.1 테스트할 것

| 범주 | 예시 |
|---|---|
| **비즈니스 로직** | 할인 계산·정산·권한 검사 |
| **버그가 한 번 났던 자리** | 같은 버그 재발 방지 (regression test) |
| **계산·변환 함수** | 날짜 포맷·금액 계산·정규식 |
| **API 엔드포인트** | 주요 시나리오의 요청·응답 |
| **결제·인증** | 실패하면 큰 사고 |

### 2.2 테스트 안 할 것

| 범주 | 이유 |
|---|---|
| **자명한 코드** | `getter`/`setter`·단순 props 전달 |
| **외부 라이브러리 자체** | React·Express 가 동작하는지 검증 |
| **임시 코드** | 한 번 쓰고 버리는 스크립트 |
| **순수 UI 디테일** | 색·간격·폰트 (디자인 검토로) |

### 2.3 100% 커버리지의 함정

테스트 커버리지는 의미 있는 지표지만 100% 는 함정입니다. 자명한 코드까지 다 테스트하면 변경 비용만 늘어남. 권장:

- **백엔드 비즈니스 로직: 70~80%**
- **프론트엔드 비즈니스 로직: 50~60%**
- **유틸·계산 함수: 90% 이상**

## 3. 처음 도입할 5개 단위 + 2개 통합

처음 출시할 때 권장하는 최소 세트.

### 3.1 단위 테스트 5개

다음 5가지 영역에서 각 1개씩.

**1. 핵심 비즈니스 로직** — 가장 중요한 계산·결정 로직.

```python
def test_split_amount_between_couple():
    couple = Couple(members=[user_a, user_b])
    result = split(couple, amount=10000)
    assert result == {user_a.id: 5000, user_b.id: 5000}
```

**2. 권한 검사** — "이 사용자가 이 자원에 접근 가능한가".

```python
def test_user_cannot_access_other_couples_transaction():
    transaction = make_transaction(couple_id=1)
    user = make_user(couple_id=2)
    assert can_view(user, transaction) is False
```

**3. 입력 검증** — 잘못된 입력이 거부되는지.

```python
def test_create_transaction_rejects_negative_amount():
    with pytest.raises(ValidationError):
        CreateTransactionInput(amount=-100, merchant="x")
```

**4. 시간·날짜 처리** — 거의 항상 함정이 숨음.

```python
def test_dashboard_summary_uses_user_timezone():
    summary = build_summary(user_tz="Asia/Seoul", utc_transactions=...)
    assert summary.month == "2026-04"  # KST 기준
```

**5. 변환·포맷팅** — 금액·날짜 표시.

```python
def test_format_currency_korean():
    assert format_currency(12345) == "12,345원"
```

### 3.2 통합 테스트 2개

**1. Happy Path 한 시나리오** — 가장 핵심적인 사용자 흐름.

```python
def test_couple_can_share_and_view_transaction(client, db):
    # 가입·초대·연결·거래 생성·정산 화면 조회
    user_a = signup(client, "a@example.com")
    couple = create_couple(client, user_a)
    code = create_invitation(client, user_a, couple)

    user_b = signup(client, "b@example.com")
    accept_invitation(client, user_b, code)

    create_transaction(client, user_a, amount=10000, merchant="스벅")

    summary_a = get_summary(client, user_a)
    summary_b = get_summary(client, user_b)

    assert summary_a == summary_b  # 둘이 같은 화면을 본다
    assert summary_a.total == 10000
```

**2. 인증 실패 케이스** — 토큰 없거나 만료됐을 때.

```python
def test_protected_endpoint_returns_401_without_token(client):
    response = client.get("/transactions")
    assert response.status_code == 401
```

이 7개만 있어도 출시 후의 큰 사고를 거의 막습니다.

## 5. 테스트의 구조 — AAA 패턴

좋은 테스트는 다음 3단계로 구성됩니다.

```
Arrange   ← 준비 (테스트 데이터·환경 설정)
Act       ← 실행 (테스트 대상 호출)
Assert    ← 검증 (기대 결과 확인)
```

```python
def test_split_amount():
    # Arrange
    couple = Couple(members=[user_a, user_b])

    # Act
    result = split(couple, amount=10000)

    # Assert
    assert result == {user_a.id: 5000, user_b.id: 5000}
```

이 구조를 지키면 테스트가 읽기 쉬움.

### 5.1 한 테스트 = 한 가지

한 테스트에 여러 검증을 몰아넣지 마세요. 실패 시 원인 파악이 어려움. 한 테스트는 한 시나리오의 한 측면.

### 5.2 좋은 테스트 이름

테스트 이름이 곧 명세입니다.

```python
# 나쁨
def test_user(): ...

# 좋음
def test_user_cannot_access_other_couples_transaction(): ...
def test_signup_rejects_duplicate_email(): ...
```

이름만 봐도 무엇을 검증하는지 알 수 있어야.

## 6. 테스트 픽스처와 모킹

### 6.1 픽스처 (Fixture)

테스트마다 반복되는 준비 작업을 분리.

```python
# pytest fixture
@pytest.fixture
def user(db):
    user = User(email="test@example.com")
    db.add(user)
    db.commit()
    return user

def test_user_creates_transaction(user, client):
    # user 가 자동으로 준비됨
    ...
```

### 6.2 모킹 (Mocking) — 외부 의존 가짜로

테스트에서 외부 API·시간·랜덤을 가짜로 대체.

```python
def test_send_welcome_email(mocker):
    mock_send = mocker.patch("app.email.send")
    welcome_user(user)
    mock_send.assert_called_once_with(user.email, "환영합니다")
```

### 6.3 진짜 DB vs 인메모리

| 방식 | 장점 | 단점 |
|---|---|---|
| **진짜 DB** (테스트용 Postgres) | 운영과 같은 동작 | 느림 |
| **인메모리** (SQLite) | 빠름 | 운영 DB 와 미묘한 차이 |
| **모킹** | 매우 빠름 | 진짜 동작 검증 안 됨 |

권장: 단위 테스트는 모킹·인메모리, 통합 테스트는 진짜 DB. **Testcontainers** 같은 도구로 Docker Postgres 를 테스트마다 띄우는 패턴이 표준화되고 있음.

## 7. CI 통합 — 자동 실행

테스트는 **PR 마다 자동 실행** 되어야 가치가 있습니다. 사람이 수동으로 돌리면 까먹습니다.

### 7.1 GitHub Actions 예시

```yaml
# .github/workflows/test.yml
name: Test
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install -r requirements.txt
      - run: pytest
```

### 7.2 실패 시 머지 차단

GitHub repo 설정에서 "Status check 통과해야 머지 가능" 옵션 켜기. 실패한 테스트가 main 에 들어가지 않도록.

### 7.3 병렬 실행

테스트 수가 많아지면 병렬 실행으로 시간 단축.

```bash
pytest -n auto  # pytest-xdist
```

## 8. 자주 빠지는 함정

### 함정 1. "다음에 추가하자"

다음에는 안 추가됩니다. 첫 PR 부터 같이 추가하는 습관.

### 함정 2. 테스트가 너무 깨지기 쉬움

코드의 사소한 변경에 테스트가 줄줄이 깨지면 변경 비용이 커서 결국 테스트를 지움. 테스트는 **결과**를 검증하지 **구현**을 검증하면 안 됨.

### 함정 3. 픽스처가 너무 복잡

10단계 픽스처가 필요한 테스트는 코드 자체에 문제가 있을 수 있음. 함수가 너무 큰 의존을 받고 있을 가능성.

### 함정 4. Mock 만 가득

모든 외부 의존을 모킹하면 진짜 동작이 안 검증됨. **단위는 모킹, 통합은 진짜로**.

### 함정 5. 테스트 안에 무작위·시간

`Math.random()`·`datetime.now()` 가 테스트마다 다른 값 → flaky 테스트 (가끔 실패). 시간·랜덤은 의존성 주입으로 고정.

### 함정 6. 한 테스트가 다음 테스트에 영향

한 테스트가 DB 에 데이터를 남기고, 다음 테스트가 그것에 영향을 받음. 각 테스트는 **격리**되어야. 테스트마다 트랜잭션 롤백 또는 클린업.

### 함정 7. 커버리지 100% 강박

모든 줄을 테스트하면 변경 비용 폭증. 비즈니스 로직 위주.

### 함정 8. CI 없이 로컬만

로컬에서만 돌아가는 테스트는 시간이 지나면 안 굴러감. CI 자동화 필수.

### 함정 9. E2E 만 잔뜩

E2E 는 느리고 깨지기 쉬움. 너무 많이 쌓이면 PR 한 번이 30분씩 걸림. 단위·통합 위주.

### 함정 10. "테스트 짤 시간이 없어"

이건 함정의 함정입니다. 테스트가 없으면 변경 비용이 점점 커져서 **결국 더 많은 시간**이 듭니다. 5개라도 시작.

## 9. 한 셜 더

### 9.1 TDD (Test-Driven Development)

테스트를 먼저 쓰고, 그 테스트가 통과하도록 코드를 짜는 방식. 익숙해지면 디자인이 자연스럽게 좋아집니다. 처음에는 어색할 수 있으니 작은 함수부터 시도.

```
Red → Green → Refactor
실패하는 테스트 → 통과시키기 → 정리
```

### 9.2 BDD (Behavior-Driven Development)

테스트를 자연어에 가깝게 적는 스타일.

```python
# given_when_then 패턴
def test_when_user_signs_up_with_existing_email_then_returns_409():
    # given
    existing = make_user(email="a@example.com")
    # when
    response = client.post("/signup", json={"email": "a@example.com", ...})
    # then
    assert response.status_code == 409
```

### 9.3 Property-Based Testing

수많은 무작위 입력으로 테스트. Hypothesis (Python)·fast-check (JS).

```python
@given(amount=integers(min_value=0, max_value=10**9))
def test_split_is_total_preserving(amount):
    result = split(couple, amount=amount)
    assert sum(result.values()) == amount
```

### 9.4 Contract Testing

마이크로서비스 환경에서 서비스 간 계약 검증. Pact 가 대표 도구.

### 9.5 추가 키워드

- **Snapshot Testing** — 출력의 스냅샷을 저장해 변경 감지.
- **Mutation Testing** — 코드를 일부러 바꿔 테스트가 잡는지 확인.
- **Visual Regression** — UI 의 픽셀 차이 감지.
- **Performance Testing** — 응답 시간·처리량 측정 (다음 레슨).
- **Chaos Engineering** — 의도적 장애 주입.
