# AI-DO PMS MVP PRD

## 1. 문서 개요

### 1.1 제품명

**AI-DO PMS**

### 1.2 문서 목적

본 문서는 AI-DO 내부 업무 포털 안에서 동작하는 **경량 프로젝트 관리 도구(PMS)** MVP의 요구사항을 정의한다.

제품 방향은 아래 두 가지를 결합한다.

- `Linear` 스타일의 빠르고 낮은 인지부하 UX
- `Jira`의 최소 구조만 가져온 가벼운 실행 관리 기능

이 문서는 독립 SaaS를 설계하기 위한 문서가 아니라, **AI-DO 포털의 PMS 도메인**을 정의하기 위한 문서다.

### 1.3 배경

기존 전통적 PM 툴은 기능이 많고 설정이 복잡해 초기 도입 비용이 높다. 반면 지나치게 단순한 보드형 툴은 프로젝트 단위 관리, 책임자 지정, 이력 추적, 대시보드 확인이 부족하다.

AI-DO PMS는 먼저 **실제 프로젝트 운영에 필요한 핵심 관리 기능**을 안정적으로 제공해야 하며, 복잡한 고급 PM 제품군의 기능은 이후 단계적으로 확장한다.

또한 백엔드는 표준화된 REST API와 일관된 CLI를 중심으로 설계하여, 향후 사람뿐 아니라 자동화 스크립트나 에이전트 클라이언트도 같은 인터페이스로 프로젝트 관리를 수행할 수 있어야 한다.

향후 AI-DO 챗봇이 PMS 데이터에 접근하더라도, 별도 비공개 경로가 아니라 **동일한 PMS API 계층**을 통해 조회와 변경을 수행할 수 있어야 한다.

### 1.4 제품 목표

- 팀이 **10분 내 프로젝트를 생성**하고 첫 작업을 등록할 수 있어야 한다.
- 사용자는 **리스트/보드 중심 UI**에서 업무를 빠르게 확인하고 수정할 수 있어야 한다.
- 프로젝트 단위로 상태, 담당자, 우선순위, 라벨, 댓글, 활동 내역을 추적할 수 있어야 한다.
- 관리자는 대시보드에서 프로젝트 상태를 간단히 파악할 수 있어야 한다.
- REST API는 일관된 리소스 구조, 필터, 정렬, 페이지네이션을 제공해야 한다.
- CLI는 주요 프로젝트/이슈 작업을 API와 동일한 개념으로 실행할 수 있어야 한다.

### 1.5 비목표

MVP 범위에서 아래 기능은 제외한다.

- Wiki 기능
- 문서관리/문서개정 관리
- 제조업 전용 프로젝트 모델
- AI 기반 제안 기능
- 고급 권한 정책(RBAC 세분화)
- 커스텀 워크플로우 빌더
- 간트 차트
- 자동화 룰 엔진
- 스프린트/사이클 운영
- 외부 연동(Slack, GitHub, Figma 등)
- 고급 리포팅 및 예측 분석
- 다중 조직 간 협업
- 파일 첨부 대용량 처리

### 1.6 향후 확장 방향

다음 항목은 중요하지만 이번 MVP에서 바로 풀지 않는다.

- 제조업 내부 프로젝트 확장
- 문서관리/위키 기능의 별도 도메인화
- 승인 체계 고도화
- 부서/프로세스별 세부 워크플로우
- 에이전트/자동화 클라이언트 고도화

즉, 이번 PMS MVP는 **현대적인 프로젝트 관리 도구의 핵심 기능을 먼저 구현하는 1단계**에 집중한다.

## 2. 타깃 사용자

### 2.1 주요 사용자군

1. **프로젝트 리드 / PM**

   - 프로젝트 생성 및 운영
   - 우선순위 조정
   - 전체 진행 상황 확인

2. **실무 담당자**

   - 본인 할당 작업 확인
   - 상태 변경
   - 댓글 작성
   - 작업 업데이트

3. **관리자 / 의사결정자**

   - 프로젝트 현황 확인
   - 지연/우선순위 높은 작업 파악

### 2.2 핵심 사용 시나리오

- 프로젝트 리드가 프로젝트를 생성한다.
- 팀원들이 프로젝트에 참여해 작업을 등록하고 담당자를 지정한다.
- 작업은 상태별로 보드/리스트에서 관리된다.
- 팀원은 댓글과 활동 로그를 통해 변경 이력을 확인한다.
- 리드는 대시보드에서 프로젝트 진행률과 우선순위 높은 작업을 확인한다.
- 웹 UI와 CLI는 동일한 PMS 개념 모델을 사용한다.

## 3. 제품 원칙

### 3.1 UX 원칙

- 빠른 탐색: 주요 동작은 1~2 클릭 안에 가능해야 한다.
- 낮은 인지부하: 화면 요소는 최소화하고 정보 위계를 명확히 한다.
- 키보드 친화성: 이후 확장성을 고려해 단축키 적용이 쉬운 구조로 설계한다.
- 즉각적 피드백: 상태 변경, 저장, 댓글 등록 시 즉각 반영한다.

### 3.2 기능 원칙

- PMS는 AI-DO 포털 내부 도메인으로 동작한다.
- 핵심 데이터는 **Project > Work Item** 구조로 관리한다.
- MVP에서 사용자 노출 용어는 `Issue`를 사용하지만, 내부 구조는 향후 확장을 고려해 `Work Item`으로 설계할 수 있어야 한다.
- 사용자는 작업 단위로 일하고, 관리자는 프로젝트 단위로 본다.
- 모든 핵심 변경은 최소한의 Activity Log에 기록한다.

### 3.3 API / CLI 원칙

- 백엔드는 **resource-first REST API**로 설계한다.
- API 리소스는 예측 가능한 경로와 명확한 명사 구조를 사용한다.
- 목록 API는 기본적으로 필터, 정렬, 페이지네이션을 지원해야 한다.
- 동일한 도메인 동작은 웹 UI와 CLI가 같은 개념 모델을 공유해야 한다.
- CLI는 별도 우회 로직이 아니라 API 클라이언트 성격으로 설계하는 것을 원칙으로 한다.
- 향후 자동화 도구나 에이전트가 붙더라도 별도 전용 인터페이스 없이 API/CLI로 제어 가능해야 한다.
- 향후 챗봇이 PMS를 조작하더라도, 같은 인증/권한/감사 규칙을 통과하는 공식 API만 사용해야 한다.

## 4. 정보 구조

### 4.1 엔터티 구조

- **Project**
  - 여러 Work Item을 포함
  - 상태, 진행률, 참여자 정보를 가짐
- **Work Item**
  - 실제 작업 단위
  - MVP에서는 `Issue`로 표기
  - Status, Assignee, Priority, Label, Comment, Activity Log와 연결

### 4.2 관계 정의

- Project 1:N Work Item
- Work Item N:1 Status
- Work Item N:1 Assignee(User)
- Work Item N:N Label
- Work Item 1:N Comment
- Work Item 1:N Activity Log

### 4.3 향후 확장 가능 구조

향후 제조업이나 운영형 프로젝트로 확장할 경우, `Work Item Type`을 아래처럼 확장 가능해야 한다.

- Issue
- Task
- Risk
- Decision
- Action Item

단, MVP에서는 이 구조를 구현하지 않고 설계 여지만 남긴다.

## 5. 기능 요구사항

## 5.1 Project

### 목적

업무 묶음 단위 관리

### 요구사항

- 사용자는 프로젝트를 생성, 조회, 수정, 보관(archive)할 수 있다.
- 프로젝트는 이름, 설명, 상태, 생성일, 참여자 정보를 가진다.
- 프로젝트 상세 화면에서 관련 작업을 볼 수 있어야 한다.
- 프로젝트별 기본 뷰는 Board와 List를 제공해야 한다.

### 필수 필드

- Project Name
- Description
- Status (`Planned / Active / Completed / Archived`)
- Owner
- Created At

### 수용 기준

- 프로젝트 생성 후 작업을 바로 등록할 수 있어야 한다.
- Archived 프로젝트는 기본 목록에서 숨김 처리할 수 있어야 한다.

## 5.2 Issue

### 목적

실제 실행 작업 관리

### 요구사항

- 사용자는 이슈를 생성, 조회, 수정, 삭제할 수 있다.
- 이슈는 프로젝트에 소속되어야 한다.
- 이슈 제목은 필수값이다.
- 이슈는 상세 설명을 가질 수 있다.
- 이슈는 상태, 담당자, 우선순위, 라벨을 가진다.
- 이슈 상세 화면에서 댓글과 활동 로그를 확인할 수 있어야 한다.

### 필수 필드

- Title
- Description
- Status
- Assignee
- Priority
- Labels
- Created By
- Created At
- Updated At

### 수용 기준

- 이슈 생성 후 보드/리스트에 즉시 반영되어야 한다.
- 필수 입력값 누락 시 저장이 차단되어야 한다.

## 5.3 Status

### 목적

이슈 진행 상태 표준화

### 기본 상태

- Backlog
- Todo
- In Progress
- Done
- Canceled

### 요구사항

- 프로젝트는 기본 상태 세트를 사용해야 한다.
- 사용자는 이슈 상태를 변경할 수 있어야 한다.
- 보드 뷰는 상태 컬럼 기준으로 이슈를 표시해야 한다.

### 수용 기준

- 상태 변경 시 이슈 위치와 Activity Log가 즉시 갱신되어야 한다.

## 5.4 Assignee

### 목적

책임자 명확화

### 요구사항

- 각 이슈에는 1명의 담당자를 지정할 수 있다.
- 담당자 미지정 상태를 허용한다.

### 수용 기준

- 담당자 필터로 본인 작업만 볼 수 있어야 한다.

## 5.5 Priority

### 목적

업무 우선순위 판단 지원

### 기본 우선순위

- No Priority
- Low
- Medium
- High
- Urgent

### 요구사항

- 사용자는 이슈 우선순위를 설정/변경할 수 있다.
- 리스트 및 상세 화면에서 우선순위를 확인할 수 있어야 한다.
- 대시보드에서 High/Urgent 건수를 볼 수 있어야 한다.

### 수용 기준

- 우선순위 변경이 즉시 목록과 상세에 반영되어야 한다.

## 5.6 Label

### 목적

이슈 분류 및 필터링 지원

### 요구사항

- 사용자는 프로젝트 내 라벨을 생성할 수 있다.
- 이슈에 복수 라벨을 부여할 수 있다.
- 라벨 기준 필터링이 가능해야 한다.

### 예시

- infra
- backend
- frontend
- security
- pilot
- blocker

### 수용 기준

- 라벨 추가/삭제 시 이슈 상세와 목록에 반영되어야 한다.

## 5.7 Comment

### 목적

이슈 단위 커뮤니케이션 기록

### 요구사항

- 사용자는 이슈 상세에서 댓글을 작성할 수 있다.
- 댓글은 작성자, 작성 시각을 보여야 한다.
- 사용자는 본인 댓글을 수정/삭제할 수 있다.

### 수용 기준

- 댓글 등록 즉시 스레드에 반영되어야 한다.

## 5.8 Activity Log

### 목적

변경 이력 추적

### 기록 대상 이벤트

- 이슈 생성
- 제목 수정
- 설명 수정
- 상태 변경
- 담당자 변경
- 우선순위 변경
- 라벨 추가/삭제
- 댓글 등록

### 요구사항

- 시스템은 핵심 변경 이력을 자동 기록해야 한다.
- 사용자는 이슈 상세에서 활동 로그를 시간순으로 볼 수 있어야 한다.

### 수용 기준

- 주요 필드 변경 시 로그가 누락되지 않아야 한다.
- 로그는 누가, 무엇을, 언제 변경했는지 보여야 한다.

## 5.9 Dashboard

### 목적

프로젝트 상태 요약 제공

### MVP 위젯

- 전체 프로젝트 수
- Active 프로젝트 수
- 전체 이슈 수
- Status별 이슈 수
- 우선순위별 이슈 수
- 내 할당 이슈 수
- 최근 업데이트된 이슈 목록

### 요구사항

- PMS 홈에서 간단한 요약 대시보드를 볼 수 있어야 한다.
- 프로젝트 상세에서도 프로젝트 기준 통계를 볼 수 있어야 한다.

### 수용 기준

- 새 이슈 등록/상태 변경 시 대시보드 수치가 반영되어야 한다.

## 5.10 API Surface

### 목적

웹 UI, CLI, 향후 자동화 클라이언트가 공통으로 사용할 수 있는 안정적인 PMS 인터페이스 제공

### MVP 범위

- Project API
- Issue API
- Comment API
- Activity Log API
- Dashboard summary API

### 요구사항

- REST API는 `/api/v1/pms/...` 하위에 일관되게 배치해야 한다.
- 기본 리소스는 `projects`, `issues`, `comments`, `activity-logs`를 사용한다.
- 읽기 API는 목록/상세를 분리하고, 쓰기 API는 생성/수정/보관을 명확히 나눠야 한다.
- 목록 API는 상태, 담당자, 우선순위, 라벨 기준 필터를 지원해야 한다.
- 정렬과 페이지네이션 규칙은 모든 목록 엔드포인트에서 일관되어야 한다.
- CLI가 사용할 수 있도록 응답 스키마는 안정적이어야 한다.

### 수용 기준

- 프로젝트와 이슈 주요 작업이 UI 없이도 API만으로 수행 가능해야 한다.
- 목록 조회 결과가 필터/정렬 기준에 맞게 일관되게 반환되어야 한다.
- CLI가 동일 API를 사용해 생성/조회/수정 흐름을 수행할 수 있어야 한다.
- 향후 챗봇이 붙더라도 추가 백도어 없이 공식 API만으로 CRUD가 가능해야 한다.

## 6. 사용자 흐름

### 6.1 최초 진입 흐름

1. 로그인
2. PMS 진입
3. 첫 Project 생성
4. 첫 Issue 생성
5. Board/List에서 관리 시작

### 6.2 일반 이슈 처리 흐름

1. 프로젝트 진입
2. 이슈 생성
3. 담당자 지정
4. 우선순위 지정
5. 상태 변경
6. 댓글로 협업
7. 완료 처리

### 6.3 API / CLI 활용 흐름

1. 사용자가 프로젝트 또는 이슈를 연다.
2. 웹 UI 또는 CLI가 동일 API를 호출한다.
3. 시스템이 일관된 리소스 응답을 반환한다.
4. 사용자는 UI 또는 CLI에서 결과를 확인하고 후속 작업을 수행한다.

### 6.4 향후 챗봇 활용 흐름

1. 사용자가 챗봇에 PMS 관련 요청을 보낸다.
2. 챗봇은 PMS 전용 비공개 로직이 아니라 공식 REST API를 호출한다.
3. 인증, 권한, 감사 로그 규칙은 웹 UI와 동일하게 적용된다.
4. 챗봇은 조회 또는 CRUD 결과를 사용자에게 반환한다.

- API와 CLI 모두 동일한 권한 검사를 따라야 한다.
- 향후 챗봇이 수행하는 CRUD도 동일한 권한 검사와 감사 로그 기록을 따라야 한다.

- 외부 툴 연동

- 제조업 전용 work item type
- 문서관리/위키 연계
- 에이전트/자동화 클라이언트
