# 두원공조 AI 시범도입 계획

## 목표

- 3개월 안에 무엇을 실제로 검증할지 범위를 맞춘다.
- 문서 RAG, PLM 조회, 포털/PMS, TF 내재화의 우선순위를 정한다.
- 컨설턴트와 TF의 역할 분담, 주간 운영 방식, 의사결정 구조를 맞춘다.
- 첫 4주에 바로 착수할 항목과 선행 조건을 확정한다.
- 아직 미정인 항목은 오늘 회의에서 결정하거나 후속 액션으로 넘긴다.

## 기술 전제와 서비스 설계 방향

- 하드웨어 스펙상 초거대 언어 모델이 아니라 `300억~1000억` 파라미터 규모의 오픈웨이트 모델을 사용하는 것을 전제로 한다.
- 따라서 범용 챗봇처럼 긴 컨텍스트를 계속 누적하거나 완전 자유형 자연어 검색을 전면에 두는 방식은 이번 사업의 기본 전략으로 보지 않는다.
- 전반적인 사용자 경험은 `무엇이든 물어보는 챗봇`보다 `특정 업무를 정형화한 업무형 시스템`에 가깝게 설계한다.
- 사용자는 업무 유형, 조회 대상, 조건을 선택하고 시스템은 그 선택에 따라 `SQL 조회`, `RAG 검색`, `키워드/메타데이터 검색`, `혼합형 검색` 중 적절한 템플릿을 수행하는 구조로 간다.
- 입력도 자유 서술 하나에만 의존하지 않고 업무별 템플릿, 선택형 조건, 가이드 문구를 함께 제공해 작은 모델의 해석 부담을 줄인다.
- 결과도 자유 대화형 답변보다 `표`, `카드`, `출처`, `핵심 요약`, `다음 액션`이 포함된 정형 포맷을 기본으로 하여 일관성을 높인다.
- 모델이 확실하지 않은 경우에는 추측형 답변보다 재질문, 조건 보완 요청, 조회 실패 사유를 명확히 반환하도록 설계한다.
- 업무 정형화와 사용자 경험을 위한 AI 에이전트도 현업이 직접 수정, 조합, 확장할 수 있는 형태로 설계한다.
- 다만 초기 개발 환경, 공통 템플릿, 기본 하네스, 운영 구조의 첫 세팅은 컨설턴트가 우선 구축하고 TF가 이를 이어받아 사용하는 방식으로 시작한다.

## 이번 3개월에서 만들 것

### 1. 문서 RAG

- `mcloudoc` 문서를 대상으로 업무별 검색 템플릿과 근거 기반 답변 제공
- 자유형 대화보다 문서 유형, 업무 주제, 품목, 프로젝트 등으로 좁혀서 검색하는 흐름 우선
- 결과는 문서 원문, 페이지, 파일 경로 등 출처를 확인할 수 있는 구조로 제공
- PDF, 오피스 문서 우선
- 이미지, 도면 등은 향후 추진 과제

### 2. PLM 조회

- 현업 질문을 템플릿화된 질의 흐름으로 받아 PLM 데이터를 조회할 수 있는 구조 마련
- 사용자 선택에 따라 SQL 생성형 조회와 사전 정의 조회를 구분해 적용
- 조회 대상은 읽기 중심으로 제한
- 결과는 표 형태 조회와 간단한 해석/요약까지 정형 포맷으로 제공

### 3. 통합 포털/PMS

- 문서 RAG와 PLM 조회의 공통 진입점을 `업무 카드형 UI`로 제공
- 범용 챗창 하나보다 업무별 메뉴와 화면 흐름을 우선 구성
- TF 과업, 일정, 이슈를 관리하는 최소 기능 PMS 구성
- 이후 AI 서비스가 추가되어도 붙일 수 있는 구조로 시작

### 4. TF 내재화

- 프롬프트 작성, AI 활용, 바이브 코딩 실습을 사업 안에서 같이 진행
- TF가 직접 수정하고 실험해보는 구조로 운영
- 현업이 업무 템플릿, 에이전트 흐름, 결과 포맷을 직접 수정할 수 있는 형태로 만든다
- 템플릿, 평가셋, 운영 하네스를 TF가 이해하고 직접 보완할 수 있도록 한다
- 사업 종료 시점에는 TF가 운영과 경미한 개선을 이어갈 수 있도록 한다

## 운영 원칙

- 이번 사업은 `3개월 안에 핵심 범위를 검증`하는 시범사업으로 본다.
- 목표는 기능 시연이 아니라 `실제 업무에 써볼 수 있는 수준`까지 올리는 것이다.
- 외부 API 없이 온프레미스 기준으로 진행한다.
- 기술 검토보다 실제 업무 시나리오 검증을 우선한다.
- 작은 모델의 한계는 모델 교체보다 `업무 템플릿`, `검색 파이프라인`, `출력 표준화`로 우선 보완한다.
- 범용 대화형 UX보다 `업무별 진입점 + 조건 선택 + 정형 결과` 흐름을 기본값으로 둔다.
- 현업이 직접 에이전트와 템플릿을 다룰 수 있도록 개발/운영 환경을 단순하고 명시적으로 구성한다.
- 3개월 내 우선 범위를 마무리하고, 남는 보완 과제는 필요 시 추가 지원 항목으로 정리한다.

## 하네스 엔지니어링 적용 원칙

- 업무 시나리오별로 프롬프트, 검색 방식, 도구 호출 순서, 출력 포맷을 분리한 하네스를 운영한다.
- SQL 조회는 허용 스키마, 테이블 범위, 검증 규칙, 실패 응답 규칙을 포함한 별도 하네스로 관리한다.
- 문서 RAG는 전처리, 청킹, 검색, 재정렬, 답변 생성, 출처 표기를 하나의 고정 파이프라인으로 관리한다.
- 대표 질의셋, 기대 결과, 통과 기준을 둔 평가 하네스를 만들고 변경 시 회귀 검증한다.
- 모델이 애매한 답을 만드는 경우를 줄이기 위해 출력 스키마, 금지 응답, fallback 규칙을 명시한다.
- 운영 중 쌓이는 실제 질문을 평가셋에 계속 반영해 품질을 안정화한다.

## 역할과 협업 방식

### 컨설턴트

- 주 2~3일 현장 지원
- 나머지 기간은 원격으로 설계 검토, 질의응답, 개발 지원, 결과 리뷰 진행
- 현장에서는 요구사항 정리, 핵심 설계, 집중 개발, 교육/워크숍, 중간 리뷰 중심으로 운영
- 현업이 직접 다룰 수 있는 에이전트 개발 환경, 공통 템플릿, 기본 하네스, 초기 구성은 컨설턴트가 우선 세팅한다

### AX TF

- 현업 시나리오 정의
- 우선 문서/데이터 범위 선정
- 결과 검증과 피드백
- 업무 템플릿과 AI 에이전트의 현업 관점 수정 및 확장
- 바이브 코딩 실습 및 운영 방식 습득

### 운영 방식

- 주간 단위로 목표 설정, 실행, 리뷰 진행
- 컨설턴트 현장 일정에 맞춰 핵심 회의와 집중 작업 배치
- 일상 진행은 TF 중심으로 이어가고, 컨설턴트가 주간 단위로 방향과 품질을 잡는 구조로 운영
- 결정이 필요한 이슈는 포털/PMS 또는 별도 공용 채널에서 추적

## 3개월 추진 흐름

### 1개월차: DGX Spark 없이 먼저 할 수 있는 일에 집중

- 전제: RAG용 기본 서버와 데이터 접근 준비는 가능, `DGX Spark`는 약 1개월 후 도입 예정
- `mcloudoc` 연계 범위 확인, 샘플 문서 확보, 문서 유형 분류
- OCR/전처리/메타데이터 기준 정리
- 문서 수집, 색인, 검색 파이프라인 기본 골격 준비
- PLM 업무 질문 수집, 조회 대상 테이블/컬럼 후보 정리
- Text-to-SQL용 스키마 분석과 질의 샘플셋 정리
- 업무별 입력 화면, 검색 템플릿, 결과 템플릿 정의
- 현업이 직접 수정 가능한 에이전트 구성 방식과 개발 환경 초안 마련
- 포털/PMS 최소 구조와 메뉴 흐름 정의
- TF 대상 기초 교육, 프롬프트 실습, 바이브 코딩 환경 온보딩
- 품질 평가 기준, 평가 하네스, 중간 데모 시나리오 합의

### 2개월차: 장비 도입 후 핵심 기능 본격화

- 온프레미스 LLM/임베딩/재정렬 모델 구성
- 문서 RAG 답변 생성 품질 검증 및 개선
- PLM 자연어 질의, SQL 생성, 승인 흐름 구현
- 프롬프트, 라우팅, 출력 스키마, fallback 규칙을 포함한 업무별 하네스 적용
- 포털에서 RAG와 PLM 기능 연결
- TF가 직접 에이전트 설정과 템플릿을 수정하는 운영 흐름 적용
- TF 실습 과제를 실제 서비스 수정/개선 중심으로 전환

### 3개월차: 통합 검증과 현업 적용

- 업무 시나리오 기준 통합 테스트
- 검색 품질, 답변 정확도, 조회 결과 표현 방식 보정
- 평가셋 기반 회귀 점검과 운영 기준 정리
- TF 주도 수정 및 확장 실습
- 운영 기준, 인수인계 대상, 잔여 과제 정리
- 실제 적용 후 보완이 필요한 항목은 후속 지원 대상으로 정리

## 작업 스트림별 완료 기준

### 문서 RAG

- 우선 문서 범위에 대해 검색이 가능해야 한다.
- 답변에 출처가 표시되어야 한다.
- 사용자가 자유 질문만 하지 않아도 업무 템플릿으로 원하는 자료에 도달할 수 있어야 한다.
- 현업이 "찾을 수 있다" 수준이 아니라 "바로 참고해 쓸 수 있다"는 평가가 나와야 한다.

### PLM 조회

- 우선 시나리오에 대해 자연어 질의가 가능해야 한다.
- 조회는 읽기 전용 기준으로 통제되어야 한다.
- SQL 생성과 실행 과정이 검증 가능한 하네스로 통제되어야 한다.
- 결과가 현업 검증 기준을 통과해야 한다.

### 포털/PMS

- 사용자 입장에서 두 서비스를 한 곳에서 접근할 수 있어야 한다.
- 챗봇 하나가 아니라 업무 목적별 진입 화면과 결과 포맷이 정리되어 있어야 한다.
- TF 운영에 필요한 최소 과업 관리 기능이 있어야 한다.
- 이후 기능 추가가 가능한 구조로 시작해야 한다.

### TF 내재화

- TF가 프롬프트와 바이브 코딩으로 간단한 수정/확장을 직접 시도할 수 있어야 한다.
- TF가 업무 정형화용 에이전트와 사용자 경험 구성 요소를 직접 수정할 수 있어야 한다.
- TF가 템플릿과 평가 하네스를 이해하고 유지보수할 수 있어야 한다.
- 운영 중 발생하는 경미한 이슈를 TF가 스스로 분류하고 처리 흐름을 이해해야 한다.

## 오늘 회의에서 결정할 항목

- `mcloudoc` 1차 대상 문서 범위
- PLM 1차 조회 대상 업무 시나리오
- PLM 우선 테이블/컬럼 범위
- 포털/PMS에서 이번 3개월 안에 넣을 최소 기능
- TF 참여 인원별 실제 투입 시간
- 중간 데모와 최종 검증의 판단 기준
- 데이터 반출, 권한, 보안 관련 운영 원칙

## 리스크와 전제조건

- TF가 현업 업무와 병행하므로 주간 확보 시간이 분명해야 한다.
- `mcloudoc`와 PLM 접근 권한이 초기에 정리되어야 한다.
- 문서 품질이 낮은 경우 OCR 정확도 이슈가 있을 수 있다.
- PLM 스키마가 복잡하면 우선 범위를 좁혀 시작해야 한다.
- DGX Spark 도입 전에는 생성 품질보다 데이터 준비와 검색 기반 마련이 우선이다.
- 작은 모델에 범용 챗봇 기대치를 두면 품질 편차가 커질 수 있으므로 업무 템플릿 설계가 선행되어야 한다.
- 일정 안에 끝내려면 "전사 공통 플랫폼"보다 "우선 시나리오 검증"에 집중해야 한다.
