# 근태 도메인 설계 계약

이 문서는 근태(commute) 도메인의 **향후 데이터 소유권, 저장 위치, 수집 방식, 결재 흐름**에
대한 설계 정본이다.
근태는 역할별로 여러 앱(개인근태 / 부서장 / 인사담당자 / 부서근태 담당자)이 같은 데이터를 공유하므로
`apps/` 가 아니라 `domains/` 에 둔다.

앱 등록·노출 계약은 [앱 플랫폼 등록 계약](../app-platform/README.md),
인사 사용자·조직 동기화는 [HR 동기화 계약](../hr/README.md)과
[ADR 0008](../../../adr/0008-hr-sync-snapshot-baseline-policy.md)을 따른다.

> **현재 구현 상태:** 이 변경은 기본 비활성·숨김 상태의 Mock UI 프로토타입과 앱 카탈로그만
> 등록한다. commute 테이블·마이그레이션·API·RBAC·미디어 연결·수집 worker는 아직 없다.
> 운영 활성화 전에 이 문서의 설계를 별도 Core Enablement 변경으로 구현하고 검증해야 한다.

> 1~3절은 근태에 한정되지 않는 공통 규칙이다. 다른 앱이 데이터 모델을 설계할 때 이 절을 인용해도 된다.

## 1. 저장 위치와 스코프 (공통 규칙)

| 항목            | 값                                                                    |
| --------------- | --------------------------------------------------------------------- |
| DB              | 플랫폼 공용 PostgreSQL (앱별 DB를 따로 만들지 않는다)                 |
| 모델            | `apps/api/src/ai_do_api/domains/<domain>/models.py`                   |
| 스키마 변경     | `apps/api/alembic/versions/` — 수기 마이그레이션, 단일 head 유지      |
| 모델 등록       | `core/model_registry.py` 와 `alembic/env.py` 양쪽에 import 추가        |
| 테이블 접두사   | 도메인명 (`commute_*`, `hr_*`, `legacy_issue_*`)                      |
| 주기 작업       | `apps/worker` Celery task + `celery_app.py` 의 `beat_schedule`         |

### `workspace_id` 를 쓰지 않는다

근태는 회사 tenant 전체 데이터다. [HR 동기화 계약](../hr/README.md)이 정한 대로
**회사 tenant는 배포와 데이터베이스 경계로 식별**하므로 `workspace_id` 컬럼을 두지 않는다.
개인 데이터는 `user_id` 로 스코프한다.

개인근태 앱은 `availability_scope="platform"` + `resourceScope="personal"` 이다
([ADR 0006](../../../adr/0006-platform-personal-global-apps.md)). 즉 workspace 없이도 동작해야 한다.

## 2. 데이터 소유권 (공통 규칙)

앱 데이터는 **누가 정본인가**로 먼저 가른다. 이걸 섞으면 나중에 어느 값을 믿어야 하는지 알 수 없게 된다.

| 구분                | 정본       | 예시                                             |
| ------------------- | ---------- | ------------------------------------------------ |
| 앱이 생성하는 데이터 | 우리       | 신청·결재 워크플로, 첨부, 결재 이력              |
| 외부에서 수집한 데이터 | **경우에 따라 다름** | 아래 참조                                |

수집 데이터의 정본 여부는 **자동으로 결정되지 않는다.** 도메인마다 명시해야 한다.

- **HR 사용자·조직**: 외부가 정본. 우리는 snapshot 보존 + projection 적용만 한다
  ([ADR 0008](../../../adr/0008-hr-sync-snapshot-baseline-policy.md)).
- **근태 기록**: **우리가 정본이다.** 아래 3절 참조.

## 3. 외부 수집 후 우리가 정본이 되는 패턴 (공통 규칙)

원천이 외부여도 수집 후 우리 DB를 정본으로 삼는 경우, 다음을 스키마와 잡에 명시해야 한다.

1. **수집 출처 추적** — `source_system`, `source_key`, `ingested_at`, `ingest_run_id`.
   정본이라도 "이 값이 언제 어느 실행으로 들어왔는지"는 남겨야 장애를 추적할 수 있다.
2. **덮어쓰기 규칙** — 우리 쪽에서 보정한 값이 다음 수집에 덮이면 안 된다.
   행 단위로 `is_manually_adjusted` 같은 잠금 플래그나 필드별 우선순위를 정한다.
3. **멱등 upsert** — 같은 구간을 재수집해도 중복 행이 생기지 않도록 자연키에 unique 제약을 건다.
4. **수집 실패 가시성** — 실행 결과(성공/실패/건수)를 남기고 관리자 화면에서 확인 가능해야 한다.

## 4. 근태 기록 — 구현 후 우리가 정본

구현 후 출퇴근 기록과 휴가 발생·사용·잔여는 **외부 근태 서버에 쌓이지만, 1시간 주기로 수집해
우리 DB에 적재하고 그 뒤로는 우리가 정본**으로 삼는다. 실제 API는 이 저장소만 조회하도록 한다.

```
[외부 근태 서버]  --(1시간 주기 수집)-->  [AI-DO PostgreSQL]  -->  화면·집계
                                             ^ 정본
```

| 원천                     | 담는 내용                        | 정본 |
| ------------------------ | -------------------------------- | ---- |
| ERP + 그룹웨어 (통합)    | 인사정보 (사용자·조직)           | 외부 |
| 근태 원천                | 출퇴근 기록                      | 우리 |
| 근태 원천                | 휴가 발생 / 사용 / 잔여          | 우리 |

### 원천 위치 (2026-07-28 기준, 임시)

**통합 DB 저장소가 개발 예정**이며 그때까지는 아래 경로를 정본으로 본다.
두 DB 모두 아직 구축 전이므로 경로는 설정값으로 두고 하드코딩하지 않는다.

| 대상        | 위치                              | 갱신     |
| ----------- | --------------------------------- | -------- |
| 근태 DB     | `C:\projects\AI-Do\commute\db`    | 수시     |
| 인사정보 DB | `C:\new\6 db make`                | **매시간** |

인사정보 DB는 **ERP와 그룹웨어 인사정보가 통합된 형태**다. 어느 한쪽만이 아니다.

> `commute/.gitignore` 에는 `DB/` 와 `db/` 를 **둘 다** 넣어야 한다.
> Windows 는 `core.ignorecase=true` 라 `DB/` 가 `db/` 도 걸러주지만
> Linux·macOS·CI 러너에서는 걸러지지 않아 근태 DB(PII 포함)가 커밋된다.

향후 수집 잡은 `apps/worker` Celery beat 에 1시간 주기로 등록한다
(`hr.sync_groupware`, `capture-erp-hr-snapshot-daily` 와 같은 자리).

### 그룹웨어의 위치

**그룹웨어는 메인이 아니다.** 도우미 형태로 HTML 코드만 전달하며, **AI 포털이 메인 시스템**이다.
현재 그룹웨어에 위임하고 있는 것은 로그인 비밀번호 검증뿐이다
(`users.auth_provider='groupware'`, [그룹웨어 연동 정보](../../../interfaces/groupware/auth-http-database.md)).

## 5. 앱이 소유하는 데이터 — 신청과 결재

신청 3종(야근·근태·특근)은 **단일 테이블 + `kind` 판별자**로 둔다.
결재 상태·결재자·사유·첨부·이력·목록 조회가 3종에서 동일하기 때문이다.
테이블을 나누면 결재 워크플로와 첨부 처리가 3벌이 된다.
`kind` 별 필수/금지 컬럼은 CHECK 제약으로 강제한다.

```
commute_attendance_codes      근태(공제) 코드 마스터
commute_requests              신청 1건 (kind = OVERTIME | ATTENDANCE | HOLIDAY_WORK)
commute_request_approvals     결재 이력 (단계별 1행)
commute_request_attachments   증빙 첨부 (media:{id} 참조)
commute_ingest_runs           수집 실행 1회 (성공/실패·건수·오류)
commute_attendance_daily      일자별 근태 기록 (수집 적재, 우리 정본)
commute_leave_balances        휴가 발생·사용·잔여 (수집 적재, 우리 정본)
```

위 목록은 **구현된 스키마가 아니라 제안 설계**다. 향후 Core Enablement는 단일 Alembic head에서
마이그레이션과 모델을 함께 추가하고, router·personal-scope RBAC·OpenAPI/generated client·미디어
수명주기·수집 worker·통합 테스트까지 같은 변경에서 검증한다.

### 휴가 잔여는 근태코드 단위로 관리한다

`commute_leave_balances` 는 `(user_id, attendance_code, period_year)` 가 자연키다.
연차=7, 월차=6, 생일휴가=22 처럼 코드마다 잔여가 따로 있어
`annual / monthly / etc` 3분류로 묶으면 기타휴가 종류별 잔여를 표현할 수 없다.
화면의 `LeaveSummary{annual, monthly, etc}` 는 이 테이블의 projection 으로 만든다.

### 휴가 사용 내역은 별도 테이블을 두지 않는다

`commute_attendance_daily` 에서 `attendance_code` 가 휴가 종류인 행을 뽑으면 사용 내역이 된다.
반차·시간 휴가의 소진량은 같은 행의 `leave_days`(0.5 등)에 담는다. 정본을 둘로 나누지 않는다.

### `commute_requests` 주요 컬럼

| 컬럼                          | 비고                                                     |
| ----------------------------- | -------------------------------------------------------- |
| `user_id`                     | 신청자                                                    |
| `kind`                        | OVERTIME / ATTENDANCE / HOLIDAY_WORK                      |
| `attendance_code`             | 근태 신청만. `commute_attendance_codes.code` FK           |
| `start_date` / `end_date`     | 여러 날 신청은 날짜당 1행 (야근·특근) 또는 기간 1행 (휴가) |
| `start_time` / `end_time`     | 일수 단위 휴가는 NULL                                     |
| `half_day` / `hours` / `days` | 근태 신청 (반차·시간 단위)                                |
| `has_dinner`                  | 야근 — 저녁 휴게 공제 기준                                |
| `break_minutes`               | 특근 — 휴게 공제                                          |
| `minutes`                     | 인정 실근로 시간 (공통)                                   |
| `premium_minutes`             | 특근 — 가산 포함 환산                                     |
| `compensation`                | 특근 — ALLOWANCE / COMP_LEAVE                             |
| `status`                      | 아래 6절                                                  |
| `approver_user_id`            | 상신 시점 결재자 (代부서장 여부를 role 로 함께 보존)      |
| `groupware_doc_no`            | 특근 — 그룹웨어 결재 문서번호                             |

### 결재 이력을 별도 테이블로 두는 이유

`status` 컬럼 하나로는 **어느 단계에서 반려됐는지** 구분할 수 없다.
특근은 4단계라 부서장 반려와 그룹웨어 반려가 같은 `REJECTED` 로 보인다.
향후 `commute_request_approvals` 에 단계별 처리 이력을 남기면 반려 지점이 드러나고,
화면의 단계 진행 표시도 실제 이력에서 그릴 수 있다.

## 6. 결재 흐름

결재자는 **부서장 1인**이며 사용자가 고르지 않고 인사 정보로 자동 결정된다.
**파트장은 결재선에 쓰지 않는다.**

### 야근 · 휴가 · 유연근무

```
신청자 → 부서장 결재 완료(효력 발생) → 인사담당자 확인
```

인사담당자 확인은 **확인 수준**이라 결재를 막지 않는다. 상태로 두지 말고 `hr_checked_at` 시각만 기록한다.

### 특근

```
신청자 → 부서장 결재 → 부서근태 담당자 → 그룹웨어 결재선(부서마다 다름)
      → 승인 후 부서근태 담당자 확정 → 앱/웹 결과 반영
```

부서장 승인은 중간 단계이고 **최종 확정은 부서근태 담당자가 넣는다.**
그룹웨어 결재선은 부서마다 달라 **앱이 결재자를 그리지 않고** 진행 단계와 문서번호만 표시한다.

### 상태 값

| 상태                 | 의미                        | 사용 |
| -------------------- | --------------------------- | ---- |
| `PENDING`            | 부서장 결재 대기            | 공통 |
| `TIMEKEEPER_REVIEW`  | 부서근태 담당자 처리중      | 특근 |
| `GROUPWARE_APPROVAL` | 그룹웨어 결재 진행중        | 특근 |
| `APPROVED`           | 승인 완료                   | 공통 |
| `REJECTED`           | 반려                        | 공통 |

취소 상태(`CANCELED`)는 두지 않는다. 부서장 결재 전(`PENDING`)까지는 **흔적 없이 삭제**하고,
결재가 시작된 뒤에는 신청자가 삭제할 수 없다.

### 부서장 대리 (代부서장)

부서장이 휴가·출장 등으로 부재할 때만 지정된 대리인이 결재 권한을 대리한다.

- **부서장 본인이 관리**한다.
- 부서장이 관리할 수 없는 상황이면 **인사담당자가 설정·수정**할 수 있다.
- 신청 레코드에는 상신 시점의 결재자 role 을 함께 남겨 대리 결재 이력을 보존한다.

## 7. 근태코드 마스터

향후 레거시 ERP 의 Deduction Code 표(1~30)를 `commute_attendance_codes` 에 1:1로 보존한다.
`code` / `name` / `days_hours_type` / `day_time` 은 원본 컬럼이고,
`category` / `hours` / `is_provisional` / `requires_reason` / `allows_attachment` 는 앱용 파생 컬럼이다.

카테고리는 원본 표의 `Deduction category` 를 그대로 따른다. 코드별 정렬 순서도 원본과 같다.

| 카테고리 | 항목 |
| -------- | ---- |
| 출장 (3) | 출장 · 파견 · 해외출장 |
| 교육 (2) | 교육 · 해외연수 |
| 휴가 (17) | 월차 · 연차 · 생리 · 경조 · 졸업 · 숙직 · 반차 · 근속 · 생일 · 정년 · 대체 · 1·2·3·5·6·7시간 |
| 훈련 (2) | 예비군훈련 · 민방위훈련 |
| 기타 (6) | 산재 · 휴직 · 공상 · 결근 · 휴업 · 기타 |

- 코드 번호는 **화면에 노출하지 않는다.** 내부 식별자로만 쓴다.
- `is_provisional=true` (코드 25~30, 시간 단위)는 ERP 에 아직 없는 코드다. 연동 전 생성이 선행돼야 한다.
- 4시간 코드가 없는 이유는 반차(19)가 4시간이기 때문이다.
- DB 의 `name` 은 레거시 원문 보존용이다. **화면 문구는 DB 값을 그대로 쓰지 않고**
  `apps.personalAttendance.codeNames.<labelKey>` 리소스(ko-KR/en-US)에서 해석한다. 카테고리·결재
  상태·휴가 종류도 같은 방식으로 enum 값 → 리소스 키로 표시한다(`web` 의 `attendance-labels.ts`).
- 그래서 `category` 는 **DB 는 원본 한글**(`출장`/`교육`/`휴가`/`훈련`/`기타`), **web 은 enum**
  (`TRIP`/`TRAINING`/`LEAVE`/`DRILL`/`ETC`)이다. API 를 붙일 때 응답 직렬화 계층에서 이 매핑을
  수행하고, 한글 값을 그대로 프론트로 내보내지 않는다.

## 8. 미결 사항

Core Enablement 구현 전에 확정이 필요하다. 현재 UI 값은 Mock이며 서버 계약이 아니다.

| 항목                                        | 현재 처리                                  |
| ------------------------------------------- | ------------------------------------------ |
| 근태·인사정보 DB 스키마                      | DB 구축 전 — 위치만 확정(4절), 통합 DB 저장소 대기 |
| 수집 후 우리 보정값의 덮어쓰기 규칙         | 제안 컬럼(`is_manually_adjusted`)과 잡 정책 모두 미구현 |
| 그룹웨어 결재 상태를 앱이 받는 방법          | 미정 — 담당자 직접 입력 vs 폴링/웹훅       |
