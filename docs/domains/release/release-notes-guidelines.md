# 릴리즈 노트 작성 기준

Open ALM 릴리즈 노트는 엔드유저가 읽는 안내다. 무엇이 좋아졌는지, 사용
흐름에서 무엇이 달라졌는지, 사용자가 직접 해야 할 일이 있는지를 먼저
설명한다.

## 정본

- 릴리즈 노트 문구 기준은 이 문서를 정본으로 둔다.
- Agent skill은 이 문서를 링크만 하고, 전체 기준을 중복 작성하지 않는다.
- 제품에 노출되는 릴리즈 노트에는 사용자가 알아야 할 내용만 쓴다.

## 작성 원칙

- 쉬운 한국어로 사용자에게 생기는 변화를 쓴다.
- 훑어보기 쉬워지는 경우 영향 영역을 적는다: `PMS`, `회의`, `Open ALM Desktop`.
- "개선했습니다", "추가했습니다", "볼 수 있습니다", "수정했습니다"처럼 결과가
  분명한 표현을 쓴다.
- 모달에서 빠르게 읽을 수 있도록 항목은 짧게 쓴다.
- 새로고침, 재설치, 업데이트처럼 사용자가 해야 할 일이 있으면 명확히 적는다.
- 내부 구현 용어는 피한다: API 경로, DB 마이그레이션, 저장소 호스트명,
  localhost, MinIO, query 이름, 프레임워크 이름, 배포 방식.
- 검증되어 배포된 동작만 쓴다.
- 이모티콘이나 아이콘은 과하지 않게 쓴다. 릴리즈 노트 하나에 1~2개 정도만
  사용하고, 읽기 쉽게 만드는 경우에만 넣는다.

## 기술 변경을 사용자 언어로 바꾸기

구현 상세가 아니라 사용자가 겪던 문제나 좋아진 점으로 바꿔 쓴다.

| 피할 표현 | 권장 표현 |
| --- | --- |
| `PMS 및 회의 첨부 다운로드가 내부 localhost 저장소 주소가 아닌 API 경유 URL로 동작합니다.` | `PMS와 회의에서 첨부파일 다운로드가 되지 않던 현상을 개선했습니다.` |
| `release_notes 테이블과 dismiss API를 추가했습니다.` | `업데이트 소식을 처음 접속할 때 확인할 수 있습니다.` |
| `Gantt optimistic update rollback flicker를 수정했습니다.` | `간트에서 일정을 늘리거나 줄일 때 화면이 깜박이며 원래 길이로 돌아가 보이던 현상을 줄였습니다.` |
| `Desktop 0.1.18 update feed latest.yml을 교체했습니다.` | `Open ALM Desktop Windows/Linux 최신 설치 파일을 받을 수 있습니다.` |

## 기본 구성

seed 데이터, 관리자 입력 문구, 릴리즈 모달 문구를 준비할 때는 아래 구조를
기본으로 한다.

```text
제목: 2026년 6월 15일 업데이트

요약:
PMS와 Open ALM Desktop 사용 중 불편했던 다운로드와 업데이트 확인 흐름을 개선했습니다.

주요 변경:
- PMS에서 첨부파일 다운로드가 되지 않던 현상을 개선했습니다.
- 업데이트 소식을 처음 접속할 때 확인할 수 있습니다.
- Open ALM Desktop Windows/Linux 최신 버전을 받을 수 있습니다.

필요한 조치:
- 이미 접속 중인 사용자는 새로고침 후 확인해 주세요.
```

## 같은 날짜에 여러 번 배포하는 경우

같은 날짜에 여러 번 배포하더라도 각 릴리즈는 별도 내역으로 남긴다.

- 릴리즈 키는 겹치지 않게 쓴다: `YYYY-MM-DD-01`, `YYYY-MM-DD-02`,
  `YYYY-MM-DD-desktop-018`.
- 제목은 의도를 구분할 수 있게 쓴다.
  - `2026년 6월 15일 업데이트`
  - `2026년 6월 15일 추가 업데이트`
  - `2026년 6월 15일 긴급 개선`
- 릴리즈 내역 화면에서는 날짜별로 묶고, 같은 날짜 안에서는 시간이나 제목으로
  구분한다.
- 처음 접속 모달에 읽지 않은 릴리즈가 여러 개 있으면 최신순으로 보여주거나,
  UI가 지원하는 경우 같은 날짜 아래에 묶어서 보여준다.
- 같은 날짜라는 이유로 기존 게시 릴리즈를 덮어쓰지 않는다. 나중에 추가된
  변경을 사용자가 알 수 있도록 새 릴리즈로 게시한다.

## 플랫폼별 안내

- 데스크톱 릴리즈는 실제 배포된 플랫폼만 쓴다.
- macOS가 포함되지 않았으면 `전체 데스크톱`이 아니라 `Windows/Linux`라고 쓴다.
- 설치 파일을 다시 받아야 하면 그 사실을 직접 적는다.

## 게시 전 체크리스트

게시 전에 아래를 확인한다.

- 비개발자가 무엇이 달라졌는지 이해할 수 있는가?
- 내부 호스트명, API 이름, 인프라 용어를 피했는가?
- 영향 영역과 필요한 조치가 분명한가?
- 같은 날짜에 여러 업데이트가 있으면 순서가 분명한가?
- 이모티콘이나 아이콘을 과하게 쓰지 않았는가?
