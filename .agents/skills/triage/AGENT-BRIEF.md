# Writing Agent Briefs

An agent brief is a structured GitLab issue comment that records whether an AFK agent can implement the work without hidden decisions. Readiness is represented by the brief, checklist, and the `ready-for-agent` label.

## Requirements

- Describe observable behavior and durable interfaces, not a sequence of code edits.
- Include enough current-state evidence to avoid repeating triage.
- Make every acceptance criterion independently verifiable.
- State unresolved external dependencies and scope exclusions explicitly.
- Link owning documentation or accepted ADRs when they constrain the work.
- Avoid line numbers and incidental file paths that are likely to move.
- Do not declare the issue implementation-ready while a product, security, data, or architecture decision remains open.

## Template

```markdown
> *This was generated by AI during triage.*

## Agent brief

**Summary:** One-line description of the required outcome

**Current behavior:**
What happens now, including reproduction or repository evidence.

**Desired behavior:**
What must be observable after the work, including relevant error and edge cases.

**Contract constraints:**

- Existing interface, domain rule, or accepted ADR the change must preserve
- Required authorization, audit, migration, or compatibility behavior

**Acceptance criteria:**

- [ ] Specific externally verifiable criterion
- [ ] Relevant automated check or test passes
- [ ] Documentation or migration contract is updated when applicable

**Out of scope:**

- Adjacent behavior that this issue must not change

**Validation:**

- Command or harness that verifies the result
```

Use the current GitLab labels: `bug` for defects, `needs-triage` while required information remains, and `ready-for-agent` only after posting a complete brief with no unresolved checklist item.
